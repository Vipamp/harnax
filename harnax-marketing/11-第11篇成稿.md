## 正文

### 一、先问四个问题,再点数能答几个

周一早上,有人依次问了四句话:

1. "上周三下午那批会话,AI 一共调了多少次工具,有没有失败的?"
2. "哪个模型上周吃得最多?"
3. "上次给那个 MCP 服务签发令牌,是谁点的、成没成?"
4. "这些记录,万一被人改过怎么办?"

四个问题的答案是不一样的:**第 2 个在页面上能答;第 1 和第 3 个库里都有,但读要你自己连数据库;第 4 个我们只做了一半。** 一个能答,两个要连库,半个没做——这一篇就说这个落差。

先立一个词表,后面都用它:记消耗的那张叫**用量表**,记动作的四张(过程、工具调用、令牌授权、网关调用)叫**留痕表**。五张表全在你自己的 MySQL 里,四张在 `harnax_admin` 库、网关那张在 `harnax_router` 库;写它们的是执行服务和网关,中间不经过任何第三方。

### 二、写这一路:一次调用一行,而且是原文

**用量表一次模型调用一行。** 它挂在模型调用的收尾事件上。选这个位置是有理由的:流式和只拿最终结果两条路都从同一条中间件链上过,读的是同一个累计值——所以"看着它一个字一个字吐"和"只等一个整答案",记下来是同一个行数。这个粒度有测试钉住:每个 agent 恰好一个记录器,记录器不跨会话共享。

**工具调用表一次调用一行。** 成功和失败是两条分支,各写各的那一行——所以一次调用恰好一行,不会落两行;失败那行的 `result` 里存的是 `ERROR: <异常消息>`。

**过程表不是一行一个动作**,它跟着流式增量走:工具输出的文本每来一段非空增量就落一行。所以一次调用可能落几行,也可能落几十行,取决于对方吐成多少片。这个量级差别要提前说清,别按"一次调用一行"去估容量。

**记的是原文,不是摘要。** 过程日志里那一行是 `Call tool: '工具名' with input '入参原文'`,工具输出同理;工具调用表的 `args` 是入参序列化后的 JSON,`result` 是返回值的原文。四个写入类里搜 `mask`、`redact`、`truncat`、`substring`、`maxLen`,零命中——**没有脱敏,也没有截断**。工具设计文档自己也写着:"入参与返回值都会进库,敏感值应当在工具方法内部避免回显。"这句我们照抄过来:该由工具自己收敛的东西,系统没有替你做。

**写失败不会把对话写崩。** 三处留痕的写入都是 catch 住只打日志,注释里一句 "Do not throw exception to avoid affecting main flow";用量表在适配器里 rethrow、由中间件接住,降级成一条 warn;授权审计那里也写着 "Failing to write it must not fail the call"。代价是:统计这一路出故障时,你少一行记录,而回答照发。

### 三、读这一路:五张表里,只有两张能查回来

这是本篇最想写清楚的一段。**三张留痕表在生产代码里没有读路径**:

- 工具调用表的 mapper 里只有一条 `insert`,连 `<select>` 都没有。注释是自己写的:"no select/update/delete belongs here"。
- 令牌授权表同样只有 `insert`。
- 过程表有 select / delete / update 三条语句,但**生产代码一个调用方都没有**;它的注释也很老实:"insert: the only statement with a production caller"。

管理台里搜这三张表,零命中。产品文档里那句是我们自己写的原话:"调用日志只写不读:平台没有工具调用统计页面,`tool_call_log` 需要直连数据库查。"

关于授权表,还要多补一句它**记的是什么**:它记的是令牌决策——签发、刷新、吊销,每决策一行,带操作者、会话、结果和耗时;它不存令牌本身,也不存响应正文,注释给的理由是"不是这个授权归属人的管理员也会读这张表"。表里预留了"调用"和"鉴权失败"两个取值,但生产代码写不出来,至今只在测试里出现过。所以这张表的名字容易让人以为"每次 MCP 调用都留一条",**不是**。

能读回来的,一处半:

**头一处是用量看板。** 形态可以说得很具体:7 张数字卡(总费用、总输入、总输出、总消耗、活跃智能体、活跃会话、使用模型数)+ 3 个饼图 + 4 条折线,按模型 / 智能体 / 会话 / 总体四个维度分组,时间桶有 hour / day / week / month 四档,默认查近 7 天、粒度默认 `day`。全部是查询时实时聚合,没有预计算表。

**另外那半处在网关**:它自带一张控制页,不在管理台里,要另开一个地址看。它真的在读那张网关日志:分页,按会话 / 实例 / agent / 状态 / 最小耗时过滤,列表和总数共用同一个 WHERE,所以分页和总数说的是同一批行。这张表只记"哪一次调用、多久、成没成",列里有状态码、耗时、错误消息、路由到的实例,**唯独没有请求体和响应体**;耗时算的是请求真正结束的时刻,不是首字节;流式和挂起端点靠异步回调落行,用原子标志保证只落一次。

还有一个容易混的点,单独说一句:你在管理台里确实能回看一段对话的"执行过程"——但那个**不是从这三张留痕表查的**,它来自会话的运行时状态,读回来的是思考、正文、工具名与入参。同一件事在两处存着,而只有其中一处有页面。

### 四、这张"账单"算不出钱

三层都落空,一层层给:

1. 用量表的 `fee` 列每次写入都是 `BigDecimal.ZERO`,注释原话 "Fee temporarily set to 0, can be calculated based on model billing rules later"。
2. 这一列的类型是 `decimal(10,0)`。**零位小数,连"分"都存不下。**
3. 前端那张"总费用"卡片渲染成 `¥0.00`;把维度从 token 切到"费用",三个饼图和折线全部归零。

全仓没有单价表、没有计费规则、没有预算,搜 `cost` 命中的全是英文散文。所以"用量可控""超额自动拦截"这类话我们不说。这张表能给你的到此为止:哪个模型、哪个 agent、哪个会话、什么时候、吃了多少 token。

顺带排掉两个名字引起的误会:库里确实有个限流器,但它按 API Key 限的是**每分钟请求数**(默认 60),跟 token 无关;另一个叫 `turnBudget` 的东西是回合的秒数。

### 五、能摊到人头上吗:不能。但这张表的租户做法值得单独讲

用量表的维度只有 agent / session / model / tenant / 时间,**没有用户列**。要把消耗算到某个人头上,得自己拿 `session_id` 去关联会话的创建者——而会话那张表的归属主键是创建者,租户条件是可以跳过的(第 8 篇写过)。这道关联留给你做,不是系统做好的。

反过来,这张表有一处做法我愿意当卖点讲,但范围要圈死:它是全系列唯一一张"缺省即读不到"的表。mapper 里的注释原话是 **"a missing tenant has to read as nothing, not as everything"**——租户谓词刻意不包 `<if>`,`tenantId` 是非空参数,解析不出租户的调用方读到的是 0 行而不是全表;一条 `tenant_id` 为空的历史行不匹配任何值,也就不进任何租户的合计。这是**这一张表**做的取舍,不是全系统都这样,请别把它当一句通用承诺读。

另外两个数字细节:被删掉的模型、agent、会话,它们的历史消耗**仍然计入**分维度聚合——用的是 LEFT JOIN,注释写明"去掉这些行会让分维度的合计与旁边的总体对不上";会话那个饼图前端只画前 10 个,SQL 不截断。

### 六、它防篡改吗,它会不会自己长到天边

**关于防篡改,准确说法只有一半。** 三张留痕表在 SQL 层刻意不提供删改语句,授权表 mapper 的注释写得很硬:"an audit table that the application can rewrite is not an audit table"。但这是**应用层不给入口**,不是**数据库拦得住**:部署脚本给应用账号的权限是 `GRANT ALL PRIVILEGES ON harnax_admin.*`。全仓没有哈希链、没有 WORM、没有签名链、没有只读账号;搜到的那些 `SHA-256` / `HMAC` 命中,用途全是口令、API Key、PKCE 和 JWT。所以"审计表不可篡改"这句我们不写,"应用不提供修改它的入口"这句是真的。

**关于会不会自己长大:不会清,因为没有任何东西在清它。** 有保留期的只有调度域那两张表(执行日志 90 天、触发锁 7 天),而且两个数字是代码里的裸常量、不可配置。观测域这几张搜 `delete` / retention / partition 全部零命中:没有分区、没有按月建表、没有容量告警。再往下一层:MySQL 跑在 `STRICT_TRANS_TABLES` 下,而 `process_log.message` 和 `tool_call_log.args` / `result` 都是 `text`——**64KB 是硬顶,写入端没有任何截断保护**(对照很扎眼:网关那张表自己做了逐列 `cut()`,偏偏留痕这一路没有)。超长的行会被数据库拒绝,而拒绝又被 catch 吞掉,于是**丢的是那一行,不报错、不告警**。日志文件本身交给 Docker 默认驱动,compose 里没有一行 `logging:` 配置;挂在 `/app/logs` 上那几个卷是堆转储目录,不是日志目录。清理、轮转、采集,这三件都是你的事。

**网关那张表还会静默丢行。** 它是这五张里唯一异步的:先攒在内存缓冲,满 50 条或者每 5 秒批量落库;缓冲上限 10000,超了就丢弃新到的行并累加计数器;整批被 schema 拒掉时逐行重插,只丢真正报错那一行。它甚至有两个计数器方法(`droppedCount()` / `poisonedCount()`),但**除了测试没人调用**,也不暴露在任何端点上。所以能写的只有"每丢 100 条,日志里 warn 一次";"丢弃可监控"不能写。

### 七、想把一条链串起来,串不动

**没有 traceId。** `traceId` / `trace_id` / `X-Trace-Id` / `spanId` / `correlationId` 在 Kotlin 主链路零命中。全链路能追的锚点只有 `session_id`;`request_id` 只有网关那一张表有,授权表、工具调用表、执行账本都没有。网关里设 MDC 的只有非流式那一条路径,流式路径的代码注释明确写着不设。网关到执行服务之间没有 trace 头的传播实现。所以"全链路追踪"这四个字我们不用。

**有一个 id 是造出来的。** 定时任务那一跳的会话 id 形如 `task-{任务 id}-{agent id}-{一段 uuid}`,由调度侧生成。后果不是"没记录"——这一跳的用量和过程照样入库——而是**会话列表里查不到它**:管理台只给 web 和小程序会话建会话行,`chn-` 前缀和 `task-` 前缀没有。看板那一格只能把裸 id 当标签显示。你要按会话做归因,这个前缀得自己认得出来。

**时间这一条要收窄。** 这几张表全是 `DATETIME` + 服务端本地时钟写入,没有 UTC 归一。JDBC 时区上,admin / agent / scheduler / channel 都是 `Asia/Shanghai`,出厂 compose 也给网关显式传了同一个时区,**默认部署是一致的**;只有你不套这份 compose、直接用网关那份集群配置里的默认连接串(那一条写的是 UTC),两边才会错开。这句不能说成"跨服务时钟不一致",那是错的。

### 八、所以这一篇留下三件事

把上面的话收成一句:**"记下来了"和"看得见"是两件事,"看得见"和"算得清"是两件事,"算得清"和"改不了"还是两件事。** 第一半我们做完了,第二半有几件得你自己接上:

- **要读工具层,就自己连库。** 那三张表的读路径不在交付里,`SELECT` 是你的;或者拿网关那张控制页当模板——它证明了这类表应该怎么被读。
- **要保留期、要轮转、要采集,自己挂。** cron 加 `mysqldump`、logrotate、Prometheus 抓 Actuator。这里有个坑要提醒:只有 channel / scheduler / router 三个服务配了 `management`,admin 和执行服务连这个段都没有,采集范围得你自己补。
- **要防篡改,自己做一个只读账号 + 一份导出归档。** 系统把原文写全了,没给你封存的那一半。

下一篇是这个系列的最后一篇:我们把前十一篇评论区里问得最多的问题攒到一起答,顺带给一张整个系统的地图。
