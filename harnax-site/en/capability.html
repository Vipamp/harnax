Runtime mechanisms

Four runtime mechanisms, and what each one owes you

Each mechanism gets three paragraphs: the problem it solves, what the code actually does, and what it hands back to you. The third paragraph never gets cut.

Fig 1 · Three clocks that must not be mixed

Session-pinned routing

The problem

A conversation is not one request. The ReAct loop's context, the workspace files, and a state parked waiting for a human confirmation are not in the database — they are in one process's memory and disk. The "stateless service plus round-robin load balancer" model fails outright here.

How it is done

The session binding is one shared table living on Redis — standalone or Sentinel only, and it has to stay noeviction. The gateway sends later requests for the same session back to the same executor instance, and the gateway's own replicas share that one binding. Three clocks turn "the process stopped" into something decidable: the executor reports every 10 seconds, the gateway re-reads every 5, and a heartbeat older than 30 seconds is dead. New sessions are assigned at random weighted by session count; only a failover target takes the minimum. The pinning decision deliberately looks at health and draining and never at the circuit breaker: a session that is producing output steadily should not be moved because of one blip.

What you give up

The step that waits for confirmation physically cannot be moved: the parked body is a thread held by future.get(), a 600-second window sliced into 30-second keep-alives. Snapshots land only at the end of a round, so a crash loses the last stretch, and that round's half-emitted output is not replayed. Streaming failover covers connection errors only, and stops the moment the first event has been emitted. If Redis goes away there is roughly 30 seconds of heartbeat warmth left, and the instance registry throws rather than "keeps serving".

Outward HTTP is always 200, and the failure is written in the response code or in a stream event — retry logic has to read those two, not the transport status. The front end does not reconnect on its own, and there is no retry button on the page.

Fig 2 · Two locks, and three rulers that must not be mixed

Clustered scheduled firing

The problem

The scheduler runs 3 replicas — does the task you put in the early morning fire on all three? If the one that caught it dies halfway, who picks it up? Does that day's briefing simply get missed?

How it is done

Firing rights go to the Quartz JDBC cluster JobStore. Layer one is the cluster row lock, which decides who gets the trigger; layer two is us colliding a unique key (task_id, trigger_time) into our own trigger-lock table, which decides who owns this fire. The execution log has six statuses, and that state machine lives in SQL WHERE clauses rather than in code — only the execution thread that produced a result may write a terminal status. Three rulers, each with one job: a 60-second diff reconciliation against the business table, a 5-minute round that reaps rows sitting past 1.5 times their own timeout, and a 30-second status throttle. A shift you never rostered is not yours: a trigger for a task this node has never registered is refused outright and handed back.

What you give up

Dying after the fire is not re-issued: the task row gets flipped to timeout 5–7.5 minutes later while that remote run is still going and nobody owns it. No retry, no alerting egress. No fencing, no idempotency, and the same task can be dispatched twice — idempotency has to be built into your business logic. There is no "next fire time" column on the page; that value exists only inside the schedule tables. Editing a cron expression resets the task to disabled.

The takeover window is derived on paper: the integration test ClusterSingleFireIT verifies only "several replicas, one task, one fire". It covers neither takeover nor load balancing nor the real call chain. The stack starts as a single replica; how many replicas you want has to be declared explicitly.

Skill lifecycle

The problem

A skill package is not a few lines of prompt. It gets unzipped into the sandbox, read back by file tools, and becomes part of the model's executable surface. So every step between its source and its duty deserves a hard constraint.

How it is done

Before storage it passes 9 content-scan rules. A hit is written into the scan report that comes back synchronously, the skill is stored in the disabled state, and it becomes usable only after a human confirms — detained first, reviewed after. The three source types each carry their own constraint: Git runs a protocol allowlist, so addresses that could reach a local or external program are excluded explicitly; npm installs with --ignore-scripts, giving a package's hooks no chance to run; ZIP has four ceilings (5000 entries, 20 MiB per file, 200 MiB total, depth 512) and going past one throws SecurityException instead of truncating. Two locks interlock: a skill in the disabled state cannot be bound to an agent, and a skill that still has a binding cannot be disabled or deleted — a security verdict is the single exception. One assembly caps at 1000 skills; past that it is refused, never silently truncated.

What you give up

No version history and no rollback — a change is a change. Status holds two values, and "awaiting review" lands in the disabled cell of the data model; there is no approval queue and no owner hand-off. Skills can be stored in but never exported out of the admin console. The AI-authored-skill capability was built and then switched off deliberately: the write switch defaults to closed and the skill repository is read-only for agents. A scan hit is handled as "route it to a human with a safety reason", not as a hard refusal — so do not read this line as "it will always catch it". The dangerous-list constant table lives on the execution engine's side and cannot be re-verified from this repository.

Team-level skills project to the lead, agent-level skills to the members; the lead has no file tool and cannot read the projected directory, and the system logs a WARN about precisely that — the implementation-level evidence behind "the lead has knowledge, but no hands".

Fig 4 · Five write paths, two read paths

Execution records

The problem

"Recorded" and "visible" are two different things. Five tables are written; only two of them come back on a page.

How it is done

The usage table holds one row per model call, hung on the call-finished event, so streaming and non-streaming give the same reading. The tool table holds one row per call with the raw arguments and the raw return value. The process log follows streaming deltas, so a single call may write dozens of rows — capacity cannot be estimated as one row per call. The gateway's call log records only which call, how long, success or failure: it deliberately carries no body, measures duration to the point where the request truly ends, and is written asynchronously in batches — 50 rows or every 5 seconds. The dashboard itself is 7 stat cards, 3 pie charts and 4 series lines, grouped along four dimensions with four time buckets, all aggregated live.

What you give up

Three of the ledger tables are written but not read by the application layer, so reading them directly means connecting to the database yourself. The usage table has no user column, so nothing can be counted per head; fee is always 0 and that column's precision cannot hold a cent, which is why the site does not talk money. No quotas, no thresholds, no alerting — the rate limiter limits requests per minute, nothing else. The four tables in the observability domain carry no cleanup statement at all, and their TEXT columns have a hard ceiling while the writer has no truncation guard. The call chain has no global identifier; the only thing that strings it together is the session id. The "execution process" you can look back at on the page comes from runtime state, not from those three ledger tables.

A failed write is always caught — you lose a row, not the answer. The one item in this list that is unreadable by default is the usage table: with no tenant condition it returns empty rather than everything.
