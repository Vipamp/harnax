Runtime mechanisms

Four runtime mechanisms, and what each one owes you

Each mechanism gets three paragraphs: the problem it solves, what the code actually does, and what it hands back to you. The third paragraph never gets cut.

Fig 1 · Three clocks that must not be mixed

Session-pinned routing

The problem

A conversation is not one request. The ReAct loop's context and the sandbox workspace's files are not in the database — they are in one process's memory and local disk. The "stateless service plus round-robin load balancer" model fails outright here.

How it is done

The session binding is one shared table living on Redis — standalone or Sentinel only, and it has to stay noeviction. The gateway sends later requests for the same session back to the same executor instance, and the gateway's own replicas share that one binding. Three clocks turn "the process stopped" into something decidable: the executor reports every 10 seconds, the gateway re-reads every 5, and a heartbeat older than 30 seconds is dead. New sessions land by random draw weighted by 1/(sessions + 1); a failover target is picked first, and if it turns out busier than twice the average, the choice falls back to the candidate with the fewest sessions among those at or under 1.5 times the average. The pinning decision deliberately looks at health and draining and never at the circuit breaker: a session that is producing output steadily should not be moved because of one blip.

What you give up

Waiting for a human runs down two paths, and they tolerate a move differently: in a plain session a tool confirmation closes the round, and the pending call is stored in the ASKING state, so another instance can pick it back up; the team sub-run is the thread held by future.get() — a 600-second window sliced into 30-second keep-alives, and it physically cannot be moved. Snapshots land only at the end of a round, so a crash loses the last stretch, and that round's half-emitted output is not replayed. Streaming failover covers connection errors only, and stops the moment the first event has been emitted. If Redis goes away, the registry's read path still keeps a last-known fallback while its write path and "give me every live instance" throw; the binding has a shadow cache of its own, which is not limited by the 30 seconds of heartbeat warmth.

Most business failures really do come back as HTTP 200, with the reason written in the response code or in a stream event — but "always" does not hold: a workspace file download past the size ceiling returns 413 and a missing one returns 404, and the authentication and cross-origin path returns 401 and 403. Retry logic has to read the transport status together with those two fields. The front end does not reconnect on its own, and there is no retry button on the page.

Fig 2 · Two locks, and three rulers that must not be mixed

Clustered scheduled firing

The problem

The scheduler runs 3 replicas — does the task you put in the early morning fire on all three? If the one that caught it dies halfway, who picks it up? Does that day's briefing simply get missed?

How it is done

Firing rights go to the Quartz JDBC cluster JobStore. Layer one is the cluster row lock, which decides who gets the trigger; layer two is us colliding a unique key (task_id, trigger_time) into our own trigger-lock table, which decides who owns this fire. The execution log has six statuses, and that state machine lives in SQL WHERE clauses rather than in code: the execution thread that produced a result writes success and failure, the reaping scan writes timeout, and each of the two carries its own "this row is still mine" status guard. Three rulers, each with one job: a 60-second diff reconciliation against the business table, a 5-minute round that reaps rows sitting past 1.5 times their own timeout, and a 30-second status throttle. The ones that step aside are the disabled nodes, not "a shift someone else rostered": shared storage will hand a job one node never registered to another, and as long as that node's scheduler.enabled is on it fires anyway — only a node with it switched off leaves the fire to someone else.

What you give up

Dying after the fire is not re-issued: a row still open waits until it passes 1.5 times its own timeout before the reaping round writes it back — at the default 300 seconds that is 7.5 minutes at the earliest and 12.5 minutes at the worst — while that remote run is still going and nobody owns it. No retry, no alerting egress. No fencing, no idempotency, and the same task can be dispatched twice — idempotency has to be built into your business logic. There is no "next fire time" column on the page; that value exists only inside the schedule tables. Editing a task sends it back to the disabled state whichever field you changed, and you have to start it again by hand.

The takeover window is derived on paper: the integration test ClusterSingleFireIT verifies only "several replicas, one task, one fire". It covers neither takeover nor load balancing nor the real call chain. The replica count is not written in compose; the deploy script's SCHEDULER_REPLICAS decides it, and the default is two.

Fig 3 · Projection converges every round, it does not append

Skill lifecycle

The problem

A skill package is not a few lines of prompt. It gets unzipped into the sandbox, read back by file tools, and becomes part of the model's executable surface. So every step between its source and its duty deserves a hard constraint.

How it is done

Before storage it passes 9 content-scan rules. A hit is written into the scan report that comes back synchronously, the skill is stored in the disabled state, and it becomes usable only after a human confirms — detained first, reviewed after. The three source types that go through that ingest flow each carry their own constraint (the platform's own built-in kind has no source to refresh): Git runs a protocol allowlist, so addresses that could reach a local or external program are excluded explicitly; npm installs with --ignore-scripts, giving a package's hooks no chance to run; ZIP has four ceilings (5000 entries, 20 MiB per file, 200 MiB total, depth 512) and going past one throws SecurityException instead of truncating. Two locks interlock: a skill in the disabled state cannot be bound to an agent, and a skill that still has a binding cannot be disabled or deleted — a security verdict is the single exception. One install request submits at most 1000 of the selected skill names; past that it is refused, never silently truncated.

What you give up

No version history and no rollback — a change is a change. The skill table's own status holds two values, and on its row "awaiting review" lands in the disabled cell; but the queue on the draft side is real: four states — pending / approved / rejected / expired — with a reviewer, a review time and a rejection reason, and promotion re-runs the scan and writes into the review log. What is missing is assignment and multi-stage co-signing, not the queue. Skills can be stored in but never exported out of the admin console. The AI-authored-skill capability was built and then switched off deliberately: the write switch defaults to closed and the skill repository is read-only for agents. A scan hit is handled as "route it to a human with a safety reason", not as a hard refusal — so do not read this line as "it will always catch it". The dangerous-list constant table lives on the execution engine's side and cannot be re-verified from this repository.

Team-level skills project to the lead, agent-level skills to the members; the lead has no file tool and cannot read the projected directory, and the system logs a WARN about precisely that — the implementation-level evidence behind "the lead has knowledge, but no hands".

Fig 4 · Six tables, three read back

Execution records

The problem

"Recorded" and "visible" are two different things. Six tables are written; only three places on a page read them back.

How it is done

The usage table holds one row per model call, hung on the call-finished event, so streaming and non-streaming give the same reading. The tool table holds one row per call with the arguments and the return value, but each of the two is cut to 2000 characters, the whole collection can be switched off, and its rows land asynchronously in batches. The process log follows streaming deltas, so a single call may write dozens of rows — capacity cannot be estimated as one row per call. The gateway's call log records only which call, how long, success or failure: it deliberately carries no body, measures duration to the point where the request truly ends, and is likewise written asynchronously in batches — 50 rows or every 5 seconds. The last table, mcp_call_log, records MCP token issue, refresh and revocation, not MCP calls themselves — the tool-name column it reserves stays empty. The dashboard itself is 7 stat cards, 3 pie charts and 4 series lines, grouped along four dimensions with four time buckets; the usage and gateway lines aggregate live, while the tool line reads an hourly table folded ahead of time.

What you give up

Two of the ledger tables are written but not read by the application layer, so reading them means connecting to the database yourself. The usage table has no user column, so nothing can be counted per head; fee is always 0, that column's precision cannot hold a cent and the repository has no unit-price table either — yet the dashboard still renders a ¥0.00 card. No quotas, no thresholds, no alerting — the rate limiter limits requests per minute, nothing else. Cleanup covers one place only, the tool invocation detail: a day's rows go after 90 days once that day has been folded into the hourly table, while the other tables carry no delete statement at all and the process log's TEXT column has a hard ceiling with no truncation guard on the writer. The call chain has no global identifier; the only thing that strings it together is the session id. The "execution process" you can look back at on the page comes from runtime state, not from these ledger tables.

A failed write is always caught — you lose a row, not the answer. The one item in this list that is unreadable by default is the usage table: with no tenant condition in the SQL it returns empty rather than everything, and figures show up only because the interface side fills in a default tenant.
