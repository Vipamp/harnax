Deployment

It runs on your own machine, and this page lists what that asks of you

One compose file, one build script, ten service blocks. This page lays out their resource ceilings, the go-live order, and the string of things you have to supply afterwards — line by line.

Ten service blocks and the ceiling each one carries

This table is the entire content of the compose file in the repository: 9 blocks are the system itself, and the tenth is the bundled weather demo MCP that shows how an external tool gets wired in. It is not in the build script's list of six images — compose builds it in place.

Except for the entry's 80 and 443, every port published to the host is a five-digit number starting with 2, so it never collides with another project already holding the usual database and cache ports.
ServiceRolePublished to hostLimits for this block
mysql Carries the five business databases: the databases are created by the first-boot init script, the tables by each service's own migrations yes 1 core / 1024M
redis Shared routing state: session bindings, the instance registry, re-selection locks and breaker state. Standalone or Sentinel only, and it must stay noeviction — once memory pressure evicts the routing keys, sessions quietly lose their binding and the locks go with them, which is worse than a failed write yes 0.5 core / 768M
minio Object storage: cross-restart snapshots of sandbox workspaces, CLI package archive yes 1 core / 512M
admin The admin console back end, and the main writer into the business databases yes 2 cores / 1024M
router Session gateway: sends a request back to the same executor instance according to the session binding, re-checks health, breaks the circuit, proxies streams yes 2 cores / 1024M
scheduler Scheduled firing and execution; Quartz cluster state lives in its own database; the replica count is decided only on the command line and deliberately absent from compose no — reachable only inside the container network 1 core / 768M
agent-service The execution engine and the sandbox lifecycle; its container mounts the host Docker socket in order to open sandboxes yes 2 cores / 2048M
channel-service The IM access layer: persistent connections and callbacks for Feishu, DingTalk and WeCom yes 1 core / 768M
mcp-server The bundled weather demo MCP, showing what registering, authorizing and calling an external tool looks like yes 0.5 core / 256M
frontend nginx: SPA static assets, the reverse proxy to each service, and the 443 entry — HTTPS is configured, but you bring your own certificate yes, 80 and 443 1 core / 256M

Limits total 12.0 cores / 8448M; reservations total 4.5 cores / 2688M.

Those two totals are not a starting specification. Nothing in the repository states a minimum machine; they are ceilings this compose writes for itself, not an answer to "how big a box do I need". Size the machine against your own session volume, sandbox concurrency and where the model runs.

Go-live order: one script, four steps

The build genuinely needs network — Maven and npm fetch dependencies, and we are not hiding that. At runtime there is no reporting path, and every egress point is configuration.

  1. Pre-install mvn, node and docker. The build script checks that the first two exist and stops to tell you which one is missing.
  2. Run bash build.sh. It produces six service images — admin, router, agent-service, scheduler, frontend, plus the channel-service that carries Feishu, DingTalk and WeCom access — and prepares the default sandbox image and the CLI package shelf.
  3. Put your own certificate in place. The 443 server points at /etc/nginx/ssl/server.crt and .key, the ssl/ directory is not in the repository, and there is no self-signed helper anywhere in it. With no certificate in place the symptom is "the entry does not start": nginx fails during configuration load, and port 80 does exactly one thing — send people to 443 — so it will not quietly degrade to plain HTTP.
  4. Run bash deploy-all.sh. It is a cold start: the whole stack comes down and comes back, including every scheduler replica. In cluster form you must pass --scale scheduler=N; the replica count is not in compose, so dropping that argument scales you back to one machine. To swap the image of a single service, use deploy-service.sh, which stops and starts scheduler replicas one at a time.
Triggers pile up during the cold start. Between the stack going down and mysql's health gate plus the JVM coming back, expired triggers that were missed are dropped outright under the DoNothing policy for tasks with concurrent=0 — not re-issued, not retried, not alerted. Run it in a quiet window; for ordinary image swaps use the single-service rolling path.

The operations list you take on after go-live

Four buckets: what must be changed, what you must add yourself, what we did not build, and what we decided against. The last bucket is not modesty — it is a design choice.

Default values you must change

The shipped password and the three kinds of secret are strings published in the repository: the admin password, the JWT secret, the AES key, the internal API secret, plus the object-storage and database passwords. Only the session gateway's redis mode — which requires noeviction on the cache side — carries one startup check that refuses a placeholder secret; the other services merely log a WARN when they hit one.

Encryption covers key material only (AES-256-GCM); conversation bodies and tool arguments go into the database plaintext.

Components you must add yourself

Certificates (the step above); backup and restore — there is no export script anywhere in the repository, only one line in the specification saying that a backup is mandatory before a migration, and what you back up is the whole database, not just the session tables.

Prometheus scrape configuration and alert rules; container stdout rotation and ceilings depend on the host's Docker daemon configuration, and compose has no section for it.

What we did not build

Container orchestration — this compose file is all there is, and there is no third way to run the system. An alerting egress — after a failure nobody is on it, only logs, metrics and health status.

Cleanup for the observability tables: only the two scheduler-domain tables have hardcoded retention (execution logs 90 days, the lock table 7 days, neither configurable). The remaining ones have no delete statement at all, and there is no partitioning or capacity guard either.

What we decided against

Running stdio-type MCP: that path would have the executor's container spawn the process, and that container mounts the host Docker socket, so there is no isolation on the running side. The switch defaults to closed.

AI-authored skills: the capability exists, the write switch defaults to closed, and the skill repository is read-only for agents. These two are decisions, not a backlog.

What it sends out: three classes

No telemetry at runtime, no version check, no license validation; metrics are only ever scraped, passively, by you. Outbound traffic comes in the three classes below, and each of them is configuration.

Models

Three protocol families: DashScope, OpenAI-compatible, Ollama. The address is configuration, and an OpenAI-compatible baseUrl can point at an internal address; Ollama defaults to localhost:11434 and that family does not read an API key at all.

External MCP

The url you register in the admin console — any address, which may equally be an internal one. The bundled demo MCP takes this same path. Switched off or never registered, this class of traffic simply does not exist.

IM platforms

The access domains of the three platforms — Feishu, DingTalk, WeCom — are written in source constants. Channels are enabled one at a time: a channel you do not enable has no connection pointing at it.

What "private deployment" means precisely here: the egress points are the three classes — model, external MCP, IM — every one of them configuration, with no reporting path at runtime. It does not mean "it never communicates with anything outside". The build needs network, and retrieval is a keyword implementation that does not even need an embedding model: those two sentences are two faces of one fact.
