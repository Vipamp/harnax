This page decides how far a sentence can be stated clearly

The other pages say what the system does. This one covers three things: which functions we cannot state clearly, which common wordings we narrowed on purpose, and what each assertion rests on.

Where we cannot state it clearly, we do not sell it as a function

These lines are not "not written yet". Each was checked against source and cannot be stated the way it is usually stated. Left is the usual claim, right is what holds.

Usual claimWhat is true
stdio-type MCP can at least be registered Not even registration is allowed by default: registering is refused on the spot, and runtime adds several more layers of interception. The switch lives on the deployment side and defaults to closed.
The reasoning iteration cap is adjustable The field genuinely exists on the engine side — the iteration cap in AgentSpec, default 10 — but no production code ever assigns it: the agent table has no such column and the admin form has no such input. At runtime it stays at that default.
Channel capabilities can be toggled in the admin console The form carries connection fields (credentials, callback url, listen mode) plus one on/off switch for auto-listening. Capability bits — whether this channel streams, for instance — are overridden at compile time inside each adapter and have no configuration entry at all.
A finished scheduled task posts its result back into the group That link does not exist: the end of an execution writes only the execution log, visible in the admin console. No result appears on its own in a Feishu, DingTalk or WeCom group.
Directing a team from a group chat Team mode hangs on the web- prefix alone — the console and iOS share that one create endpoint — and neither mp- nor chn- carries a team field when it is created. What runs in an IM group is a single AI employee.
Every MCP call leaves a record That table does have a writer, but what it writes are authorization decisions: token issuance, refresh and revocation. The tool-name column it reserves is left empty by production code and filled only in tests.
All observability writes are asynchronous Three shapes do not collapse into one sentence: the usage table and the process log are written synchronously a row at a time; tool invocation detail goes through a buffer flushed at 64 rows or after 200 milliseconds; the gateway's call log has its own buffer flushed at 50 rows or every 5 seconds; and the hourly table is not written by events at all — the admin console folds it once an hour. Both buffers drop the newest row and count the drop when the queue is full.
Files can be delivered straight to every channel The capability bit does exist in the channel adapter, but this site does not present it as a function: it is open on exactly one IM adapter, and that is not a channel we promote here.
Why this table belongs on the site. For a system meant to run for years, the failure surface is worth reading before the capability surface. Every line above is "checked, and it cannot be said that way", not "not checked yet".

Wording we narrowed on purpose

These claims are not false, but stated as they usually are they outrun what the code can back. Left is the usual wording, middle is the wording this site actually uses.

Usual wordingWording used hereWhy it was narrowed
Nobody can get past a dangerous operation Dangerous commands and sensitive paths are forced into human confirmation The enforcement point sits inside a third-party kernel this repository cannot re-verify, so no absolute wording.
The lead carries no tools at all The lead carries no business tools, no MCP, no sandbox, and keeps only 3 team-orchestration tools A whitelist really exists, but "no tools at all" is false.
Visual scheduling A cron expression field plus 5 common presets There is no drag-and-drop editor.
Tokens are decrypted at runtime Key material is encrypted with AES-256-GCM in storage and decrypted on the admin side before dispatch What the executor receives is plaintext; encryption covers only the stretch inside the database.
We verify PKCE Authorization requests are required to carry PKCE The challenge is verified on the authorization server's side; our side only enforces that it is carried.
Every kind of request retries only on failure Streaming fails over only while nothing has been delivered yet; non-streaming retries on connection errors and server-side status The two paths have different conditions, and a stream that has emitted any event is not retried.
The breaker trips after 5 failures By default 3 consecutive failures break the circuit for 30 seconds (gateway side) The 5 is a breaker threshold of its own — the channel service calling into the gateway, open for 30 seconds as well — not a message retry parameter. The retry lives elsewhere: three attempts in each platform's HTTP client. Two breakers sitting side by side are exactly what gets conflated.
Sandboxes are reused without limit A keep-alive pool capped at 100, reaped after 30 minutes idle There is a real limit, and reaping happens in a background sweep.
The usage dashboard shows how much was spent A usage dashboard grouped by model, agent and session That fee column always writes zero, its precision cannot even hold a cent, and there is no unit-rate table anywhere in the repository.
Tenants are completely separated A tenant is a grouping dimension for configuration and statistics; the main isolation on the session list is really the creator There is a web-layer tenant interceptor, but it only parses the request header, checks membership and writes a thread context — it adds no condition to the SQL. Filtering is a hand-written WHERE in each mapper, and the by-id batch reads for skills and agents are missing it.
Full-flow automated test assurance The login path has end-to-end cases, and the persistence layer starts a real database with Testcontainers End-to-end coverage lives in one separate test module and consists of the 5 authentication cases; business pages have zero end-to-end cases. The console's own jest suite is essentially pure-function unit tests with a single render-level case, and that one is login too.
The mobile app is feature-complete The iOS client already covers teams, skills, memory and scheduled tasks, and a mini program exists as a project of its own; neither has been verified on a real device "Under construction" understates what iOS actually covers, and "complete" overstates what has been verified. Coverage counts the feature directories in the repository; verification status can only be stated against a real device. The older mobile project is down to four pages and is wired into no build script.
There is only one direction to narrowing. Turn "always" into "the mechanism", turn "it has everything" into "which layer has it". Wherever a sentence was changed that way, the other pages of this site use the changed version.

Where the wording comes from

Every functional statement on this site was written by reading source directly; product documentation is only ever a lead, and the evidence is always what the repository has committed.

How each line is judged

A claim earns its place on the page by landing on a concrete file:line: whether a field exists is read from the DTOs and the migration scripts, how something behaves from the implementation and its tests, what the default is from the configuration defaults and that compose file. Where documentation and code disagree, the page follows the code.

Evidence is always taken from what the repository has committed, never from uncommitted working-tree changes. That discipline was written down after being bitten once: one draft read local uncommitted deployment files and turned an entry that was already configured into one that was "not configured yet".

This page was itself inside the re-audit. Reading the source again by domain overturned more than a dozen statements that had looked correct — how many observability tables there are, which node a scheduler step-aside actually yields to, whether an approval queue exists at all, whether port 80 only redirects. So nothing below claims to be covered by one finished checklist: each line went back to the code, and each line can be overturned again.

Updated 2026-10-12. A stale claim is worse than stale copy, so this date sits on the page alongside the claims.

The machine gate

The copy is held by one zero-dependency script that runs five checks: banned wording has zero hits site-wide; every number in body text must be on a traceable whitelist; if a sentence's first half is written, its second half must be in the same paragraph; the two language trees have identical table of contents, anchors and links; and the palette's contrast is computed from WCAG relative luminance.

The gate has to be provably working itself: it ships with a fixture containing several seeded violations, and the run fails if it does not catch them.

If this page and the code disagree, that is a defect. There is no "close enough" setting on this site. If any description disagrees with actual behaviour, please report it as a bug — naming the page and the section is enough.
