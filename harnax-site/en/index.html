Entry points you can see

Four things you can watch it do

Not a demo reel. Each entry point can say which chain it walks and at which step it stops and waits for a person.

One

Give it work in a group chat

The group parses 10 kinds of slash command, case-insensitive (/approve, /deny, /clear, /stop and /compact are only some of them; adapted for Feishu, DingTalk, WeCom and other channels); the approval request goes back into the same group, and the suspended step resumes once it is cleared. One thing to say up front: a command that takes arguments keeps only its name in the group, so the argument is dropped when it is forwarded. Reconnects with exponential backoff; with several replicas one MySQL named lock decides who is listening.

Two

It works the night shift while you sleep

cron expressions plus 5 common presets; tasks, trigger locks and execution logs live in the scheduler's own database, so a restart does not lose them. Execution logs carry six states, and a row still open past 1.5× its own timeout is marked dead by the reaper.

Three

Work one AI cannot finish goes to a team

The lead keeps only 3 orchestration tools — no business tools, no MCP, no sandbox; members keep their own tools and skills. A delegation cap of 20, 900 seconds per member turn and 20 MiB per artifact file are enforced at runtime — but they are configuration defaults, not hardcoded constants; change them and the enforcement follows the new values.

Four

It stops and waits for your signature

Commands and file operations run inside a separate container, with argument-level scanning for dangerous commands and sensitive paths; a hit becomes a human approval request carrying the safety reason. Workspace snapshots go to object storage, so a restart can pick them back up.

Group chat and team are two separate scenarios: team mode hangs on the web- session prefix alone — the console and iOS share that one create endpoint — and neither mp- nor chn- carries a team field when it is created. What runs inside an IM group is a single AI employee. The two do not stack.
Runtime mechanisms

Four mechanisms you cannot see

Four decisions determine whether it can run for a long time: where state lives, who owns this fire, how a skill gets into the library, and what each step leaves behind.

Fig 1 · Which state survives a machine swap

Why a session sticks to one machine

The problem

Part of the agent's mutable state is not in the database — it is in one process's memory and on its local disk: the ReAct loop's context and the sandbox workspace. The "stateless service plus round-robin balancing" model stops working here.

How it is done

Waiting for approval runs down two paths and must not be told as one: in a plain session a tool confirmation closes the round, and the pending call is stored in the ASKING state and rebuilt by id once it is cleared, so another instance can pick it back up; the team sub-run is the thread held by future.get() — a 600-second window sliced into 30-second keep-alives, and it physically cannot be moved. Three clocks turn "the process stopped" into something decidable: report every 10 seconds, recheck every 5, declare dead after 30, so detection lands 20–35 seconds later. New sessions land by random draw weighted by 1/(sessions + 1); on failover, a candidate busier than twice the average is traded for the smaller one.

What you give up

A snapshot is written at the end of a turn, so a crash loses the last one, and the half-streamed output of that turn is not replayed. Streaming fails over only on a connection-class error, and only before the first event has been emitted.

What is pinned is the executor instance; the gateway itself runs several replicas sharing the same binding table. The stickiness exists because someone is waiting for an answer, not for load balancing. That shared table lives in Redis: standalone or Sentinel only, and it must keep noeviction.

Fig 2 · Two locks, and a window you should not misread

"Fired once" and "done once" are two different claims

The problem

Scale the scheduler to 3 replicas: do all three strike the eight o'clock task? And if the one that fired dies moments later, does today's briefing still go out?

How it is done

Two locks: Quartz's cluster row lock decides who receives the trigger, then we drive the unique key (task_id, trigger_time) on our own trigger-lock table to decide who owns this fire. The takeover window is 22.5–52.5 seconds, under the 60-second misfire threshold.

What you give up

A death after the fire is never re-issued: a row still open waits until it passes 1.5× its own timeout before the reaping round marks it timed out — at the default 300 seconds that is seven and a half minutes at the earliest, twelve and a half at worst — while the run over there is still going and nobody owns it. Idempotency is not something this system can hand you — it has to live in your business logic.

The takeover window is derived on paper. The integration test ClusterSingleFireIT covers single firing only; takeover, balancing and the real call chain are not covered.

Fig 3 · Detained first, reviewed second, on duty third

A skill is not a prompt snippet

The problem

A skill package is a pile of files that gets unpacked into a sandbox and read by file tools. Should someone gate it before it enters the library?

How it is done

Nine content-scan rules run before import; a hit is written into the scan report returned with the call, and the skill is stored disabled — usable only after a person approves it. Each of the three source kinds that reaches the library has its own hard constraint (the built-in kind does not come this way): Git goes through a protocol allowlist, npm installs carry --ignore-scripts, and ZIP has four ceilings that raise SecurityException rather than truncating. Projection converges every turn against a sha256 manifest; no difference means zero writes.

What you give up

There is no version history and no rollback — change it and it is changed; the skill's own status field holds two values. But the approval queue is real: a draft an AI proposes walks four states — pending / approved / rejected / expired — with the reviewer, the review time and the rejection reason recorded, and promotion re-runs the scan and writes it into the log. What is missing is assignment and multi-stage co-signing, not the queue itself. The AI-authored-skill capability was built, its write switch defaults to closed, and the skill repository is read-only for the agent.

Fig 4 · Six tables, three of them readable

Six tables written, three of them readable

The problem

"Recorded" and "visible" are two different things, and "visible" and "reconcilable" are two more.

How it is done

The usage table takes one row per model call, and streaming and non-streaming produce the same reading. The gateway log records which call, how long, succeeded or not — deliberately without the body — and lands asynchronously in batches. Tool invocation tracing is asynchronous too: by default it waits until 64 rows have piled up or the refresh interval passes, arguments and return value are each cut to 2000 characters, and the whole collection can be switched off. The remaining three — usage, process log and MCP token authorization — are the synchronous writes, a row at a time, and that MCP table records token issue, refresh and revocation, not MCP calls themselves.

What you give up

Two trace tables have no read path in the application: to see them you connect to the database yourself. The fee column is always 0, and its precision cannot even hold a cent; no unit-price table exists anywhere in the repository, yet the dashboard still renders a ¥0.00 card. There are no quotas, thresholds or alerts, the rate limiter only limits requests per minute, and a call chain has no global identifier — the only thing that strings it together is the session id.

Ways to run it

Three ways to run it, instead of the usual plan table

There are no plan tiers here. The choices are "where does state live" and "does the model leave the building", not "how many seats".

CACHE_TYPE=local

Single machine

  • SQLite plus an in-process cache, no external dependency
  • The same routing logic still picks an instance, retries and trips the breaker
  • Right for getting the chain working before talking about scale

cluster profile

Cluster

  • MySQL + Redis; Redis is standalone or Sentinel only, and must keep noeviction
  • The binding's read-modify-write happens in one Lua script, so concurrent writes cannot clobber it
  • The scheduler's replica count reaches --scale through the script's SCHEDULER_REPLICAS; compose writes no replica count, and the default is two

Three protocol families

Models can stay inside

  • DashScope, OpenAI-compatible and Ollama — three protocol families
  • Ollama defaults to localhost:11434 and that branch never reads an apiKey
  • The OpenAI-compatible baseUrl may be an internal address and port
  • Retrieval is keyword-based, so not even an embedding model is needed
Every factory default is a string published in this repository: change the passwords and the three kinds of keys yourself. If you skip this, none of the boundaries on this page hold.

Boundary summary

Four things we did not build

They are on the front page because they find you in the first week of running this. Admitting a boundary is harder, and worth more, than finishing the pitch.

Missing

Backup and restore tooling

What you must do: the backup scope is more than one database — conversations and observations sit in the admin database, tasks and execution logs in the scheduler's own database, and the routing table in a third one. You schedule the backups and you run the restore drill.

Missing

An alerting egress

What you must do: nobody notifies you when the night shift fails. Only three services expose a scrape endpoint — the gateway, the scheduler and the channel service; the admin console and the executor expose none. Scraping, thresholds and the on-call route are all your job.

Missing

Version rollback and owner hand-off

What you must do: a skill has only a pointer to its current version, and no rollback. The draft approval chain does record state, reviewer, review time and rejection reason — but that is a queue, not a hand-off: there is no assignment and no multi-stage co-signing.

Missing

Container orchestration

What you must do: compose is the only delivery form. Moving these ten blocks onto a multi-node orchestrator means writing that inventory yourself.
