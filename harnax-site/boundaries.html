这一页负责把话说清楚到哪个程度

站内其它页在讲它做了什么，这一页讲三件事：哪些功能我们说不清、哪些常见说法被我们主动收窄、以及每一条断言凭什么写在这里。

说不清的功能，我们就不说成功能

这几条不是「暂时没写」，是查过源码之后确认无法按常见说法讲出来。左边是那句常见的说法，右边是实情。

常见说法实情
stdio 型 MCP 能先登记起来 默认连登记都不允许：登记即拒，运行期还有多层拦截。开关在部署侧，默认关闭。
推理迭代上限可调 字段在引擎侧真实存在（AgentSpec 的迭代上限，默认 10），但没有任何生产代码给它赋值：agent 表没有这一列，管理台表单也没有这一项。运行期恒为那个默认值。
渠道能力可以在管理台开关 表单里只有连接类字段（凭据、回调地址、监听模式）加一枚「自动监听」启停开关。能力位——比如这一路渠道走不走流式——编译期就覆死在各适配器实现里，没有任何配置入口。
表单里选得到的供应商类型就是它支持的 两个前端给的候选不是一套：管理台只列 dashscope／openai／ollama，小程序那张表单多列 azure、deepseek、zhipu、moonshot、anthropic 与 other。运行期认的还是这三种——其余类型保存得进库，等装配模型时才在执行服务日志里落一条 Unsupported provider type，会话按「模型配置不存在」那个错误码失败，报错指不到真实原因。
定时任务跑完把结果发回群 这条联动不存在：执行链结束只写执行日志，管理台可见，飞书、钉钉、企业微信的群里都不会自动出现结果。
在群里指挥一个团队 团队模式只挂在 web- 这一种前缀上（网页与 iOS 共用这个创建入口），mp- 与 chn- 创建时都不带团队字段——IM 群里跑的是单个 AI 员工。
每一次 MCP 调用都留一条记录 那张表确实有写入方，但写进去的是令牌的签发、刷新与吊销这类授权决策；表里预留的工具名列生产代码一律留空，只有测试会填它。
所有观测都是异步落库 三种形状混不成一句话：用量表与过程日志同步单条写；工具调用明细走缓冲，攒到 64 行或过 200 毫秒才落；网关那张调用日志另有一套缓冲，50 行或 5 秒落一次；小时表不是事件写的，是管理台每小时折一次。两处攒批在队列满时都丢新行并计数。
文件能直发到每个渠道 渠道适配里确有这个能力位，但站内不把它当功能讲：它只在某一个 IM 适配上打开，而那个渠道我们不在这里推广。
为什么把这张表放在官网上。一个能长期运行的系统，失效面比能力面更值得先看一遍。上面每一条都是「查过、确认不能那么说」，不是「还没查」。

被主动收窄的表述

这些说法不是假的，但按原样讲会超出代码能背书的范围。左列是常见写法，中列是站内实际采用的写法。

常见写法站内写法为什么要收窄
危险操作谁都绕不过 危险命令与敏感路径强制转人工确认 强制点在第三方内核里，本仓无法复核，不能用绝对化的话。
主管不带任何工具 主管不带业务工具、不接 MCP、不给沙箱，只保留 3 个团队编排工具 白名单真实存在，但「不带任何工具」是假的。
可视化排班 cron 表达式输入，外加 5 个常用预设 没有拖拽编辑器。
令牌在运行期解密 密钥类字段以 AES-256-GCM 加密落库，下发前在管理面解密 执行侧收到的就是明文，加密只覆盖库里那一段。
我们校验 PKCE 授权请求强制携带 PKCE challenge 的校验在授权服务器那侧，我们这一侧只负责强制携带。
各类请求只在失败时重试 流式仅在结果尚未送达时才做故障转移；非流式对连接错误与服务端错误状态重试 两条路径的条件不同，已经吐出任何事件的流不再重试。
熔断 5 次失败 默认连续 3 次失败熔断 30 秒（网关侧） 5 次是渠道服务调用网关那一路的熔断阈值，同样开闸 30 秒，不是消息重试参数——重试另有出处，是各平台自己 HTTP 请求层那 3 次。两套熔断摆在一起最容易被混着说。
沙箱无限复用 保活池上限 100，空闲 30 分钟回收 有真实限额，回收由后台清扫完成。
用量看板显示花了多少钱 按模型、Agent 与会话维度的用量看板 那个 fee 列恒写零，精度连「分」都存不下，全仓没有单价表。
多租户之间完全隔开 租户是配置与统计的分组维度，会话列表的主隔离其实是创建者 Web 层确实有一个租户拦截器，但它只解析请求头、校验归属、写线程上下文，不给 SQL 加任何条件；过滤全靠在每条 Mapper 里手写 WHERE，技能与 agent 的按 id 批读就有漏网的。
全流程自动化测试保障 登录链路有端到端用例，持久层用 Testcontainers 起真实数据库 端到端全貌集中在一个独立测试模块里，且只有认证链路那 5 条用例；业务页面零端到端用例。管理台前端那套 jest 基本是纯函数单测，只有一条渲染级用例，也是登录。
移动端功能齐全 iOS 客户端已覆盖到团队、技能、记忆与定时任务，小程序另有一套工程；两者的真机验收都没做过 「建设中」低估了 iOS 的实际覆盖面，「齐全」又超出已验证的范围。覆盖面按仓库里的功能目录算，验收状态只能按真机说；更早那套移动端工程只剩四个页面，也没有接进任何构建脚本。
收窄的方向只有一个。把「绝对化」改成「机制」，把「都有」改成「在哪一层有」。凡是被这样改过的句子，站内其它页就用改后的那一版。

口径从哪来

站内的每条功能描述都直接读源码写出来，产品文档只当线索；判据一律取仓库里已提交的内容。

判据方式

一条断言要落到具体的 文件:行号 才写进页面：字段存不存在看 DTO 与迁移脚本，行为怎么样看实现与测试，默认值多少看配置项缺省与那份 compose。文档与代码对不上时以代码为准，页面上按代码写。

判据一律取仓库已提交的内容，不取工作区里尚未提交的改动。这条纪律是踩过一次才写死的：有一版成稿读了本地未提交的部署文件，把已经配好的入口状态写成了「还没配」。

这一页也在重审范围内。按域重读源码之后改掉了十几处原本看着写准了的说法，例如观测表的数量、调度让行让的是谁、审批队列到底存不存在、80 端口是不是只做跳转。所以下面这些表述不声称已被某一份一次性清单全覆盖——它是一条条回代码核的，也是一条条可能被再次推翻的。

机器闸

站内文案由一个零依赖脚本把关，五种检查各跑一遍：禁用词全站零命中；正文里出现的每个数字都要在可回溯白名单里；写了前半句就必须同段写后半句；中英两棵树的目录、锚点与链接逐项相等；配色按 WCAG 相对亮度算对比度。

闸自己也要能被证明有效：它带一份夹具，里面埋着几条违规，跑不出这些违规就判失败。

如果这一页和代码不一致，那就是缺陷。站内没有「差不多」这一档。发现任何一条描述与实际行为不符，欢迎直接把它当 bug 报出来——报的时候带上是哪一页的哪一节，够用。
