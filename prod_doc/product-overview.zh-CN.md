# Harnax 产品描述

> 项目性质：个人独立项目，架构设计、接口契约、全部实现与部署环境均为本人独立完成，非职务作品。本文按当前代码库实际能力整理。规模口径：21 个 Maven 模块（11 个顶层 + agent/channel 子模块）、5 个可独立部署服务，后端全量 Kotlin（主代码 552 个文件约 6.1 万行、测试约 8.1 万行，不含前端），另有 React 管理台与 uni-app 移动端。

## 1. 一句话定位

Harnax 把 AI Agent 从「一次调用」做成「可长期运行的系统」：配置化装配、可中断可恢复的流式执行、沙箱隔离的工具执行、会话粘性的多实例路由、集群化定时触发，以及 Web 与 IM 多渠道接入。

它解决的工程问题是：Agent 的可变状态（ReAct 循环上下文、workspace 文件、等待人工确认的挂起态）不在数据库里，而在某个进程的内存与磁盘上。一旦要横向扩容、要定时自启、要从 IM 侧触达，「无状态服务 + 轮询网关」的模型就会失效，整套架构都围绕这个约束展开。

## 2. 分层与模块

| 层 | 模块 | 职责 |
|----|------|------|
| 配置与能力中心 | `harnax-admin` | Agent 规格、模型服务商、MCP、Skill、工具、API 凭证管理 |
| Agent 运行时 | `harnax-harness-core`、`harnax-agent-service` | AgentSpec 解析执行、模型与工具适配、SSE/批式通道 |
| 会话网关 | `harnax-session-router` | 「会话 → 实例」放置决策与转发、健康探测、熔断 |
| 调度 | `harnax-scheduler` | 定时触发的 Agent 任务，独立数据源 |
| 渠道接入 | `harnax-channel`（sdk / feishu / wechat / dingtalk / wecom / service） | 回调解析、流式回传、平台差异屏蔽 |
| 工具与执行环境 | `harnax-tools-sdk`、`harnax-agent-utils`、`harnax-tools-external`、`sandbox-plugins`、`harnax-cli` | 工具契约、模型与 MCP 适配、沙箱内 Go CLI |
| 前端 | `harnax-webui`、`harnax-app` | React 管理台与 uni-app 移动端 |

技术栈：JDK 21 + Kotlin（主代码无 Java 源码）+ Spring Boot 4 + MyBatis + MySQL + Redis + Quartz + Jackson 3 + WebFlux/Reactor；Agent 能力内核基于 AgentScope 2.x；交付形态为 Docker Compose 一键起全链路（含 MySQL/Redis/MinIO 与前后端共 10 个容器）。

## 3. 核心能力

### 3.1 声明式 Agent 装配

`AgentSpec` 把一个 Agent 定义为可序列化描述：模型标识、系统提示词、最大迭代数、工具集、MCP 服务、Skill 包、CLI 工具链与执行计划。运行时不依赖具体配置来源，而通过 8 个 Adaptor SPI（模型配置、MCP 配置、Skill、Token 统计、过程日志、工具调用日志、计划便签、令牌来源）反向获取信息，因此同一份执行内核既可嵌在服务里，也能脱离配置中心独立运行。模型侧适配 DashScope、OpenAI 兼容协议、Ollama 与 Anthropic。

### 3.2 流式、批式、确认与中断

对话事件建模为密封类族（正文流、思考流、工具调用、工具结果、工具确认、结束、错误），SSE 与批处理通道复用同一套事件语义，渠道侧可自选流式或分片长轮询。除对话与流式端点外，另有确认、命令、按会话中断三类旁路端点，配合状态持久化实现挂起后回到同一实例续跑。

### 3.3 隔离的工具执行环境

工具、CLI 与 Skill 在 Docker 沙箱内执行，镜像可按 CLI 规格现场构建，并有保活池与 MinIO 快照支撑状态回收。执行前经权限引擎与危险输入检测拦截，过程日志与工具调用日志异步落库，形成可回溯的执行记录。

### 3.4 会话粘性与部署形态

Router 只持有三份状态：实例注册表、会话绑定与熔断状态，本身不承载业务数据。它提供会话粘连路由、5 秒健康探测、基于 CAS 的故障转移、requestId 幂等与三态熔断；数据面支持单机形态（SQLite + 进程内状态，零外部依赖）与集群形态（MySQL + Redis，跨键操作用 Lua 脚本保证原子性），Redis 不可用时经影子缓存与快照降级放行。明确不支持 Redis Cluster（跨槽脚本无法满足）是有意取舍。

### 3.5 集群化定时触发

调度把触发权交给 Quartz JDBC 集群 JobStore，用数据库租约取代「各节点自行触发 + 业务表唯一键抢锁」，消除多副本重复触发；对账采用差异式同步而非删除重建，并配套执行记录、优雅停机与带宽限期的僵尸执行回收。人工确认所需的中断投递区分「已送达 / 未命中实例 / 调用失败」三态。

### 3.6 多渠道接入

渠道层把「平台如何把消息送进来」抽象为回调推送与长连接两种通信模式，由同一套解析与回传管线承接；回调侧统一处理挑战回显、签名校验失败拒绝与各平台差异化应答体。消息去重、文本分片与基于 MySQL 命名锁的单实例监听权抢占，保证多副本部署下不重复回复。

### 3.7 出向授权与凭证安全

接入需授权的远程 MCP 服务时，刷新令牌集中保管并自动续期，运行期按调用上下文注入访问令牌；落库的敏感凭据以 AES-256-GCM 加密。

## 4. 工程质量与可观测

各服务按独立数据源由 Flyway 版本化脚本演进库表；集成测试以 Testcontainers 拉起真实 MySQL/Redis 而非 mock，另有 Playwright 端到端用例；运行期以调用日志、过程日志与可复现的 curl 级调试日志为观测口径，并针对 SSE 单独处理代理缓冲与响应缓存。

## 5. 当前边界

定位为自托管、单人可运维项目：未做 K8s 化，也无线上并发与延迟指标可引用；早期部分文档与代码存在滞后，一切以代码与配置默认值为准。
