## 1. Goals and acceptance

Three, each one decidable:

1. **`/compact` really compacts.** After a session has run a few turns, sending `/compact` replaces the model-side context with a summary, and the next turn's `input_token` in `token_stats` drops accordingly; one `/compact` costs one extra summarization call and nothing else.
2. **The page always shows every original bubble.** Whether the session was compacted once or ten times, the bubble sequence returned by `GET /api/agent/chat/history/{sessionId}` is verbatim what it was before compaction, and no "compaction summary" bubble ever appears. This is the plan's primary assertion.
3. **Occupancy is queryable.** `GET /api/agent/context/{sessionId}` returns the estimated occupancy, the real occupancy, the window value and its source in one call, so the caller can decide "do I still want to compact manually" and "how far away is the automatic trigger". The ratio is computed from the real occupancy (the `token_stats.input_token` path) while the two estimated numbers keep answering the trigger question — measurements show the two are not proportional, so both are returned and each serves its own criterion. That reading and an on-demand compaction entry point both live on the webui session chat page (section 7), so a demo needs no curl; when no reading is available the whole title bar block is absent rather than showing a `0%`.

## 2. Three facts that determine the shape

**Fact one: compaction is already running, and all harnax has to add is a controlled entry point and a reading.**
The field initial values of `HarnessAgent.Builder` are `compactionConfig = CompactionConfig.builder().build()` and `disableCompaction = false` (`HarnessAgent.java:1227,1230`); `CompactionMiddleware` is installed when all three of "compaction not disabled ∧ `compactionConfig` non-null ∧ the summary model (the config's own, else the builder's model) non-null" hold, and under the default assembly all three hold (`HarnessAgent.java:2600-2609`). Upstream's initial values are: `triggerMessages=50`, `triggerTokens=0` (the dynamic tier = model window − `reserved=20_000`, falling back to `FALLBACK_TRIGGER_TOKENS=160_000` when the model cannot report a window), `keepMessages=20`, `keepTokens=-1` (the dynamic tier = `min(8_000, max(2_000, available × 0.25))`), `flushBeforeCompact=true`, `offloadBeforeCompact=true` (`CompactionConfig.java:273-286`, `:67`). Harnax pins that same set verbatim as its own tier at the assembly layer (section 5.1); the only value it pins differently is `offloadBeforeCompact = false`. The window comes first from the model row's `context_window` (section 6) and, when that is left empty, core infers it from the model name prefix (`ModelContextWindows.java:151`) — the window is a per-model quantity, while what the tier pins is the trigger/reserve/prune set of knobs.
So "supporting compaction" is not introducing a new mechanism: it is **adding a controlled entry point and visibility to a mechanism that is already running**.

**Fact two: harnax's user-visible history *is* the model context.**
`loadSessionMessages()` at `HarnessAgentLauncher.kt:1035-1048` had exactly one way of reading before this change — return `agentState.context` (that sentence still holds today, but it is now the function's second fallback tier, the first being section 4's archive); only two places read it — `DefaultAgentRunner.kt:353-356`'s `/chat/history` and `TeamHistoryReplay.kt:44`'s member bubble merge. There was no second store.
Consequence: compaction overwriting `context` trims the user's chat log along with it. **Unless this changes, criterion 2 of section 1 cannot hold, so separating history is not an optional refinement — it is a precondition of shipping compaction.**

**Fact three: the `/compact` command path is already fully connected; only the server-side implementation was missing.**
`harnax-protocol/src/main/kotlin/com/agnetix/harnax/agent/protocol/AgentRequest.kt:67,90,199` already parses `/compact 500` into `CommandType.COMPACT` with `args="500"`; `POST /api/agent/command` at `AgentController.kt:77-86` already accepts it; the webui has the keyword-to-command mapping at `harnax-webui/src/pages/session/components/ChatWindow.tsx:957`; iOS sends it just as well — the slash-command table at `harnax-ios/Sources/HarnaxFeatures/Chat/ChatSlashCommand.swift:33` registers `compact`, `run(command:rawText:)` at `ChatViewModel.swift:1517` packages it as a `CommandAgentRequest`, and the contract enum is at `harnax-ios/Sources/HarnaxCore/Contract/AgentRequest.swift:9`. `CommandResponse` (`harnax-protocol/src/main/kotlin/com/agnetix/harnax/agent/protocol/CommandResponse.kt:13`, with `result: Any?` at `:16`) carries a `result` field that can hold a structured payload directly.
`executeCommand` in `DefaultAgentRunner.kt` (`:247`) answered the COMPACT branch (`:264`) with `Compact not yet implemented`. **No command shape has to be invented and no client has to change — the only thing missing was that one branch's implementation.**

Every upstream API on-demand compaction needs is public in 2.0.4 and reachable from the assembly layer, with no upstream modification: `ConversationCompactor.compactIfNeeded(...)` (signature `ConversationCompactor.java:92-96`), `CompactionConfig`, `TokenCounterUtil.calculateToken(List<Msg>)` (`TokenCounterUtil.java:73`), `HarnessAgent.getDelegate()/getModel()/getWorkspaceManager()/getStateStore()` (`HarnessAgent.java:492,496,246,504`), and `ReActAgent.getAgentState(userId, sessionId)` with `ReActAgent.saveAgentState(userId, sessionId)` (`ReActAgent.java:4447,4691`). Upstream's own overflow fallback `forceCompactAndRetry` (`HarnessAgent.java:1058-1101`) is the same recipe and can be copied.

## 4. Full history separated from model context

The approach: **archive session messages one by one into an append-only table and point the history read path at it; the model context stays what `AgentState.context` holds, and compaction may overwrite it however it likes.**

A new table `session_message`, in the same database as `agent_state` (the `agentscope` session database), created by the writer itself with `CREATE TABLE IF NOT EXISTS` during initialisation — the same practice as `MysqlAgentStateStore.kt:51-68` — so it does not enter admin's Flyway baseline and this table needs no database rebuild.

```sql
CREATE TABLE IF NOT EXISTS session_message (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id VARCHAR(255) NOT NULL,
    session_id VARCHAR(255) NOT NULL,
    msg_id VARCHAR(64) NOT NULL,
    role VARCHAR(16) NOT NULL,
    msg_name VARCHAR(128) NULL,
    json_value LONGTEXT NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_session_msg (user_id, session_id, msg_id),
    KEY idx_session_order (session_id, id)
)
```

| Design point | Decision | Reason |
|---|---|---|
| Unique key | `(user_id, session_id, msg_id)`, `msg_id` taken from `Msg.id` | core's `Msg` carries a UUID and serialises it with the JSON (`Msg.java:113,139`), so the same message keeps the same id across turns and across processes. The span of the key must equal the span of reads and writes: both `load` and `delete` carry a `user_id` predicate, this key is where the idempotent write lands, and losing one dimension lets a later bucket collide into the earlier bucket's rows — the measured shape is the second bucket `load`ing an empty history, so the page sees nothing at all in that bucket. The case `the same message id archived under two owner buckets keeps one row per bucket` guards this. Because the table is created by the writer with `CREATE TABLE IF NOT EXISTS`, it will not rebuild the key on a table that already exists, so a development machine that ran the older code on this branch has to `DROP TABLE session_message` for the new key to take effect; this table has not reached any deployment environment, so there is no such step in production |
| Conflict handling | `ON DUPLICATE KEY UPDATE`, the body replaced only when **the newer version is longer**, with `role`/`msg_name` following the same version | upstream rebuilds message objects under the same id in both directions: `withGenerateReason`/`withContent`/`withMetadata` at `Msg.java:668,687,704` each hand `this.id` straight back to the constructor (`:672,689,706`) with a longer body, while `ConversationCompactor.pruneToolResults` (`ConversationCompactor.java:510-588`) replaces long tool results with a head-plus-tail preview during compaction and **keeps the original id** (`:578`), giving a shorter body. In 2.0.4 pruning is on by default (`CompactionConfig.java:285` takes `PruneConfig.defaults()`, thresholds `protectTokens=40_000`/`minimumTokens=20_000`/`maxOutputChars=2_000`, `:576-578`). So "arrives later" does not mean "more complete", and keeping the longest body is what stops one compaction from shortening a bubble. The order of the three `SET` clauses is the load-bearing wall of this design: MySQL 8 evaluates the `ON DUPLICATE KEY UPDATE` assignments left to right, so a later clause reads **columns already updated by this same statement**, which is why the body clause has to come last — placed first, both length comparisons would run with both sides already equal, and `role`/`msg_name` would stay pinned to the oldest version and disagree with the body. H2's `MODE=MySQL` does not evaluate this way and accepts both orders for the same SQL, so this criterion can only be guarded by a real-database case: `MysqlSessionMessageStoreMySQL8Test` (Testcontainers `mysql:8.0`), which asserts that body, `role` and `msg_name` all follow the longest version together |
| Write points | at the end of every turn read the live context in full and archive each message idempotently; at assembly, if that session's bucket has no archive yet, first persist the already-saved context once; `/compact` additionally writes once before compacting | append-only plus a full back-fill each round means **automatic compaction needs no in-turn hook**: middleware ordering means harnax never gets the context "at the moment before compaction overwrote it" (`CompactionMiddleware` hands the trimmed `input` to its downstream inside `onReasoning`, `CompactionMiddleware.java:132-147`), so "grab a copy before compaction" is not reachable through it. What the per-round back-fill covers is "the previous round already archived whatever is about to be trimmed", but for an older session whose archive is still zero rows, the round that carries its first new message is exactly the exception to that invariant — the head automatic compaction trims in that round was never archived. The fix moves one archiving point ahead of the round: at assembly completion (`HarnessAgentLauncher.kt:919`) ask `store.hasArchive(userId, sessionId)` (a `LIMIT 1` existence query, not a count, and no body read-back) and if there is nothing, `backfillArchive()` writes the already-persisted context first. Once per assembly rather than once per round; after that each round's full back-fill covers it, and on restart the archive is already non-empty so it is skipped. The manual one is user-pressed and can write first: for an older session that is still zero rows in the archive (the fallback branch on the next line exists precisely for those), a manual compaction would erase the head messages from `context` and from the fallback reading at the same time, so the command treats "the archive accepted the write" as a precondition and refuses if it did not (section 5 step 2) |
| Ordering | the local auto-increment `id` | the session database connection uses `serverTimezone=UTC` (`SessionConfig.kt:44`) while the primary database uses `Asia/Shanghai`, so time columns across the two are not comparable. The timestamp shown to users comes from `Msg.timestamp`, which `MessageLogConverter.kt:44-66` already reads today |
| Serialization | `JsonUtils.getJsonCodec().toJson(msg)`, read back into `Msg` | the same codec as `MysqlAgentStateStore.kt:77`, so the exact shape of tool calls, tool results and image blocks is preserved: `MessageLogConverter` needs no change and the client contract needs no change |
| **Exclusion** | skip `msg.name == ConversationCompactor.SUMMARY_MSG_NAME` (constant value `__compaction_summary__`, `ConversationCompactor.java:65`) | the summary message is built by `buildSummaryMessage` (`:454`) with `.role(MsgRole.USER)` (`:471-472`), so archiving it puts an extra user bubble carrying the whole summary text on the page — a direct violation of criterion 2 in section 1. The framework's synthetic reminders (`METADATA_SYNTHETIC` at `Msg.java:102`) are never written into context — the class comment of `TaskReminderMiddleware.java:45-48` states verbatim that it is "only appended temporarily into the reasoning input, never written into `AgentState.context`, therefore never persisted, compacted or recalled", so no extra check is needed |

Read path: `loadSessionMessages()` consults `session_message` first; with **zero rows** for that session it falls back to the existing `agentState.context`, then to legacy `memory_messages`. The fallback branches stay because sessions created before this release have an empty archive until the user sends a new message, and without a fallback there would be nothing to page through.

Collateral changes:

- Member child sessions are covered automatically — `TeamHistoryReplay.kt:44` calls exactly this method, so member bubbles become full as well.
- Deleting a session must delete its archive: `clearSession` at `DefaultAgentRunner.kt:480-489` already recurses into member child sessions, so follow it.
- The user bucket is the hidden invariant of this chain: the compaction write-back, the archive reads and writes, and the history read path must land in the same user bucket. All three sides normalise an empty value to `__anon__` (`MysqlAgentStateStore.kt:70,247`, `ReActAgent.java:394-399`), while harnax's single wrapper construction point passes no userId (`HarnessAgentLauncher.kt:891-916`, the field defaults to `null`, see `HarnessAgentWrapper.kt:91`) and the history read path hard-codes `""` (`HarnessAgentLauncher.kt:1036`) — today both sides land in the same bucket. The moment either side starts passing a real user id on its own, the hard-coded `""` diverges from the live slot, and the symptom is "it compacted but the history reads back the old one".
- An archive write failure does not affect the answer, but it is retried once and logged as warn. Reason: this data cannot be regenerated (unlike `TokenStatsMiddleware.kt:68-78`, where the loss is "one statistics row short"); and because every round back-fills in full, the next round naturally recovers whatever was missed — only messages trimmed before that are truly lost.

**One pre-existing limitation that must be stated**: automatic compaction has been running by default all along (section 2 fact one), so the early messages it trimmed before this release are neither in `context` nor anywhere else, and **cannot be recovered**. Compactions after this release do not lose anything: the per-round full back-fill covers later rounds, and the first back-fill at assembly covers the session's own first round. One window remains — the case where that first back-fill write itself fails (the session database is reachable but the write errors), handled exactly like the "archive write failure" row of section 8: warn, the next round's back-fill self-heals, and only a head trimmed before that point is truly lost.

## 5. `/compact` command compaction

The entry point is the `COMPACT` branch of `executeCommand` at `DefaultAgentRunner.kt:247`. The runner side only performs precondition checks and result mapping; steps 3–5 (fetch the live `AgentState`, compact, overwrite plus persist only on success) live in harnax-harness-core's `ContextCompactionService.compact(...)`, and step 2 lives in the wrapper's own `archiveContext()`; both are exposed through `HarnessAgentWrapper.compactManually(keepTokens)` — the agent, sessionId and user bucket keys are all taken from the wrapper itself, which is precisely how section 4's last invariant is held: a caller cannot introduce a second userId. Six steps:

1. Precondition checks (table below).
2. `archiveContext()` back-fills the archive; if it returns false (no archive table / the live context cannot be read / still failing after two retries) the command returns a failure — this command may not trim content the page has no copy of.
3. `val delegate = harnessAgent.delegate`; refused if the live `AgentState` cannot be fetched.
4. `ConversationCompactor(model, MemoryFlushManager(workspaceManager, model)).compactIfNeeded(rc, context, forceConfig, agentId, sessionId)` (constructor `ConversationCompactor.java:70`, `MemoryFlushManager.java:95`), with `rc` built as `RuntimeContext.builder().sessionId(sessionId).userId(userId ?: "")`, the same shape as `HarnessAgentWrapper.kt:492`.
5. Null/failed-string check on the result → only on success overwrite `state.contextMutable()` (`AgentState.java:176`) and call `delegate.saveAgentState(userId, sessionId)` (`ReActAgent.java:4691-4700`, which reaches `MysqlAgentStateStore` again through the `agent_state` key). It writes to the database only when `stateCache` already holds that slot (`:4696-4699`), and step 3's own `getAgentState(userId, sessionId)` creates the slot with `computeIfAbsent` (`:4449-4462`), so in this flow "read the live state, then save" always lands. 2.0.4 wrapped that write in `persistAgentStateCas` (call site `:4699`), but for harnax it is still an unconditional overwrite — see row 3 of section 3.
6. Return `CommandResponse.success(sessionId, message, result = {beforeTokens, afterTokens, beforeMessages, afterMessages, window, windowSource})`.

| Decision point | Decision |
|---|---|
| Compaction tier | `AutoCompactionTier.command(keepTokens)` — the tier of section 5.1 with exactly three fields changed (values in 5.1's table). `triggerMessages(1)` is verbatim the same shape as upstream's overflow fallback (`HarnessAgent.java:1071`) and means "the user pressed the command, do not block me behind a threshold"; whether it is worth compacting is decided by the cutoff check — when there are not enough messages to leave a `keepMessages=20` tail, upstream returns `Optional.empty()` outright (`ConversationCompactor.java:112,118`) and we answer "this conversation is still too short to leave a tail, so there is nothing to compact" |
| Meaning of `args` | `/compact <N>` → `keepTokens = N` (keep roughly N tokens of tail). Absent means the dynamic tier. Non-numeric or ≤0 → ignored, defaults used, and `message` says it was ignored |
| flush / offload | **both off.** Confirmable in code: the two steps are each gated by `config.isFlushBeforeCompact()` (`ConversationCompactor.java:136`) / `isOffloadBeforeCompact()` (`:156`), and with them off each is an empty `Mono` — no LLM call paid, no file written. Trade-off: leaving them on would keep a `sessions/<id>.jsonl` raw copy, but that file is neither visible in harnax's artifacts nor in the delete-session list, and on the lead side it lands under the host's `user.dir` subtree, so neither the user nor the operator can retrieve it; meanwhile flush pays an extra model call and writes daily reports with no read-back entry point. So manual compaction pays only the one summarization call. The `disableTranscript()` in row 1 of section 3 shares this reasoning: file artifacts left by a default path are handled as "unreachable output counts as no benefit". The automatic path runs the same pair of knobs as `flush = true` / `offload = false`; the criteria are in section 5.1 |
| Concurrency gate | refused if that session has a running stream or blocking call (`activeStreams` at `DefaultAgentRunner.kt:87`, `activeCalls` at `:96`; the existing use of the same pair of predicates at `:110`). Overwriting `context` mid-turn races for the same object as the turn-ending `saveStateToSession` (`ReActAgent.java:475`). Compaction itself `registerCall`/`unregisterCall` across the whole span of that write (same as a blocking turn, `DefaultAgentRunner.kt:134-141`), so a second compaction of the same session is refused by the same gate and, during compaction, that session's agent cannot be evicted and released; what remains open is the other direction — starting a new turn while a compaction runs is not refused, see section 11 |
| Session scope | only the root session is compacted. `task-` prefixed sessions are refused outright (the precedent of the capability-switch row at `:1078`); individual team member child sessions are out of this round — a member's context is the automatic path's job when the member finishes its own turn |
| Summarization failure | **do not persist, return failure directly.** Upstream swallows the summarization exception into the strings `"(Summarization failed: …)"` / `"(Summary unavailable)"` and still returns a "compaction result" (`ConversationCompactor.java:375,382`). On the automatic path that is an acceptable degradation; on the manual path it means replacing the model context with a chunk of error text which, because of section 4's separation, the user cannot see, and the next turn answers straight from it — the criterion is that the first result message has `name == __compaction_summary__` and its body **contains** `(Summarization failed` or `(Summary unavailable)`. "Contains" rather than "starts with", because the marker is not at the start: `buildSummaryMessage` prefixes the fixed lead-in `"Here is a summary of the conversation to date:\n\n"` (`ConversationCompactor.java:467`) and the marker can only land after it; and the single cost of "contains" is treating a genuine successful summary that happens to mention that wording as a failure — in this direction a false positive is cheap (the command is retried and the context is untouched), while a false negative is expensive |
| Agent not cached | rebuilt normally through `getOrCreateAgent` (after the `cachedAgent` null check at `:774-787`, built at `:794`); compaction does not have to be exclusive to "active sessions" |
| Blocking and timeouts | this command chain returns `ResultVo<CommandResponse>` synchronously end to end (router `AgentProxyController.kt:105-113`, agent-service `AgentController.kt:77-86`) while `compactIfNeeded` returns a `Mono`, so the implementation `block()`s in place for that one summarization call. That suffices: the router's read timeout for JSON proxying is 600s (`harnax-session-router/src/main/resources/application.yml:103`), webflux `request-timeout` is 1800s (same file `:22`), one summarization call is far inside both, and the same order of magnitude as `HarnessConfig.turnTimeoutSeconds = 300` (`harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/config/HarnessConfig.kt:33`). No asynchronous channel is opened for it |
| Falling back to the store copy | forbidden. `getLiveAgentState()` at `HarnessAgentWrapper.kt:293-314` returns a copy deserialized from the database when the delegate is absent; modifying that copy and calling `saveAgentState` silently no-ops (it only saves slots already in the cache). This compaction path accepts only the delegate |

### 5.1 The automatic compaction tier

Both paths share one tier, in `harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/compaction/AutoCompactionTier.kt`: the assembly chain calls `agentBuilder.compaction(AutoCompactionTier.auto())` in `HarnessAgentLauncher.kt` immediately after the `disableTranscript()` block, and the command path calls `AutoCompactionTier.command(keepTokens)`. The criterion for the values is "these are the numbers this runtime runs on", not "these are upstream's current defaults" — `AutoCompactionTierTest` carries a drift sentinel that compares `auto()` field by field against `CompactionConfig.builder().build()`, so the day upstream moves any default value it turns red. That is a signal for a human to decide, not a bug to fix.

| Constant | Value | Meaning |
|---|---|---|
| `TRIGGER_MESSAGES` | 50 | the message-count line |
| `TRIGGER_TOKENS` | 0 | 0 = dynamic on the model window. The window is a per-model quantity (`model.contextWindowSize`; the `context_window` the operator fills on the model row reaches the model object through `ModelHelper.kt:64/82/104`), so pinning an absolute value would leave a small-window model permanently below the line |
| `RESERVED_TOKENS` | 20 000 | the margin the dynamic trigger line steps back — the subtrahend of section 6's threshold |
| `KEEP_MESSAGES` | 20 | how many messages to keep when no window can be inferred |
| `KEEP_TOKENS` | -1 | -1 = the dynamic tail tier |
| `KEEP_TOKENS_MIN` / `_MAX` / `_RATIO` | 2 000 / 8 000 / 0.25 | the three parameters of the dynamic tail `min(MAX, max(MIN, usable × RATIO))` |
| `PRUNE_PROTECT_TOKENS` | 40 000 | the most recent so many tokens of tool results never take part in pruning |
| `PRUNE_MINIMUM_TOKENS` | 20 000 | pruning only actually runs once the prunable total passes this line |
| `PRUNE_MAX_OUTPUT_CHARS` | 2 000 | characters kept per item when a pruned result becomes a head-plus-tail preview |
| `PRUNE_EXCLUDED_TOOLS` | `read_file, memory_search, memory_get, session_search` | the last three are either read-only already or removed from the assembly, so pruning them buys no headroom |

`auto()` and `command()` differ in **exactly three** fields: `triggerMessages` (1), `flushBeforeCompact` (false), `offloadBeforeCompact` (false), plus the optional `keepTokens` argument. `AutoCompactionTierTest` compares everything outside those three field by field, so the two paths cannot each grow their own knob.

Three items are written out explicitly but deliberately not pinned to a value, each with its reason: `summaryPrompt` **references** `CompactionConfig.DEFAULT_SUMMARY_PROMPT` (improvements to the summarization wording should be followed, and this is following them in code); `model` stays null (the summary runs on the agent's own model); `truncateArgs` stays null (tool-argument truncation is not enabled — where upstream enables it the constants are 500/1000 characters and not configurable, which is one of the reasons section 3 refused the transcript channel).

The three criteria for `offloadBeforeCompact = false` on the automatic path: upstream's step is `MemoryFlushManager.offloadMessages` (`MemoryFlushManager.java:207-216`), which runs `new SessionTranscriptWriter(...).appendMessages(...)` — the **same writer** and the same key layout (`agents/<agentId>/sessions/<sessionId>`, `SessionTranscriptWriter.java:86`) as the per-turn transcript that `disableTranscript()` closes; its only consumer in harnax, `session_search`, is explicitly removed (`removeTool("session_search")` in `HarnessAgentLauncher.kt`); and this copy is not within `clearSession`'s deletion scope either. `flushBeforeCompact` stays true: before compaction it extracts the prefix that is about to be trimmed into the day's memory ledger, and the memory domain reads that channel. Turning offload off introduces no new failure surface — upstream already swallows its exception and continues (`ConversationCompactor.java:153`).

## 6. Context occupancy ratio

Two numerator conventions are reported together because they do not answer the same question:

| Field | Source | Terminology |
|---|---|---|
| `estimatedTokens` | `TokenCounterUtil.calculateToken(context)` | upstream's ruler: characters / 2.5 plus a structural allowance per message and per tool block (the constants at `TokenCounterUtil.java:49-58` and the method at `:73`), thinking folded through the same ruler as body text (`:132`). **Exactly the same source as the automatic compaction trigger**, so it answers "would compaction trigger" |
| `lastCallInputTokens` | the most recent `token_stats.input_token` row for that session | the billed truth, written one row per model call by `TokenStatsMiddleware.kt:41-67`. It includes the system prompt and the tool manifest, which `context` does not, and it reflects the previous turn, so after compaction it only drops on the next turn. **It is not proportional to the estimate**: side-by-side readings from the same session and turn on the real stack gave six pairs — 669/4245, 2330/4604, 4974/4961, 3770/4934, 7573/4868, 3807/5157 — plus another session's 3618/6278 and 447/4468; the estimate is as low as one tenth of the bill and at most slightly above it, because the thinking the estimate counts is never replayed into later turns while the bill carries a system prompt and tool manifest the estimate can never see. So the two numbers cannot be converted into each other and can only each answer its own question |
| `contextWindow` | three-tier fallback: the new model domain column `model.context_window` → upstream `getContextWindowSize()` (`ChatModelBase.java:38-40`; when the builder was given no value, `ModelContextWindows.lookup` matches the model name by longest prefix and returns 0 on a miss, `ModelContextWindows.java:151`) → `160_000` | `windowSource` takes `MODEL_FIELD` / `UPSTREAM_TABLE` / `FALLBACK`, so the caller knows whether this denominator was configured or guessed |
| `ratio` | `lastCallInputTokens / contextWindow` when a billing row exists, `estimatedTokens / contextWindow` when the session has no billing row yet | display value, and the criterion for "do I still want to compact manually" — it answers "how full did the real request make the window", so the numerator must be the billed real number rather than a self-computed estimate. The fallback covers only the single case "assembled but not one model call made yet", where the estimate is the only readable quantity. The case `the ratio divides the billed number while the estimate keeps answering for the trigger` guards this; `estimatedTokens` itself is unchanged and stays on the same number as the trigger criterion |

The three-tier value from the row above is deliberately *not* used as the minuend: the middleware only ever sees the number the model reports, and once the two diverge, a case where all three tiers miss would report `160_000 - 20_000 = 140_000` while the actual fallback is `160_000` — a wrong threshold is worse than no threshold |
| `messageCount` | `context.size` | the same criterion as `triggerMessages` |

## 8. Boundaries, failures and limitations

| Situation | Behaviour |
|---|---|
| Conversation too short, the cutoff cannot leave a tail | returns success with `result.afterTokens == beforeTokens`, `message` explains there is nothing to compact; no overwrite, no persist |
| The `/command` request body is missing the polymorphic discriminator `type` | refused at the session-router's inbound deserialization (`AgentProxyController.kt:105`'s parameter type is `CommandAgentRequest`, and the router's own `GlobalExceptionHandler` returns `code: 500` with `missing type id property 'type'`); the request never reaches agent-service. The webui always sends `type` in its command body (`harnax-webui/src/pages/session/components/ChatWindow.tsx:1020`), so this only hits callers talking to the router directly |
| Summarization model call fails | returns failure, neither `context` nor the database changes, the user can retry verbatim |
| The caller disconnects before the server finishes | the overwrite already `block()`ed is not rolled back (the server does not know the connection dropped). When the user re-sends `/compact`, the cutoff check classifies the already-compacted session as "nothing to compact", so no second summarization happens — the command is idempotent-safe |
| The delegate cannot produce a live state | step 2 of section 5 refuses first: no live context readable means the archive cannot be written, and `message` says the session is not recorded. The internal delegate check (step 3) is therefore defence in depth and is never reached first on the command path |
| That session has a stream or blocking call in flight | returns failure |
| A `task-` session or member child session receives the command | returns failure, explaining that only the lead or a plain session is supported |
| The client hangs up early during a streaming turn | the user message of that turn already reached `context` and is archived normally; the unfinished answer exists on neither side — the live context and the archive each gain only that one user message. The next normal turn's full back-fill picks it up, so compaction can never touch "content the page has no copy of" |
| Archive write fails | warn plus one retry; the answer is not rolled back. The next round's full back-fill self-heals, and only messages trimmed before then are truly lost |
| `/compact` arrives while the archive cannot be written | returns failure, with `context` and both databases untouched (step 2 of section 5 makes this a precondition). The command may not trim content the page has no copy of |
| A compaction contains an over-long tool result | upstream's prune replaces the tool result in the live context with a head-plus-tail preview and keeps the original id (section 4's conflict-handling row); the model sees the preview while the table the page reads keeps the longest body, so bubbles do not shorten |
| A second `/compact` on the same session | refused while the first is still running (compaction itself holds `activeCalls`), so two overwrites never race over the same context |
| All three window tiers miss | `windowSource = FALLBACK`, `contextWindow = 160_000`; the endpoint still returns normally but `ratio` is an approximation |
| This instance has no agent for that session (after a restart, or the session is bound elsewhere) | the reading cannot be produced and no agent is created for it: `DefaultAgentRunner.loadContextUsage` only consults `agentCache` and returns `ResultVo.error` on a miss, saying this instance does not hold the session. The window denominator belongs to that session's model, and only the assembly knows which model that is — paying one admin spec round trip plus a full tool assembly for one reading is not worth it, and the number is recomputed next turn anyway. The row above covers "assembled but the model reports no window", this row covers "never assembled at all" |
| The two shapes in which no occupancy reading exists | bound but **not held by this instance**: `code: 500` plus `No context held for session <id> on this instance - usage needs the live agent` (this is what reading an old session after a restart gives). **Never bound** (the router finds no bound instance): `code: 200` with `data: null`, because `proxyLoadContext` returns `ResultVo.success(null)` directly at the missing `boundInstance(sessionId)` step (`SessionRouterService.kt:400`). Neither means "occupancy is 0": callers must branch on whether `data` is null and on `code`, and must not read `null` as an empty session |
| `model.context_window` was filled with a number larger than the real window | the server does not validate (it cannot); the consequence is that automatic compaction is postponed and `ratio` reads low — the denominator was inflated. The form states "if left empty the runtime infers it from the model name" |
| `model.context_window` was filled with a number smaller than the real window | the other side of the same ruler: automatic compaction comes early and **on every round** — an extra summarization call per round, and `ratio` above 1 for as long as it stands. Measured shape: at 4000 upstream clamps `triggerTokens` to half the window, 2000 (`triggerMessages` is still 50, so the message-count gate does not fire first), and after six batch-mode rounds every round from the fourth onward compacted, with the live context settling at 3 messages while the page grew to 14. The reason not to validate is the same as the row above, but what this side bites is the wallet rather than the memory |
| Older sessions (created before the release) | archive empty → the read path falls back to `agent_state.context`, so paging behaves exactly as today; the archive starts building once a new message is sent |
| Moved to 2.0.4 but did not call `disableTranscript()` | every round writes another batch of truncated transcript segments to object storage or the host disk; the page is unaffected but deleting the session does not remove them (section 3 row 1). This is an assembly defect rather than a runtime degradation, guarded by test 9 |
| The denominator is corrupted so `ratio` leaves the representable range | neither client may crash: webui's `formatContextPercent` rounds and prints as usual, iOS's `percentText` clamps to `Int.max` (`Int(Double)` out of range is a fatal error in Swift, and `ratio.isFinite` cannot catch the branch that only overflows after multiplying by one hundred). Whether a reading exists is still decided by `isReadable`; the clamp only concerns "how to draw a number that does not fit" |
| The user cancels the compaction request before it returns | the command already ran on the server and cancelling only abandons the answer: neither client treats this as "never happened" — iOS still re-fetches the reading (matching the re-read in webui's `finally`) — but neither the banner nor a bubble appears, so the screen never claims a compaction it did not see |

## 9. Test plan

The primary assertions (missing any one of them means section 1 is not done):

1. **Compaction does not change history**: build a session whose context message count exceeds `keepMessages`, take a `loadHistory` snapshot → issue the `COMPACT` command → take another snapshot, and assert the per-message bodies and the count are identical, and that the new list contains no bubble carrying `__compaction_summary__` or its summary text. Stub the summarization call with a fake model so the test never hits a real model. Run the same criterion again on a session whose **archive is empty** (the test may not call `archiveContext()` itself first, otherwise it steps exactly around the path step 2 of section 5 exists to guard): the command writes the head it is about to trim into the archive by itself, and only then may the page still be full.
2. **Compaction really shrinks the model-side context**: in the same case assert the `agent_state.context` message count is smaller afterwards and that its first message has `name = __compaction_summary__` (`AgentState.context` and history read two different datasets; this assertion *is* the evidence of the separation).
3. **Archive idempotence and back-fill**: write a larger version of the same `msg_id` across two consecutive rounds, assert one row whose body is the latter; then write a **shorter** version (the kind of id-preserving preview upstream's prune produces), assert the body is still the longest one — a shortened page is section 1's assertion breaking; assert no duplicate rows across rounds. Then assert that the same `msg_id` under two user buckets keeps one row each with its own body (the span of the unique key equals the predicate span of `load`/`delete`, section 4's first row). Finally assert the first back-fill at assembly: with an empty archive it persists the already-saved context, and with an archive that already has rows it does not even read the live state (that one existence query is all it costs).
4. **Failure does not overwrite**: stub the summarization to throw, assert `context` unchanged, `agent_state` not rewritten, and the command returns failure.
5. **Concurrency gate**: issue the compaction command while the session is in `activeCalls`, assert failure and `context` unchanged; in the opposite direction assert that for the entire span of a compaction the session really is in `activeCalls` and is removed after the command returns (a second compaction is therefore refused by the same gate).
6. **Occupancy ratio**: one case per window tier (column configured / column empty but the model name hits upstream's table / neither), asserting `windowSource` and how `ratio` is computed; one more asserting `estimatedTokens` is verbatim equal to `TokenCounterUtil.calculateToken` on the same context (so no second estimation implementation creeps in); one last asserting that when this instance has no agent for the session the reading is not produced at all and `createSingleAgent` is called zero times (the criterion of that section 8 row).
7. **Meaning of `args`**: `/compact 500` lands as `keepTokens=500`; `/compact abc` is ignored and the default tier is used.
8. **Deleting a session deletes the archive**: after `clearSession`, `session_message` has zero rows for that session, and the same for member child sessions.
9. **The transcript middleware was not installed**: after one conversation round, assert no `events/` segment object exists in the workspace or the store (key layout `TranscriptStore.java:30-33`), i.e. that `disableTranscript()` really closed the channel section 3 row 1 says is on by default.

How to run: the repository's existing recipe (JDK 21, probe Docker first to decide whether ITs are excluded). `session_message` is created by the writer, so both the H2 path and the real-database path are testable without a rebuild.

## 11. Explicitly out of this round

- Closing the three switches `disableMemoryTools()` / `disableToolsConfig()` / `disableAtPathExpansion()`.
- Using `session_message` for cross-session retrieval (the `session_search` kind of capability).
- Carrying user-visible history on upstream's transcript or `TranscriptStore` — row 1 of section 3 already gives the reasons for refusing it (the truncation constants are not configurable, and it records the post-compaction live context).
- `mp_chat_message` in the mp module (that module is decided as deprecated): not reused, not migrated.
- The other direction of the concurrency gate: while a compaction runs, a user chat message is **not** refused (`activeCalls` is only read on the compaction side). When they collide, both sides write the same live `AgentState`: the page is unaffected (the archive is append-only and keeps the longest body, and each side's per-round full back-fill loses nothing), what is at risk is the model side — either the compaction is overwritten back by the turn-ending `saveStateToSession` (the command did nothing, retry fixes it), or the just-finished turn drops out of `context` (the model forgets it on the next page, though the page still shows it). Three-way exclusion would require spreading the busy predicate across chat's three entry points, while the exposure window is one summarization call long, so this round ships only the half that says "a compaction never races a compaction or a turn over the same context".
