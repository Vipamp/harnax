# Harnax MCP Outbound Authorization Design (English)

> Chinese version: [mcp-authorization-design.zh-CN.md](./mcp-authorization-design.zh-CN.md).
> This document only covers **how harnax authenticates and is authorized to upstream MCP servers while acting as an MCP client**; for `mcp_server` CRUD, encryption/masking and config delivery see [mcp-management.en-US.md](./mcp-management.en-US.md), for the tool-side authorization stance see [tool-integration-design.en-US.md](./tool-integration-design.en-US.md).
> Inbound authentication (who is calling harnax: JWT / API Key / internal secret) is out of scope, although section 5 reuses `api_key.user_id`.
> **This is a design document**: unlike the other prod_doc files, it describes work that is not implemented yet; section 10 is the source of truth for implementation progress.

## 1. Conclusions first

1. harnax is only an OAuth 2.1 **client** and **credential vault** — not an identity provider, and not an MCP server.
2. Refresh tokens live **in admin only**, are never delivered to the agent runtime and never enter the model context; the runtime exchanges a short-lived access token with admin before each upstream call.
3. The runtime injection point is agentscope's `McpClientBuilder.httpRequestCustomizer`, which is a **per-request callback**, so token rotation does not require rebuilding the MCP client.
4. The blocking prerequisite was **identity propagation**: the runtime used to build agents with a hardcoded `UserIdentifier(0)`, so "which user is behind this session" was lost long before an MCP client was constructed. **P1 has closed this** (see §2.2). Without it, per-user authorization cannot exist.
5. Phases: P0 security stop-the-bleed → P1 identity propagation → P2 OAuth client → P3 runtime injection → P4 remaining methods. P0 and P1 are done, and P2 has done P2-1 / P2-2 / P2-3 / P2-5 (P2-2 including its admin-side frontend, P2-5 the user-side authorization entry and the JWT-carrying code-exchange endpoint; see section 12), leaving only the P2-4 token issuing.

## 2. Current state

### 2.1 The three upstream authentication methods already supported

| Method | Carrier | Code location | Granularity |
|--------|---------|---------------|-------------|
| No authentication | — | Leave `mcp_server.headers` / `env_params` empty | Service level |
| Static credential (`Authorization: Bearer x`, any custom header, stdio environment variable) | JSON entries in `headers` / `env_params`; `secret=true` entries go through AES-256-GCM | Written at `McpServerServiceImpl.kt:102-103`, decrypted on delivery at `InternalApiController.kt:379-380`, assembled at `McpHelper.kt:142-148` | **Shared per service** — everyone uses the same copy |
| Key hand-typed into `command` | stdio command line | Not recommended, effectively plaintext in the DB | Service level |

Capability boundary: only "static, shared inside the tenant, typed by an administrator" is covered. As soon as an upstream requires OAuth 2.1 (authorization code + PKCE), requires per-user identity, or issues expiring tokens, the current state cannot cover it.

### 2.2 Three break points in the identity chain

```
Browser ──JWT──▶ admin (/api/admin/**)               ✅ the user is known: JwtAuthenticationFilter.kt:80-90
      └─X-Api-Key─▶ router (/api/router/**)          ✅ break 1 closed (P1): ApiKeyInfo / AuthContext carry userId
                       └─ChatAgentRequest─▶ agent-service
                                                ✅ break 2 closed (P1): AgentRequest.kt:27-32 carries userId
                                                     └─DefaultAgentRunner.kt:74,95,210
                                                        ✅ break 3 closed (P1): UserIdentifier(request.userId)
```

- Break 1: the `api_key` table **already has** `user_id` (`V1__init_schema.sql:357-388`, `uk_user_permanent (user_id, key_type)`); the validation chain simply drops it — admin's `POST /api/admin/internal/api-keys/validate` response has no `userId`, so the `ApiKeyInfo` built at `RemoteApiKeyStore.kt:38-41` lacks the field, and `AuthContext.kt:8-15` only carries `callerId = keyInfo.name` (`ExternalApiKeyValidator.kt:24-30`).
- Break 2: `ChatAgentRequest(sessionId, message, imageUrls, requestId)` has no user field; `AgentSpecInfoResponse` (`InternalApiController.kt:79-87`) does not return one either — it stops at `tenantId`.
- Break 3: `UserIdentifier` is `data class UserIdentifier(val userId: Long)` (`ToolCallContext.kt:16-18`), and all three call sites pass 0.
- **How P1 closed them**: `api-keys/validate` returns `userId` → `ApiKeyInfo.userId` → `AuthContext.userId` → `AgentRequest.userId` (`abstract val userId: Long?` on the sealed base) → `UserIdentifier(request.userId)`; a null `userId` now means "no end user" instead of being faked as 0. On the router side `AgentProxyController.resolveUserId` sets the rule: **the authenticated user's userId overrides whatever the body claims**, and only service-level callers (which resolve the user themselves) keep their own value.
- The other entry points have no user available either (P1 only wired the web / router API-key path; these three are still unconnected): Feishu uses `openChatId` as the sessionId (`FeishuAdaptor.kt:77`) with no user-binding table; scheduled tasks run as `task-<id>-<uuid>` with a service-level key (`SchedulerServiceImpl.kt:239`, `RouterClient.kt:101`); the CLI uses the internal secret, so the principal is `internal-service`.
- The good news: `session.creator` is a **username** (web writes `currentUsername`, `SessionServiceImpl.kt:165`; the mini-program writes a numeric id, `MpSessionService.kt:64`), so `sessionId → username → sys_user.id` is resolvable server-side without trusting anything the client reports. **This is the path chosen in section 6.**

### 2.3 The key boundary at runtime

- `harnax.aes.secret-key` exists only in `harnax-admin/src/main/resources/application.yml:126-127`; it appears in no agent/router/channel yml, and `AesUtil` only exists in the admin source tree (zero grep hits in the other modules).
- Therefore **config is already decrypted to plaintext on delivery** (`InternalApiController.kt:609-631`); the runtime implementation is `PlaintextMcpConfigDecryptor`, which only parses JSON and warns if the stored `[{...secret:true}]` shape ever leaks through.
- This boundary is decisive for the design: the credential vault must live in admin, and the runtime may only ever receive an **already-exchanged, short-lived** access token.

## 3. Method inventory and selection

| Upstream method | In scope | Phase | Rationale |
|-----------------|----------|-------|-----------|
| None / static API key / custom header / stdio env | ✅ existing | — | Good enough as-is, but needs the masked write-back guard (P0) |
| Basic Auth (user + password) | ✅ | P4 (0.5d) | It is a fixed header; folded into the `auth_type` enum |
| **OAuth 2.1 authorization code + PKCE (per user)** | ✅ main line | P2 + P3 | The direction the MCP spec forces for HTTP transports; the same shape as enterprise offerings (Auth0 Token Vault / Arcade / Composio / Scalekit / MCP gateways) |
| OAuth2 `client_credentials` (service-level M2M) | ✅ | P4 (2–3d) | Reuses P2's client registration and P3's injection channel, minus human consent and the callback |
| RFC 9728 protected-resource discovery + AS metadata + Client ID Metadata Documents | ✅ the discovery part | P2 | Halves the form; `authorization_servers` locates the AS automatically |
| Dynamic Client Registration DCR (RFC 7591) | ⚠️ optional | end of P2 | Lower spec priority than pre-registration and CIMD; enable when an upstream demands it |
| OIDC `id_token` passthrough / JWT assertion (RFC 8693 token exchange) | ❌ deferred | — | Needs our own IdP plus AS cooperation; no scenario today |
| mTLS (per-tenant client certificate) | ⚠️ feasible | P4 (5–8d) | **Verified feasible**: `customizeStreamableHttpClient` / `customizeSseClient` hand over the real `java.net.http.HttpClient.Builder`, so `sslContext` / `proxy` / `authenticator` are reachable; what is missing is certificate issuance and rotation operations |
| Cloud signing (SigV4 / GCP SA / Azure MI) | ❌ | — | 2–4d each plus an SDK; handle case by case |
| External credential vault / third-party MCP gateway | ❌ | — | A decision-level change introducing an external dependency; this design builds its minimal usable version |
| Exposing harnax as an MCP server | ❌ | — | No MCP server transport anywhere in the repo; separate design |

## 4. Overall architecture

```
                    ┌──────────────────────── admin (the only key holder)─────────────────┐
Browser ──auth code─▶│ /api/admin/mcp/{id}/oauth/*  ── OAuthClientRegistry ──┐             │
  (redirect+callback)│                                                      ▼             │
                    │                              mcp_oauth_client ┐  ┌─▼───────────┐   │
                    │  mcp_user_credential (refresh, AES-GCM) ──────┘  │ TokenService │   │
                    │  mcp_call_log (call-level audit) ◀────────────────│  exchange    │   │
                    └───────────────▲──────────────────────┬───────────┴─────────────┴───┘
                                    │ shared secret        │ POST /internal/mcp/access-token
                                    │ (InternalApiAuthFilter) │ body: sessionId + mcpId
                                                             ▼
                          agent-service: MCP client assembly (HarnessAgentLauncher.kt:174-188)
                                    │  McpClientBuilder.httpRequestCustomizer (per-request callback)
                                    │  in-process cache key=(mcpId,userId), TTL=expiresAt-60s
                                    ▼
                              upstream MCP server   Authorization: Bearer <access token>
```

Key points:
- The user authorizes once in the browser (P2); every later session then exchanges access tokens with admin from the stored refresh token, transparently to the user (P3).
- The runtime **holds no long-lived credential**, only an in-process access-token cache sharded by (mcpId, userId) with a TTL.
- The exchange endpoint accepts only `sessionId`; the user is resolved by admin from `session.creator`, so a self-reported `userId` is never taken (spoofing prevention).

## 5. Data model (migrations V25 / V26; V23 is the name unique key, V24 is taken by the agent / session tenant backfill)

### 5.1 New `mcp_server` columns (V25)

| Field | Description |
|-------|-------------|
| `auth_type` | `NONE` (default, equals today's behaviour) / `STATIC_HEADER` (today's `headers`, made explicit) / `BASIC` / `OAUTH2`. `NONE` + `STATIC_HEADER` + `BASIC` need none of the section 6 flow |
| `oauth_config` | **Non-sensitive only** JSON: `authorizationServer` (nullable — empty means run discovery), `scopes`, `audience`, `resourceIndicator` (whether to send the RFC 8707 `resource`, default true). `client_id` / `client_secret` are deliberately not here — they belong to `mcp_oauth_client` |

Generated column and unique key: `auth_type` takes no index; `oauth_config` has the same nature as `headers` (plain JSON text, not encrypted, because no secret may appear in it).

The whitelist is enforced by the **type**, not by filtering code: `oauth_config` is carried by the `McpOAuthConfig` DTO whose fields are exactly the four above, so an extra key (`client_secret`, `refresh_token`, ...) has nowhere to land during deserialization and cannot reach the column. The callback origin allow-list (`callback_allowed_origins`) is not in the first version: the callback address is already pinned by the exact `callback_url` match in section 5.2, and another configurable allow-list would only add one more place to get wrong.

`McpServerServiceImpl` enforces these rules on create / update (each violation raises `BizException`; nothing is silently corrected):

- `auth_type` must be one of `NONE` / `STATIC_HEADER` / `OAUTH2`; an omitted value means `NONE`. `BASIC` has a column but no runtime that honours it yet, so it is rejected — storing a value the runtime ignores tells the administrator "configured" while the request still goes out bare.
- `type=stdio` rejects `OAUTH2`: a stdio server has no HTTP request to attach a token to.
- `oauth_config` is only allowed with `auth_type=OAUTH2`, and the column is cleared when `auth_type` leaves `OAUTH2` (the update semantics are "a provided value replaces the stored one, an omitted one stays", so clearing has to be explicit).
- A non-empty `authorizationServer` must start with `http(s)://`, because the admin process actually issues requests to it during discovery.
- A stored `oauth_config` that fails to parse is treated as unset and logged at warn, so one corrupt row cannot break the list endpoint.

V25 performs **no backfill**: `NONE` and `STATIC_HEADER` take the same code path, and `headers` also holds plain routing headers, so a derived label would be indistinguishable from a decision. Every historical row stays `NONE`, and an administrator who wants the `STATIC_HEADER` label picks it explicitly.

### 5.2 `mcp_oauth_client` (V26) — the client identity at the AS, shared per (tenant, AS)

| Field | Description |
|-------|-------------|
| `tenant_id` / `issuer` | Owning tenant and the AS `issuer` (compared as an exact string, see section 9); `issuer` is `COLLATE utf8mb4_bin` |
| `client_id` / `client_secret_enc` | client_id from pre-registration or CIMD; the secret is `AesUtil`-encrypted and masked on read, same convention as `headers` |
| `registration_source` | `MANUAL` / `DCR` / `ID_METADATA`, so rotation knows where the row came from |
| `authorization_endpoint` / `token_endpoint` / `registration_endpoint` / `revocation_endpoint` / `scopes_supported` | Discovery snapshot, so every request does not have to hit the AS |
| `callback_url` | Exact value (`COLLATE utf8mb4_bin`); the AS requires an allow-list match, no prefix matching |
| `active_client_id` (generated column) + `uk_mcp_oauth_client_tenant_issuer_client` | Follows the V15 / V23 soft-delete unique-key pattern: the generated column turns NULL once `active = 0`, unique indexes ignore NULL, so a client can be registered again after deletion |

`issuer` and `callback_url` use a binary collation while the rest of the table keeps the default: MySQL's default collation folds case, but RFC 8414 compares `iss` and RFC 6749 compares `redirect_uri` as exact strings, so a case-insensitive match would silently reuse another authorization server's registration. The cost is that an administrator who mistypes the issuer's case gets "no registration" instead of a hit — better to register again than to merge two ASes.

The reuse lookup `selectByTenantAndIssuer(tenantId, issuer)` carries `ORDER BY id LIMIT 1`: the unique key allows several `client_id` values under one issuer, and there has to be a deterministic answer, otherwise discovery would keep registering a second client for an AS the tenant already talks to. The mapper has exactly three methods — `selectByTenantAndIssuer` / `insert` / `updateById` — and the `updateById` SET list is deliberately unconditional, because "the AS dropped DCR support" has to write `registration_endpoint` back to NULL; a null-checking SET list would leave a dead endpoint in the table to be called again. The row identity columns (`tenant_id`, `issuer`) stay out of the SET list, as in `mcp_server`.

### 5.3 `mcp_user_credential` (V26) — the authorization result per user × MCP service

| Field | Description |
|-------|-------------|
| `tenant_id` / `user_id` / `mcp_id` | Unique triple (`uk` on `(tenant_id, user_id, mcp_id)`); `user_id` is `sys_user.id`, not a username |
| `refresh_token_enc` | AES-GCM ciphertext, **admin only**, absent from every response DTO |
| `access_token_enc` / `access_expires_at` | Snapshot used to survive process restarts and to decide early refresh; once expired it counts as missing |
| `scopes` | The scopes actually granted (an upstream may trim what was requested) |
| `status` | `ACTIVE` / `NEEDS_CONSENT` (refresh failed, or rejected with 403 `insufficient_scope`) / `REVOKED` |
| `last_error` / `last_refreshed_at` | For troubleshooting; `last_error` must not contain token material |

Implementation notes (this is how V26 built the table):

- **No `active` column and no soft delete.** Revoking updates the row in place: both ciphertext columns go to NULL and `status` becomes `REVOKED`; re-consenting overwrites the same row. A soft-deleted row would keep occupying `(tenant_id, user_id, mcp_id)` and block the insert that a re-consent needs. Hard deletion happens only when the MCP server itself is deleted (`deleteByMcpId`, in the same transaction as the `agent_mcp_binding` cleanup).
- The `updateById` SET list is **unconditional**: a null-checking list can never write NULL back, so a revoke would leave a token in the database that still works while the administrator believes it is revoked.
- `selectByUserAndMcp(tenantId, userId, mcpId)` puts the tenant inside the condition rather than filtering afterwards, matching the tenant rule in section 4.
- The mapper has four methods — `selectByUserAndMcp` / `insert` / `updateById` / `deleteByMcpId` — and no list method: rows are addressed by "who, for which server", there is no paging scenario, and another entry point would only be another way to skip the tenant condition.

### 5.4 `mcp_call_log` (V26) — call-level audit

`tenant_id` / `user_id` / `mcp_id` / `session_id` / `tool_name` / `action` (`ISSUE` / `REFRESH` / `REVOKE` / `CALL`) / `outcome` (`OK` / `AUTH_FAILED` / `NEEDS_CONSENT` / `ERROR`) / `latency_ms` / `create_time`. Result and latency only — **no request body, no Authorization header**. The first version may batch these asynchronously from the `McpHelper` side so tool calls are not blocked.

`action` was added after the design was written: with only `outcome`, "the token exchange failed" and "the tool call failed" look identical in the audit, while the first points at the authorization chain and the second at the tool. The mapper is `insert`-only, no update and no delete — an audit table the application can rewrite is not an audit table. `user_id` is nullable so a runtime call whose session owner could not be resolved still leaves a record.

## 6. Authentication flows

### 6.1 Service onboarding and discovery (administrator, once)

```
1. Create the MCP service with auth_type=OAUTH2, url only
2. POST /api/admin/mcp/{id}/oauth/discover
     ├─ no authorization_server: GET {url}/.well-known/oauth-protected-resource (sub-path first, then root)
     │  or read WWW-Authenticate: resource_metadata="..." from the upstream 401
     ├─ take authorization_servers[0] → that AS's issuer
     └─ AS metadata (fall back to /.well-known/openid-configuration for OIDC) → endpoints + scopes_supported
3. Client source, by priority:
     pre-registration (admin types client_id/secret) > CIMD > DCR (only when the upstream supports it)
4. Result written to mcp_oauth_client (reused per (tenant, issuer), never registered twice)
```

Failure stance: if discovery fails, show the administrator the error — **do not degrade to a static header**.

That has now landed with **P2-2** (implementation and rules item by item in `mcp-management` §3.5): the two endpoints, the four AS metadata candidates, `mcp_oauth_client` reused per (tenant, issuer), and the discovered issuer written back into `oauth_config`. Two differences from the diagram above: step 3 today has exactly one route — an administrator typing the credentials — since CIMD and DCR belong to P4; and when discovery succeeded but no client has been registered, that row's `client_id` is an empty string, which is an explicit state ("endpoints known, client not registered") that the §6.2 path must refuse.

### 6.2 First-time user authorization (authorization code + PKCE)

```
User clicks "Authorize" → GET .../oauth/authorize-url
   admin generates state(random) + code_verifier(random) and keeps them in server-side memory (short TTL)
   together with tenant/user/mcp/issuer/pkce/resource/requested scopes, then builds:
     authorize?response_type=code&client_id=..&redirect_uri=..&scope=..
              &code_challenge=BASE64URL(SHA256(verifier))&code_challenge_method=S256
              &resource=<MCP url>          ← RFC 8707, pins the audience; tokens must not be passed through MCP
              &state=..
   → browser redirects to the AS → user logs in and consents → AS redirects to
     redirect_uri = the front-end route /mcp/oauth/callback?code=..&state=..
   → the landing page first wipes the query with history.replace, then calls
     POST /api/admin/mcp/oauth/exchange with the JWT the browser already holds
   → admin takes the caller's identity → burns the state → then checks in order: the upstream reported an
     error / no such pending request / it belongs to somebody else / there is no code
   → only when none of those holds does it exchange code+verifier for tokens (with redirect_uri and resource)
   → strictly checks iss == the issuer from §6.1 and aud contains resource → encrypts into mcp_user_credential(ACTIVE)
   → answers one plain sentence + the scopes actually granted + the expiry (no field in that response can hold a token)
```

Constraints: `redirect_uri` must match the registered value exactly (what is registered is the address of a **front-end page**, not an endpoint of this service); `state` is one-time and burned on every branch, and an entry whose owner is not the caller is refused; the landing page displays no token and never writes `code`/`state` to any persistent storage; scopes are requested as the minimal set the MCP tool surface needs.

This flow **shipped with P2-3**. How it was built:

- Server-side state in memory, not a table: one `PendingAuthorization` in `McpOAuthStateStore` holds (tenant, user, mcp, issuer, verifier, redirect_uri, resource, requested scopes) with a 5-minute TTL, a global 500-entry cap, a further cap of 5 per person (added in round fifteen, counted through `countFor(userId)` **before** the verifier and the state are minted), and a `consume` that removes before it checks expiry. Memory was chosen because a code is itself single-use and minute-scale; putting it in a table would turn "replay protection" into "replay protection after a restart". The cost is stated plainly: **an admin restart interrupts a consent that is in flight**, and the user has to start again. Both caps refuse explicitly, each with its own honest sentence (the per-person one names the cap and the longest possible wait) rather than dropping the request silently; the 500 entries are a budget everybody shares, so without a per-person limit in front of it one logged-in user with a script could fill it.
- The exchange carries the JWT, so the `state` no longer authenticates anybody: the AS redirect lands on **one route of the front end**, and that page calls `POST /api/admin/mcp/oauth/exchange` with the browser's own JWT, so the identity comes from the Spring Security authentication context. `pending.userId` is therefore demoted from an identity to an assertion about "who should this consent be recorded under": disagree with the caller and it is refused with a warn log (only the mcpId and the two userIds are logged, never the code or the verifier). That comparison runs **before any field the request body carries** (fixed in round fifteen) — otherwise somebody who has learned another person's `state` could cancel that person's authorization in flight by POSTing an `error` of their own, and that warn would not say a word; conversely, when the AS really did report an `error`, the upstream reason is handed to the page **even if the pending entry has aged out**, because in that case nothing was stored and nothing is left to burn. This service has no unauthenticated OAuth entry point any more, and the two carve-outs the old callback needed — in `SecurityConfig` and in `JwtAuthenticationFilter` — have been deleted. This is exactly how **F6** closed; see §8 item 7.
- PKCE is **unconditionally `S256`** (the decision §12.1 had parked): discovery deliberately does not snapshot the AS's `code_challenge_methods_supported`, because OAuth 2.1 and MCP both make PKCE mandatory; an AS that cannot do `S256` fails on its own side and admin never downgrades to `plain`.
- Two things are checked before anything is stored: the response-level `iss` and the JWT-claim `iss` are both **byte-equal** to the discovered issuer (same rule as `utf8mb4_bin`), and `aud` must contain this flow's `resource`.
- The "endpoints known, client not registered" empty `client_id` state (§6.1) is refused when the authorization starts, so no user is sent to the AS with `client_id=` to hit someone else's error page.
- Three guards against mid-flow changes: a `scope` on the request that is wider than `mcp_user_credential.scopes` (VARCHAR 512) is refused (truncating it records a scope list nobody agreed to on the user's behalf); when the token is exchanged the service row is re-read by `pending.mcpId` through the tenant-guarded `McpServerService.getMcpServer`, and a row that is gone, has been moved out of the tenant the flow started in, is no longer `OAUTH2`, or whose `url` no longer equals the `resource` the `state` pinned, all refuse the exchange (the code was minted for the old address, so storing it would park a key that opens nothing).
- What the exchange hands the front end is a JSON answer, and a refusal is a plain sentence plus the next step rather than an HTTP status (`authorized=false`): the `code` is already spent, so the page cannot retry it. The upstream `error_description` is appended to that sentence in the AS's own words (capped at 200 characters, userinfo stripped) and React renders it as a text node — this is the same protection as "run it through `HtmlUtils.htmlEscape` before it reaches HTML", only with the layer moved, and the same convention used for the upstream strings `listTools` brings back. On success the `scopes` in that answer are **the list the written column recorded**, not the raw `scope` field of the token response (RFC 6749 §5.1 makes it optional, and an AS granting exactly what was asked may omit it; answering with that empty list would show the landing page no scopes while `status` on the detail page reads the same column and shows two a few seconds later — fixed in round fifteen). Nothing in the whole answer contains token material.

### 6.3 Runtime consumption (per session)

```
Agent assembly (HarnessAgentLauncher.kt:174-188)
  auth_type=OAUTH2 → McpClientBuilder.httpRequestCustomizer { rb, _, _, _ ->
      rb.header("Authorization", "Bearer " + tokenCache.get(mcpId, userId))   ← captured in the closure, see §7
  }
Every tool call issues an HTTP request → the customizer fires → cache hit injects directly
  miss / near expiry → POST /api/admin/internal/mcp/access-token {sessionId, mcpId}
      admin: sessionId.creator → sys_user.id → check the (user,mcp) row is ACTIVE
             → return the access token if unexpired, otherwise refresh (rotate, then overwrite ciphertext)
             → return token+expiresIn+scope → write mcp_call_log
      no credential / refresh dead → 401 with code=NEEDS_CONSENT → row set to NEEDS_CONSENT, UI asks to re-authorize
```

### 6.4 Expiry, revocation and deletion

- Revocation (**shipped with P2-3**, `POST .../oauth/revoke`): **the local copy is always cleared** (row set to `REVOKED`, both ciphertexts written back to NULL, `last_error` cleared too). Upstream, a single RFC 7009 request is sent only when that registration row recorded a `revocation_endpoint`, and `token_type_hint` prefers `refresh_token` — an access token dies of age within minutes, while a refresh token keeps minting new ones, and a compliant server revoking it kills the whole grant. **Six situations each answer with one honest sentence, and none of them cover for another**: no revocation endpoint ("the copy at the authorization server stays usable until it expires"), no stored token left, a ciphertext that no longer decrypts (the AES key changed — "it will not decrypt" is neither "there was no token" nor "upstream said no", and it must **not** stop the local clear: revoking is the user's only way out), the registration row is gone (this grant cannot be attributed to any AS, and the answer says to run discovery again), upstream accepted, upstream refused ("local cleared, upstream not"). A refusal is not retried and does not flip the row to `NEEDS_CONSENT`: that would take an observed call, which belongs to the §6.3 exchange side (P2-4). The shape of these six sentences is round thirteen's; the reasoning is in `mcp-management` §7.12.
- Deleting an MCP service: `deleteMcpServer` (`McpServerServiceImpl.kt:209-233`) clears `agent_mcp_binding` and `mcp_user_credential` for that server inside the same transaction; `mcp_oauth_client` is deliberately untouched, because one row is "this tenant's client identity at that AS" and other services may still be using it.
- Changing the auth type (added in round fifteen): when `updateMcpServer` moves `authType` away from `OAUTH2`, all of that server's `mcp_user_credential` rows are cleared as well. Leaving them behind turns them into dead data — reading and revoking a credential both pass through `requireOAuthServer` first (which refuses anything that is not `OAUTH2`), so after the change **the user can neither see nor revoke their own grant** and what is left is ciphertext nobody is in charge of. The policy matches the delete path: clear the rows locally and `warn` with how many, while the copies on the authorization server's side are never presented for revocation and expire on their own (actually revoking upstream means the user clicks revoke on each grant **before** the auth type changes). Whether "this request turned OAuth off" is decided by a `wasOAuth` read **before any field is overwritten**; a server that never had OAuth (including pre-V25 rows whose `authType` is null) never queries that table at all.
- User disabled / left the tenant: the credential row is kept but the exchange endpoint refuses it (status unchanged), so user credentials are never deleted by mistake.
- A public MCP (`is_public=1`) shares the **service configuration** inside its tenant, never **another user's credential**: the exchange endpoint always looks up the current session's own user.

## 7. Runtime injection (code level)

1. Add `authType` and `oauthScopes` to `McpDetailDto` (`harnax-entity/.../dto/McpDetailDto.kt:10-37`) and to the runtime `McpConfig`; when `OAUTH2`, the `Authorization` entry from `headers` is no longer injected (the two are mutually exclusive — validated with a warning at assembly time).
2. In `McpHelper.createMcpClient` (`McpHelper.kt:100-148`), branch on `authType` to attach `httpRequestCustomizer`, and set `timeout(...)` / `initializationTimeout(...)` at the same time.
3. **The user identity for the token must come from the closure, not from `McpTransportContext`.** Measured: `McpClientWrapper.callTool(name, args, meta)` puts `McpMeta` into the JSON-RPC body only and does **not** write `McpTransportContext.KEY` into the Reactor context, so `customize(...)` always receives `EMPTY`. Consequence: "which user" can only be decided **when the client is built**, so the agent cache in `DefaultAgentRunner` (`:58-64`, Caffeine, 30 minutes) has to be owner-aware. As built, the key stays `sessionId` while the cached value (`CachedAgent`) records the `userId` the agent was created for, and a request whose `userId` differs from the cached owner invalidates the entry and rebuilds — otherwise different users would share one client and one token.
4. No "refresh and retry once on 401": the customizer cannot retry (`McpSyncHttpClientRequestCustomizer.customize` returns `void` and there is no retry hook). Instead **refresh ahead of expiry** (`expiresAt - 60s`) plus a single-flight cache, so a concurrent session does not fire several exchanges. If the upstream revokes early, that call fails and the entry is judged expired, and the next request self-heals — visibly failing a tool call is preferable to swallowing an authentication error.
5. stdio has no HTTP header to inject, so it does not support OAuth; it keeps using `env_params`, and the UI warns against saving a masked secret as-is (the P0 fix already covers this server-side).
6. SSE transport works the same way (`customizeSseClient`); the first version shares one customizer with `streamablehttp`.

## 8. Security constraints (each maps to a spec clause or an incident)

1. **Never pass tokens through the MCP protocol itself** (confused deputy): tokens go in the HTTP `Authorization` header, and `resource` pins the audience (OAuth 2.1 for MCP).
2. Refresh tokens exist only encrypted inside admin; they appear in no `McpDetailDto`, `McpServerResponse` or `AgentSpecInfoResponse`.
3. Tokens are compared, never consumed: `iss` must be **exactly equal** to the discovered `issuer`, and `aud` must contain the target resource (RFC 8707). Those two comparisons require reading the JWT claims, so what P2-3 ships is **decode without verifying** — no code path here uses the token's contents; it is only forwarded verbatim to the MCP server, which is the party that validates it. An opaque token cannot be inspected at all, and that case is **logged rather than counted as a pass**: the resource binding then rests on the single assumption that the AS honoured the `resource` parameter.
4. Least-privilege scopes; record the difference between requested and granted scopes.
5. **Never escalate silently**: a 403 `insufficient_scope` only sets `NEEDS_CONSENT` and asks the user to re-consent; no automatic re-authorization.
6. Public clients (which cannot hold a secret) must use PKCE plus refresh-token rotation; a failed rotation marks the row `NEEDS_CONSENT`.
7. `state` and `code_verifier` are one-time, short-TTL and bound to the initiator. **From round fourteen on, what this constraint binds is credential ownership, not identity**: the exchange goes through `POST /api/admin/mcp/oauth/exchange`, the caller is authenticated by JWT, and the pending entry the `state` recognizes only answers "who should this consent be recorded under" — disagree with the caller and it is refused (the `state` is burned on every branch first, so a phished `state` does not get even one attempt). The old gap — "a JWT-less callback plus a `state` the initiator made up = somebody else's consent can be recorded under your name" (**F6**) — closes with it; the implementation details and the parts that were not verified are in `mcp-management` §7.13; round fifteen then fixed the order of the checks along this chain (the ownership comparison has to run before the request body is read), see §7.14. **The residue has to be said out loud**: this blocks "take A's authorization link, trick B into consenting, and have it land under A", it does not block "a logged-in user completing an authorization for themselves" — the latter is what this path is for. As for **who is logged in at the AS when the consent button is clicked**, that is the AS's own session's decision; this service neither sees it nor controls it: the `state` only guarantees this consent was given to this service (`resource`), not who clicked.
8. Logs and `last_error` reuse the `redact()` convention (see the credential-leak lesson skill-management R2-3); nothing after `Bearer` may be printed.
9. The exchange endpoint requires the `InternalApiAuthFilter` shared secret (`InternalApiAuthFilter.kt:37-49`) and accepts only `sessionId`; the next step is to move it onto the short-lived `InternalTokenProvider` JWT (`InternalTokenProvider.kt:14-76`) and retire the static secret.
10. Audit (`mcp_call_log`) cannot be switched off; `tool_call_log` is only "excluded" from `MybatisTenantInterceptor.EXCLUDED_TABLES` on paper — that interceptor is commented out end to end and does nothing — so tenant isolation must be written explicitly in SQL.

## 11. Relation to existing documents and known defects

- The name unique key `V23` and `selectByName(name, tenantId)` belong to P0 and have landed; section 2.1 of `mcp-management.en-US.md` now reads "unique within the tenant" instead of "globally unique name", with the implementation recorded in its §7.3.
- This design does not change `agent_mcp_binding` semantics: a binding remains "which MCP services this agent uses + the environment-parameter snapshot"; user authorization is resolved **per person at runtime** and never enters the binding table.
- The known leftover "`AgentMapper.xml` neither maps nor inserts `agent.tenant_id`" closed together with P1: the resultMap and the insert now carry the column, `selectAgentList` has a tenant condition, and the single-row read `AgentServiceImpl.getAgent` decides ownership against the current tenant (a foreign row answers as missing), which `updateAgent` / `toggleAgentStatus` / `deleteAgent` and `AgentController`'s single-row read all go through; on the mp side `MpAgentService.getAgentDetail` and `MpSessionService.createSession` refuse cross-tenant using `sys_user.tenant_id`. On the `session` side a session is stamped with the current tenant on create (no longer relying on the DDL default) and `selectSessionList` gained the tenant condition. The delivery path follows the same rule: `selectByIds` has no tenant condition and should not (an internal call carries no trustworthy `X-Tenant-ID` to inject), so `InternalApiController.buildAgentSpecResponse` compares against `agent.tenant_id` — a foreign server appears in neither half of the answer and is never even decrypted. `V24__backfill_agent_session_tenant.sql` gives historical rows their real tenant by the creator's primary tenant (the rule `V22` used for `mcp_server`); without it the new filters would first hide a tenant-2 owner's own agents and sessions. The test schema's `agent` block had neither `tenant_id` nor prod's actual keys — it carried an invented `UNIQUE KEY uk_name` prod does not have; it is now aligned with `V1__init_schema.sql:195-215`. There is also only **one** test schema left: `MySQLContainer.withInitScript("schema-test.sql")` loads `harnax-entity/src/test/resources/schema-test.sql`, while the same-named file under `harnax-admin` sat on no classpath reference and had drifted (still `UNIQUE KEY uk_name`, no V23 generated column), so keeping two copies would only let the drift continue and the admin copy was deleted.
- Two things P1 deliberately did not close: `HarnessAgentWrapper.userId` is still never populated by `HarnessAgentLauncher`, so the state-store key still contains no user — changing it would move already-persisted session state keys; and Feishu / scheduled tasks / the CLI still arrive with `userId` null (see §2.2), so before P2's exchange endpoint can report `NEEDS_CONSENT` for them, those entrances have to be wired to a user identity first.
- During P2-2 a **shipped-but-dead configuration** was found and fixed: `harnax-admin/application.yml` hung `base-url` under `admin:`, while the readers use `@Value("\${app.base-url:...}")` (`ChannelServiceImpl` and the deployment doc both do), so `APP_BASE_URL` never reached the code and channel callbacks always fell back to `http://localhost:8080`. It now lives at the top level under `app:`. This matters to this design directly: OAuth's `redirect_uri` must match the registered value exactly (§6.2), so reading it through the same defect would have every real deployment's first authorization rejected by the AS. Fixing `application.yml` was only half of it — round eleven wired the deployment side: the admin service in `docker-new/docker-compose.yml` now passes `APP_BASE_URL` explicitly, `.env.example` lists the key with a note that `redirect_uri` is compared as an exact string, and `docs/deploy-harnax-admin.md` moved the setting out of its "cannot be overridden by environment variable" table into the environment-variable table. A deployment that leaves it unset still sends `http://localhost:8080` as every `redirect_uri`. Round fourteen split the two uses apart: a new `app.frontend-base-url` (`APP_FRONTEND_BASE_URL`, falling back to `app.base-url` when empty) governs **the origin the browser is sent back to** and is what the default OAuth `redirect_uri` is built from, while channel callbacks keep using `app.base-url` — leaving it unset is correct behind the shipped nginx proxy on one origin, and wrong in development, where the SPA is on :8000 while admin is on :8080.
- The current MCP connection-failure stance is "warn and continue assembling; `status=0` is skipped outright" (see mcp-management §7.2 round three). **Authorization failure is not "skippable"**: a missing credential must land explicitly in `NEEDS_CONSENT` and be visible to the user, never silently dropping a tool.
- The P2-3 verification claim needs its boundary stated: the whole chain (initiate → state → exchange → token → store → revoke) is covered by **unit tests**, with outbound HTTP stubbed at the `RemoteJsonFetcher` layer. The §10 acceptance line "walk discovery → authorize → store → revoke against a Keycloak/test AS" **has never run against a real authorization server**, and in particular no implementation's actual reaction to the `resource` parameter has been observed. Until an AS instance is wired up, that acceptance item is not done. After round fourteen this is a harder statement: `redirect_uri` now points at a front-end route, a shape no AS has ever accepted, and the administrator has to register the new address at the AS by hand first — otherwise the very first authorization breaks on the AS's side before any of our code is involved.
- Pending authorization state lives in **one JVM's memory** (§6.2). The current deployment is a single instance, so this holds; once admin runs multiple replicas, the **exchange** can land on a replica that never saw this `authorize-url`, and what the user sees is "this authorization request is unknown or has expired". Multi-replica needs either sticky routing or a shared replacement for `McpOAuthStateStore` (Redis or similar) — one of the two, and retrying does not fix it. Round fourteen turned "the callback lands on the wrong replica" into "the exchange lands on the wrong replica"; **this constraint has not gotten stricter**, only the subject changed. The per-person cap of 5 added in round fifteen lives in that same memory and is therefore counted per replica as well: with several replicas one person's usable allowance becomes 5 times the replica count, which is not a new problem but the other face of the same premise.
- What is still open after this round, split honestly between "left open on purpose" and "cannot be closed here", so nobody reads the guard rails as a finished perimeter:
    - **Loopback and RFC1918 stay reachable by decision**, not by omission: self-hosted authorization servers live in those ranges, including this project's own docker-compose setup. The floor refuses only link-local / any-local / multicast addresses and `metadata.google.internal`. The cost is stated: an admin deployed on an interface that can reach a cloud metadata service directly is not protected by this floor against a second hop that comes back around.
    - **DNS rebinding is not part of the claimed capability**: the address is resolved here once for the judgement, and `HttpClient` resolves it again when it actually connects, so a name that changes its mind in between walks past the check. Closing that needs a custom `SocketFactory` or network isolation, which is a network concern, not this fetcher's.
    - **There is no role layer**: `SecurityConfig.kt:50-51` stops at `.authenticated()`, so any signed-in user can start a discovery for a row of their own tenant — that is, ask the server to request an address they typed. The assumption "only administrators use admin" is what holds this up today; revisit it once roles exist. The same shortcut appears as `McpServerServiceImpl.currentTenantId()` (`:82`), which falls back to tenant 1 when the context is empty.
    - **Spring Security is left with one `permitAll()` business path**: `/api/admin/internal/**`, where what actually gates the door is the shared secret in `InternalApiAuthFilter` — a passing secret counts as "authenticated", and this has to be re-read before P2-4's exchange endpoint is mounted there (already noted in §8 item 9). The other one, `/api/admin/mcp/oauth/callback`, was deleted in round fourteen together with F6 (the remaining `permitAll` entries are login / captcha / `mp/auth` / swagger, all of which were public to begin with). It used to be **an endpoint anyone outside could knock on**: what a wrong guess bought was one notice page plus one warn log line, and the 500-entry cap in `McpOAuthStateStore` was the bound on memory. That whole wall has now moved onto the JWT-carrying `POST /oauth/exchange` — without an identity you do not even get into the judgement — and the 500-entry cap is still there, but it no longer bounds a resource strangers can reach; round fifteen then put a per-person cap of 5 in front of the "our own users clicking furiously" side, so one logged-in user cannot fill the budget everybody shares.
- While adding V26 this round, a **boot-level** defect was found and fixed: the comment body above `deleteById` in `PlanNoteMapper.xml` contained `A -- B`, and an XML comment may not contain consecutive hyphens, so MyBatis failed to parse that file. All three services set `mybatis.mapper-locations` to `classpath*:mapper/*.xml`, so one unparseable file means the `SqlSessionFactory` cannot be created and **admin / scheduler / router all fail to start** — not "one feature is broken". This also explains why the whole block of `harnax-entity` mapper integration tests was red: it was never Docker, it was this same parse failure, and with it fixed those tests pass against local Docker. `harnax-entity` now has `MapperXmlParseTest`, which needs no Docker: it parses every mapper XML on the classpath and separately looks for `--` inside comment bodies (the parser only reports "not well-formed" and never says it was a comment), so this class of problem explodes in the test phase instead of at startup.
