## 1. Overview

MCP (Model Context Protocol) servers are one of the external tool sources for agents, alongside built-in tools (`BUILTIN`) and HTTP proxy tools (`HTTP`). MCP entity management **shares the same layering** as the tool system but not its lifecycle: built-in tools converge against code at startup via `BuiltinToolAutoRegistrar`, whereas every MCP server is maintained by hand through the pages and the APIs — CRUD is its complete lifecycle. The layers:

- **harnax-entity**: `McpServer` / `AgentMcpBinding` entities and mappers;
- **harnax-admin**: MCP server CRUD, encrypted secret storage, masked echo, connectivity tests, binding management, and config delivery;
- **harnax-agent-service / harness-core**: runtime MCP client assembly per agent configuration.

## 2. Data Model

### 2.1 mcp_server (MCP server master table)

Entity: `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/McpServer.kt`

| Field | Description |
|-------|-------------|
| `name` / `description` | Server name and description. The name is **unique within a tenant** (migration `V23__add_mcp_server_name_unique_key.sql`: generated column `active_name` + `uk_mcp_server_tenant_active_name (tenant_id, active_name)`). Before V23 the production table had **no** name unique key at all (only `KEY idx_tenant_id`), and uniqueness relied entirely on the application's **global** `selectByName`: a concurrent create could produce two live rows with the same name, while a name taken by another tenant was unusable here |
| `type` | Transport type: `stdio` / `sse` / `streamablehttp` (default) |
| `command` | Execution command (stdio type only) |
| `url` | Server URL (sse / streamablehttp types) |
| `headers` | HTTP headers JSON, format `[{"key":"Authorization","value":"...","secret":true}]`; values of `secret=true` entries are stored **AES-256-GCM encrypted**. It can only carry a **service-level static credential** (one copy shared by the whole tenant, never expiring); per-user authorization is covered by mcp-authorization-design |
| `envParams` | Env parameters JSON (process environment for stdio type), same format as `ToolEnvParamEntry`, secret entries encrypted; shares the masked write-back rule with `headers` (see 3.3) |
| `authType` | Upstream authentication mechanism (migration `V25`): `NONE` / `STATIC_HEADER` / `BASIC` / `OAUTH2`, constants in `McpAuthTypes`. The admin side only accepts `SUPPORTED = NONE / STATIC_HEADER / OAUTH2` — `BASIC` has a column but no runtime (the enum value is reserved for P4; submitting it today fails with "not wired into the runtime yet"), and unknown values are refused for the same reason: **storing is delivering**, a branch the runtime cannot recognise is harder to debug than a plain `NONE`. `NONE` and `STATIC_HEADER` take the same code path (both just read `headers`); the label exists to be readable to an administrator |
| `oauthConfig` | Non-sensitive OAuth configuration JSON (`V25`), serialised from `admin/dto/McpOAuthConfig.kt`: `authorizationServer` (leave it empty and it is discovered from the MCP server's own RFC 9728 metadata, see 3.5), `scopes`, `audience`, `resourceIndicator` (whether to send the RFC 8707 `resource` parameter). **Deliberately a typed DTO rather than free-form JSON**: client credentials and tokens have no field on it, which is what keeps them out of a column that is echoed back to the form in plaintext. Legal only when `authType=OAUTH2`; leaving OAuth clears it to null |
| `status` | Enabled state (0 disabled / 1 enabled). Delivered with `McpDetailDto`; at session assembly the launcher skips servers with `status=0` instead of creating a client |
| `isPublic` | Public state (0 private / 1 public); the entity, the create request, and the column default (migration `V22`) all default to 1. List visibility is `is_public = 1 OR creator = current user`, with the tenant filter layered on top (see below) |
| `creator` / `tenantId` | Creator and tenant. `tenantId` is written from `TenantContext` at creation time and appears in both the resultMap and the insert; when a `tenantId` is passed, the list query appends `AND tenant_id = #{tenantId}` — same convention as CLI and skills, so `is_public` only shares within a tenant and another tenant's public servers no longer show up in your list. **Single-row reads and writes are tenant-scoped too**: `getMcpServer(id)` compares the loaded row against the current tenant and treats a foreign row as absent, and `updateMcpServer` / `toggleMcpServerStatus` / `deleteMcpServer` all enter through it. That layer is mandatory — `MybatisTenantInterceptor.intercept` is commented out (it rewrites nothing) and `selectById` carries no tenant predicate, so without it a guessed auto-increment id would edit or delete another tenant's server |
| `active` | Logical delete flag (0 deleted / 1 active) |

### 2.2 agent_mcp_binding (agent-MCP binding table)

Entity: `AgentMcpBinding.kt`

- `agentId` / `mcpId`: the binding relationship, with `(agent_id, mcp_id)` as a unique key (migration `V19__add_mcp_binding_unique_key.sql`, which first collapses duplicate rows and keeps the last-written one); the application layer also de-duplicates with `distinctBy { mcpId }` in `saveMcpBindings`, mirroring the tool side;
- `envBindings`: env variable binding JSON snapshot (envKey + `envVarId` or `customValue`). **Note this channel only feeds `ToolEnvContext` for ToolBox tools — it is NOT injected into the MCP client itself** (see section 6).

The table used to carry `enable_skip` (`"true"` / `"false"` strings), meaning "skip or not when no `mcp_server` row is found". The name never matched the behavior: when the server is unreachable, `McpHelper.createMcpClient` and `registerMcpClient().block()` throw straight through, beyond the flag's reach; and the one path it did cover — a missing config record — is the same story as on the tool side, where skipping only trades "throw" for "warn", which is no choice anyone actually needs. The column has therefore been dropped along the whole chain (migration `V20__drop_mcp_binding_enable_skip.sql`), together with `McpSpec.skipIfMissing` and the `AGENT_MCP_NOT_FOUND` error code: a missing config always warns and skips now, matching the tool-side behavior after `V17`.

### 2.3 McpDetailDto (internal API delivery carrier)

Entity: `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/dto/McpDetailDto.kt`

The full MCP configuration delivered by the Admin internal API to agent-service (including server-level `status`), eliminating direct queries of the `mcp_server` table from agent-service. `headers` / `envParams` are **decrypted into plain JSON objects before delivery** (`{"KEY":"value"}` shape): the AES key lives only on the admin side, and the receiving `PlaintextMcpConfigDecryptor` just parses plain text instead of decrypting.

This carrier currently has **no** `authType` / `oauthConfig` field: V25's two columns stop at the admin side, and passing the authentication mechanism to the runtime is the first thing P3 of the authorization design has to add.

### 2.4 The three V26 OAuth tables (client and credentials are wired, audit is not)

Migration `V26__add_mcp_oauth_tables.sql` created three tables. Their columns and trade-offs are recorded item by item in mcp-authorization-design §5.2–5.4; what belongs here is how far each of them has been wired up:

- `mcp_oauth_client`: the client registration per tenant × authorization server (one row per `client_id`, shared by every MCP server of that tenant sitting behind the same AS), with `client_secret_enc` holding ciphertext. **Wired by P2-2**: the discovery and registration endpoints write this table, rules in §3.5;
- `mcp_user_credential`: the grant per user × MCP server, the only place access and refresh tokens live. **Wired by P2-3**: a successful exchange writes the ciphertexts and sets `status=ACTIVE`, revoking clears both ciphertext columns back to NULL and sets `status=REVOKED`, rules in §3.6;
- `mcp_call_log`: append-only audit — outcome and latency, no request bodies and no `Authorization` values. Its writer is the P2-4 issuance endpoint, and **no code writes it yet**.

The first two have entities and mappers and are covered by `McpOauthClientMapperTest` / `McpUserCredentialMapperTest`; `McpCallLogMapper` exposes **only** `insert`, which is how "append-only" is enforced — there is no other method to call. The delete cascade is on that path too: `deleteMcpServer` also deletes this server's `mcp_user_credential` rows — with the server gone there is nothing to present a grant to, and leaving ciphertexts behind for a deleted row is pure blast radius. `mcp_oauth_client` is deliberately **not** touched on that path: one row represents this tenant's client identity at that authorization server, and other MCP servers behind the same AS are still using it.

## 3. Admin Management Flow

Implementation: `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/controller/McpServerController.kt` + `service/impl/McpServerServiceImpl.kt`, prefix `/api/admin/mcp`.

|----------|--------|-------------|

Until round fourteen a seventh class sat here too, `McpOAuthCallbackController` (`GET /oauth/callback`, answering HTML with no authentication at all); it has been replaced by the exchange endpoint and deleted, reasons in §7.13.

### 3.2 Create / Update Validation and Encryption

1. **Name uniqueness**: checked via `selectByName(name, tenantId)` **within the current tenant**; duplicates throw `BizException`; the database side is backstopped by `V23`'s `uk_mcp_server_tenant_active_name (tenant_id, active_name)` (a concurrent create hits the index, and `ApiErrors` maps that index name to a sentence instead of leaking SQL into the response);
2. **Type-field linkage validation** (`validateTypeAndFields`): `stdio` requires `command`; `sse` / `streamablehttp` require `url`; other types are rejected;
3. **Secret encryption**: `headers` via `SecretFieldEncryptor.serializeWithEncryption`, `envParams` via `serializeToolEnvParams`, encrypted then serialized to the DB (only `secret=true` entries are encrypted);
4. **Masked write-back**: on update, `headers` / `envParams` are re-serialized only when present in the request, and both calls also pass **the column the row already holds** — the detail API echoes masks, so an untouched field comes back masked and must keep the stored ciphertext rather than have the mask encrypted (see 3.3 and 7.3);
5. **Defaults**: on create, `type` defaults to `streamablehttp` (matching the entity and the DDL), `status` / `isPublic` default to 1 when the request omits them, and `V22` has aligned the `is_public` column default to 1 as well — so a direct `INSERT` that bypasses the app behaves the same way;
6. **Update semantics**: every field of `McpServerUpdateRequest` (`name` / `description` / `type` / `command` / `url` / `status` / `isPublic`) is nullable, so **omitting one keeps the stored value** (`updateMcpServer` copies them field by field with `?.let`); when present they overwrite the entity, and the SET list of `updateById` includes the `status` column and refreshes `update_time` explicitly. The on/off switch on the list page goes through `/toggle/{id}`, which uses the dedicated `updateStatus` statement;
7. **Tenant**: creation writes the current `TenantContext` tenant (falling back to the default tenant 1 outside a request context). The insert statement previously did not write `tenant_id` at all, so every row stayed in the default tenant; the same migration that enables the list filter (`V22`) therefore backfills `tenant_id` once from the creator's tenant first. The `/{id}` endpoints (details / update / toggle / delete) load the row through `getMcpServer` and compare tenants, so another tenant's id reads as "not found".
8. **Authentication mechanism** (`resolveAuthType` / `validateAuthType` / `writeOAuthConfig`, landed with P2-1): `authType` defaults to `NONE` and must be in `McpAuthTypes.SUPPORTED`; both `BASIC` and unknown values are refused (the former being a fake switch — a column with no runtime behind it); `OAUTH2` may not be combined with `type=stdio`; `oauthConfig` is legal only under `OAUTH2` — carrying it on a non-OAuth server is an error rather than a silent drop — and its `authorizationServer` must be an http(s) URL. On update these checks run against the **merged row** (fields the request omits are evaluated as their stored values) and before `updateById`, so turning an OAuth server into stdio is refused too; leaving `OAUTH2` clears `oauth_config` to null. Each assertion is in `McpServerServiceImplTest.AuthTypeTests` (10 cases, numbered MCS-13 to MCS-22 in `docs/unit-test-cases.md` §5.3).

### 3.3 Masked Echo

`McpServerResponse.fromEntity` decrypts secret entries then masks them: length > 7 shows "first 3 chars + `****` + last 4 chars", otherwise `******`; decryption failures also show `******`. The frontend never sees plaintext secrets.

The mask is a **two-way convention**: since the frontend only ever sees a mask, an untouched field is submitted back as a mask, and the write side has to recognise it. Both `serializeWithEncryption` and `serializeToolEnvParams` detect it with `value.contains("****")` (`******` contains `****`, so both shapes are covered) and, on a hit, carry over the ciphertext of the same `key` / `envParamName` from the column the row already holds. When there is nothing to carry over (the entry was renamed, or the row never had one) they throw `BizException` and ask for a re-entry — the mask is never encrypted as if it were a plaintext value.

That convention used to belong to JSON entry lists alone. `mcp_oauth_client.client_secret_enc` is a **single column** holding a secret that also has to come back masked, so the same detection was lifted into `SecretFieldEncryptor.resolveSecret(provided, storedEncrypted)`: `null` keeps the stored value, a mask keeps the stored ciphertext (and throws "re-enter it" when there is no ciphertext to keep rather than encrypting the mask), a blank string clears it explicitly — the normal shape of a public PKCE client — and anything else is encrypted as a new value. The three ways of "not changing it" each mean something different.

### 3.4 Encryption Infrastructure

- `SecretFieldEncryptor` (`harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/util/`): implements the `McpConfigDecryptor` interface (defined in `harnax-common`), based on `AesUtil` (AES-256-GCM);
- `McpConfigDecryptor` (`harnax-common/src/main/kotlin/com/agnetix/harnax/common/mcp/`): cross-module decryption SPI with two methods, `decryptToMap` (headers) and `decryptToolEnvParamsToMap` (envParams).

### 3.5 OAuth Discovery and Client Registration (P2-2)

Implementation: `admin/controller/McpOAuthController.kt` + `service/impl/McpOAuthServiceImpl.kt`, with every outbound request going through `admin/util/RemoteJsonFetcher.kt`. This layer only does the setup an administrator performs once per (tenant, authorization server): discover the endpoints, put one `mcp_oauth_client` row in place, register the client credentials. **It exchanges no tokens, and the runtime still has no per-user injection path** (that is P3). The rules:

1. **Admission gate**: both endpoints load the row through `McpServerService.getMcpServer(id)` — that is where the tenant guard lives (round four, §7.4) — so another tenant's id answers "not found"; then they require `authType == OAUTH2` and a non-blank http(s) `url`. Every URL is trimmed before it is judged (a row stored with stray whitespace around it must not surface as a raw `URI.create` failure) and checked against the width of the column it is going into (`issuer` 255, every other URL 500): MySQL answers an over-long value with a 1406 or, with strict mode off, truncates it — and a truncated identity column leaves a registration no token ever matches again. Selecting OAuth on the form only makes these two endpoints available; the server itself keeps connecting through `headers`.
2. **Issuer resolution order** (RFC 9728 first, error only after every route fails): ① `oauthConfig.authorizationServer`, typed by the admin (source `CONFIG`); ② the protected-resource metadata derived from the MCP server url, three candidates — the path-inserted form `origin/.well-known/oauth-protected-resource/mcp/path`, the appended form `origin/mcp/path/.well-known/oauth-protected-resource`, and the host root; ③ one plain GET on the MCP url, reading the `resource_metadata` pointer out of its `WWW-Authenticate` challenge with a regex — quoted or bare, since the quotes are a convention rather than the spec (source `RESOURCE_METADATA`) — some servers say nothing else. The **first** entry of `authorization_servers` wins (more than one logs at info). Hand-typed and advertised issuers clear the same bar, and an issuer is held tighter than a plain URL: no userinfo, query or fragment (none of the three is carried into the metadata URL, so storing one leaves a value nobody ever confirmed) and the trailing slash is dropped, because the lookup that reuses a registration is byte-exact and a slash would create a second authorization server. A metadata document is untrusted input about where harnax will send users, so no `file://`.
3. **Four AS metadata candidates**: `.well-known/oauth-authorization-server` and `.well-known/openid-configuration`, each tried both path-inserted and appended (the latter last, because it is what pre-RFC servers and most OIDC libraries actually serve). A document counts only if it has both `authorization_endpoint` and `token_endpoint`, and those two values clear the same http(s) + width check as a hand-typed address — they are the addresses P2-3 redirects a browser to and POSTs a `code` plus `client_secret` to (and, from P2-4 on, a refresh), so storing a bad one moves the attack surface into the database. An *optional* endpoint offered at an unusable value is dropped with a `warn` instead: losing an optional capability is not a reason to fail discovery, but keeping a bad address in a table that credentials get posted to is. If the document declares its own `issuer` that is **not exactly equal** to the one queried, it is refused — RFC 8414 requires equality, and storing a foreign issuer would make every later token fail its own issuer check in a way nobody traces back to this row. A document that declares **no** issuer is judged by where the issuer came from: accepted when the admin typed it (somebody vouched, and it is the only way out), refused when an untrusted document advertised it, because there the two documents never cross-check each other.
4. **Failures are loud**: every candidate's reason is joined with `; ` into one `BizException` message (`Cannot locate the authorization server for <url>: ...` / `No usable authorization server metadata for <issuer>: ...`), truncated at 600 characters — each reason can carry an upstream message of its own and the whole thing appears in an API response body. Addresses in those messages are stripped of userinfo first. Nothing ever downgrades to "just use a static header and carry on" — a half-discovered server that still reads as configured is how a runtime later sends an unauthenticated request on someone's behalf.
5. **One row per (tenant, issuer)**: when `selectByTenantAndIssuer` hits, only the endpoints are refreshed and `client_id` / `client_secret_enc` / `callback_url` are carried over from the loaded row, because the SET list of `updateById` is unconditional (§7.5 item 2) — not carrying them would unregister the client on the next discovery. On a miss the insert leaves `client_id` an **empty string**, meaning "endpoints known, no client registered yet", which the authorize-url path refuses (implemented by P2-3: both starting a flow and exchanging a code refuse it, see §3.6 rule 1). A null `registration_endpoint` / `revocation_endpoint` is written as null on purpose: that is exactly the fact "this AS stopped offering DCR" that has to be recorded.
6. **The issuer write-back moves one column**: whenever the issuer did not come from `oauthConfig` (routes ② and ③), a successful discovery writes it back through `McpServerMapper.updateOAuthConfig(id, json)`. This used to be `updateById(whole row)`, whose SET list is unconditional: discovery would overwrite status / headers / name from a row it read minutes earlier, undoing somebody else's edit — and destroying the ciphertext too, the day a read ever returns a decrypted view. Discovery owns `oauth_config`, so it writes `oauth_config` (plus `update_time = NOW()` — that row really did change; what `McpServerMapperTest` pins is that nothing else moves).
7. **callback_url default**: a new row gets `${app.frontend-base-url}/mcp/oauth/callback` — that is a **front-end route** (the authorization landing page, §3.6 rule 3), not an endpoint of this service; when `app.frontend-base-url` is unset it falls back to `app.base-url` (behind the shipped nginx both are proxied on one origin, so the fallback is the right answer; in development the SPA is on :8000 while admin is on :8080, so it has to be set explicitly). `McpOAuthClientRequest.callbackUrl` may override it, and the override clears the same http(s) + width check first. What the authorization server compares byte-for-byte is exactly the value stored in this column, so **changing those two environment variables does not change the existing rows**: the one written at registration time has to be re-saved by hand (the page raises a mismatch warning for it). Before round fourteen the default of this column was `${app.base-url}/api/admin/mcp/oauth/callback`, pointing at an unauthenticated endpoint that has since been deleted.
8. **Registering a client**: `client_id` is required and validated **before any write**, so a request that cannot finish leaves no half-populated row; `clientSecret` goes through the three-way `resolveSecret` at the end of 3.3; `registration_source` is `MANUAL` on both paths for now (DCR is P4). Manual registration runs one discovery first if the row has no endpoints — those are the addresses the flow actually redirects to and may not be left empty. This path **re-validates the stored issuer** (that column may have been edited by hand or left by an older build), because it is the one that attaches a `client_secret` to it.
9. **An unreadable `oauth_config` stops discovery**: a blank column means "not configured yet", a column that will not parse means drift in data this feature serialized itself — and discovery rewrites that column. Continuing with defaults would replace the scopes the admin typed with an empty list and report that as a success. The same rule governs the MCP edit form: a request that leaves `authorizationServer` out keeps the issuer already stored (otherwise editing one scope orphans that discovery), while a request that supplies an unusable one is still refused.
10. **The echo carries no secret**: `McpOAuthDiscoveryResponse` returns only the boolean `clientSecretPresent`; plaintext never leaves admin. It also returns `issuerSource` (so the page can say whether this was discovered or typed) and `unknownScopes` (the requested scopes this AS does not know — otherwise a typo surfaces as a 400 after a user has already been sent to log in). One DTO serves both endpoints; a separate "client response" was deliberately not invented.
11. **Outbound guard rails (`RemoteJsonFetcher`)**: harnax does call out elsewhere (`McpServerServiceImpl.listTools`, channels, the registry); what this component owns is the one route whose **target comes from an administrator or an upstream document**, which is why the protocol allow-list and the address floor live here: http(s) with a host required; cloud metadata targets refused (link-local, any-local and multicast addresses plus hostnames like `metadata.google.internal`, checked before any connection is opened — loopback and the private ranges are deliberately left reachable, because self-hosted authorization servers live there, this project's own docker-compose among them); `Redirect.NEVER` (a 302 is not followed — a test proves it with a counter); 5s connect / 10s request timeouts; a 64KB body cap **plus a real read deadline** (draining an `ofInputStream` body happens on this thread where the request timeout cannot reach it, so an address that trickles bytes needs its own bound); a body-read failure wrapped in `RemoteFetchException` like everything else (otherwise one reset connection crashes the whole discovery instead of moving to the next candidate); only a JSON **object** counts as metadata (an array or a scalar answers "nothing is published here" as surely as HTML does); and every `WWW-Authenticate` header joined, because a gateway may split the challenge and the pointer can be in either part. These are a floor, not a policy: the address judged here is resolved again by the connection, so DNS rebinding is out of scope. P2-3 added `postForm` to it — a form POST carrying `code` / `client_secret` / tokens leaves through this one exit as well, so the exchange and the revocation inherit every protocol, address, redirect, timeout and size rule above; and the top-level `normalizeIssuer` in the same file is the one issuer normalization discovery and authorization now share, because two copies would let one extra trailing slash typed by an admin mean "registered under one row, no row found at authorize time".

Fixed on the way, a **shipped-but-dead property**: `base-url` sat under `admin:` while the readers use `@Value("\${app.base-url:...}")` (`ChannelServiceImpl` and the deployment doc both do), so `APP_BASE_URL` never reached the code and channel callbacks always fell back to `http://localhost:8080`. `application.yml` now has it at the top level under `app:`, which is also where OAuth's `redirect_uri` reads it — otherwise the new feature would have inherited the same defect. Tests: 49 cases in `McpOAuthServiceImplTest` (issuer resolution 14 / metadata 11 / discovery writes 11 / client credentials 11 — everything round eight added sits in the "how far may an address or a document go before it counts as usable" group; round fourteen adds two under "where should the browser come back to", pinning that a configured `frontend-base-url` is obeyed and that `base-url` is used only when it is absent), 16 in `RemoteJsonFetcherTest` (a real JDK `HttpServer`: html and array bodies, oversized body, 401 challenge including one split across two headers, redirect never followed, metadata address and hostname, userinfo redaction, the body of a failing response, form POST encoding), 6 `ResolveSecretTests` in `SecretFieldEncryptorTest`, 12 in `McpServerServiceImplTest.AuthTypeTests` (including "an edit does not erase the discovered issuer"), and two `updateOAuthConfig` cases in `McpServerMapperTest` (only that column moves; a deleted row is not revived).

### 3.6 Authorization Code + PKCE and Credential Storage (P2-3)

Implementation: `admin/controller/McpOAuthController.kt` (four JSON endpoints: start, exchange, status, revoke) + `service/impl/McpOAuthUserServiceImpl.kt`, with the pending state in `admin/util/McpOAuthStateStore.kt` and every outbound call still leaving through `RemoteJsonFetcher.postForm`. What this layer does is the part that happens **once per person per MCP server**: start a consent, turn the result the authorization server sent back to the browser into a credential, read the state, revoke. **It does not inject tokens into the runtime** (P3) and does not exchange tokens on behalf of a session (P2-4). The rules:

1. **Admission gate**: `authorize-url` / `status` / `revoke` all load the row through `McpServerService.getMcpServer(id)` first (that is where the round-four tenant guard sits) and then require `authType == OAUTH2`, and they require **a current user** — an authorization belongs to a person, so a missing userId from `UserContextUtil` is an error, never a fallback of the kind `currentTenantId()` does by landing on tenant 1. Refusing to start or to exchange also covers a configuration whose issuer cannot be parsed, a missing registration row, and a row whose `client_id` is still the empty-string placeholder discovery left behind (§3.5 rule 5): sending `client_id=` to the AS only lets someone else's error page do our talking. The exchange endpoint passes that same user gate, but it has **no `{id}` to pick from**: which server is being authorized can only be said by the pending entry the `state` names (rule 3).
2. **`state` pins every premise of this consent**: one `PendingAuthorization` holds (tenant, user, mcpId, issuer, code_verifier, redirect_uri, resource, requested scopes), with a 5-minute TTL, a global cap of 500 entries, a further cap of 5 per person (`countFor(userId)` is counted **before** the verifier and the state are minted, so a refused attempt leaves no material behind at all), and `consume` invalidating on read (expiry is checked after removal, so an empty string and a missing entry give the same answer). In memory rather than in a table: a code is itself a one-shot, minute-scale object. Two consequences are stated plainly — **an admin restart interrupts a consent in flight**, and **multiple replicas need sticky routing** (an exchange that lands on a replica which never issued this `authorize-url` can only show "unknown or expired request"). Both caps are explicit refusals, each with its own true sentence, never a silent eviction: 500 is a budget **everybody shares**, so without a per-person limit in front of it one logged-in user with a script could fill it and leave everyone else unable to start an authorization for a whole TTL (added in round fifteen, see §7.14). Since round fourteen the pinned `userId` **is no longer what identifies anyone**: its job is to answer "whose account should this consent be recorded under", and the exchange compares it against the caller once — a mismatch is refused (rule 3), so forwarding an `authorize-url` to somebody else to click leaves them with nothing of the initiator's credential either.
3. **The exchange runs on the JWT, and `state` is only a one-time anti-CSRF token**: the authorization server's redirect lands on a **front-end page** (`harnax-webui/src/pages/mcp/oauth-callback.tsx`, route `/mcp/oauth/callback`), which calls `POST /api/admin/mcp/oauth/exchange` with the JWT the browser already holds. Identity therefore comes from the Spring Security authentication context, and `state` is demoted to the credential answering "did you start this pending entry": the caller's identity is resolved first (no identity, an error, and the **pending entry is left as it was** — somebody with no identity cannot even burn someone else's `state`), then `consume` burns that token **before any branch** (a consent the authorization server refused is over as well, and a `state` still alive is a token-minting request anyone can retry), and ownership is compared **before anything the request body says**: when the pending entry belongs to somebody other than the caller the answer is one sentence saying "this was started in another session" while the warn log carries **only the mcpId and the two user ids** — never the code, never the verifier, which are material meant for the token endpoint. That comparison has to come first: otherwise somebody who has learned another person's `state` could cancel that person's authorization in flight simply by posting an `error` of their own, and the warn that exists to detect consent phishing would not say a word about it (fixed in round fifteen, see §7.14). Conversely, when the AS really did report an `error`, **the upstream reason is handed to the page even if the pending entry has aged out** — in that case nothing was stored and nothing is left to burn, and the authorization server's own words are worth more to the page than "unknown or expired request". This comparison is itself the consent-phishing detector: when someone forwards the link, the victim sees a failure page and the attacker gains nothing. This service no longer receives the authorization server's browser redirect, and the two carve-outs `SecurityConfig` and `JwtAuthenticationFilter` had opened for the callback went with it.
4. **How the parameters are built**: `redirect_uri` comes from the registration row, never derived from the current request (the AS compares bytes, and that column holds what the administrator registered); a `scope` argument overrides the server-side configuration and is de-duplicated, and anything wider than the 512 characters of `mcp_user_credential.scopes` is **refused** (truncating it would record a grant nobody agreed to); `resource` is sent only when `oauthConfig.resourceIndicator` is set and `url` is non-empty; `audience` is sent only if configured; PKCE is **unconditionally `S256`**, with no downgrade path for whatever the AS metadata happens to say about `code_challenge_methods_supported` (decision and reasoning in mcp-authorization-design §6.2).
5. **The token exchange and what it checks**: the exchange first re-reads the server row by `pending.mcpId` through `McpServerService.getMcpServer` — this route carries an identity now, so it goes through the very tenant guard used everywhere else (a server the caller cannot see simply is not found) — and after loading it asserts that `server.tenantId` still equals the tenant the state pinned; a row that has gone, moved tenant, stopped being `OAUTH2`, or whose `url` no longer equals the `resource` the state pinned, stops the exchange (the code was minted for the old address; storing the result would park a key that opens nothing). The form carries `grant_type` / `code` / `redirect_uri` / `client_id` / `code_verifier`, plus `client_secret` in the body per RFC 6749 §4.1.3 when one is registered; a non-2xx answer becomes one sentence built from the upstream `error` / `error_description` (cut at 200 characters, userinfo stripped), and a 200 that is not a JSON object fails the same way; no `access_token` means no success. **Whether that upstream sentence can be read at all depends on the outbound layer parsing the body of a failure** — before round thirteen `RemoteJsonFetcher` parsed only 2xx bodies, so this sentence was in practice always a bare "HTTP 400" (§7.12 item 1). Two things are compared before anything is stored: `iss` — at the response level and again inside the JWT claims — must be **byte-equal** to the discovered issuer, and `aud` must contain this flow's `resource`. JWT claims are **parsed, not verified** — this code does not consume token content, it forwards it verbatim to the MCP server — and an opaque token that will not parse is **logged, not treated as a pass**.
6. **Storage semantics**: both tokens are encrypted by `AesUtil` into `access_token_enc` / `refresh_token_enc`; a fresh exchange **replaces** the refresh token outright (keeping the old one keeps a minting path nobody just consented to); `scopes` records what was actually granted and falls back to what was requested, and **a granted list wider than the 512 characters is not recorded at all** (`scopes=null`, with `last_error` saying how wide it was, what the column holds, and that it was therefore left out) — rule 4's "refuse rather than truncate" works on the request side because the caller can narrow the parameter, while nobody can narrow an answer the AS chose, and a cut-off list ends with a scope fragment no one granted; `status=ACTIVE`, `last_error` cleared apart from that note, `last_refreshed_at` stamped; an existing row goes through `updateById` (this table has no soft delete and its SET list is unconditional, which is exactly what lets revocation write NULL back); a new row goes through `insert`, and a collision on `uk_mcp_user_credential_tenant_user_mcp` (two authorizations of the same user for the same server landing at once) is caught: this exchange's token is written onto the row that won rather than reporting a database failure for a grant that did happen. **The `scopes` in the exchange answer are the list that column recorded**, not the raw field from the token response: RFC 6749 §5.1 makes `scope` optional, so an AS granting exactly what was asked may omit it, and answering with that empty list would show the landing page no scopes at all while `status` — reading this same column — shows the requested ones on the detail page a few seconds later (fixed in round fifteen, see §7.14). Requesting more scopes than granted only warns.
7. **How the state is read**: the query is always by (tenant, user, mcpId) — nobody sees another person's row; `REVOKED` never comes back to life; an `accessExpiresAt` in the past means **not usable** (refresh arrives with P2-4, and a page must not display an authorization the runtime cannot spend); a row with no expiry reads as usable; `lastError` is echoed verbatim (it can only ever have been a redacted sentence to begin with).
8. **Revocation**: local cleanup always happens (`REVOKED` plus both ciphertexts written back to NULL, `last_error` included); upstream is contacted once, with RFC 7009's `token_type_hint` preferring `refresh_token`, and only when the registration recorded a `revocation_endpoint`. An unreachable or refusing upstream does not fail the operation. **Six situations each answer with its own true sentence, and none of them borrows another's wording** (details in mcp-authorization-design §6.4): upstream accepted, upstream refused, no revocation endpoint (the RFC 7009 sentence belongs only to a server that genuinely does not support it), a ciphertext that will not open (the AES key changed since it was written — "cannot be decrypted" is neither "there was no token" nor "the upstream said no"), a registration row that is gone (which authorization server the grant came from can no longer be resolved, and that answer carries `POST /api/admin/mcp/{id}/oauth/discover` as the way back), and a row with no token left. Database exceptions go through `ApiErrors` so no table name escapes.
9. **Where no token appears**: not in the response DTOs, not in the logs, not in `last_error` — a log line says which scopes were recorded, what `expiresIn` was, and whether a refresh token came back. Scope names are not credentials (the `status` endpoint returns them to the browser anyway), but not one byte of a token reaches the log. `McpOAuthExchangeResponse` has four fields, `authorized` / `message` / `scopes` / `accessExpiresAt`, and **not one of them can hold a token**, while the credential's resting place is that one ciphertext column — answering it back to the browser would be a leak with no consumer. A **refusal of the exchange is a plain sentence rather than an HTTP status**: the `code` has already been spent, the page cannot retry it, so all it can show is the upstream reason (`error` / `error_description` joined as written, cut at 200 characters) together with "please start the authorization again". The old guard "the upstream `error_description` goes through `HtmlUtils.htmlEscape` before it reaches a page" has become "it travels as JSON and React renders it as a text node", the same policy as the upstream strings `McpServerServiceImpl.listTools` brings back; and the landing page wipes `?code=&state=` out of the address bar **before it sends the request** (`history.replace`), so those values sit on one local object inside the effect and go out immediately — never written to localStorage, never reaching a third-party script.
10. **Tests**: 62 in `McpOAuthUserServiceImplTest` (start 13 / exchange 32 / status 7 / revoke 10 — round fourteen rewrote the "callback" cases into the "exchange" group, and those additions are branches only the exchange model has: the state belongs to somebody else, there is no login context, no table at all is queried when the `state` is not recognized, the returned `state` carries no `code`, the upstream's own words are cut to the budget, the response body carries no token material, the target server is decided by the pending entry; round fifteen adds four more — one user cannot take the whole shared 500-entry budget, a fabricated `error` cannot cancel somebody else's authorization in flight, the upstream reason is still reported after the state has aged out, and when the AS omits the optional `scope` the answer reports what was recorded; round thirteen's real outbound HTTP cases are still in `RemoteJsonFetcherTest` (16), see §7.12 item 1. On the stubbing side: outbound is stubbed at `RemoteJsonFetcher` while `McpOAuthStateStore` is the real thing — what needs pinning is that the challenge sent out and the verifier presented back are the same value and that a `state` is spendable once), 7 in `McpOAuthStateStoreTest` (the new one pins that a per-user count counts only that user and sweeps the expired entries first), 12 in `McpServerServiceImplTest.AuthTypeTests` (round fifteen's two pin that credentials are cleared only when leaving `OAUTH2`, and that a server which stayed on it or never had it is never looked up in that table at all), and `McpOAuthControllerTest` grown from 13 to 16 (the three new ones guard the error semantics the exchange endpoint shows the world); the 4 cases of the old `McpOAuthCallbackControllerTest` were deleted along with the controller it tested. **No real authorization server has been exercised**: the mcp-authorization-design §10 acceptance line "discovery → authorize → store → revoke against Keycloak or a test AS" is not done, and in particular no implementation's actual reaction to the `resource` parameter has ever been observed; the new `redirect_uri` shape, pointing at a front-end route, has not been exercised by a single case either (§7.13 and §7.14).

## 4. Agent Binding and Config Delivery

1. **Binding save**: when an agent configuration is saved, `AgentServiceImpl.saveMcpBindings` deletes then re-inserts `agent_mcp_binding` rows; repeated `mcpId`s inside one request are collapsed by `distinctBy`, with the `(agent_id, mcp_id)` unique key as the database-side backstop. Before writing, the batch is validated with a single `McpServerMapper.selectByIds`: an id that resolves to no live server of the caller's tenant (deleted, never existing, or belonging to another tenant) aborts the whole request with `BizException` instead of leaving a binding row that delivery would later skip with `?: continue` — that failure only shows up in the log, while the page reads "configured but the tool is missing". `envBindings` is written as a snapshot via `serializeEnvBindings` — global env variable references (`envVarId`) are resolved to `envVarName` plus the decrypted `envValue`, custom values are stored as `customValue`. Reverse cleanup: deleting an MCP server removes all of its bindings so no row points at a gone server;
2. **Config delivery**: when agent-service requests an agent configuration, `InternalApiController.buildAgentSpecResponse` delivers two payloads:
   - `mcpDetails`: full `McpDetailDto` list (`headers` / `envParams` are plain objects decrypted before delivery, and `status` travels along). The bound `mcpId`s are de-duplicated first, then every server is fetched by a single `McpServerMapper.selectByIds` batch — same shape as the tool side, the per-binding N+1 is gone; bindings whose server row is missing, and bindings whose server belongs to a tenant other than the agent's own, are both warned out — `selectByIds` itself has no tenant condition (an internal call carries no trustworthy `X-Tenant-ID` to inject), so the comparison basis is `agent.tenant_id`;
   - legacy `mcpList` JSON: rebuilt from **the bindings whose server row actually resolved** (a binding pointing at a deleted server stays out of here — otherwise its `env_bindings` would still reach `ToolEnvContext` and contradict `mcpDetails`), with `env_bindings` already resolved to plaintext via `resolveEnvBindingsJson` (`envVarId` resolves to the **latest** decrypted value of the global variable, falling back to the snapshot).

## 5. Runtime Assembly Flow (agent-service)

```
AgentSpecResolver.buildAgentSpec()
    ├─ mcpDetails → McpSpec(mcpId)
    └─ mcpList env_bindings → merged into ToolEnvContext (read by ToolBox tools)
            ▼
HarnessAgentLauncher.createAgentBase()
    Iterates agentSpec.mcpServices:
    ├─ McpConfigAdaptorImpl.getConfig(mcpId)
    │     Only source: mcpDetails pre-delivered by admin in AgentSpecContextHolder (DTO → entity conversion, status included)
    │     No direct DB read: that row carries ciphertext and this service has no AES key (see §7.15 item 4)
    ├─ Config found + status == 0 → logs info and skips (no client, and not reported as missing either)
    ├─ Config found + status == 1 → McpHelper.createMcpClient(
    │        mcpConfig, isAsync,
    │        mcpConfigDecryptor?.decryptToMap,            // headers parse/decrypt
    │        mcpConfigDecryptor?.decryptToolEnvParamsToMap // envParams parse/decrypt
    │     )
    │        └─ throws → logs a warning and skips this one server, the rest is still assembled; the half-built client is closed
    └─ Config missing → logs a warning and skips (no switch anymore, and no AGENT_MCP_NOT_FOUND either)
            ▼
McpHelper.buildMcpConfig() dispatches by type:
    ├─ stdio          → StdioMcpConfig(command, env = envResolver(envParams))
    ├─ sse            → SseHttpMcpConfig(url, headers = configResolver(headers))
    └─ streamablehttp → StreamableHttpMcpConfig(url, headers = configResolver(headers))
            ▼
McpClientBuilder builds the client (buildSync / buildAsync) → agentBuilder.addMcp(...)
            ▼
The clients built in this pass are stored with the agent in HarnessAgentWrapper.mcpClients
Cache eviction / session destroy → wrapper.release(): closes every client first, then closes the agent
(`HarnessAgent.close()` does not free MCP clients — see §7.15 item 1)
```

Other runtime entry points:

- `McpHelper.listTools`: used by the Admin connectivity test / list_tools endpoints; `initialize()` blocks with a 10-second timeout, failures throw `MCP_CONNECTION_FAILED`; **the client is closed in a finally block whatever the outcome** — every "test connectivity" click builds one, and the stdio variant leaves a child process behind;
- `McpHelper.createMcpClient`: the async path bounds `buildAsync()` with `.block(60s)`, and a `null` build result throws `MCP_CLIENT_CREATE_FAILED` with the server name rather than becoming an NPE on the caller's next line;
- Both resolvers still fall back to `{ emptyMap() }` when `null`, but the container no longer passes `null`: harness-core registers `PlaintextMcpConfigDecryptor` as the fallback, which only parses the plain JSON objects Admin delivers (former TODO-1 fixed that way).

## 6. Two Channels for Env Variables and Secrets (Easily Confused)

| Channel | Configured at | Applies to | Decrypted when |
|---------|---------------|-----------|----------------|
| `mcp_server.headers` / `envParams` | The MCP server's own config (Admin MCP edit page) | **The MCP client itself** (auth headers / stdio process environment) | **Before Admin delivers them** (`InternalApiController.plainConfigJson` / `plainToolEnvJson`); agent-service only parses the plain text |
| `agent_mcp_binding.envBindings` | The env-variable form when binding an MCP to an agent | **ToolEnvContext** (read by ToolBox tool methods); NOT injected into the MCP client | At Admin delivery time (`InternalApiController`), already plaintext |

### 7.2 Fixed (2026-09, round three: all TODOs cleared)

**1. The `enable_skip` switch removed outright (former TODO-1)**

The original TODO offered two routes: push the skip decision down into client creation and registration, catching the exceptions at both sites, or rename the field and spell out its scope. Review chose a third: the switch had no semantics worth keeping. The single case it covered — "no `mcp_server` row found" — had already been settled on the tool side as warn-and-continue (see `V17`); connection failures always bypassed it, and swallowing those as well would let an agent that cannot reach a single tool come up silently, which is harder to diagnose than a hard failure. So:

- migration `V20__drop_mcp_binding_enable_skip.sql` drops the `agent_mcp_binding.enable_skip` column;
- the matching field is gone from entity `AgentMcpBinding`, `McpConfig` (request DTO), `McpDetailDto`, `AgentResponse.McpItem`, and `SessionResponse.McpItem`; the "allow skip" switches in the two frontend forms and their i18n copy were removed alongside;
- `McpSpec.skipIfMissing` and `HarnaxErrorCode.AGENT_MCP_NOT_FOUND` are deleted, and `HarnessAgentLauncher` now uniformly `log.warn`s and continues the build on a missing config;
- `V17` had written "MCP keeps its column", a premise that no longer holds, and `V20`'s comment contradicts it explicitly (migration text is immutable, so only a later statement can say so).

**2. Batch query on the delivery path (former TODO-2)**

`McpServerMapper` gained `selectByIds`, and `InternalApiController` now fetches all bound servers in one batch while assembling `mcpDetails`; the skill delivery right next to it (both the direct-binding and the CLI-linked routes) had the same N+1 shape and was converted in the same change. A missing row only warns and never throws, so the legacy `mcpList` and `skillList` are both generated from "the bindings that resolved" now, keeping the two halves consistent.

**3. Stale capability columns dropped (former TODO-3)**

`agent.mcp_list` was only the visible sample of a wider problem: `createAgent` never assigns `agent.mcp_list` / `agent.skill_list` / `agent.tool_list` or `session.mcp_list` / `session.skill_list`, so those columns held their create-table defaults forever while the readers were still in place — the MCP / skill lists on the session detail page were always empty, and so were the `mcpList` / `skillList` that scheduled tasks delivered to the agent. Migration `V21__drop_stale_capability_list_columns.sql` drops those 5 columns, and the readers were redirected: `SessionServiceImpl.convertToResponse` rebuilds both lists from the two binding tables by `session.agentId` (a session has no binding table of its own — it follows the agent it is bound to), and `InternalApiController.getAgentTaskSpec` likewise reads the binding tables by `agent.id`. Note that `AgentSpecResolver` parses the **response field** `mcpList.env_bindings`, which is unrelated to the dropped columns.

**4. Tenant filter added to MCP list queries (former TODO-4)**

The filter won over "state the single-tenant premise", because CLI and skills already had a `tenant_id` convention and MCP was the lone outlier. `selectMcpServerList` gained a nullable `tenantId` and appends `AND tenant_id = #{tenantId}` when non-null; `McpServerServiceImpl.page` passes `TenantContext.getTenantId() ?: 1`. Visibility change: another tenant's servers marked public no longer appear in your list, matching CLI / skills.

**5. `is_public` column default aligned (former TODO-5)**

### 7.3 Fixed (2026-09, round four: secret and tenant boundaries)

**1. The masked write-back overwrote real credentials with the mask (P0)**

The detail API (`McpServerResponse.fromEntity`) masks secret entries, `UpdateForm.tsx` loads those masks straight into the form, and `serializeWithEncryption` did not distinguish "a new value" from "the mask we sent you" — it just encrypted whatever arrived. So an edit that never touched the key (changing the description is enough) replaced the credential with `encrypt("Bea****oken")`, silently, and the breakage only surfaced when the MCP server refused to connect. Both serializers now take a second argument (the JSON this row already holds) and, on a mask, carry over the stored ciphertext for that `key` / `envParamName`; when there is nothing to carry over they throw `BizException` and ask for a re-entry — after the operator renames a key, both "keep silently" and "overwrite silently" lose data, so only an error is recoverable. Mask detection reuses the existing convention `contains("****")` (same as `ModelProviderServiceImpl`), which covers both shapes (`first3****last4` and the fixed `******`); the price is that a real value containing four consecutive asterisks reads as unchanged, the same trade the api-key mask already makes.

**2. Tenant ownership on single-row access (P1)**

The previous round filtered the list, but not the `selectById` path: `MybatisTenantInterceptor.intercept` is entirely commented out (it rewrites no SQL), so update / toggle / delete worked across tenants for anyone who could guess an id. `getMcpServer(id)` is now the single entry point: it compares the loaded row against the current tenant and returns `null` for a foreign one, and `updateMcpServer` / `toggleMcpServerStatus` / `deleteMcpServer` all load through it. A foreign id and a missing id share the answer "MCP server not found" rather than distinguishing themselves, so the endpoint cannot be used to probe ids. Historical binding rows behave exactly as before (skipped with `?: continue` at delivery), with no new "deleted" complaint.

**3. Name unique key (P1)**

Since the table was created, `mcp_server` has had nothing but `KEY idx_tenant_id` and plain indexes; name checking lived only in the application's `selectByName`, so a concurrent create could produce two live rows with the same name — and while the list had become tenant-scoped, that lookup was still global, so a name taken by another tenant was unusable. Migration `V23__add_mcp_server_name_unique_key.sql` first renames historical same-tenant duplicates (`LEFT(name,80) + '#dup-' + id`, keeping the lowest id), then adds the `V15`-style generated column `active_name` (`IF(active = 1, name, NULL)` VIRTUAL) plus `uk_mcp_server_tenant_active_name (tenant_id, active_name)`: MySQL unique indexes ignore NULL, so a soft-deleted name becomes available again. The application's `selectByName` gained a nullable `tenantId` to match, following `SkillRepositoryMapper.selectByName`; `ApiErrors.DUPLICATE_INDEX_MESSAGES` registers the index name so a collision answers "An MCP server with this name already exists in your tenant" instead of dumping SQL into the response.

**4. Binding id validation (P1)**

See section 4: `saveMcpBindings` batch-validates before writing and rejects the request when an id does not resolve.

**5. `update_time` never moved**

The SET list of `updateById` assigns `update_time = #{updateTime}` explicitly, and `updateMcpServer` never refreshed that field — so every edit wrote the stale timestamp back, the column's `ON UPDATE CURRENT_TIMESTAMP` does not fire on an explicit assignment, and a list sorted by update time looked frozen. The update now stamps `LocalDateTime.now()`.

**6. Optionality of the update request fields**

`name` / `description` / `type` / `command` / `url` in `McpServerUpdateRequest` changed from "non-null with a default" to nullable, so omitting one keeps the stored value (same convention as `status` / `isPublic` from the previous round), and `updateMcpServer` now copies them field by field with `?.let`. Previously a partial submit that only changed the url also cleared `description` to an empty string and forced `type` to its default. For `name`, only an omitted value means "unchanged": an empty string is rejected outright (`MCP name cannot be empty`), and the duplicate check runs against the row's own tenant via `selectByName(name, mcpServer.tenantId)`.

**7. Two test root causes**

- `SecretFieldEncryptorTest` built a plain `ObjectMapper()`, which cannot bind the constructor parameters of Kotlin data classes, so `deserializeEntries` returned entries with empty fields — that was the real cause of the class's 6 failures (previously recorded in skill-management as "pre-existing failures unrelated to MCP"). Switching to `jacksonObjectMapper()`, the same builder the production `JacksonConfig` bean uses, turned them all green. The lesson: the fixture's mapper must be the same one the class under test is injected with, otherwise "serialization works, deserialization returns nothing" slips right past the logic under test.
- In `harnax-entity`'s `schema-test.sql`, `mcp_server` carried `UNIQUE KEY uk_name (name)` — an index production never had (V1 only has `idx_tenant_id`). The test database was asserting a constraint that does not exist in production; it now matches V23.

**Still open**: the tool-side and CLI-side twins of the masked write-back (`AgentToolServiceImpl` and `CliServiceImpl`) were left in place; the shared helper already existed, so each was a one-argument wire-up. Round ten closed all three sites those two services hold, plus a fourth found on the way in env variables (see §7.9). The other half of this paragraph — the cross-tenant binding resolving at delivery — needed `agent.tenant_id` first and is done in round five (see §7.4).

### 7.4 Fixed (2026-09, round five: tenant ownership actually lands)

**1. `agent.tenant_id` mapped, inserted and decided per row (OAuth design P1)**

The same shape as round four's MCP defect: `AgentMapper.xml` had no `tenant_id` in its resultMap or insert column list, so whatever `AgentServiceImpl` assigned never reached the row and every agent stayed in the default tenant 1. The column is now mapped and inserted, `selectAgentList` gained an optional `tenantId` condition (same shape as `selectMcpServerList`), the single-row read `AgentServiceImpl.getAgent` compares it against the current tenant and answers "missing" for a foreign row, and `updateAgent` / `toggleAgentStatus` / `deleteAgent` all go through that read — a writer that skips the guard turns the list filter into decoration. On the mp side `MpAgentService.getAgentDetail` and `MpSessionService.createSession` refuse cross-tenant using `sys_user.tenant_id`. `updateById` deliberately omits `tenant_id`: ownership is not an editable field.

**2. `session.tenant_id`**

`SessionServiceImpl.createSession` never wrote the column at all (only the mini-program path did, following its agent), so every web session landed in the default tenant. Creating a session now stamps the current tenant and `selectSessionList` filters by it, with the same convention as `agent`.

**3. Delivery filters MCP by the agent's tenant**

Round four's leftover: `selectByIds` has no tenant condition, so a cross-tenant binding stored before `V23` still resolved and had its credentials decrypted into the spec. An internal call has no trustworthy `X-Tenant-ID` to inject, so the only comparable basis is the agent's own tenant: `buildAgentSpecResponse` takes an extra `agentTenantId` (all three resolution entrances already hold the `Agent` entity) and drops foreign server rows with it — absent from both halves of the answer, and `secretFieldEncryptor` is never called (test case IAD-06). Consistent with `McpServerServiceImpl`'s visibility rule: `is_public` holds within a tenant, there is no cross-tenant sharing.

**4. `V24__backfill_agent_session_tenant.sql`**

Both filters above are a regression risk before any backfill: historical rows all sit in tenant 1, so a tenant-2 user would first lose sight of **their own** agents and sessions. They are therefore backfilled with the creator's primary tenant (`sys_user.tenant_id`) — the rule `V22` used for `mcp_server`. `session.creator` has two shapes (a username on the web path, a numeric user id on the mini-program path), so each gets its own join guarded by `REGEXP '^[0-9]+$'` to keep the statements disjoint. Migrations are immutable, so `V22` stays as shipped and this is a new `V24`; the OAuth design's planned `V24` / `V25` shift to `V25` / `V26`.

### 7.5 Fixed (2026-09, round six: the OAuth data model and admin-side validation)

**1. What landed (P2-1 of the OAuth design)**

The command and its two traps (must pass `-am`, must set `TESTCONTAINERS_RYUK_DISABLED=true`) are recorded in `docs/unit-test-cases.md` §17.

**2. Four decisions worth defending**

- `V25` **performs no backfill**: `NONE` and `STATIC_HEADER` take the same code path, and `headers` also holds plain routing headers, so a derived label would be indistinguishable in the database from a decision an administrator made. Every historical row stays `NONE`; whoever wants the `STATIC_HEADER` label picks it explicitly.
- `mcp_oauth_client.issuer` and `callback_url` carry `COLLATE utf8mb4_bin`. MySQL's default collation folds case, while RFC 8414 compares `iss` and RFC 6749 compares `redirect_uri` as exact strings — a case-insensitive match would let `https://as.example.com` and `HTTPS://AS.EXAMPLE.COM` hit the same registration row, i.e. merge the client identities of two authorization servers. The cost is stated rather than hidden: lookups on those two columns are binary too, so an administrator typing the wrong case gets no match (which is the desired behaviour — a false match is more dangerous than no match), while human-facing text columns keep the table default so they stay searchable without thinking about case. Pinned by `selectByTenantAndIssuer should match the issuer exactly`.
- `mcp_user_credential` has **no soft-delete column**: revoking updates in place (both ciphertexts written back to NULL, `status=REVOKED`) so the user's re-consent can reuse the `(tenant_id, user_id, mcp_id)` row; a soft-deleted row would keep occupying the unique key and the re-consent insert would fail. Where soft delete is wanted — `mcp_oauth_client` — it is the `V15` / `V23` generated-column trick: the unique key includes `active_client_id`, which becomes NULL once `active = 0`, and MySQL ignores NULLs in unique indexes, so a registration can be re-created after deletion.
- The SET list of `updateById` is **unconditional** (not assembled from `<if>` blocks), so any new nullable column on an entity must be cleared explicitly in the application like `oauth_config` is; otherwise "omitted on update" means "keeps the old value" and, after leaving OAuth, the UI would keep rendering scopes nothing uses. Same reasoning for the reuse lookup: `selectByTenantAndIssuer` carries `ORDER BY id LIMIT 1`, so two concurrent discoveries settle on the same registration instead of each keeping one.

**3. A boot-level defect found on the way**

The comment body in `PlanNoteMapper.xml` contained consecutive hyphens, which XML comments do not allow, so MyBatis failed to parse the file; all three services set `mybatis.mapper-locations` to `classpath*:mapper/*.xml`, so one unparseable file means no `SqlSessionFactory` and **admin / scheduler / router all fail to start** — and it is also why the whole `harnax-entity` mapper integration block was red (previously filed as "environmental"; see the correction in `docs/unit-test-cases.md` §17). After fixing the comment, `MapperXmlParseTest` was added: Docker-free, parses every mapper XML on the classpath and separately looks for `--` inside comment bodies. The same round deleted `harnax-admin/src/test/resources/schema-test.sql` — `MySQLContainer.withInitScript` loads the `harnax-entity` copy, the admin copy sat on no classpath reference and had already drifted, so there is now exactly one test schema.

**4. What this round did not do**

P2-2 (authorization server discovery and client registration) landed in round seven (see §7.6 and §3.5). P2-3 (authorization code + PKCE, storing and revoking credentials), P2-4 (the internal issuance endpoint and `mcp_call_log` writes), P2-5 (the frontend authorize entry) and P3 (delivering `authType` / `oauthConfig` and injecting per-user tokens at runtime) were not started at the time. **The runtime still had exactly one path: read the service-level static credential from `headers`.** Selecting `OAUTH2` on the page only stored the intent (the page itself arrived in round nine, §7.8; what the sentence is about — nothing downstream reading that value — still holds).

### 7.7 Fixed (2026-09, round eight: the trust boundary of discovered data)

**What this round was looking for**

The P2-2 functional chain was sound; the problems were all in one class — **it treated untrusted input as one of its own**. Discovery reads JSON off somebody else's server, and the endpoints and issuer it stores are what P2-3 redirects a browser to and P2-4 posts a `client_secret` to. Three review passes produced five groups (the rules themselves were folded into §3.5; what is recorded here is why the code had been written the other way):

- **Stored addresses were never validated**: `authorization_endpoint` / `token_endpoint` went into the row straight from the document, so `javascript:` and over-width values could land there (over-width becomes a silent truncation of a `varchar(500)` outside strict mode, and a truncated row is a registration no token matches). The required endpoints now clear the same http(s) + width bar as a hand-typed address; an optional endpoint that fails it is dropped with a warn — discovery should not die over a broken optional capability, but neither should a bad address survive in a table credentials are posted to.
- **One cross-check was missing**: a document with no `issuer` field used to be read as "field absent, fine". That is harmless when the admin typed the issuer and fatal when an untrusted document supplied it, because then two documents each assert half the chain and neither confirms the other. The latter is now refused, and the message names the way out (type `oauthConfig.authorizationServer`).
- **Whole-row write-back**: `rememberIssuer` called `updateById(mcpServer)`, whose SET list is unconditional, so discovery overwrote status / headers / name from a row it had read minutes earlier; `McpServerMapper` gained the targeted `updateOAuthConfig(id, json)` (`McpServerMapperTest` checks column by column that nothing else moves). A second, plainer consequence was fixed with it: an ordinary MCP edit erased the discovered issuer and orphaned the registration — "the request did not carry this field" now means "do not change it".
- **An unreadable column read as unset**: a non-blank `oauth_config` that failed to parse continued with defaults, and since discovery rewrites that column, the result was the admin's scopes replaced by an empty list behind a "discovery succeeded" response. It now aborts with instructions.
- **`RemoteJsonFetcher` had holes in its own guard rails**: exceptions during the body read (reset connection, truncated chunked body) escaped the `RemoteFetchException` contract it advertises, so one bad connection crashed discovery instead of moving to the next candidate; the 64KB cap had no teeth because draining the stream is not covered by the request timeout, which needed a real deadline; only the first `WWW-Authenticate` header was read; only the quoted form of `resource_metadata` was parsed; there was no floor under cloud metadata addresses; and failure text echoed the raw URL, which may carry userinfo. Each is fixed, and the class comment now says out loud that these are a floor rather than a policy — the address is resolved again by the connection, so DNS rebinding is beyond this layer.

**Deliberately not done**: no `@Transactional` on `discover` / `saveClient` (the outbound waits add up to roughly 80s, so wrapping them pins a pooled connection that long, while all network I/O happens before the two writes and each write is idempotent and self-healing); no block on loopback or RFC 1918 (self-hosted authorization servers live there); no requirement that the endpoints share an origin with the issuer (cross-origin authorization servers are spec-legal); `code_challenge_methods_supported` is neither read nor stored in this round — that decision point belongs to P2-3 and is recorded in the P2-3 row of `mcp-authorization-design` §12.1.

**Verification**: `harnax-admin` unit tests 1653 → 1677, all green; `harnax-entity` 230 → 232 (for how the numbers are counted and why the `tests` attribute of a surefire XML cannot be trusted, see `docs/unit-test-cases.md` §17).

### 7.9 Fixed (2026-09, round ten: every site of the masked write-back, at once)

Round four fixed the MCP site (§7.3 item 6). The shape of the defect: the detail API returns a secret as a mask → the edit form sends that mask straight back → the backend encrypts the mask as if it were a new value and stores it, destroying the real credential in place. This round closes every remaining site of that shape and collapses the rule from three copies into one definition.

**1. Four sites**

- **CLI `env_params` (live data loss through the UI)**: `pages/cli/components/CliForm.tsx` prefills the mask the detail API returned, while `CliServiceImpl.updateCli` called `serializeToolEnvParams` without `storedJson` — so the mask was treated as a fresh value and encrypted, turning `KUBECONFIG` and friends into a run of asterisks. Passing the row's own `cli.envParams` as the second argument makes it the same shape as the MCP fix from round four.
- **Tool `http_headers`**: `AgentToolServiceImpl.serializeHeaders` only ever had the "encrypt" path, and `updateAgentTool` never handed it the row's current JSON. It now delegates to `serializeWithEncryption(entries, storedJson)` and update passes `existing.httpHeaders`.
- **Tool env params (different shape, needs one extra read)**: `agent_tool_env_param` is its own table and the update is "delete by tool id, then batch insert". By the time anything needs to know whether a mask can be carried over, the row is gone and there is no second copy of the ciphertext left to read — so the read has to move before the delete: `storedEnvSecrets(id)` collects `envParamName → ciphertext` for rows with `secret == 1` and a non-blank `defaultValue`, and `saveToolEnvParams` resolves each entry against it. This one was not a one-argument wire-up: round four's leftover note counted the tool side as one site, but it is two (a headers column and an env-param table).
- **Env variables (the exposure is on the API; the frontend already avoids it)**: `pages/env-variable/components/UpdateForm.tsx` never prefills a mask for a sensitive row and omits `envValue` entirely when left blank, so the page cannot reach the defect. The endpoint is public though, and `updateEnvVariable` would still encrypt a returned mask — so the same check now lives server-side: a masked value keeps the row's current (already encrypted) `envValue` untouched.

**2. One definition of the rule**: `SecretFieldEncryptor` gained `resolveEnvParamValue(entry, storedSecrets)` plus a private `storedEnvSecrets(entries)` that collects the ciphertext map out of the previous JSON (a different thing from the same-named private method on the tool service, which reads it from the row table — each covers one storage shape), and `serializeToolEnvParams` now calls them. "Non-secret or blank stores as-is / a fresh value encrypts / a mask carries the stored ciphertext / a mask with nothing to carry throws a `BizException` naming the parameter" exists once, shared by the JSON-column form (CLI, MCP) and the row-table form (tools). It used to exist twice inside `SecretFieldEncryptor` (once in `serializeWithEncryption`, once inlined in `serializeToolEnvParams`) plus a third degraded copy in the tool service's `saveToolEnvParams` that just encrypted unconditionally — and that third copy was the defect. `serializeToolEnvParams` and the tool service now both go through `resolveEnvParamValue`, and the same stroke deleted `SecretFieldEncryptor.encrypt` (no production caller left): keeping a public "take a value, encrypt it" method is leaving the door open for the next version of this bug.

**3. The rejection must not be wrapped**: the `BizException` from `resolveEnvParamValue` (`Secret value of "TOKEN" cannot be kept, please re-enter it`) was being caught by the outer `catch (e: Exception)` in the tool's create / update and rewritten as `Failed to update agent tool: ...`, which drops the "please re-enter it" half — the only part a user can act on. Both sites now have a `catch (e: BizException) { throw e }`, matching how `requireManageableTool` is handled (create has no POST route today, so that clause keeps the two paths consistent rather than fixing a reachable path).

**4. Reachability**: both tool sites are only reachable by calling the API directly — `pages/tool` is a list with no write entry at all and the server has no POST create route (only `PUT /update/{id}`, `PUT /toggle/{id}` and delete). The CLI site is the page's default action, so real credentials were being destroyed. The env-variable site is fixed on the interface, the page was already safe.

**5. Not done**: the same shape for `mcp_oauth_client.client_secret` was closed in round seven by `resolveSecret`'s three states (§7.6) and was left alone here; the model provider's `api_key` still has its own mask check inside `ModelProviderServiceImpl` (`value.contains("****")`), deliberately not folded into `SecretFieldEncryptor` — there is no `storedJson` to pass there, the shape differs by one leg, and merging would bend both sides. One more site turned up by the same sweep, different shape and still open: `BuiltinToolAutoRegistrar` stores an annotation's `defaultValue` verbatim, with no encryption when the parameter is `secret = true` (today the only secret-typed builtin parameter, `SMTP_PASSWORD`, has no default, so no plaintext credential is sitting in the table; on read, `maskValue` falls back to `******` when decryption fails instead of erroring). That is a convention, not an enforced rule — enforcing it means routing the sync path through the encryptor too.

**Tests**: `SecretFieldEncryptorTest` env-param group +2 (a mask with no ciphertext to carry names the parameter; a blank secret default is not encrypted); `CliServiceImplTest` +1 (update hands the row's `envParams` to serialization); `EnvVariableServiceImplTest` +1 (a masked sensitive value keeps the stored ciphertext); `AgentToolServiceImplTest` 36 → 39, adding "reads the ciphertext before deleting" (with an ordering assertion that `selectByToolId` precedes `deleteByToolId`), "the resolver's `BizException` surfaces unwrapped" and "header serialization receives the row's JSON"; three create-side cases now assert "the map handed to the resolver plus the value stored from its return", because the service no longer calls `encrypt` itself; the round-trip case for the deleted wrapper now encrypts through `AesUtil` and reads back through `decrypt`.

**Verification**: one `TESTCONTAINERS_RYUK_DISABLED=true mvn test -pl harnax-admin -am` run is green end to end, `harnax-admin` unit tests 1677 → 1684; `harnax-entity` stays at 232 (untouched this round). The baseline in `docs/unit-test-cases.md` §17 was recalibrated against this run.

### 7.10 Fixed (2026-09, round eleven: reading MCP front to back)

The first ten rounds fixed one place at a time. This one re-read MCP as chains — browser request down to runtime assembly — with the new authentication method as the focus. The four defects found and fixed:

### 7.11 Done (2026-09, round twelve: authorization code + PKCE and credential storage, P2-3)

This round connected break points 1 and 2 of §7.10: the per-user endpoints exist, and something writes `mcp_user_credential` in production. The rule-by-rule wording lives in §3.6; what belongs here is the trade-offs and their costs. The design basis is `mcp-authorization-design` §6.2 / §6.4.

**Landed**: `service/McpOAuthUserService.kt` + `service/impl/McpOAuthUserServiceImpl.kt` (start / callback / status / revoke), `util/McpOAuthStateStore.kt`, `controller/McpOAuthCallbackController.kt`, DTOs `dto/{McpOAuthAuthorizeResponse,McpOAuthStatusResponse,McpOAuthRevokeResponse,McpOAuthCallbackResult}.kt`; the three JSON endpoints are mounted on the existing `McpOAuthController` rather than a new controller, so their authorization story stays the same as the two management endpoints'. **The runtime is untouched**: no exchange endpoint (P2-4), and `McpDetailDto` still carries no `authType` (P3) — what this round ships is consenting and keeping, not spending.

**Four decisions worth writing down**:

- **PKCE is unconditionally `S256`**, and discovery does not snapshot the AS's `code_challenge_methods_supported`. This "settle it before starting" note had been sitting in that §12.1 table for several rounds; it is now settled: OAuth 2.1 and MCP both make PKCE mandatory, and a metadata document that omits the field does not mean the feature is missing. An AS that really cannot do it fails on its own side, and admin never downgrades to `plain`. A downgrade path would first need a column on `mcp_oauth_client` and a way to carry "what the document said" to the exchange step — neither worth pre-paying to avoid one failure.
- **`state` lives in memory, not in a table.** A code is itself one-shot and minute-scale; storing it in a table would dress up the correct semantics ("a restart invalidates it") as "a restart can resume it". The costs are in §3.6 rule 2: an admin restart breaks a consent in flight, and multiple replicas need sticky routing or a shared store. The current deployment is a single instance, so this holds.
- **Refuse rather than half-record**: a `scope` wider than 512 characters is refused (truncation would record a list nobody consented to), a registration row with a blank `client_id` is refused (arriving at the AS with `client_id=` lets someone else's error page speak for us), and a server whose `url` moved mid-flow stops the exchange (the code was minted for the old address; storing the result parks a key that opens nothing). All three say "make the user do it again" rather than "store something we do not trust".
- **Reading the state does not present an unspendable grant as usable**: a past `accessExpiresAt` means unusable, because refresh arrives with P2-4 — the runtime can do nothing with that token today, so showing "authorized" would be a lie.

**Two existing implementations converged on the way**: `normalizeIssuer` moved from a private method in `McpOAuthServiceImpl` to the top level of `RemoteJsonFetcher`, so discovery and authorization share one normalization (one extra trailing slash typed by an admin cannot become "registered under one issuer, no row found now"); `RemoteJsonFetcher` gained `postForm`, so the token POST carrying code and client secret goes through the same guard rails (protocol allow-list, address floor, no redirects, read deadline, body cap, userinfo redaction) instead of a second `RestTemplate` bolted on beside them.

**The security hop is two doors, not one**: `SecurityConfig` `permitAll()`s `/api/admin/mcp/oauth/callback`, and `JwtAuthenticationFilter.shouldNotFilter` skips the same path. The first alone is not enough — the browser is being redirected back by the authorization server and still attaches whatever bearer the tab holds, possibly expired, and the filter would reject it as a 401 before any authorization logic runs, showing "request failed" instead of the outcome of the consent.

### 7.12 Fixed (2026-09, round thirteen: reading P2-3 again against the same standards)

This round adds no feature. It takes the ten rules of §3.6 and reads them back against the code, looking specifically for the breaks that stay **green in unit tests and false in production**. Five are fixed; one is recorded **without** a fix, because changing it means changing the security model and that needs a decision first.

**1. The authorization server's reason for refusing an exchange never reached the page (`RemoteJsonFetcher`)**
`exchange()` parsed `json` only when the status was 2xx, while `McpOAuthUserServiceImpl.answerOrThrow` reads `json.error_description` in exactly the **non-2xx** branch — that code has been dead since the day it landed: RFC 6749 §5.2 puts the reason in the body of the 400, and all the user ever got was a bare "HTTP 400". The `response.json?.optString("error")` inside `revokeUpstream`'s warn log was likewise always `null`. Parsing now happens for any body, keeping only a JSON object, while `RemoteFetch.ok` is still decided by the status alone: all three discovery consumers (`McpOAuthServiceImpl` lines 173 / 213 / 267) short-circuit on `if (!fetch.ok)` before touching `json`, treating the document as absent, so nothing there changed.
**Why the tests missed it**: the stub in `McpOAuthUserServiceImplTest` hands back a hand-built `RemoteFetch(400, null, readTree(...))`, i.e. the stub parses the body **on behalf of the code under test**, so that assertion can never go red. The cases added therefore sit at the **outbound** layer (real HTTP: §5.7 RJF-03 re-asserted, RJF-14 for the form POST, RJF-15 for an empty body), and the round leaves behind a review rule: **once a stub does the work the code under test is supposed to do, that assertion is arguing for the defence**.

**2. Rotating the AES key used to strand a grant in the database**
`revoke` called `aesUtil.decrypt(...)` directly, and `AesUtil.decrypt` throws when the key has changed or the ciphertext was edited by hand — so the user's revoke click became a 500, **and revoke is the only way out they have**. A ciphertext that will not open is now treated as absent: the local row is cleared regardless (`REVOKED`, both ciphertexts back to NULL, `last_error` too) and the message says it was the decryption that failed, which is why nothing went upstream.

**3. Wrong attribution in a revocation answer**
When the registration row is gone (deleted before re-running discovery, or the issuer changed) `client == null`, and the code fell through to "this authorization server publishes no revocation endpoint (RFC 7009)". The two sentences differ in **where they send you next**: one needs re-discovery and re-registration, the other says "wait for it to expire" — pointing a person at a road they cannot walk. It is its own sentence now, and it carries `POST /api/admin/mcp/{id}/oauth/discover` inline, matching how every other refusal in this feature names the next click.

**4. An over-wide granted scope list is no longer truncated**
It used to be `granted.joinToString(",").take(512)`, which ends the list with a scope fragment nobody granted, and `status` then echoes that as "these are the granted scopes". The list is now **not recorded at all** (`scopes=null`) with `last_error` stating how wide it was, what the column holds, and that it was therefore left out; `status` stays `ACTIVE` — the grant happened, this table just cannot hold its shape. This does not contradict round twelve's "refuse rather than truncate": that refusal is on the **request** side, where the caller can narrow the parameter. Here the answer came from the AS and nobody can narrow it, so the choice is record-all or record-nothing.

**5. A concurrent callback reported a real grant as a database failure**
One user clicking authorize twice for one server puts two callbacks into `insert` at once; `uk_mcp_user_credential_tenant_user_mcp` lets one win and the loser throws `DuplicateKeyException` → the page says "authorization failed" while the AS did consent, and the token that exchange produced is an orphan nobody holds. The exception is now caught: the row that won is re-read and this callback's token is written onto it with `updateById` (unconditional SET, keyed by id, exactly what is needed). **The cost, stated plainly**: the later write overwrites the earlier one, so the first token stops being resolvable locally and stays valid upstream until it expires or the user revokes again — the same trade-off as the "replace outright" rule in §3.6 rule 6.

**F6: the callback's identity model has a known gap; deliberately not fixed this round** (closed in round fourteen along option (b) below — see §7.13)
`state` pins **who started** the authorization, not **who clicked consent in the browser**. An attacker legitimately asks for an `authorize-url` under their own JWT, sends the full link (with its `state`) to a victim, the victim consents at the AS, and the callback comes back carrying **the victim's code** while the pinned userId is the attacker's — so the attacker's account gains a token minted from the victim's identity. This is a property of the two doors in §3.6 rules 2 and 3, not a missed step: the callback carries no JWT, `state` is its only credential, and `state` is generated by whoever asks.
Both ways out carry a price, and the direction should be chosen before coding. **(a)** When issuing the `authorize-url`, set a `SameSite=Lax` + `HttpOnly` cookie in the same browser and require it before a `state` can be consumed — this binds "the initiator" to "the browser that consented", at the cost of needing a same-site top-level navigation from the AS (a new tab, `target=_blank` or a cross-site form POST drops the cookie, and the user reads "unknown request"). **(b)** Move the exchange out of the callback: the callback only lands a one-time redirect handle, and the frontend (P2-5) calls a JSON endpoint with its JWT to do the exchange — `state` drops to a replay guard and the JWT carries the identity, at the cost of the callback page becoming "back to the app" rather than "here is your result", and half of P2-3's chain being rebuilt. This round records it and leaves the model alone, because (b) **is** the P2-5 frontend entry point: which one is built first decides the shape of the other.

**Tests**: `harnax-admin` unit tests **1754 → 1760** (+6: `RemoteJsonFetcherTest` 14 → 16, `McpOAuthUserServiceImplTest` 47 → 51 — the four new cases being "an over-wide granted list is not recorded at all", "a unique-key collision falls through to the row that won", "an undecryptable ciphertext still clears locally with its own reason", "a missing registration row does not borrow the RFC 7009 sentence"). `harnax-entity` stays at 232 (no mapper change). Full regression `TESTCONTAINERS_RYUK_DISABLED=true mvn -o -pl harnax-admin -am test` exits 0 with all 1760 green; style is held by `spotless:check` in the `validate` phase. Inventory sync: `docs/unit-test-cases.md` §5.7 (RJF-03 re-asserted, RJF-14/15 added), §5.9 (MOU renumbered 47 → 51, the four groups now start 12 / callback and exchange 22 / status 7 / revoke 10), and §17's baseline recalibrated for the eighth time.

**Not finished and not verified**:

- **Still no real authorization server exercised** (as in §7.11). Fix 1 is precisely why that has a cost: what `error_description` actually looks like, whether each implementation really follows §5.2 for a 400 body, what they say when `resource` is refused — all unobserved. All that can be claimed now is "the reason can reach the page", not "the reason is a useful sentence".

### 7.13 Fixed (2026-09, round fourteen: F6 closed by moving the exchange behind JWT, and the user-side entry shipped)

That **F6** of §7.12 is the only security gap this document has carried for thirteen rounds, each time written as "move once the direction is decided". This round closes it along the (b) recorded then: **this service no longer receives the authorization server's browser redirect**, `redirect_uri` points at a front-end route instead, and the landing page calls a new endpoint with the JWT the browser already holds to do the exchange. Identity therefore comes from the Spring Security authentication context rather than from a string the initiator generates and an attacker carries straight back. On the way it also wired the entry point into `authorize-url` / `status` / `revoke`, which had sat in design §9.1 for a long time with zero frontend callers (P2-5).

**1. The deleted entry point was the one hop on this chain that took no JWT**

`McpOAuthCallbackController` (`GET /api/admin/mcp/oauth/callback`) is gone together with its `McpOAuthCallbackResult`, and so are `SecurityConfig`'s `permitAll()` and the `JwtAuthenticationFilter.shouldNotFilter` skip for that same path — from now on `/api/admin/internal/**` is the only `permitAll` business path left in admin that still needs an authentication decision, and that one is really held by `InternalApiAuthFilter`'s shared secret (the remaining `permitAll` entries are login / captcha / `mp/auth` / swagger, which were public to begin with). This is not tidying up redundancy: on that path the only thing that could prove "who you are" was `state`, and `state` is generated by the initiator, so A forwarding an `authorize-url` to B to click at the AS writes the token B's consent minted into A's credential row.

**2. The new endpoint's path carries no `{id}`**

`POST /api/admin/mcp/oauth/exchange` takes `McpOAuthExchangeRequest` (`code` / `state` / `error` / `error_description`, all four nullable — because **the AS decides which of them to send**: a consent that went through carries the first two, a refusal the last two, and a `state` nobody ever issued can arrive with anything at all). Which server is to be authorized **can only** be said by the pending entry the `state` identifies; putting an id in this path would pair a phished `state` with a server the caller picks. Its segment count differs from the `/{id}/oauth/**` routes, so nothing collides.

**3. The order of the decisions is deliberate**

Take the caller's identity → `stateStore.consume(state)` (**burned first, whichever branch comes after**) → if the AS reported an `error`, answer with that sentence → no pending entry answers "this authorization request is unknown or has expired" → `pending.userId != caller` refuses → an empty `code` refuses → the exchange. Burning before judging continues the invariant of §3.6 rule 2: had the ownership-mismatch branch put the pending entry back, an attacker could retry one phished `state` over and over. A mismatch warns with **only the mcpId and the two user ids**, never the `code`, never the `verifier` — that is material meant for the token endpoint.

**4. How the exchange reads the server row got stricter, not looser**

In the callback era there was no identity at all, so the only option was a direct `selectById` keyed by the tenant the state pinned. This route has an identity now, so the row is loaded by `pending.mcpId` through `McpServerService.getMcpServer` (a server the caller cannot see simply answers "not found"), and after loading it asserts `server.tenantId == pending.tenantId` (moving the row out of its original tenant does not pass either). `McpOAuthUserServiceImpl` consequently no longer needs `mcpServerMapper` as a constructor parameter.

**5. A refusal is a sentence, not an HTTP status**

`McpOAuthExchangeResponse` = `authorized` + `message` + `scopes` + `accessExpiresAt`, and **no field in it can hold a token**. Refused by the AS, `state` unrecognized, ownership mismatch — each answers `authorized=false` plus one line on what to do next: the `code` is already spent, the page cannot retry, and a 401/500 would only suggest that clicking again might help. A `BizException` keeps its own words (those sentences were written for a person to read), every other exception is folded through `ApiErrors.message` — a database error does not reach the browser wearing its table name. The guard that used to be "the upstream `error_description` is HTML-escaped before it goes on the page" is now "it travels as JSON and React renders it as a text node", the same policy as the upstream strings `listTools` brings back.

**6. Frontend: the landing page plus the per-user authorization block on the detail page**

`/mcp/oauth/callback` is a `layout: false` front-end route (`pages/mcp/oauth-callback.tsx`) whose first act is to read the query off the URL and wipe it with `history.replace`, so those values sit on one local object inside the effect and go out immediately. The two places in `src/app.tsx` that send an unauthenticated visitor to `/login?redirect=` now special-case this path: the target becomes `/context/mcp` instead of the pathname with its search attached — otherwise `code` and `state` would be written into the login page's address bar and travel on with the redirect. The detail page's `OAuthPanel` gained a per-user authorization block (it reads `status` on mount, a three-state badge + authorize (same-page navigation) + revoke (second confirmation, echoing one of the backend's six sentences) + the granted scopes / expiry / `lastError` shown directly), and it warns out loud when the registered row's `callback_url` differs from the default the current configuration computes — once this shape changed, the AS byte-comparison failure is something that **will** happen rather than something that might. The copy keys grew from 52 to 74 (`pages.mcp.oauth.*`, same order in both languages).

**7. Configuration: the callback's origin and the API's origin are split apart**

`app.frontend-base-url` (`APP_FRONTEND_BASE_URL`) is new, affects only `defaultCallbackUrl()`, and falls back to `app.base-url` when unset. Behind the shipped nginx both are served on one origin, so not configuring it is still right; in development the SPA is on :8000 while admin is on :8080, and not configuring it would send users to a port with no page on it. **No migration script, no compatibility layer, no relay endpoint left standing**: `mcp_oauth_client.callback_url` is a registration value stored per (tenant, issuer), so an old row either gets its client re-saved from the page, or the administrator edits the AS-side `redirect_uri` back to the old shape — and the latter no longer works for this round's new shape. This is the round chosen to change the shape because V25/V26 have never been applied to a real environment and no real AS has ever been exercised, so changing it now costs nothing.

### 7.14 Fixed (2026-09, round fifteen: walking the whole chain again after F6 was closed)

Round fourteen replaced the source of identity, and the order of the checks along the chain changed with it — and order carries meaning here. This round re-read the code in the order the flow actually happens (start → consent → exchange → store → read state → revoke → change configuration) and found five real problems (three in the backend, one in the frontend, one in the wording of a document), fixed all of them, and gave each its own case. What they have in common: **none of them is "the feature was not built"; each is "it was built, and on some boundary it either said something untrue or left a path somebody else could walk"**.

**1. The ownership comparison has to come before "what the AS reported"**

Round fourteen's `exchange` ran: resolve identity → burn the `state` → answer the AS `error` if there is one → pending entry missing → refuse on an ownership mismatch. That middle `error` branch therefore sat in front of the ownership comparison, and **somebody who has learned another person's `state` could cancel that person's authorization in flight simply by POSTing an `error=access_denied` of their own** — while the warn that exists to record consent phishing would not say a single word about it, because the request never reached the comparison. The fix moves the ownership comparison ahead of every field the request body carries: decide first whether this pending entry is the caller's, refuse and warn if it is not, and only then look at what the AS said. A second ordering problem with the same root went with it: the `error` branch now **reports the upstream reason even when the pending entry has aged out**, because in that case nothing was stored and nothing is left to burn, and the AS's own words are worth more to the page than "unknown or expired request" (an aged-out entry and one somebody else started are two different facts and should not be covered by the same sentence).

**2. The scopes in the exchange answer are the recorded list, not the raw field from the token response**

`redeem` used to hand the scope list parsed out of the token response straight to the landing page. RFC 6749 §5.1 makes `scope` **optional**: an AS granting exactly what was asked may leave it out entirely, so the landing page showed zero scopes, and a few seconds later the user was back on the detail page where `status` — reading the same column — showed two. One person, two contradictory answers. The answer now carries the list parsed from **the column that was written**, which also makes the "wider than 512 is not recorded at all" rule self-consistent: what cannot be recorded reads as an empty list, so the page sees what the database holds instead of seeing a long list the database has nothing of.

**3. No badge is drawn when the state could not be read**

The per-person authorization block on the detail page used to keep the previous badge (or the initial "not authorized") when the `status` request failed. "Not read yet" and "read, and there really is no credential row" are two different facts: the first knows nothing, so a badge must not assert "not authorized" on its behalf; a failed re-read after a successful revocation is worse — the database has already changed, and keeping the old badge is a lie. A `grantUnknown` flag was added, both failure paths set it, the badge renders as `null` while it is set, and the three states belong only to an answer that was actually received. (The backend's "no row" serializes to `{"authorized": false}`, which is a truthy object, so that branch still shows "Not authorized" and is never mistaken for unknown.)

**4. Leaving `OAUTH2` clears the per-person credentials with it**

`updateMcpServer` used to clear only `oauth_config`. The problem: reading and revoking a per-person credential both pass through `requireOAuthServer` first (which refuses anything whose `authType` is not `OAUTH2`), so after changing a server's auth type from `OAUTH2` to `NONE`, **the `mcp_user_credential` rows already there could neither be read nor revoked** — ciphertext nobody was left in charge of. It now follows the same policy as the delete path: clear the rows locally, `warn` with how many were cleared, and say plainly that the copies on the authorization server's side were never presented and expire on their own. `wasOAuth` is read **before any field is overwritten** — once `auth_type` has been applied, this method can no longer tell whether the request turned OAuth off. A server that never had OAuth never queries that table at all — and there is no such thing as a pre-V25 row whose `authType` is null (the column is `NOT NULL DEFAULT 'NONE'`, the entity field is a non-null `String`): the one and only test is whether the stored row's `auth_type` was `OAUTH2`.

**5. That 500-entry budget of in-flight authorizations was shared by everybody**

`McpOAuthStateStore` had one global cap only. A logged-in user with a script could fill it and leave everyone else unable to start an authorization for a whole TTL (5 minutes) — the only self-inflicted denial of service left apart from §7.13's "multiple replicas need sticky routing". A cap of 5 per person was added; `countFor(userId)` is counted **before the verifier and the state are minted** (sweeping expired entries first, so a refused attempt leaves no material behind), and the refusal says both the cap and how long the wait can be.

**6. One place where a document was wrong (the fix is in the document, not the code)**

§3.6 rule 9 used to say "a log line says only whether a refresh token came back and what `expiresIn` was". The `log.info` that actually runs also prints the recorded scope names. Scope names are not credentials — the `status` endpoint returns them to the browser anyway — so the code was right and the document had left one item out; it now says what happens. A document stricter than the code is more dangerous than the reverse: a reader takes it for a guarantee that does not exist.

**Tests**: `harnax-admin` unit tests **1768 → 1775** (net +7: `McpOAuthUserServiceImplTest` 58 → 62, `McpServerServiceImplTest` 40 → 42, `McpOAuthStateStoreTest` 6 → 7). A targeted run of the four changed classes passes with all 127 cases green, and the full regression `TESTCONTAINERS_RYUK_DISABLED=true mvn -o -pl harnax-admin -am test` exits 0. Inventory sync: `docs/unit-test-cases.md` §5.3 (MCS-20 extended, MCS-23 / MCS-24 added), §5.9 (MOU-12 / 13 / 15 rewritten and MOU-59 to MOU-62 added — the ids are appended at the end and each case sits in its own group's table, so no existing id and no cross-reference moved), §5.10 (MOS-07), and §17's baseline recalibrated for the tenth time.

**Not finished and not verified**:

- All five fixes go **as far as the unit tests**. The attack shape in item 1 (learning somebody else's `state` and POSTing a fabricated `error`) has never been reproduced in a real browser, and there is still no real AS; item 4's credential cleanup was verified against a stubbed mapper only, never against real rows in Testcontainers.
- Item 5's per-person cap lives **in memory**: with several replicas each counts its own, so the usable allowance is 5 times the number of replicas. That is the same premise as §7.13's "multiple replicas need sticky routing", not a new problem.
- Item 4 clears locally only: the grant copies on the upstream authorization server were never presented for revocation and expire on their own. Actually revoking upstream means the user has to click revoke on each grant **before** the auth type is changed.
- Three things the review confirmed are **not defects**: timestamps are displayed as raw ISO strings by an app-wide convention (`DetailPageHeader` and `EntityCard` do the same), there is no `StrictMode` anywhere in the repository (so a double-run effect in development posting the exchange twice is not a live risk), and `detail.tsx` already mounts this panel only when `authType === 'OAUTH2'`.

### 7.15 Fixed (2026-09, round sixteen: reading from the config page down to client shutdown)

Round fifteen followed the authorization chain; this one covers the **runtime side**: management CRUD → authentication → wizard binding → harness assembly → client lifecycle. Ten findings: four on the assembly side (each does real damage), four on the management/wizard surface, two at the authentication boundary.

**1. MCP clients were never closed (resource leak)**

`HarnessAgentLauncher` builds a fresh client per agent, `DefaultAgentRunner` caches agents by sessionId in Caffeine (`expireAfterWrite` 30 minutes plus a size cap), and eviction just dropped the map entry. The assumption was that `HarnessAgent.close()` took the clients with it — checking the jar's bytecode says otherwise: its `close()` is `shutdownTaskRepository` + `WorkspaceIndex.close` + `ReActAgent.close()` (unbind the state saver, clear the state cache) and **nothing in it touches the MCP clients registered on the `Toolkit`**; `Toolkit` has no close either, only `registerMcpClient` / `removeMcpClient`. The stdio case is more concrete still: an unclosed client keeps its child process alive.
The fix takes ownership back: the launcher collects the `List<McpClientWrapper>` as it builds them, they travel with the agent inside `HarnessAgentWrapper`, and a new `release()` closes each client separately (one failure does not stop the rest) before calling `harnessAgent.close()`, guarded by an `AtomicBoolean` so eviction and session destroy cannot double-close. `removalListener` and `destroyAgent` both go through `release()` now.
Closing against an in-flight request is a separate problem: when an entry is evicted a stream may still be running, and closing outright would interrupt a conversation in progress. If `activeStreams` holds the session, the wrapper goes into `pendingRelease` and is drained by the two `doFinally` blocks (`streamProcess` / `confirm`) that clear the in-flight marker. **The non-streaming `process()` has no such marker** and can still be interrupted by an eviction — an accepted residual risk this round; it does not hold the SSE window, so the exposure is far smaller.
The other half of the same root cause was `McpHelper.listTools`: every "test connectivity" click built a client and never closed it. The whole body is now in try/finally.

**2. One server that cannot be built used to kill the whole agent (failure amplification)**

An exception from `createMcpClient` propagated all the way to `buildAgent`, so "three servers bound, one bad url" meant "this session is entirely unusable" with nothing on screen but an agent-init failure. That one server is now skipped after a `log.warn` and the rest is assembled; **the half-built client is closed first** (when `buildAsync` times out the underlying connection may already be up). The same edit bounds `buildAsync().block(60s)` and throws `MCP_CLIENT_CREATE_FAILED` when the build returns `null` — that null used to become an NPE on the next line — and since that error code's message template has no placeholder, the server name is reported by `log.error` rather than squeezed into the exception text.

**3. Concurrent cache loading handed an agent to the wrong user**

Caffeine runs one loader per key, so the losing thread **waits and takes the result** — but that loader resolved the MCP config and the user-level env with *its own* caller identity. Two people touching the same sessionId for the first time at once (a shared session, or one user with two tabs plus a permission switch) meant the loser got an agent built with the winner's identity, containing the winner's decrypted credentials. The result is now re-checked against the current user; on a mismatch the entry is removed with the conditional `asMap().remove(key, entry)` (conditional so a third party's fresh entry is never deleted by mistake) and rebuilt, and a second mismatch refuses rather than reusing. `CachedAgent` therefore carries a `userId`.

**4. The "query the database as fallback" path is gone**

`McpConfigAdaptorImpl` used to fall back to `McpServerMapper.selectById` when the context missed. That row is now **guaranteed** to be wrong: the AES key stays in admin (the decrypt-before-delivery decision in §7.1), so `headers` / `env_params` in the table are ciphertext, and a fallback read would hand ciphertext to the client as if it were a real header — unconnectable and undiagnosable. It also bypassed the tenant filtering done at the admin exit. The `mcpServerMapper` constructor parameter is removed and a miss is a single warning. The tool / skill / model adaptors keep their DB fallback: the columns they read are not encrypted.

**5. Paging parameter names did not match**

`mcp.ts` sent `current` / `size`; `McpServerController.pageMcpServer` binds `pageNum` / `pageSize`. Spring filled in the defaults, so page N of the MCP list was always page 1 and the page size could not be changed. This is the quiet kind of bug: nothing on screen looks wrong.

**6. The wizard no longer prefills masks**

The env-variable defaults for a binding come from the server config, and secret entries only carry a mask (`****`). Prefilling them stores the mask as the value in `agent_mcp_binding`, which resolves to a row of asterisks at runtime. Secret entries now start empty.

This data flow has **two clients**. The first pass only fixed `McpConfigPanel` in the web UI, while `buildEnvBindings` in `harnax-wechat-app/miniprogram/pages/agent/form/index.ts` reads the very same `McpServerResponse.fromEntity` (`maskSecret = true`) and was left out — closed in the same round. On the mini program the masked string becomes `customValue` in `toEnvBindingPayload`, and `AgentServiceImpl.serializeEnvBindings` has **no** mask handling on the binding path at all (mask carry-over only exists on the server-config path), so it is stored verbatim and delivered verbatim into `ToolEnvContext`: the tool receives a truncated fake secret while the input box looks filled in. The same `e.secret ? '' : e.defaultValue || ''` now applies there.

**What leaving it empty costs, stated plainly**: `required` is only a red tag — neither front end validates it on submit and `saveMcpBindings` does not check it either, so an empty value is accepted and the parameter resolves to an empty string at runtime. This section's first draft claimed "required ones are caught by submit validation", which is not true; corrected. A real enforcement point would be either front-end validation or a lookup of the `envParams` definition inside `saveMcpBindings` — neither exists today.

**7. Switching type no longer leaves the other side's fields behind; the wizard no longer double-binds**

After `streamablehttp → stdio` the row still carried the old `url`, and the other direction kept `command` and `env_params`. `updateById` writes every column unconditionally, so "clearing really clears" already held in the backend — nobody was doing the clearing. The service now nulls the opposite fields according to the new type (`url` / `command` are non-null on the entity so they get `""`; `headers` / `env_params` are nullable so they get `null`), and the forms do the same on type change so the submit does not carry the old value back.

Duplicate binding is a two-client problem as well. The web UI dropdown hides servers already bound in this pass (the `!mcpConfigs.some(...)` line in `McpConfigPanel`). Every mini-program card shares one `mcpRange` and `pickerIndex` is an index into it, so filtering by index would misalign the cards that already have a selection — the mini program therefore **refuses the selection** and shows a toast, using the same predicate as the web UI (excluding the card being edited). The write path already had `distinctBy { it.mcpId }`, so the unique key `uk_agent_mcp_binding_agent_id_mcp_id` is never hit — but the consequence of relying on it is "add two identical cards, save, come back to one, with no message", which the UI has to prevent first.

**8. Moving the url moves the resource, so old grants are cleared**

RFC 8707 binds a token to its resource, so after `url` changes the `mcp_user_credential` rows obtained against the old address can **never** be accepted again while `status` keeps answering "authorized". When `wasOAuth && the url actually changed` the grants are now deleted with a warning carrying the count — same rule as round fourteen's "leaving OAUTH2 clears" (computed before any field is overwritten; resubmitting an unchanged url is not a move). The edit form says so next to the url field, before an admin pays the cost.

**9-10. Two authentication tightenings found on the way (not in MCP's own files)**

- `InternalTokenProvider` now stamps `typ=internal` on tokens it issues and `verifyToken()` only classifies a bearer as `INTERNAL_SERVICE` when that claim is present. Previously any Bearer that passed verification with `harnax.auth.internal.shared-secret` *was* an internal service — and since deploy docs require `jwt.secret` to be identical between admin and agent-service, an operator who also puts that value in the internal secret turns every browser login token into service credentials that reach `@InternalOnly`. A token without `typ` but with `userId` is now `EXTERNAL_API` (authenticated, but not into internal endpoints); one with neither is rejected. The router monitor page and webui's `X-Api-Key` fallback are unaffected — neither needs `@InternalOnly`. See `harnax-auth/AUTH-DESIGN.md` §3.1.
- `AgentProxyController.resolveUserId` gained audit output: a body claim that contradicts the authenticated identity logs a WARN (caller, claimed id, real id) and an adopted body id without an authenticated identity logs an INFO. The rule itself is unchanged; what is new is that "who spoke for whom" is retrievable afterwards. See the agent-proxy section of `harnax-session-router/README.md`.

**Tests and what was not verified (this round differs from the previous ones)**:

- **Nothing was compiled and no unit test was run** (local machine resource limits, as instructed). The **1775** baseline in `docs/unit-test-cases.md` §17 is therefore **uncalibrated** and still the round-fifteen measured figure. Of the three suites this round touched, only `McpServerServiceImplTest` lives in `harnax-admin` (+2: the url move, and "an unchanged url is not a move"); the other two do not — `McpConfigAdaptorImplTest` (agent-service, 7 → 6: the two DB-fallback cases went away with the path) and `InternalTokenProviderTest` (harnax-auth, +3: the `typ` assertion, a user JWT classified as external, an identity-less bearer rejected). Following that document's own discipline (recalibrate by running, or do not write a number) this round records the deltas and no new total.
- Items 1–3 are concurrency / lifecycle defects: unit tests do not reach real thread interleavings, and the harness was never started. Whether stdio children really get reaped, and whether two concurrent first visits really stop crossing identities, still needs manual or integration verification.
- Item 2's "the rest is still assembled" is likewise read-code only: `HarnessAgentLauncher` has no unit tests at all, it depends on the full build chain.
- Item 8's two cases assert stubbed-mapper behaviour, not rows in Testcontainers.
- The two mini-program changes added afterwards to items 6 and 7 (`buildEnvBindings` and `onMcpPick` in `pages/agent/form/index.ts`) have **nothing runnable at all**: `harnax-wechat-app` ships only `npm run tsc` (`tsc --noEmit`) and no test framework, and even that was not executed this round. Both changes are read-code only, each one a direct port of a rule the web UI already had.
- Correcting item 6 surfaced a gap that is still open: `required` env params are validated in neither front end nor in `saveMcpBindings`, so leaving one blank stores it and the parameter resolves to an empty string at runtime. Whether to enforce it, and at which layer, is undecided.

### 7.16 Fixed (2026-09, round seventeen: reading the binding line to the end, including the two tails the last round left)

Round sixteen ended with two items open: `required` env params had no enforcement point anywhere, and the non-streaming `process()` had no in-flight marker. That round read the MCP side; the same three places on the tool side were only half covered. This round finishes the binding line — five items.

**1. The tool wizard prefilled masks the same way**

Round sixteen's item 6 added `e.secret ? '' : e.defaultValue || ''` for MCP; `ToolConfigPanel` was still missing the same line. A tool's `default_value` also arrives masked on the read path (`AgentToolServiceImpl`) for secret params, so prefilling it stores the literal `abc****wxyz` into `agent_tool_binding.env_bindings` and ships it into `ToolEnvContext` with the spec — the input looks filled in, the tool gets a truncated fake key. Sensitive params now stay empty: pick a global variable to override one, or type a value.

**2. Duplicate tool bindings were unguarded on both clients**

MCP got its guard in round sixteen, tools did not: the web UI dropdown passed `options={groupedToolOptions}` without filtering out tools already bound in this wizard, and `onToolPick` accepted anything. The write path has `distinctBy { it.toolId }` underneath, so the consequence was never an error but "add the same card twice and the environment values typed into the second one are silently dropped". The web UI now filters per row (`toolOptionsFor(index)`: exclude only the *other* rows — the current row's own choice must stay in the list or its title renders as a bare id, which is also why this cannot be one shared memo); the mini-program reuses MCP's "reject on pick with a toast", because its cards share one `range` and filtering by index would misplace the already-selected cards.

**3. A reference now stores the pointer only: no mask in the snapshot, validated on save, blocked on delete**

Three symptoms of one data flow: clients submitted `displayValue` (i.e. `******` for a sensitive variable) as `envValue` → `serializeEnvBindings` wrote it verbatim into the snapshot → delivery rescued it through `resolveEnvBindingsJson` only while the variable still existed → and `deleteEnvVariable` never asked whether anything still used it.

Replacing the snapshot with the decrypted value is the cheapest fix, but it writes plaintext secrets into the `env_bindings` column: the AES key lives only in admin (§7.1's decrypt-before-delivery design), so once that column holds plaintext, the "treat ciphertext in the DB as a usable value" path deleted in round sixteen's item 4 is back through another door. What shipped is the combination instead:

- **The snapshot stores no value.** `serializeEnvBindings` writes only `envVarId` / `envVarName` for a reference. Both the read path (`parseEnvBindingsJson`) and delivery resolve by id, so the UI still shows the current value.
- **References are validated on save.** New `assertEnvVarRefsBindable`, written like `resolveBindableMcpServers`: not found, soft-deleted, or another tenant's variable — all rejected with the offending ids in the message. The same round added `resolveBindableTools` for the tool side (only MCP had this check), for the same reason: a binding to an id that cannot resolve is a log line at delivery and a still-visible tool in the UI, and a guessable cross-tenant id is worse than a missing tool.
- **Deletion is blocked.** `AgentMapper.selectByEnvVarRef` looks for `$[*].envVarId` across all three binding snapshots in one statement (`env_bindings` is TEXT, so `CASE WHEN JSON_VALID` stands in front of `JSON_EXTRACT` and a legacy non-JSON row cannot fail the whole query). A hit reports "bound by N agent(s): names… — rebind them first". That message only reaches the operator through `ApiErrors.message`; without it the controller's catch flattens it to "Failed to delete env variable" and the guard leaves nothing visible.
- Delivery now also warns when a reference resolves to nothing, so "this parameter ships empty" is at least a log line.

**4. `required` env params have an enforcement point for the first time**

Three entry points, one rule: a live `envVarId` counts as filled (delivery resolves it by id), otherwise a non-blank typed value that does not contain `****` — masked text is a display artefact, not a value. The two front ends (`validateConfigStep`, and `validateRequiredEnvParams` in the mini-program) name the parameter; `assertRequiredEnvParamsFilled` on the server is the one that can actually stop a save.

**Whether a stored default counts differs between the two**, on one criterion: can that default reach the runtime at all? An MCP's `mcp_server.env_params` is decrypted whole into the stdio process environment, so its default does arrive → it counts. A tool's `agent_tool_env_param.default_value` does not → it does not count. Verified this round: `ToolConfigAdaptorImpl` does copy `envParams` onto the runtime `AgentTool` entity, but **nothing in the repository reads that field**, and `ToolEnvContext` carries only binding values. The parameter definitions cannot come from `AgentToolService` either — that is the display view, where a secret default is masked, which cannot tell "no default" from "default hidden". The server therefore reads the table through the mapper.

**5. The non-streaming `process()` registers its in-flight run**

First confirming the premise: channel → session-router → `/api/agent/chat` does go through `process()`, not the streaming path, so round sixteen's "much smaller window" residual risk was not hypothetical. An `activeCalls` set now marks the session, `releaseAgent` checks it alongside `activeStreams`, and the call's own `finally` clears the marker and drains. The registration sits *after* `getOrCreateAgent` and wraps only `agent.call` — wrapping the whole method would race the recursive eviction caused by this method's own cache load. `interrupt()` is untouched: a blocking call has no subscription to cancel, and that route already goes through `agent.interrupt()`.

Item 3 also changed what the delete endpoint says to the page, so `EnvVariableControllerTest`'s stale "a `RuntimeException("DB error")` collapses to Failed to delete" expectation no longer describes the contract; it became two cases, one for each half (the guard's own wording reaches the page verbatim, a database exception is flattened by `ApiErrors`), written the way `McpOAuthControllerTest` already writes them. **Full pattern run `-Dtest='**/admin/**/*Test'`: 1791 tests, all green.**

The last round's note said it compiled nothing, so that line had never been type-checked.
