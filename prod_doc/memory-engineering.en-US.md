## 1. Goals and acceptance

Six items, each of them decidable:

1. **A new session can remember an old one.** If one durable fact was stated in session A inside one owner bucket (see section 3), then the model-side input of the first question asked in a session created afterwards carries `<memory_context>`, and the answer can use it. The criterion has four stages in write order (extraction is dispatched asynchronously when a turn completes, and a task pending for the same session is displaced by the one that arrives later — `MemoryFlushMiddleware.java:159-212`; before each stage, first wait for the memory background to go quiet, see section 9 row 3): once session A has ended, that bucket's daily ledger for the day, `memory/<date>.md`, has gained an entry; after the consolidator has run once, the `MEMORY.md` of the **session layer** is not empty (a single extraction never writes the consolidated draft directly — see fact six); after this stretch has been merged into one candidate and that candidate has been approved by a human, the `MEMORY.md` of the **long-term layer** contains that entry (11.1, 11.4 — the runtime side writes the long-term layer zero times); and the first-turn reasoning input of a new session B in the same bucket contains a `<memory_context>` block.
2. **No user identity means no memory domain.** Ownership is fixed at assembly time: if a delivery carries no user, that agent gets no bucket mounted, no `MemoryConfig`, and none of the four tools; the assembly log names the reason, and the delivery itself completes as usual. Anonymous callers sharing one memory is data crossing between people, not a feature; stuffing `userId` into `RuntimeContext` on every call is not a way out either — that value is simultaneously the bucketing key of `agent_state` (fact four), and filling it in for memory's sake would re-key the history of every existing session.
3. **The switches move together.** Under every tier, the two things "the model is taught how to use memory" and "memory really is read and written" hold at the same time or fail at the same time. A half-open state (the tools are in the manifest but no hook feeds them, or something reads a `MEMORY.md` that is always empty) counts as not done.
4. **The extra model calls paid per turn can be computed exactly.** The ceiling is at most 2 extractions per turn (the one from the per-turn hook, plus the one embedded in that turn if compaction triggers), plus at most 1 consolidation per bucket every 30 minutes; above that sits the single merge call that folds the session layer into a candidate, and it rides the same throttle window (30 minutes by default, the same source as the consolidation and configurable, 11.4). Of these calls only the hook one and the merge one run on the memory domain's own model; the compaction-embedded one and the overflow fallback follow that turn's main model (fact seven). Criterion: after a turn ends, count by the model that was called — the memory tier must be ≤2, and the increment on the main tier must reconcile with whether compaction or the fallback happened.
5. **Memory never enters the chat.** Neither the sequence returned by `GET /api/agent/chat/history/{sessionId}` nor the iOS and webui contracts change because of this work; content from the memory files never appears as a bubble in any session.
6. **Clearing a session does not touch memory; deleting a user does.** After `clearSession` the bucket's `MEMORY.md` is still there unchanged; after a user is deleted, that bucket's `MEMORY.md` and all of its daily ledgers are unreachable.

## 2. Seven facts decide the shape of the plan

**Fact one: for cross-session memory, upstream has only the harness set left.**
The entire core long-term memory interface family is annotated `@Deprecated(forRemoval = true, since = "2.0.0")` (`Memory.java:30-34`, `LongTermMemory.java:66-71`, `StaticLongTermMemoryHook.java:77`), and the class comment of `LongTermMemory` asks verbatim that "any cross-session persistence should be integrated at the application layer". The harness set is a two-layer ledger in file form: `memory/YYYY-MM-DD.md` is an append-only daily ledger and `MEMORY.md` is the curated layer, and who writes each layer is spelled out in the class comment at `MemoryFlushManager.java:40-52`. This plan does only this one set.

**Fact two: the default tier is "on", and harnax turns it off with a single disable.**
The field initialiser of `HarnessAgent.Builder` is `memoryConfig = MemoryConfig.defaults()` (`HarnessAgent.java:1228`), and the initial value of `flushTrigger` in `MemoryConfig.defaults()` is `FlushTrigger.always()` (`MemoryConfig.java:240`) — installing the hook therefore means **one extraction per turn and one consolidation per bucket every 30 minutes**. On the harnax side `enableMemoryHooks: Boolean = false` (`HarnessConfig.kt:30`) is translated into `disableMemoryHooks()` by `HarnessAgentLauncher.kt:859-865`, and only then is the hook absent. So today's state is not "this feature does not exist" but "this feature is on by default and has been switched off explicitly".

**Fact three: where bytes land is decided jointly by IsolationScope and the route segments, and the framework hard-codes `agentId` into the key.**
`RemoteFilesystemSpec.storeNamespace(agentId)` returns a tuple according to `isolationScope` (`RemoteFilesystemSpec.java:333-352`); each route then appends its own segment to the tail of that tuple (`:314-323`, `remoteForRoute`); `MEMORY.md` goes through the `root` segment (`:256`) and `memory/` through the `memory` segment (`:258-259`). `IsolationScope` **has no tenant dimension**, and `agentId` is always in the key — the only choices available today are the four tiers "per session / per user × agent / per agent / global"; there is no "per tenant".

**Fact four: anonymous normalisation produces three different names in three places.**
`RemoteFilesystemSpec` normalises an empty uid to `anonymousUserId`, whose literal default is `_default` (`:79`, `:344`); `IsolationScope.toNamespaceFactory()` (the one that feeds `WorkspaceManager` the local path, `HarnessAgent.java:2425`) at the USER tier with an empty uid **falls back to sessionId** (`IsolationScope.java:104-115`); and the user-bucket normalisation of `agent_state` is `__anon__` (`ReActAgent.java:394-399`). Meanwhile the userId harnax sends into `RuntimeContext` is already an empty string (`HarnessAgentWrapper.kt:489`, `:1244` — both places that assemble a `RuntimeContext` use `userId ?: ""`). If those three names are taken for "the same anonymous bucket", you get a three-way fork: written into `_default`, read back locally from `<sessionId>` as the fallback, and state read from `__anon__`.

**Fact five: a store without CAS cannot hold up the distributed gate, and both consolidation and throttled-tier extraction silently never run.**
`StoreBackedPeriodicGate.tryClaim` wins its slot through `putIfVersion(ns, name, value, expectedVersion)` (`StoreBackedPeriodicGate.java:48-72`); on the first claim `item == null`, so `expectedVersion = 0` and the store must support CAS-create-if-absent. Where `putIfVersion` is not overridden, any `BaseStore` falls back to the default implementation at `BaseStore.java:74` — **which returns false unconditionally** — and if its `get` uses the two-argument compatibility constructor in `StoreItem.java` that sets version to 0, the version read back can never be matched. harnax's `harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/minio/MinioBaseStore.kt` has been completed along exactly this line with a conditional write and a versioned `get` (section 6), but the criterion still holds when a deployment swaps in another S3-compatible tier, so the assembly does not assume it — it probes once. The consequence (probe fails and there is no retreat): while `distributedStore != null` (the sandbox branch, `HarnessAgentLauncher.kt:739-768`) the gate is never won, `MemoryMaintenanceMiddleware.java:165-169` returns `Mono.empty()` outright, consolidation and archive cleanup run zero times, and this path emits no warn. The consolidator receives exactly this same store (the `distributedStore.baseStore()` of `HarnessAgent.java:2589`), so the store-side watermark in `MemoryConsolidator.java:359-384` cannot be written either (it gives up after 5 CAS retries and logs a warn) — except that it also writes a file watermark at the same time (`:350`). **The same gate also governs extraction itself**: `MemoryFlushMiddleware.shouldFlushNow` returns a plain boolean at the `ALWAYS`/`NEVER` tiers (`MemoryFlushMiddleware.java:291-296`) without passing the gate, and only the `THROTTLED` tier goes through `periodicGate.tryClaim(...)` (`:297-298`) with the key prefix `memory-flush:` (`:310-312`), independent of maintenance's own. So when CAS is missing, "consolidation does not run" and "throttled-tier extraction does not run" are one and the same failure, while the default `always()` is immune instead. **This must have an answer before any memory switch is turned on**: either the store really delivers CAS, or the assembly detects the gap and retreats to in-process coordination (section 6); the third state — silence — is the failure this fact describes.

**Fact six: the three writer sides do not know about each other, and the reader side has one entry point.**
`memory_save` appends to `MEMORY.md` and to the day's ledger at the same time (`MemorySaveTool.java:73,76-80`); flush appends to the daily ledger only and never touches `MEMORY.md` (the comment at `MemoryFlushManager.java:218-235` states that `MEMORY.md` belongs to the consolidator); consolidation **overwrites** `MEMORY.md` wholesale (`MemoryConsolidator.java:301-303`). All three land on `WorkspaceManager`'s append/write, and append is "read the whole file + concatenate + write everything back" (`WorkspaceManager.java:370-397`); that lock is an in-process `ReentrantLock`, and the javadoc at `:366-368` of the same file says verbatim that across replicas "the append is last-writer-wins; this method does not perform CAS"; `uploadFiles` calls itself last-write-wins in its comment at `RemoteFilesystem.java:521-527` as well. On the reader side: `<memory_context>` is injected only when `WorkspaceContextMiddleware` is installed and `includeMemoryContext()` is true (`WorkspaceContextMiddleware.java:254-255,512-516`), plus the two tools `memory_search` and `memory_get` (`MemorySearchTool.java:67-87`, whose search surface is fixed by `WorkspaceManager.java:934-947` as `MEMORY.md` plus `memory/*.md`, with no cap on the number of matched entries).

**Fact seven: the three flush entry points are customisable unevenly, so "memory runs on a small model" holds at only one of them.**
The per-turn hook uses `memoryConfig.flushPrompt()` and `memoryConfig.model()` (`HarnessAgent.java:2562-2571`); the flush embedded in compaction hard-codes the default prompt and uses the compaction model (`CompactionMiddleware.java:106-107` does `new MemoryFlushManager(workspaceManager, model)` directly and never takes `memoryConfig` at all); the overflow fallback uses `flushPrompt` but follows the main model (`HarnessAgent.java:1073-1077`). That is, `flushPrompt` takes effect at two of the three places, while `memoryConfig.model` is honoured only at the hook one. The latter two are both alive in harnax: compaction is not an optional extra but the default — `compactionConfig = CompactionConfig.builder().build()` and `disableCompaction = false` are builder field initialisers (`HarnessAgent.java:1227,1230`), and `CompactionMiddleware` is installed as soon as the summary model is non-empty (`:2600-2608`); the fallback one is triggered by context overflow.

The half-open state is recorded here as well: `disableMemoryTools()` has never been called in harnax, and the disable family at `HarnessAgentBuilder.kt:148-158` does not even contain that pass-through method, so the four memory tools are advertised to the model on the tool manifest today (`HarnessAgent.java:2688-2692`); the hook that feeds them is switched off (fact two), and `enableWorkspaceContext = false` keeps the reader middleware uninstalled entirely (`HarnessAgent.java:2527`). `includeMemoryContext()` requires `disableMemoryTools` **and** `disableMemoryHooks` to be true at the same time before it returns false (`WorkspaceContextMiddleware.java:254-255`), so "switching off only one of them" necessarily leaves a half-open state.

## 3. Ownership and key layout come before the trade-offs

Fix the bucket first, then talk about switches. The bucket decides whether every item below can be verified at all.

| Tier | Tuple (`RemoteFilesystemSpec.java:333-352`) | MinIO object key (bucket `harnax-store`, prefix `store/`) | What it means for memory |
|---|---|---|---|
| `SESSION` (today) | agents, agentId, sessions, sid or `default`, segment name | `store/agents/<agentId>/sessions/<sid>/root/MEMORY.md`, `.../memory/<date>.md` | one private memory per session, no continuity across sessions — directly contradicts the goal of "cross-session memory" |
| `USER` | agents, agentId, users, uid or `_default`, segment name | `store/agents/<agentId>/users/<uid>/root/MEMORY.md`, `.../memory/<date>.md` | continuous for that user within one agent; broken by switching agents; all anonymous calls land in the single `_default` bucket |
| `AGENT` | agents, agentId, shared, segment name | `store/agents/<agentId>/shared/root/MEMORY.md` | all users of that agent share one memory — cross-user leakage |
| `GLOBAL` | global, segment name | `store/global/root/MEMORY.md` | one global copy, as above and worse |

None of the four tiers has a tenant. The only way to give memory a tenant dimension without changing upstream is: **mount `MEMORY.md` and `memory/` separately onto a `RemoteFilesystem` of a self-built namespace, through `filesystemRoute(prefix, AbstractFilesystem)` (`HarnessAgent.java:1862`)**. Feasibility is nailed down by three source points: the outer Composite wraps the caller's routes outside the spec's built-in routes (`:2482-2483`), matching is won by the longest prefix first (the ordering at `CompositeFilesystem.java:86-93` and the matching at `:108-136`), and on a hit the remainder is handed over by suffix (`CompositeFilesystem.java:129-133`). This one mount therefore covers the spec's own two routes of the same name, while **every other file and the isolation tier are left completely untouched**.

| Design point | Decision | Reason |
|---|---|---|
| Memory ownership dimension | `tenant × user × agent`, tuple `[tenants, tenantId, users, userId, agents, agentId]`, delivered by the separately mounted route above | the agent dimension is hard-coded by the framework into the default route, so keeping it is equivalent to keeping the existing shape; the tenant must enter the key, otherwise the same `userId` under two tenants shares one memory bucket |
| Isolation tier for every other file | `IsolationScope.SESSION` stays | the spec scope of the non-sandbox branch is hard-coded at `HarnessAgentLauncher.kt:771`, and that one place governs three things: the tuple of the remote key (fact three), `WorkspaceManager`'s local namespace (`HarnessAgent.java:2416-2425`), and the throttle keys of flush and maintenance (`:2564`). Sandbox container reuse is a separate knob (`:749`, taken from `SandboxConfig.kt:37`). Flipping the former would move the namespace of every route including `sessions/` along with it — that is moving house, not turning memory on |
| Anonymous calls | no ownership to bind at assembly time: no bucket mounted, no `MemoryConfig`, none of the four tools, one warn, and the delivery completes as usual | ownership is taken from the assembly arguments rather than from each call — `RuntimeContext.userId` is simultaneously the bucketing key of `agent_state` (fact four), and filling it in for memory's sake would re-key the state of every existing session. And one harnax agent instance serves exactly one user (`DefaultAgentRunner.cachedAgent` drops the cache and rebuilds when it meets an ownership mismatch), so whoever the assembly resolved is the user of this delivery, and no value the caller passes later can change the bucket's key. **The reader side is still not fully blocked**: `readMemoryMd` goes through `readWithOverride`, and once the route returns empty it unconditionally reads the host disk's `workspace/MEMORY.md` as well (`WorkspaceManager.java:819-823`); so with a bucket mounted but no `MEMORY.md` in it yet, "nothing was injected" only holds if the host template itself is empty — see section 9 row 6 |
| Storage landing | **A: the memory body stays on the MinIO file layer** — just the consolidated draft and the daily ledger, and harnax adds no memory content table | all three upstream writer sides and both reader sides read and write files; moving to a MySQL projection means either rewriting the consolidator's whole-document rewrite semantics yourself or maintaining two sources of truth. B (adding an `agent_memory` projection table) is only worth it for "editing memory on a page" or "retrieving memory semantically", and neither is a goal this round. One table is genuinely added this round, but what it holds is not memory: `memory_draft` holds **one candidate awaiting a human decision** — the text to be merged, the version of the consolidated draft it merges into, the source list and the summary (11.4); after approval the body falls back to the file layer and what the table keeps is the record of one decision |
| Memory stays out of the chat | memory content never enters session messages, and `MEMORY.md` never enters `agent_state.context` | upstream injects `MEMORY.md` only as a system prompt, never as a history message (`WorkspaceContextMiddleware.java:512-521`), and harnax's history read path at `DefaultAgentRunner.kt:338-341` renders only `agentState.context` (the `GET /chat/history/{sessionId}` at `AgentController.kt:105`). This invariant comes free, but it has to be pinned in a test |
| Deletion scope | deleting a user: that bucket's `root/MEMORY.md` plus every object under the `memory/` prefix; clearing a session: memory untouched | memory belongs to the user; clearing a session is a session-level action, and mixing the two would turn "clear the current session" into losing long-term context |
| Write ordering | one writer per bucket: flush and maintenance each serialise by bucket key, and harnax adds no third automatic write path | the last-write-wins of fact six only holds under per-bucket serialisation. `memory_save` is the model-driven second entry point, and whether it stays is decided in section 5 |

## 5. `MemoryConfig` decisions

| Field | Decision | Reason |
|---|---|---|
| `model` | a small model dedicated to the memory domain, resolved by row id within the model domain: `HARNAX_MEMORY_MODEL_ID`, where `0` reuses each agent's own main model | `MemoryConfig.java:247-261` supports a separate model; without one the main model is used (`HarnessAgent.java:2562`). Per fact seven the compaction path and the fallback path still run on the main model, so this one has to be written outside the acceptance criteria |
| `flushTrigger` | `throttled(5m)` — the second stage of the two-stage plan, now that `MinioBaseStore`'s CAS has landed | once per turn amounts to one extra extraction call per turn in a long session, but the throttled tier passes that broken gate (fact five). | `consolidationMinGap` | `30m`, taken from `harness.memory.consolidation-min-gap` (`HarnessConfig.kt:70`) rather than hard-coding the upstream default | it makes "at most one whole write per bucket every 30 minutes" a decidable clause instead of a side effect of a default; this same window is also the throttle interval that merges the session layer into a candidate (11.4), so one change moves both ends at once |
| `consolidationMaxTokens` | `4_000` (default, `MemoryConfig.java:55`) | the budget for the whole consolidated draft, which directly decides the injected token ceiling; the long-term layer's section enters the context on every call, so the injection side converts the ceiling into a character limit from this very budget and states the truncation (the closing part of 11.1) |
| `dailyFileRetentionDays` / `sessionRetentionDays` | `90` / `180` (defaults, `MemoryConfig.java:61,64`) | the retention days of the daily ledger archive and of the session JSONL files; the only new cleanup action is the approval step re-checking by version and bytes to clear the session layer (11.4, 11.5), while the daily-due archival tier is one existing mechanism shared by both layers, so no separate cleaner is built for the new layer |
| `flushPrompt` | two rules appended after the default prompt: never write cross-user or cross-tenant information; never write credentials or secrets | the extractor writes files, and once PII or a credential is in the archive it enters the model every turn inside `<memory_context>` |

## 8. Test plan

The primary assertions (missing one means section 1 is not done):

1. **Remembering across sessions**: run one turn of session A inside the bucket (a stand-in model stubs the extraction); after the memory background goes quiet, assert that the bucket's `memory/<date>.md` has gained an entry (one extraction does not write `MEMORY.md` — fact six); assert that this entry only reaches the session layer plus one pending candidate and that `root/MEMORY.md` is verbatim untouched; then run one human approval and assert that `root/MEMORY.md` contains that entry; then create session B in the same bucket and assert that B's first-turn reasoning input contains `<memory_context>` and that the entry can be searched there.
2. **No user in the delivery means no memory at all**: assemble an agent with an empty `userId`, assert that the tool manifest is empty, that the log holds exactly one warn stating the reason, and that this agent still builds (switching the memory domain off is not a failure of this request).
3. **Tenant isolation**: run one turn for the same `userId` under two tenants and assert that the two buckets have different object keys and never hit each other — this case tests the tuple of section 3 directly.
4. **The gate is really winnable**: two cases for `MinioBaseStore.putIfVersion` (creation succeeds when the object does not exist, and false is returned on a version mismatch); plus two counter-cases — with `putIfVersion` stubbed to always return false, neither the `throttled` tier's extraction nor maintenance persists anything, while the `always()` tier's extraction persists as usual (the three-part criterion of fact five).
5. **No switch ends up half-open**: three tiers of cases (all off, all on, hooks only), asserting that the combination of the two booleans "the tools are in the manifest" and "the hooks are installed" matches the matrix of section 4 row by row.
6. **Memory stays out of the chat**: finish a session that has memory and assert that the response of `GET /api/agent/chat/history/{sessionId}` contains no fragment of `MEMORY.md` or of any daily ledger.
7. **Clearing a session leaves memory alone; deleting a user does not**: two cases that assert respectively that the object is there and that it is not.
8. **Extraction failure does not affect the answer**: stub the memory model to throw, assert that the turn's answer still returns as usual, and after quiescence assert that the bucket's daily ledger and `MEMORY.md` are verbatim unchanged (a failure only logs a warn, `MemoryFlushMiddleware.java:273-277`).
9. **The per-turn call count is capped**: for one conversation turn assert exactly 1 model call on the memory tier; if that same turn triggers compaction then assert 2 calls, the second one landing on the compaction model (the ceiling of section 1 rule 4).
10. **One individual agent's answer outranks the whole domain**: with the domain on, the agent carrying `memoryEnabled = 0` has no hooks, no tools and no bucket route, and it does not trigger the store's gate probe either; the `memoryEnabled = 1` agent assembled in the same batch has all three, and the two do not affect each other. The resolution side asserts two more tiers: a payload carrying `0` maps to off, and a payload that never names the key maps to on. This is section 1 rule 3 repeated at agent granularity — a half-open state counts as not done there too.
11. **admin's read and delete hit real buckets**: this is the end-to-end IT named explicitly at the moment the decision was taken (`MemoryOwnerBucketMinioIT`, harnax-admin); it starts the whole admin service against Testcontainers' MinIO, pours objects in following the writer's key layout, and then asserts three things through JWT-carrying HTTP — that the bodies the list and detail endpoints give are the envelope's `value.content` rather than the whole JSON; that deletion clears only the prefix of the named agent while the two kinds of neighbour (another user in the same tenant, and the same user's copy under another tenant) stay byte for byte where they are; and that a caller of an empty bucket gets a successful empty list rather than an error. Calls without a JWT and agent ids that only become a path segment after decoding (`%2F`, `%5C`, `..`) are all refused before the store is reached, asserted by taking a full bucket-key snapshot before and after and comparing it verbatim equal. This case is also the reader side of the cross-module envelope contract: the envelope's literal is stored once on the writer side and once on the reader side, the two test classes name each other, and if the writer changes the shape both go red (see section 9 row 9).

The way they run follows this repository's existing recipe (JDK 21, probe Docker first and only then decide whether to exclude ITs). Bucket reads and writes may be covered with `InMemoryStore` in unit tests, but assertion 4 must hit the real `MinioBaseStore` implementation, otherwise it bypasses exactly fact five. Assertion 11 goes the other way and cannot use a stub: a mocked client only answers what the stub tells it to answer, and prefix listing, the recursive flag and the scope of deletion — these three things only hold against a real server. The list above only covers the shape of the section 1 round; the assertions for the session layer, candidate intake and human approval are itemised one by one in the reconciliation table of 11.12 and are not repeated here.

## 11. Memory layering: session granularity and long-term granularity side by side

The position in one sentence: one agent's memory splits into two layers, and there is no switch between the two layers. The **session layer** holds "what was said in this chat but has not settled yet", it is meaningful only to this one session, and every conversation that got memory has a layer of its own; the **long-term layer** holds "what has to be remembered across sessions", which is exactly the curated memory of section 3, bucketed by tenant × user × agent, and also the one every new session reads at its start. The session layer's content is produced automatically by the conversation, is automatically **merged into one candidate** at intervals and sent for a human to look at; only when the candidate is approved is the long-term layer rewritten and the session layer cleared. The long-term layer's writer is therefore the single action of approving, and the runtime side never writes it, not once. Sections 1 through 10 describe this long-term end, and adding this layer changed only its writer — moving from the full-write step to the step where a human approves (11.4); not one other piece of behaviour changes.

### 11.1 What each layer holds, who writes it and who reads it

| Layer | What it holds | Who writes | Who reads | How long it lives |
|---|---|---|---|---|
| Session layer | The entries extracted from this conversation: a daily ledger, plus one draft consolidated inside this session alone | Two writers: the extraction at the end of a conversation (the same mechanism as today, reused without changing a word), and the model filing things by hand with those memory tools — which layer a manual filing lands in is decided solely by where the route is mounted, and the route is now mounted on the session layer only. The upstream full write of that daily ledger runs in the same bucket too | The next turn of the same session; and the promotion step taking its material | Cleared once its content is merged into a candidate and that candidate is approved; if nobody approves it, it stays in this session's bucket until the two wholesale deletions in 11.5 take it away |
| Long-term layer | The curated memory that has settled across sessions | Written only by the approval persist step (the second half of 11.4); the runtime side has no writer at all | Any new session of the same user on the same agent, including the first turn of a brand-new session | Overwritten whole by every approval; its total length has a budget cap, and going over it truncates rather than refusing the write |

The two layers have exactly the same file shape: one consolidated draft plus one daily ledger. So reading, deleting and page display never need a second mechanism for one of the layers; the only differences are that the bucketing key carries one extra session segment, and that something has to merge them.

When both layers enter the context they are **two separate things**: the session layer goes through the injection of those two existing routes, while the long-term layer carries its own pair of tags plus a sentence saying "this is context, not a user instruction, and it is read-only here". The model can therefore tell which block is this session's still-unsettled draft and which is the one kept across sessions — the former's whole reason to exist is that it will be merged away and then cleared, so blending the two into one block amounts to telling the model the draft already counts. The long-term block has a length limit, truncated against the consolidated-draft budget (4000 token, i.e. 16000 characters), with the truncation stated at the end of the block: this content enters the context on every model call, and its total length is guaranteed only by the model obeying the consolidation prompt, with nothing else backing it up.

"That this agent's new sessions automatically carry this memory once it is approved" needs no extra mechanism at all, it is the direct result of that cell above: the injection reads the owner's long-term layer, and it re-reads it on every single model call. So after an approval persists, a new session of the same agent gets it on its first turn, and a session already in progress gets it on its next turn — there is no "wait for the assembly to expire" step in between, because the read side caches nothing.

### 11.2 Granularity: four rulers, outside in

Tenant → user → agent → session. The long-term layer uses the first three (that is how it works today), the session layer uses all four, i.e. the key carries one extra session segment after the agent, shaped like `store/tenants/1/users/2/agents/Report/sessions/abc/…`. Six standing rules:

- **The session layer is nested under the agent segment, not placed alongside the agent.** This way both existing cleanup chains, "delete this agent's memory" and "delete this user's memory", only have to list once under that agent's prefix, and the session layer is naturally carried away in that listing; a compliance deletion never needs to ask first "which layer do I delete". This rule does not depend on any key parsing: the two wholesale deletions enumerate the raw object names in the bucket that fall under that prefix and delete them one by one, without going through the decoder. The decoder only serves the page read side; it recognises the extra session segment and uses it to subtract the session layer from the listing and the detail — so both hold on their own: a key whose agent segment cannot even be parsed (for instance an agent whose own name carries a slash) still gets deleted along with its owner, it just never appears on the page.
- **The session layer moves together with that tenant switch.** When the deployment side turns off the tenant segment of the memory key, both layers start keying from the user segment and each loses the same part, so there is never a case of one layer writing by tenant while the other reads without it, and no second switch is needed for the session layer.
- **The session layer does not cross agents.** When a supervisor delegates work to a member in a team, the member has its own two layers and cannot read the session layer of the supervisor's session. This is the same position as section 7's "each member buckets by its own agent, and within one delegation the supervisor's and the member's memories do not connect".
- **Anonymous delivery has neither layer.** The session layer needs the user segment just as much, otherwise different people's ledgers would mix into the same key. Section 7's criterion — "if the delivery does not name a user, the whole domain is closed" — is unchanged; only the scope being closed now covers both layers.
- **Changing granularity is not moving house.** Only the two routes, the consolidated draft and the daily ledger, change keys; session state, the sandbox workspace and the isolation tier of every other file are untouched, for the same reason as section 3's "the two single-mounted routes only, everything else untouched".
- **The session segment can only deepen a bucket, never relocate it.** The session id is spliced into the key verbatim, so an id carrying a slash only adds levels — `sessions/a/b/root/MEMORY.md` is still under that agent's prefix and goes with the two wholesale deletions of 11.5. An id that tries to move the bucket upwards (`../`, or one reaching into someone else's user segment) is rejected by the store at the moment of writing, by its object-name rules: a `.` or `..` segment is not allowed in an object name. This rejection lands in the "the store cannot be read" tier, the same failure mode as 11.10's third clause, so it does not make this layer read as an empty layer. `MemorySessionKeyShapeTest` pins each of the two shapes once against real MinIO, and what it pins is "the number of objects outside the agent prefix is 0", not "it threw an exception" — on a storage tier that normalises paths itself this assertion goes red instead of quietly passing.

### 11.3 No switch: every agent that has memory always has both layers

The assembly criterion is only section 4's one "long-term memory" flag: `memory.enabled && !isLead && agentSpec.memoryEnabled` (`harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/HarnessAgentLauncher.kt:1220`). When it holds, both layers are there together — extraction lands in the session layer first, the route is mounted on the session layer, the long-term layer is injected as a read-only block, and the promotion step merges this session's layer into a candidate and enqueues it; when it does not hold, the whole domain is closed: no bucket mounted, no extraction installed, none of those four tools, and neither the injection nor promotion is installed either.

| Long-term memory | Result |
|---|---|
| off | The whole agent has no memory domain; both layers are gone at once |
| on | Two layers: extraction lands in the session layer first, is merged into a candidate that waits for human approval per 11.4, and both layers enter the model context |

So this layer is not chosen agent by agent, and there is no deployment-side default of the "flip the whole deployment to two layers" kind either: the `agent` row carries no column related to the session layer, the delivered payload carries none either, and the wizard shows only one "long-term memory" switch. The shape in the database is therefore two forward migrations running there and back on one column — `harnax-admin/src/main/resources/db/migration/V2__agent_session_memory.sql` added `session_memory_enabled`, `harnax-admin/src/main/resources/db/migration/V6__drop_agent_session_memory.sql` dropped it, and `harnax-admin/src/main/resources/db/migration/V1__init_schema.sql` never contained it (this column went through an incremental migration rather than the baseline, for the reason given in the migration row of 11.11). The verbatim copy at `harnax-entity/src/test/resources/schema-test.sql` follows the same endpoint.

There is no setting to flip between the session layer and the long-term layer: if you want one agent to keep only a single layer, the only way is to give it no memory at all.

The last relevant shape is the one deployment on the runtime side where "memory looks present but the long-term layer no longer changes": the candidate queue's adapter (`agent/adaptor/MemoryDraftAdaptor.kt`) is passed through by the Spring assembly (`harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/spring/HarnessAutoConfiguration.kt:373`), and when the bean cannot be obtained the session layer is filled as usual and the long-term layer is injected as usual — only the step that gets out of the session layer is not installed, and one warn is left naming the reason and the fix (`harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/HarnessAgentLauncher.kt:812-822`). This tier is written down here because from the page it looks exactly like "the bucket is broken": the memory page's body cell does not move at all, while every conversation really is writing its own layer.

### 11.4 Candidate intake and human approval

**Runtime side: when to merge, and who the merged result goes to.**

- **The trigger is a throttled timer, not "the session ended".** harnax has no reliable session-end signal: the vast majority of sessions simply stop sending requests, while "clear session" and "delete session" only run when the user actively performs them. Attaching promotion to those two actions would show up as some sessions' memory staying in the session layer forever. The chosen approach is that every new conversation on this session also checks whether the time has come, and merges if it has; the interval is a configuration item, 30 minutes by default, sharing its source with the long-term layer's full-write throttle; a negative value is refused at the assembly step, and `0` is a legal value meaning promotion is caught up on every single turn (one extra model call beyond this turn's own). **The "has the time come" check runs after the "does this layer hold anything" check**: taking the slot cannot be given back (this gate exposes one method only, and winning it writes the timestamp that closes the window), while the extraction that fills this layer is dispatched after the answer and costs another model round trip, so the first turn usually reads empty. Claiming the slot before reading would spend the entire window on an empty layer — and sessions shorter than one window (the majority) would then never promote even once. The "could not be read" tier is treated exactly like an empty layer: no slot taken, the window is left for whichever run fills the content first.
- **The merge stops at one candidate.** Take the session layer's consolidated draft plus the ledger entries not yet merged into it (only the direct children of the ledger segment, and names that do not read as a date do not count), hand them to the model together with the long-term layer's existing content, and produce **one complete merged long-term memory**; then enqueue, as one candidate, that text, the long-term layer body it read and the version number of that moment, and every session layer object it took as material together with the bytes it read then. **Not one byte of the long-term layer is written and not one object of the session layer is deleted**: before a human has read it, the session layer is the only copy of those entries, and a candidate nobody has looked at is no reason to throw that copy away. That the material objects enter the candidate together with their bytes is exactly the basis on which the approval step can clear only "the ones whose bytes have not changed".
- **A merged result that shrank counts as the model not finishing the job.** If the merged text is clearly shorter than the long-term layer's existing content (less than half), this attempt counts as failed: no enqueue, no cleanup, one log line left. The prompt's "do not drop entries" does not guarantee that the model really writes both halves in full, and the direction of failure must not be "a text that replaced the long-term layer is sent off to wait for a human's approval" — that is the one content of this layer that enters the context on every call, and a collapsed draft and a diligently consolidated one look exactly the same from the queue page. **This gate sets no exception for "already over budget"**: a layer that drifted above budget is the easiest one for the model to answer with a quarter of its size. An over-budget layer is still consolidated: one window takes in half of it, a few windows converge it back inside budget, and the cost is only slowness, not loss.
- **One merge has a time cap (5 minutes by default).** It runs on the blocking scheduler shared by sessions and occupies one of its workers, and it is also in the in-flight count that graceful shutdown waits for; an unbounded wait means one model that never answers holds that slice of concurrency indefinitely. The cap is set looser than a conversation turn's own timeout, because one merge has to rewrite the entire curated layer in a single completion. A timeout is handled as a failure, on the same rule as the two items above: the session layer is left exactly as it was.
- **A failure still spends the whole window, and this is accepted as it stands.** That throttled gate has only "claim", no return: after any of a model error, a timeout, a shrink, a refused read or a refused enqueue, this session has to wait out a full window before its next chance. The reason it is accepted is that the direction of failure is already safe — the material stays in the session layer verbatim, and the only cost is latency. All that is bought is a retry a few minutes earlier.
- **The enqueue step is one HTTP call, and all of its criteria live on the admin side.** The payload carries only the session id, the agent name, the two texts, one version number and the source file manifest, **no tenant and no user**: the owner, the tenant and which bucket this memory belongs in are all resolved backwards by admin from the session id (`harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/service/impl/MemoryDraftServiceImpl.kt:364`). The backwards resolution recognises three shapes — web and mini-program sessions read the creator and the agent off the `session` row; a scheduled task's session has no row in this database, so the owner is taken from the scheduler over HTTP and the agent comes from the task contract; a team member's session is a name this system builds itself (`team-<root>-m<agentId>`), whose owner is the root session's and whose agent is the one named in the tail. A `chn-` session resolves to no owner (that is a chat platform's sender id, not a user of this system), so this tier is refused outright. After resolving, three more things are checked: the agent named in the payload matches the agent name on that row (otherwise an approval would merge this conversation's text into somebody else's memory), the row and the owner share a tenant, and every path in the source manifest resolves to an object key (otherwise an approval could not clear it, and this candidate would be a dead entry).
- **One session keeps at most one pending candidate at a time.** A new merge overwrites the older one (the same layer plus a few newly written turns, so the newer copy contains the older), while a candidate that has been decided is never rewritten — it is the record of one decision, and overwriting it erases the decision. An overwrite happens only while nobody has read either of the two candidates, so the replaced digest is not an error; if an overwrite lands just after somebody has already opened it, that approval is stopped by the digest comparison (item 2 below).
- **The three kinds of answer must be told apart.** Enqueued (a candidate number is obtained), refused (a retry gets the same answer again), unreachable (admin or the network did not answer and nothing was written). The last two both leave the session layer exactly as it was, but only the third means a retry in the next window still makes sense — re-enqueuing on the second one is the runtime side burning a model call for nothing. This split lands in `MemoryDraftIntake`'s three branches and in `AgentApiClient`'s mapping (`submitMemoryDraft` in `harnax-agent/harnax-agent-service/src/main/kotlin/com/agnetix/harnax/agent/service/client/AdminApiClient.kt`: a `code` of 200 that hands out a positive candidate number is enqueued, 400 and 404 are refused, everything else is unreachable).

**Admin side: approval is the only writer of the long-term layer.**

- **All three refusals run before the write**, and none of them changes any object. One, `expectedDigest` does not match the digest this row holds now → `DRAFT_CHANGED`, and the current digest is handed back to the page along with it (the approve action only covers "the version I read", and the digest is computed from every column the overwrite decision rests on: the agent name, the session number, the pending-merge body, the long-term layer body it merges onto together with its version number, and the source manifest). Two, this row is no longer pending → `ALREADY_REVIEWED`, carrying who went before, when, and the reason for the rejection. Three, the long-term layer's version is neither the one the candidate recorded nor "this layer already holds exactly this text" → `STALE_BASE`, carrying the layer's version right now. The third is the only substantive difference between this domain and the skill-draft approval: approving a skill answers for the draft alone, while this approval has to answer "is the long-term layer I read still in place", because what it overwrites is the block that enters the context on every call.
- **What is raced for is a conditional update on the row**, and losing the race reads back the decision that already won, to the page. Two tabs of the same owner therefore produce exactly one persist.
- **The persist carries two conditions**: first this layer's version now is compared with the version number the candidate recorded (this comparison is done in this layer's code, and the version is the field inside the envelope), then the object's own ETag is handed to the storage as `If-Match` — `If-None-Match: *` when the long-term layer does not exist yet. A 412 from the storage is a refusal rather than a fault: when the condition is not met it returns false, the transaction rolls back that row race it just won, and the row is still pending on the page. An object with no ETag to read is never replaced unconditionally (it returns false and leaves one log line), because a "the read did not see it, yet the write landed on it" is exactly the action this cell guards against.
- **Cleanup runs after the persist, and each object carries its own body re-check.** Only an object whose path resolves and which at this moment still holds the very bytes the candidate recorded is deleted; one that was written during this interval is left (it belongs to a candidate nobody has read), and one that is already gone is counted in a tier of its own. What is compared is the body, not the number the storage hands out: an unprotected write can land arbitrary bytes on arbitrary versions, and what this step is about to delete is the only copy of those bytes. Every delete is read back to confirm, and if the object is still there it throws — the whole approval rolls back with it and the next approval runs the path again, instead of the queue showing "this layer has been merged away" while the conversation still holds it.
- **Approval is idempotent.** If this layer already holds exactly this text (a previous approval wrote it but did not finish clearing), this one does not write again; it only completes the cleanup, answers `APPROVED` still, and gives the layer's own current version. This is not a fallback but a state that must be reachable: writing and clearing are two storage actions, and a failure anywhere between them leaves the state right here.
- **Three hard rules.** One, the runtime side neither writes the long-term layer nor deletes the session layer; only the approve step touches both. Two, a failed intake and a failed approval both leave every object untouched: when the enqueue did not succeed the material is still in place verbatim, and when an approval is refused or rolled back both the long-term layer and the source objects stay as they were. Three, each session times on its own and each session holds at most one pending candidate; the decision belongs to the memory's owner in person rather than to a workspace administrator — the row is attributed exactly by `sys_user.id`, and another account cannot even read that this candidate exists.
- **The model used follows the memory domain's own** (section 5's model row); if none is configured it follows this agent's primary model, consistent with how extraction picks its model today, and no second piece of configuration is added. The admin side never touches a model: it only persists the text a human has read.
- **A team member's session layer is tiered by root session, and the promotion slot changes together with the key.** Within one delegation the session key the member's tier uses is derived from the root session (`harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/team/TeamRuntimeSpec.kt:59` composes `team-<rootSessionId>-m<memberAgentId>`), and both the bucket key of its session layer and the key of its promotion slot come from that session key (`harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/memory/MemoryPromotionMiddleware.kt:75`). So a member delegated by several root sessions keeps one session layer per root session, and such a layer is merged into a candidate only when that same root session speaks again and the window is due; a root session that never speaks again leaves its layers in the bucket. Reclaim is unaffected by this row: all those keys sit inside one owner prefix, and deleting this agent and deleting the user both carry them away by prefix (11.5 rows two and three). Whether this member has a session layer at all follows section 4's single long-term-memory criterion (`HarnessAgentLauncher.kt:727`); there is no per-session switch.

### 11.5 Cleanup: four reclaim paths, plus one explicit "do not clear"

| Path | Which layer it covers | Notes |
|---|---|---|
| Clear on approval | Session layer | Only an approval persist clears, and it clears only those copies whose bytes did not move; see the second-to-last bullet of 11.4's admin side |
| Deleting this agent from the memory management page | Both layers | The scope is **every raw object name** listed under this agent's prefix, deleted one by one without key parsing; the session layer is nested underneath it (11.2 first rule), so it is naturally carried away together |
| Deleting a user | Both layers | One pass per tenant the user belonged to (following the existing position from section 6, with no new code for the new layer); every pass likewise lists raw object names by prefix, so keys that cannot be parsed are carried away too |
| Expiry archiving of daily ledgers | The ledgers of both layers | The existing 90-day archiving mechanism holds for both layers equally |
| Clear session, delete session | **Neither clears** | Section 1 rule 6 is kept: those are session-data actions and touch no memory layer |

The price of "deleting a session clears nothing" is stated openly: if a deleted session still has ledger entries that were never merged, those entries thereafter have **no reader at all** (the session-layer injection recognises only that one session) and will never get another chance at being merged into a candidate (there will be no further assembly of that session); they simply stay in the bucket until the second or third row above takes them away. It is not entirely without a destination — if this session had already enqueued a candidate before it was deleted and nobody has decided it yet, approving that candidate clears them by its manifest (an object still there with its bytes unmoved is carried away); rejecting that candidate touches nothing at all. The archiving tier has one further destination: once a session-layer ledger entry reaches 90 days and is moved into `memory/archive/`, it lands one level below the ledger segment, whereas promotion takes the direct children of the ledger segment — so an archived object is never merged away and no candidate ever names it for cleanup; it is a piece of this session's history left in the bucket, not a draft awaiting settlement.

This debt is visible on the page in two places, and **there is no "consolidate now" action**: how many sessions still carry content in their layer is stated by the counter of 11.6's third bullet, and which of them have already become candidates is listed out by the review screens (11.6's fourth bullet). "Merge once right now" would have to assemble a merge with no conversation at all — the throttle slot a merge needs and the model it has to ask are both attached to the session assembly step (11.4 first bullet), and the admin side holds neither of them, so building a new cleanup chain for it is precisely the thing 11.8 rejects. The manual action the page does give for intake is **reject**: it closes a candidate without touching any object, and the material therefore returns to this session's next merge. Reclamation itself still has only the three existing routes: the next conversation on this agent reaches the window, one of the two wholesale deletions in rows two and three above carries it away, or somebody approves the candidate that already exists.

### 11.6 What is visible on the page

- The memory management page still lists **the long-term layer only**: one row per agent, the body is that cross-session consolidated draft, the dates are its ledger dates. The session layer shares one prefix with the long-term layer, so this sentence is not "list everything and hope": the read side subtracts by the parsed session segment, and both the listing and the detail keep only objects without a session segment, so an unapproved draft and that day's ledger never appear on the page just because they lie under the same prefix; the same subtraction also keeps 11.7's progress object out, since its name does not read as a date. The delete side does not even apply this subtraction — it lists raw object names by prefix, see 11.5 second and third bullets.
- The date column is empty as a rule, and this place is said out loud: extraction, the full write and the manual filings all land in the session bucket, so the long-term bucket's ledger segment grows no new files (11.7's progress object follows whichever bucket this assembly mounted, which is the session bucket, and is not listed by the page), and so this row's **date column is empty** while its body is still overwritten by every approval as usual. This is not lost memory: the new entries are lying in the session layer waiting for a candidate to be approved. What explains this cell is not some switch on the row (there is no switch to explain it with), but the counter below and the review screens.
- The session layer is not listed separately, but it has one number on the page: that row carries an extra "pending merge" counter, which counts **how many sessions under this agent still have content in their layer**, not how many objects — one session's draft together with that day's ledger is one merge, not two, and counting objects would show one and the same conversation as two outstanding merges. Which objects count as "still holds content" follows promotion's own criterion: the session's `root/MEMORY.md` draft, plus the **direct children** dated objects of the ledger segment. So neither 11.7's progress object nor the archived object of 11.5's closing paragraph is counted — after an approval they both stay in the bucket anyway, and counting them would make an agent whose every layer has been merged away show pending merge forever, which is the one answer this counter must not give. It is counted out of the same batch of object names produced by the listing's own enumeration, with no new endpoint and no new storage read, and it gives a number rather than bodies, so the first bullet's "the page lists the long-term layer only" still holds. This counter only says "the session layer still holds something"; it does not distinguish whether that content has already been enqueued — content that is enqueued while nobody has approved it is still held, and that is exactly one state that must not be missing before an approval. The listing groups before it subtracts: an agent that **only ever wrote its session layer** still occupies a row (empty body, empty dates, pending merge N), otherwise it would look on the page like "this agent has no memory".
- The review screens are this layer's new entry point, at `/agent/memory-drafts` and `/agent/memory-draft/detail/:id` (the menu sits in the "Agents" group, and the top of the memory page has a button going straight there). The queue screen lists only the **currently logged-in user's own** candidates, shows pending ones by default, and can be filtered by status, by agent name (fuzzy) and by session number (exact); each row gives the agent name, the session number, the version it merges onto (version 0 is shown as "this agent has no long-term layer yet"), the number of source files, the character count of the pending-merge body, the times it was proposed and rewritten (when the rewrite time is later than the proposal time it states that this one was merged a second time), the status, the decider and the drill-down. The detail screen puts all three things a decision needs on one and the same screen: the complete text to be merged, the original long-term layer text it merges onto, and for each session layer file taken as material its own path, word count and original text (nothing is collapsed in advance, the body is given only on expansion) — approval answers for "the version I read", so a text that cannot be read cannot be signed. The same screen also gives this candidate's digest, which is brought back verbatim on approval.
- The five outcomes each have a next step, and the page branches on `outcome` rather than on the error code: a successful approval gives the version the layer landed on plus the three cleanup counts (how many were cleared, how many were left because their bytes had moved, how many were already gone); a successful rejection states that the session layer did not move and that this material returns to the next merge; `DRAFT_CHANGED` tells you to read it again before signing and shows the new digest; `ALREADY_REVIEWED` gives who decided, when and how; `STALE_BASE` gives the long-term layer's version right now and states that the version this candidate merges onto is no longer there. This domain carries the same deliberate exception as the rest of the admin endpoints: a rejection that allows another action is carried inside the 200 envelope's `data` rather than on an error code, because an error code carries one sentence only while the page needs these fields to decide its next step, and recovering "what it just refused" by fetching again would be a race.
- The delete row and the warning at the top of the page name **both layers** of this agent (the consolidated draft, all daily records, the session memory not yet merged), because what carries them away is precisely the prefix-based sweep of 11.5's second row: it enumerates by raw object name and therefore never reaches a "clear the long-term layer only" tier in the first place, so the copy must not under-report what it deletes.
- The web page is the only consumer on the client side: neither the chat page nor iOS has a memory screen, memory never appears as a bubble, and section 1 rule 5's invariant holds for both layers after layering. Approval never appears on the chat page either — it is a decision taken against a piece of text, and it belongs to the memory management side.
- There is no route that reads a session layer's body by session: none of the memory page's three routes (list, detail, delete) is addressed by session, and the detail one subtracts first (this section's first rule). What a person can see is the verbatim snapshot one candidate took at the moment it was filed (the detail screen of this section's fourth rule), and that body is cleared on approval (11.4 management side fourth rule, 11.5 first row), so the snapshot is not what this session layer holds right now. To answer "what does this session have at the moment" the server would first need two session-addressed read routes (list by session, read one session); the key layout is already given at `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/util/MemoryObjectKeys.kt:199`. Such a screen would show **the progress still awaiting merge** rather than an archive, and a team member's session layers are tiered by root session (11.4 last rule), so listing by session would produce rows of them.

### 11.7 Consolidation progress: it follows the bucket mounted this time

- The mechanism carries a progress marker for "up to when was the last consolidation", and upstream stores it in shared storage at **one fixed location** — the `watermark` under the `["memory","consolidation"]` namespace, with no tenant, no user, no agent.
- Why this slot has to move: across the whole deployment every user and every agent reads and writes the same progress, so one consolidation by A pushes the progress to "now", and B's ledger entries that were never merged in therefore sit permanently below it and are silently skipped. The symptom is "B's memory stops growing after a while, and there is not one error in the logs". This clause has nothing to do with layering (section 2 fact five recorded the fault where this same marker could not be written; that entry recorded its availability, what is at stake here is its ownership).
- Layering makes it more necessary: the session layer and the long-term layer each need a progress of their own, and sharing one lets a single full rewrite of the session layer mark the owner's cross-session ledger as already consolidated.
- Delivered shape: the coordination-slot clause of section 6 already set the precedent of "rewrite exactly one location in this process and pass everything else through", and the same shape is used once more here — `harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/memory/BucketScopedWatermarkStore.kt` rewrites only that one upstream namespace and passes every other key through, leaving the pipeline, the prompts and the file layout untouched. The two upstream constants are private, so this repo restates them and keeps one case that reads the upstream fields back and reconciles them verbatim: change that upstream side without this repo following, and it goes red at once instead of silently dropping every bucket back onto the same address.
- The landing spot is fixed **inside the daily-ledger segment of the bucket mounted this time**, rather than opening a separate small space belonging only to the progress. The reason is reclaim: the two existing paths, delete this agent and delete the user, both list by prefix and then delete object by object, so a progress kept inside that prefix gets carried away with them; kept inside its own segment, no path ever clears it, and it then outlives the very ledger it counts — the next user handed the same bucket key would be silently suppressed from consolidating by it. Once both layers are always present, "the bucket mounted this time" is this one conversation's bucket (that spot at `harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/HarnessAgentLauncher.kt:738` is the single decision point), so routing, progress and promotion always read and write the same bucket, while two conversations of the same owner each hold one progress — the record cross-talk blocked here is one notch finer than in the single-layer shape.
- This landing spot makes the memory page see one more object, and the price is that the page must not recognise it: the page lists only entries whose name reads as a date, the progress entry does not read as a date, so it appears in neither the listing nor the detail; like the two layers, it falls inside the delete scope.
- The upstream fixed address has no readers at all: this layer writes zero to it, and neither whole deletion reaches it — the `memory/consolidation` prefix segment lies inside no owner prefix, while all four reclaim paths of 11.5 list by owner prefix. If such an object really does sit in a bucket, taking it away is one manual action on the deployment side (deleting that one by object name), not a mechanism this layer has to supply.
- Approval takes no part in this cleanup: session-layer objects are cleared only when a candidate names them (11.5 first clause), and the progress object is never named by any candidate (its name does not read as a date), so it lives on with the bucket until one of those two whole deletions.

### 11.8 What this layer does not do

No tier that is session-only and keeps no long-term memory at all (that contradicts section 1 clause 1 outright); no manual editing entry for the session layer; no automatic approval, and no "merge it in first and let a human roll it back" — the only writer of the long-term layer is the approval step; the memory management page gets no "consolidate now" manual force-merge action (P15 of 11.9; the cost and the alternative are written in the last paragraph of 11.5); no cross-agent merging of session layers; no dedicated model or dedicated capacity budget for the session layer; nothing at all in iOS or on the chat page; no newly built cleanup path (apart from the approve-and-clear of 11.4, reclaim only reuses the three existing paths of delete this agent, delete the user and archive on expiry); the daily-ledger archive mechanism is not swapped out; the management side starts no model and re-merges nothing — it only persists the one text a human has read.

### 11.10 Assertable clauses

The six clauses of section 1 continue to hold unchanged for the long-term layer; this layer adds eight more, each one assertable. Who asserts each clause, and to which level, is reconciled clause by clause in 11.12.

1. **There is exactly one assembly criterion, and it governs both layers.** When `memoryEnabled` is false the whole domain is absent: no routes mounted, no hooks installed, none of those four tools given, no injection and no promotion. When it is true both layers arrive together: in the mounted route key the segment after the agent segment is `sessions/<session>` and then `root` and `memory` (it does not stop at the owner's segment), the two blocks are separable in the model input, and the promotion step is installed only when a queue adapter exists. This is the regression anchor of this layer.
2. **Visible scope under two layers.** A brand-new conversation of the same user and the same agent gets the long-term layer on its very first turn; the next turn of that same conversation gets the long-term layer and its own session layer at once, and the two segments are separable in the input — what makes them separable is precisely that one pair of long-term-layer tags. When the long-term-layer segment is over its budget, what comes in is its head plus a line stating that it was truncated, not the whole text. After one approval, the next model call of the same agent already reads this text: no new conversation and no re-assembly needed.
3. **Neither intake nor approval failure loses a single object.** On the runtime side, under the six cases of the model throwing, the model not answering until timeout, the merge result shrinking, the read being refused, the queue being unreachable and the queue explicitly refusing intake, each one asserts that the session layer's object count and text are unchanged verbatim and that not one byte was written to the long-term layer; only the successful-enqueue case changes state, and what it changes is the candidate row in the database, not any object. On the management side the four cases of digest mismatch, already decided, version moved and row claim lost likewise assert that both layers stay as they were; when the store refuses the persist (412) that row claim rolls back with the transaction and the candidate is still open. A store fault must never be read as "this layer simply had nothing in it".
4. **Both whole deletions cover both layers.** After deleting this agent and after deleting this user, the snapshot of keys under the prefix is verbatim empty, including the not-yet-approved ones below the session segment. The scope, per that clause of 11.5, takes the raw object names listed back from under the prefix, so even the class the key parser cannot recognise (an agent id that itself carries a slash) is inside what gets asserted.
5. **Progress follows the bucket, and nobody suppresses anybody.** Two users consolidating one after another on a real store: it asserts that the second one's ledger is not skipped because of the first one's progress (that pre-existing defect named in 11.7 second clause); the same run also asserts that two conversations of the same owner each hold one progress, and that the progress really does sit in the ledger segment of the bucket mounted this time, with neither of the two page responses turning up its name or its timestamp.
6. **Clearing may be no wider than the "read, then delete" pair of actions.** Write one more entry into the session layer between the text the candidate recorded and the moment it is deleted (appending to the ledger or rewriting that draft in full), and it asserts that the newly arrived entry is still in place while the rest of what this merge took in is cleared as usual; the delete itself must be read back and confirmed — when the store reports a failed delete without throwing, what cannot be confirmed counts as not deleted and fails the whole approval, rather than letting the queue report an entry it never took away as already merged.
7. **One approval persists to one version of the long-term layer only once.** Two approvals arriving at the same time against the same base version: it asserts that the one which persisted changed the layer, that the one which missed changed neither the layer nor got recorded as decided, and that the page still shows it as an open candidate. This clause does not depend on whether the store honours conditional writes: the version comparison first looks at that field in the envelope, and `If-Match` is only the second gate; the case where the store accepts `If-Match` but does not honour it is the responsibility of the probe clause (section 6) and has nothing to do with approval.
8. **An empty layer does not spend the window.** A conversation shorter than the throttle window whose first read of the session layer comes back empty (the extraction is still on the model side): it asserts that the window was not spent; the case where the layer cannot be read does not take the window either. Were the slot claimed before reading, this class of conversation would never merge even once from then on.
