## 1. Goals and acceptance

Six items, each of them decidable:

1. **A new session can remember an old one.** If one durable fact was stated in session A inside one owner bucket (see section 3), then the model-side input of the first question asked in a session created afterwards carries `<memory_context>`, and the answer can use it. The criterion has three stages in write order (extraction is dispatched asynchronously when a turn completes, and a task pending for the same session is displaced by the one that arrives later — `MemoryFlushMiddleware.java:159-212`; before each stage, first wait for the memory background to go quiet, see section 9 row 3): once session A has ended, that bucket's daily ledger for the day, `memory/<date>.md`, has gained an entry; after the consolidator has run once, `MEMORY.md` is not empty (a single extraction never writes `MEMORY.md` directly — see fact six); and the first-turn reasoning input of a new session B in the same bucket contains a `<memory_context>` block.
2. **No user identity means no memory domain.** Ownership is fixed at assembly time: if a delivery carries no user, that agent gets no bucket mounted, no `MemoryConfig`, and none of the four tools; the assembly log names the reason, and the delivery itself completes as usual. Anonymous callers sharing one memory is data crossing between people, not a feature; stuffing `userId` into `RuntimeContext` on every call is not a way out either — that value is simultaneously the bucketing key of `agent_state` (fact four), and filling it in for memory's sake would re-key the history of every existing session.
3. **The switches move together.** Under every tier, the two things "the model is taught how to use memory" and "memory really is read and written" hold at the same time or fail at the same time. A half-open state (the tools are in the manifest but no hook feeds them, or something reads a `MEMORY.md` that is always empty) counts as not done.
4. **The extra model calls paid per turn can be computed exactly.** The ceiling is at most 2 extractions per turn (the one from the per-turn hook, plus the one embedded in that turn if compaction triggers), plus at most 1 consolidation per bucket every 30 minutes. Of those three, only the hook one runs on the memory domain's own model; the compaction-embedded one and the overflow fallback follow that turn's main model (fact seven). Criterion: after a turn ends, count by the model that was called — the memory tier must be ≤2, and the increment on the main tier must reconcile with whether compaction or the fallback happened.
5. **Memory never enters the chat.** Neither the sequence returned by `GET /api/agent/chat/history/{sessionId}` nor the iOS and webui contracts change because of this work; content from the memory files never appears as a bubble in any session.
6. **Clearing a session does not touch memory; deleting a user does.** After `clearSession` the bucket's `MEMORY.md` is still there unchanged; after a user is deleted, that bucket's `MEMORY.md` and all of its daily ledgers are unreachable.

## 2. Seven facts decide the shape of the plan

**Fact one: for cross-session memory, upstream has only the harness set left.**
The entire core long-term memory interface family is annotated `@Deprecated(forRemoval = true, since = "2.0.0")` (`Memory.java:30-34`, `LongTermMemory.java:66-71`, `StaticLongTermMemoryHook.java:77`), and the class comment of `LongTermMemory` asks verbatim that "any cross-session persistence should be integrated at the application layer". The harness set is a two-layer ledger in file form: `memory/YYYY-MM-DD.md` is an append-only daily ledger and `MEMORY.md` is the curated layer, and who writes each layer is spelled out in the class comment at `MemoryFlushManager.java:40-52`. This plan does only this one set.

**Fact two: the default tier is "on", and harnax turns it off with a single disable.**
The field initialiser of `HarnessAgent.Builder` is `memoryConfig = MemoryConfig.defaults()` (`HarnessAgent.java:1228`), and the `flushTrigger` initial value of `MemoryConfig.defaults()` is `FlushTrigger.always()` (`MemoryConfig.java:240`) — installing the hook therefore means **one extraction per turn and one consolidation per bucket every 30 minutes**. On the harnax side `enableMemoryHooks: Boolean = false` (`HarnessConfig.kt:24`) is translated into `disableMemoryHooks()` by `HarnessAgentLauncher.kt:689-695`, and only then is the hook absent. So today's state is not "this feature does not exist" but "this feature is on by default and has been switched off explicitly".

**Fact three: where bytes land is decided jointly by IsolationScope and the route segments, and the framework hard-codes `agentId` into the key.**
`RemoteFilesystemSpec.storeNamespace(agentId)` returns a tuple according to `isolationScope` (`RemoteFilesystemSpec.java:333-352`); each route then appends its own segment to the tail of that tuple (`remoteForRoute` at `:314-323`); `MEMORY.md` goes through the `root` segment (`:256`) and `memory/` through the `memory` segment (`:258-259`). `IsolationScope` **has no tenant dimension**, and `agentId` is always in the key — the only choices available today are the four tiers "per session / per user × agent / per agent / global"; there is no "per tenant".

**Fact four: anonymous normalisation produces three different names in three places.**
`RemoteFilesystemSpec` normalises an empty uid to `anonymousUserId`, whose literal default is `_default` (`:79`, `:344`); `IsolationScope.toNamespaceFactory()` (the one that feeds `WorkspaceManager` the local path, `HarnessAgent.java:2425`) at the USER tier with an empty uid **falls back to sessionId** (`IsolationScope.java:104-115`); and the user-bucket normalisation of `agent_state` is `__anon__` (`ReActAgent.java:394-399`). Meanwhile the userId harnax sends into `RuntimeContext` is already an empty string (`HarnessAgentWrapper.kt:492`, `:1247` — both places that assemble a `RuntimeContext` use `userId ?: ""`). If those three names are taken for "the same anonymous bucket", you get a three-way fork: written into `_default`, read back locally from `<sessionId>` as the fallback, and state read from `__anon__`.

**Fact five: a store without CAS cannot hold up the distributed gate, and both consolidation and throttled-tier extraction silently never run.**
`StoreBackedPeriodicGate.tryClaim` wins its slot through `putIfVersion(ns, name, value, expectedVersion)` (`StoreBackedPeriodicGate.java:48-72`); on the first claim `item == null`, so `expectedVersion = 0` and the store must support CAS-create-if-absent. Any `BaseStore` that does not override `putIfVersion` falls back to the default implementation at `BaseStore.java:74` — **which returns false unconditionally** — and if its `get` uses the two-argument compatibility constructor in `StoreItem.java` that sets version to 0, the version read back can never be matched. harnax's `minio/MinioBaseStore.kt` has been completed along exactly this line with a conditional write and a versioned `get` (section 6), but the criterion still holds when a deployment swaps in another S3-compatible tier, so the assembly no longer assumes it — it probes once. The consequence (probe fails and there is no retreat): while `distributedStore != null` (the sandbox branch, `HarnessAgentLauncher.kt:663-676`) the gate is never won, `MemoryMaintenanceMiddleware.java:165-169` returns `Mono.empty()` outright, consolidation and archive cleanup run zero times, and this path emits no warn. The consolidator receives exactly this same store (`distributedStore.baseStore()` at `HarnessAgent.java:2589`), so the store-side watermark in `MemoryConsolidator.java:359-384` cannot be written either (it gives up after 5 CAS retries and logs a warn) — except that it also writes a file watermark at the same time (`:350`). **The same gate also governs extraction itself**: `MemoryFlushMiddleware.shouldFlushNow` returns a plain boolean at the `ALWAYS`/`NEVER` tiers (`MemoryFlushMiddleware.java:291-296`) without passing the gate, and only the `THROTTLED` tier goes through `periodicGate.tryClaim(...)` (`:297-298`) with the key prefix `memory-flush:` (`:310-312`), independent of maintenance's own. So when CAS is missing, "consolidation does not run" and "throttled-tier extraction does not run" are one and the same failure, while the default `always()` is immune instead. **This must have an answer before any memory switch is turned on**: either the store really delivers CAS, or the assembly detects the gap and retreats to in-process coordination (section 6); the third state — silence — is the failure this fact describes.

**Fact six: the three writer sides do not know about each other, and the reader side has one entry point.**
`memory_save` appends to `MEMORY.md` and to the day's ledger at the same time (`MemorySaveTool.java:73,76-80`); flush appends to the daily ledger only and never touches `MEMORY.md` (the comment at `MemoryFlushManager.java:218-235` states that `MEMORY.md` belongs to the consolidator); consolidation **overwrites** `MEMORY.md` wholesale (`MemoryConsolidator.java:301-303`). All three land on `WorkspaceManager`'s append/write, and append is "read the whole file + concatenate + write everything back" (`WorkspaceManager.java:370-397`); that lock is an in-process `ReentrantLock`, and the javadoc at `:366-368` of the same file says verbatim that across replicas "the append is last-writer-wins; this method does not perform CAS"; `uploadFiles` calls itself last-write-wins in its comment at `RemoteFilesystem.java:521-527` as well. On the reader side: `<memory_context>` is injected only when `WorkspaceContextMiddleware` is installed and `includeMemoryContext()` is true (`WorkspaceContextMiddleware.java:254-255,512-516`), plus the two tools `memory_search` and `memory_get` (`MemorySearchTool.java:67-87`, whose search surface is fixed by `WorkspaceManager.java:934-947` as `MEMORY.md` plus `memory/*.md`, with no cap on the number of matched entries).

**Fact seven: the three flush entry points are customisable unevenly, so "memory runs on a small model" holds at only one of them.**
The per-turn hook uses `memoryConfig.flushPrompt()` and `memoryConfig.model()` (`HarnessAgent.java:2562-2571`); the flush embedded in compaction hard-codes the default prompt and uses the compaction model (`CompactionMiddleware.java:106-107` does `new MemoryFlushManager(workspaceManager, model)` directly and never takes `memoryConfig` at all); the overflow fallback uses `flushPrompt` but follows the main model (`HarnessAgent.java:1073-1077`). That is, `flushPrompt` takes effect at two of the three places, while `memoryConfig.model` is honoured only at the hook one. The latter two are both alive in harnax: compaction is not an optional extra but the default — `compactionConfig = CompactionConfig.builder().build()` and `disableCompaction = false` are builder field initialisers (`HarnessAgent.java:1227,1230`), and `CompactionMiddleware` is installed as soon as the summary model is non-empty (`:2600-2608`); the fallback one is triggered by context overflow.

The half-open state is recorded here as well: `disableMemoryTools()` has never been called in harnax, and the disable family at `HarnessAgentBuilder.kt:148-158` does not even contain that pass-through method, so the four memory tools are advertised to the model on the tool manifest today (`HarnessAgent.java:2688-2692`); the hook that feeds them is switched off (fact two), and `enableWorkspaceContext = false` keeps the reader middleware uninstalled entirely (`HarnessAgent.java:2527`). `includeMemoryContext()` requires `disableMemoryTools` **and** `disableMemoryHooks` to be true at the same time before it returns false (`WorkspaceContextMiddleware.java:254-255`), so "switching off only one of them" necessarily leaves a half-open state.

## 3. Ownership and key layout come before the trade-offs

Fix the bucket first, then talk about switches. The bucket decides whether every item below can be verified at all.

| Tier | Tuple (`RemoteFilesystemSpec.java:333-352`) | MinIO object key (bucket `harnax-store`, prefix `store/`) | What it means for memory |
|---|---|---|---|
| `SESSION` (today) | agents, agentId, sessions, sid or `default`, segment name | `store/agents/<agentId>/sessions/<sid>/root/MEMORY.md`, `.../memory/<date>.md` | one private memory per session, no continuity across sessions — directly contradicts the goal of "cross-session memory" |
| `USER` | agents, agentId, users, uid or `_default`, segment name | `store/agents/<agentId>/users/<uid>/root/MEMORY.md`, `.../memory/<date>.md` | continuous for that user within one agent; broken by switching agents; all anonymous calls land in the single `_default` bucket |
| `AGENT` | agents, agentId, shared, segment name | `store/agents/<agentId>/shared/root/MEMORY.md` | all users of that agent share one memory — crossing between users |
| `GLOBAL` | global, segment name | `store/global/root/MEMORY.md` | one global copy, as above and worse |

None of the four tiers has a tenant. The only way to give memory a tenant dimension without changing upstream is: **mount `MEMORY.md` and `memory/` separately onto a `RemoteFilesystem` with a hand-built namespace, through `filesystemRoute(prefix, AbstractFilesystem)` (`HarnessAgent.java:1862`)**. Feasibility is pinned by three source points: the outer Composite wraps the caller's routes outside the spec's built-in routes (`:2482-2483`), matching is longest-prefix-wins (`CompositeFilesystem.java:86-93` for the ordering and `:108-136` for the match), and on a hit the remainder is handed over by suffix (`CompositeFilesystem.java:129-133`). This one mount therefore overrides the spec's own two routes of the same name, while **every other file and the isolation tier stay completely untouched**.

| Design point | Decision | Reason |
|---|---|---|
| Memory ownership dimension | `tenant × user × agent`, tuple `[tenants, tenantId, users, userId, agents, agentId]`, delivered by the single mount route above | the agent dimension is hard-coded by the framework into the default route, so keeping it is equivalent to keeping the existing shape; the tenant must enter the key, otherwise the same `userId` under two tenants shares one memory bucket |
| Isolation tier for every other file | `IsolationScope.SESSION` stays | the non-sandbox branch hard-codes the spec scope at `HarnessAgentLauncher.kt:679-680`, and that one place governs three things: the tuple of the remote key (fact three), `WorkspaceManager`'s local namespace (`HarnessAgent.java:2416-2425`), and the throttle keys of flush and maintenance (`:2564`). Sandbox container reuse is a separate knob (`:657`, taken from `SandboxConfig.kt:37`). Flipping the former would move the namespace of every route including `sessions/` along with it — that is moving house, not turning memory on |
| Anonymous calls | at assembly time there is no ownership to bind: no bucket mounted, no `MemoryConfig`, none of the four tools, one warn, and the delivery completes as usual | ownership is taken from the assembly arguments rather than from each call — `RuntimeContext.userId` is simultaneously the bucketing key of `agent_state` (fact four), and filling it in for memory's sake would re-key the state of every existing session. And one harnax agent instance serves exactly one user (`DefaultAgentRunner.cachedAgent` drops the cache and rebuilds when it meets an ownership mismatch), so whoever the assembly resolved is the user of this delivery, and no value the caller passes later can change the bucket's key. **The reader side is still not fully blocked**: `readMemoryMd` goes through `readWithOverride`, and once the route returns empty it unconditionally reads the host disk's `workspace/MEMORY.md` as well (`WorkspaceManager.java:819-823`); so with a bucket mounted but no `MEMORY.md` in it yet, "nothing was injected" only holds if the host template itself is empty — see section 9 row 6 |
| Storage landing | **A: keep the MinIO file layer** — memory is `MEMORY.md` and the daily ledgers, and harnax adds no table | all three upstream writer sides and both reader sides read and write files; moving to a MySQL projection means either rewriting the consolidator's whole-document rewrite semantics yourself or maintaining two sources of truth. B (adding an `agent_memory` projection table) is only worth it for "editing memory on a page" or "retrieving memory semantically", and neither is a goal this round |
| Memory stays out of the chat | memory content never enters session messages, and `MEMORY.md` never enters `agent_state.context` | upstream injects `MEMORY.md` only as a system prompt, never as a history message (`WorkspaceContextMiddleware.java:512-521`), and harnax's history read path at `DefaultAgentRunner.kt:338-341` renders only `agentState.context` (the `GET /chat/history/{sessionId}` at `AgentController.kt:104`). This invariant comes free, but it has to be pinned in a test |
| Deletion scope | deleting a user: that bucket's `root/MEMORY.md` plus every object under the `memory/` prefix; clearing a session: memory untouched | memory belongs to the user; clearing a session is a session-level action, and mixing the two would turn "clear the current session" into losing long-term context |
| Write ordering | one writer per bucket: flush and maintenance each serialise by bucket key, and harnax adds no third automatic write path | the last-write-wins of fact six only holds under per-bucket serialisation. `memory_save` is the model-driven second entry point, and whether it stays is decided in section 5 |

## 6. Change list

By module, at file level:

- **harnax-harness-core**:
  - `harness/minio/MinioBaseStore.kt` gains `putIfVersion` and a versioned `get` (fact five is a hard precondition, and it also decides whether the throttled tier extracts at all). On MinIO this can be implemented with a conditional write or with "a version-number object plus `If-Match`"; if it genuinely cannot be done, the assembly must explicitly select `LocalPeriodicGate` instead (the price being one consolidation per replica) — one of the two, no silence allowed.
  - `harness/minio/StoreCasProbe.kt` and `harness/minio/ProcessLocalCoordinationStore.kt`: they turn that sentence "one of the two, no silence allowed" into code. The first time the assembly needs this gate, it creates a one-shot slot carrying a uuid inside the same namespace and runs a three-step criterion (a version mismatch must be refused, a matching version must be admitted, and slot creation with `expectedVersion = 0` against an object that already exists must be refused), which is how the two opposite failures are told apart: "the interface default always refuses" versus "the gateway takes `If-Match` but does not honour it". The verdict is remembered per process, but **only what the store actually answered** — "no answer" while the connection is down is not a verdict about the store, and recording it would pin the whole replica permanently on in-process coordination after a single MinIO restart; the verdict that was recorded is re-asked once ten minutes are up (the same reason as 11.4: repairing the storage should not require a restart). | Situation | Behaviour |
|---|---|

## 8. Test plan

The primary assertions (missing one means section 1 is not done):

1. **Remembering across sessions**: run one turn of session A inside the bucket (a stand-in model stubs the extraction); after the memory background goes quiet, assert that the bucket's `memory/<date>.md` has gained an entry (one extraction does not write `MEMORY.md` — fact six); then trigger one consolidation and assert that `root/MEMORY.md` contains that entry; then create session B in the same bucket and assert that B's first-turn reasoning input contains `<memory_context>` and that the entry can be found there.
2. **No user in the delivery means no memory at all**: assemble an agent with an empty `userId`, assert that the tool manifest is empty, assert that the log holds exactly one warn stating the reason, and assert that the agent still builds (switching the memory domain off is not a failure of that request).
3. **Tenant isolation**: run one turn for the same `userId` under two tenants and assert that the two buckets have different object keys and never hit each other — this case tests the tuple of section 3 directly.
4. **The gate is really winnable**: two cases for `MinioBaseStore.putIfVersion` (creation succeeds when the object does not exist, and false is returned on a version mismatch); plus two counter-cases — with `putIfVersion` stubbed to always return false, neither the `throttled` tier's extraction nor maintenance persists anything, while the `always()` tier's extraction persists as usual (the three-part criterion of fact five).
5. **No switch ends up half-open**: three tiers of cases (all off, all on, hooks only), asserting that the combination of the two booleans "the tools are in the manifest" and "the hooks are installed" matches the matrix of section 4 row by row.
6. **Memory stays out of the chat**: finish a session that has memory and assert that the response of `GET /api/agent/chat/history/{sessionId}` contains no fragment of `MEMORY.md` or of any daily ledger.
7. **Clearing a session leaves memory alone; deleting a user does not**: two cases that assert respectively that the object is there and that it is not.
8. **Extraction failure does not affect the answer**: stub the memory model to throw, assert that the turn's answer still returns as usual, and after quiescence assert that the bucket's daily ledger and `MEMORY.md` are verbatim unchanged (a failure only logs a warn, `MemoryFlushMiddleware.java:273-277`).
9. **The per-turn call count is capped**: for one conversation turn assert exactly 1 model call on the memory tier; if that same turn triggers compaction then assert 2 calls, the second one landing on the compaction model (the ceiling of section 1 rule 4).
10. **One individual agent's answer outranks the whole domain**: with the domain on, the agent carrying `memoryEnabled = 0` has no hooks, no tools and no bucket route, and it does not trigger the store's gate probe either; the `memoryEnabled = 1` agent assembled in the same batch has all three, and the two do not affect each other. The resolution side asserts two more tiers: a payload carrying `0` maps to off, and a payload that never names the key maps to on. This is section 1 rule 3 repeated at agent granularity — a half-open state counts as not done there too.
11. **admin's read and delete hit real buckets**: this is the end-to-end IT named explicitly at the moment the decision was taken (`MemoryOwnerBucketMinioIT`, harnax-admin); it starts the whole admin service against Testcontainers' MinIO, pours objects in following the writer's key layout, and then asserts three things through JWT-carrying HTTP — that the bodies the list and detail endpoints give are the envelope's `value.content` rather than the whole JSON; that deletion clears only the prefix of the named agent while the two kinds of neighbour (another user in the same tenant, and the same user's copy under another tenant) stay byte for byte where they are; and that a caller of an empty bucket gets a successful empty list rather than an error. Calls without a JWT and agent ids that only become a path segment after decoding (`%2F`, `%5C`, `..`) are all refused before the store is reached, asserted by taking a full bucket-key snapshot before and after and comparing it verbatim equal. This case is also the reader side of the cross-module envelope contract: the envelope's literal is stored once on the writer side and once on the reader side, the two test classes name each other, and if the writer changes the shape both go red (see section 9 row 9).

The way they run follows this repository's existing recipe (JDK 21, probe Docker first and only then decide whether to exclude ITs). Bucket reads and writes may be covered with `InMemoryStore` in unit tests, but assertion 4 must hit the real `MinioBaseStore` implementation, otherwise it bypasses exactly fact five. Assertion 11 goes the other way and cannot use a stub: a mocked client only answers what the stub tells it to answer, and prefix listing, the recursive flag and the scope of deletion — these three things only hold against a real server.

Missing any segment shows up differently: if the mapper's insert or updateById omits this line, the value lands on the DDL default 1, the wizard's "off" never gets stored, and reopening the page shows "on" again; if one of the two read paths is missing, it is one screen that shows the switch and another that does not; if one call site of the delivery is missing, the row says off while the runtime still installs memory for that agent; and if resolution were written in the authorisation direction (`== 1`), then since the wire contract's default is already 1, payloads from an older admin would still resolve as having memory (that tier is fine) — what actually gets inverted is the case where the row ends up carrying a value other than 1: this column is a default state rather than an authorisation, so out-of-range values belong on the "has memory" side.
8. The window before a flipped switch takes effect: the conclusion (the 30-minute per-session cache, and pushing REFRESH early through `refresh-sessions`) comes from reading existing code, with no real service started to reproduce it, so that row of section 7 is a description of the mechanism rather than a measured result.
9. There is no shared type between the bytes admin reads back and the bytes the runtime writes: `MinioBaseStore` is in harness-core, `MemoryRecordParser` is in harnax-admin, and the envelope the former puts around every file was at first only inferred from the source as `{"key":…,"value":{"content":…},…}`. Nothing ties the two ends at compile time, so the contract is either pinned by a literal recorded in a test, or every change depends on somebody remembering to synchronise it; a two-ended reconciliation on real buckets is needed.

## 11. Memory layering: session granularity and long-term granularity side by side

The position in one sentence: one agent's memory is split into two layers. The **session layer** holds "what was said in this chat but has not settled yet", and it is meaningful only to the current session; the **long-term layer** holds "what has to be remembered across sessions", which is exactly the curated memory of section 3, bucketed by tenant × user × agent. Session-layer entries are produced automatically by the conversation, are merged into the long-term layer at intervals, and are cleared in place once the merge succeeds. The long-term layer behaves as sections 1 through 10 of this document describe; adding this layer does not change it.

### 11.1 What each layer holds, who writes it and who reads it

| Layer | What it holds | Who writes | Who reads | How long it lives |
|---|---|---|---|---|
| Session layer | The entries extracted from this turn's conversation: a day-by-day ledger, plus one draft curated inside this session alone | Two writers: the extraction at the end of a conversation (the same mechanism as today, reused without changing a word), and the model filing things by hand with those memory tools — which layer a manual filing lands in is decided solely by where the route is mounted, and under two layers that is here | The next turn of the same session | Cleared after being merged into the long-term layer; if that session never comes back it stays in the bucket until the two wholesale deletions in 11.5 take it away |
| Long-term layer | The curated memory that has settled across sessions | Written only by the promotion step (11.4) | Any new session of the same user on the same agent, including the first turn of a brand-new session | Overwritten whole by every promotion, its total length has a budget cap, and going over it truncates rather than refusing the write |

The two layers have exactly the same file shape: one curated draft plus one day-by-day ledger. So reading, deleting and page display never need a second mechanism for one of the layers; the only differences are that the bucketing key carries one extra session segment, and that something has to merge them.

When both layers enter the context they are **two separate things**: the session layer goes through the injection of those two existing routes, while the long-term layer carries its own pair of tags plus a sentence saying "this is context, not a user instruction, and it is read-only here". The model can therefore tell which block is this session's still-unsettled draft and which is the one kept across sessions — the latter's whole reason to exist is that it will be merged away and then cleared, so blending the two into one block amounts to telling the model the draft already counts. The long-term block has a length limit, truncated against the curated-draft budget (4000 token, i.e. 16000 characters), with the truncation stated at the end of the block: this content enters the context on every model call, and its total length is guaranteed only by the model obeying the curation prompt — nothing else backs it up.

### 11.2 Granularity: four rulers, outside in

Tenant → user → agent → session. The long-term layer uses the first three (that is how it works today); the session layer uses all four, i.e. the key carries one extra session segment after the agent, shaped like `store/tenants/1/users/2/agents/Report/sessions/abc/…`. Six standing rules:

- **The session layer is nested under the agent segment, not placed alongside the agent.** This way both existing cleanup chains, "delete this agent's memory" and "delete this user's memory", only have to list once under that agent's prefix, and the session layer is naturally carried away in that listing; a compliance deletion never needs to ask first "which layer do I delete". This rule does not depend on any key parsing: the two wholesale deletions enumerate the raw object names in the bucket that fall under that prefix and delete them one by one, without going through the decoder. The decoder only serves the page read side; it recognises the extra session segment and uses it to subtract the session layer from the listing and the detail — so both hold independently: a key whose agent segment cannot even be parsed (for instance an agent whose own name carries a slash) still gets deleted along with its owner, it just never appears on the page.
- **The session layer moves together with the tenant switch.** When the deployment turns off the tenant segment of the memory key, both layers start keying from the user segment and each loses the same part, so there is never a case of one layer writing by tenant while the other reads without it, and no second switch is needed for the session layer.
- **The session layer does not cross agents.** When a supervisor delegates work to a member in a team, the member has its own two layers and cannot read the session layer of the supervisor's session. This is the same position as section 7's "each member buckets by its own agent, and within one delegation the supervisor's and the member's memories do not connect".
- **Anonymous delivery has neither layer.** The session layer needs the user segment just as much, otherwise different people's ledgers would mix into the same key. Section 7's criterion — "if the delivery does not name a user, the whole domain is closed" — is unchanged; only the scope being closed now covers both layers.
- **Changing granularity is not moving house.** Only the two routes, the curated draft and the day-by-day ledger, change keys; session state, the sandbox workspace and the isolation tier of every other file are untouched, for the same reason as section 3's "the two single-mounted routes only, everything else untouched".
- **The session segment can only deepen a bucket, never relocate it.** The session id is spliced into the key verbatim, so an id carrying a slash only adds levels — `sessions/a/b/root/MEMORY.md` is still under that agent's prefix and goes with the two wholesale deletions of 11.5. An id that tries to move the bucket upwards (`../`, or one reaching into someone else's user segment) is rejected by the store at the moment of writing, by its object-name rules: a `.` or `..` segment is not allowed in an object name. This rejection lands in the "the store cannot be read" tier, the same failure mode as 11.10's third bullet, so it does not make this layer read as an empty layer. `MemorySessionKeyShapeTest` pins each of the two shapes once against real MinIO, and what it pins is "the number of objects outside the agent prefix is 0", not "it threw an exception" — on a storage tier that normalises paths itself this assertion goes red instead of quietly passing.

### 11.3 The switch: chosen per agent, and the default is today

Alongside section 4's "long-term memory" switch, one more switch, "session memory". The two together decide four assemblies:

| Long-term memory | Session memory | Result |
|---|---|---|
| off | either | The whole agent has no memory domain: no bucket mounted, no extraction installed, none of those four tools, both layers gone at once. The session-memory switch does not take part in the decision here |
| on | off (default) | Today's behaviour, unchanged to the letter: the long-term layer only |
| on | on | Two layers: extraction lands in the session layer first, is promoted into the long-term layer per 11.4, and both layers are injected into the model |

The default combination is "on plus off", so landing this layer changes nothing about how any existing agent behaves; getting two layers requires opening them per agent in the wizard.

Flipping this switch changes exactly one thing — where the route is mounted (`HarnessAgentLauncher.kt:721`) — it moves nothing, deletes nothing and rewrites no object already on disk. Each direction produces one freeze, and both need to be known:

- **on → off: that session layer loses all three things at once.** No reader (the mounted route goes back to the long-term bucket, the `<long_term_memory>` block is therefore not installed either — it is only mounted under two layers, `:728`), no promoter (the promotion middleware and its probe both live in the `:723` block and are only assembled under two layers), and no archiver (the 90-day archiving runs over the mounted route, which now points at the long-term bucket). Whatever the session layer has not merged away stays in the bucket until deleting this agent or deleting the user takes it away (11.5 second and third bullets). This is not a leak: that prefix is still under this owner's name and still inside the scope of both of those chains.
- **off → on: the long-term bucket's ledger segment stops growing, and what it already holds is no longer retrievable.** Extraction now writes into the session bucket, so no new day-by-day ledger files grow in the long-term bucket; the old ledger entries are still listed with their dates by 11.6's listing, yet `memory_search` / `memory_get` no longer hit them — those four tools address the mounted route, which at this moment points at the session bucket. The long-term layer's curated draft is still injected and still overwritten whole by every promotion. In other words, once this switch is flipped up, "this agent's memory on the page" and "the memory the model can retrieve right now" are seen as two places for the first time.

The deployment side configures one more, but its reach is narrower than "turning the whole deployment into two layers": **the initial value when admin creates an agent** (`harnax.agent.session-memory-default`, default `false`). It takes effect only at the instant of insert, and only for **requests that do not carry this field** — the wizard always passes an explicit `0`/`1`, so it never consults this one; existing agents keep the answer they already have, and turning it on does not rewrite them. So what this one actually serves is the usage pattern "call admin's endpoint directly to create an agent and leave this field out" (curl / Swagger / API Key calls through nginx `/api/admin/`) — in this repository the only caller that creates agents is the wizard, and it always passes the value explicitly. Landing this narrowly is the result of a ruling; see P16 in 11.9. This section does not change the already-delivered matrix of section 4; that table describes the batch that is already running.

### 11.4 Promotion: when to merge, and what a merge does

- **The trigger is a throttled timer, not "the session ended".** harnax has no reliable session-end signal: the vast majority of sessions simply stop sending requests, while "clear session" and "delete session" only run when the user actively performs them. Attaching promotion to those two actions would show up as some sessions' memory staying in the session layer forever. The chosen approach is that every new conversation on this session also checks whether the time has come, and merges if it has; the interval is a configuration item, 30 minutes by default, sharing its source with the long-term layer's full-write throttle; a negative value is refused at the assembly step, and `0` is a legal value meaning promotion is caught up on every single turn (one extra model call beyond this turn's own). **The "has the time come" check runs after the "does this layer hold anything" check**: taking the slot cannot be undone (this gate exposes one method only, and winning it writes the timestamp that closes the window), while the extraction that fills this layer is dispatched after the answer and costs another model round trip, so the first turn usually reads empty. Claiming the slot before reading would spend the entire window on an empty layer — and sessions shorter than one window (the majority) would then never promote even once. The "could not be read" tier is treated exactly like an empty layer: no slot taken, the window is left for whichever run fills content first.
- **The merge action**: take the session layer's curated draft plus the ledger entries not yet merged, hand them to the model together with the long-term layer's existing content, produce **one complete merged long-term memory**, and write it back to the long-term layer. The write-back carries a version comparison: if anyone (including another session of the same user) changed the long-term layer meanwhile, this attempt is abandoned outright — no re-read and retry — because the material is still in this session layer and the next turn's conversation will merge again against whichever long-term layer is newer then; when the long-term layer does not exist yet, the "must not exist yet" precondition is used instead. Never a blind overwrite.
- **Cleanup proceeds object by object, each object with its own body re-check.** Clearing the session layer after a successful write-back starts by re-reading that one object and confirming its **bytes have not changed** since this read, and only then deletes it; if it was written in the meantime it is not deleted and is left for the next merge. What is compared is the body, not the version number the store hands out: an unprotected write can land arbitrary bytes on arbitrary versions, and what this step is about to delete is the only copy of those bytes. After deleting, read back to confirm it really went away — a storage object of this layer, on a failed delete, only logs a line and returns normally; without the confirmation, entries that were never carried away would be counted as settled and the next window would merge them again. The session layer's day-by-day ledger is append-only, and one and the same conversation can add new entries to it during a model round trip, so "what I read is no longer what is there" is a state that genuinely happens, not a theoretical one. This re-check compresses the dangerous window from "a whole model round trip" down to "between one read and one delete", and it lands on the smallest possible action: cleanup is not allowed to be wider than that. The consolidation progress object in the bucket does not participate in cleanup — it counts when ledger entries were written, and keeping it is what stops the next full write from re-reading entries this layer no longer has. The delete on the storage side, "does not throw even on failure, leaves one log line", is kept as it is: its signature is the kind that returns nothing, and making it throw would fail the whole maintenance round of expiry archiving. Each place that needs confirmation confirms for itself — this layer's cleanup reads back per the half-rule above, and the admin side's two wholesale deletions each throw and count. The remaining exposed surface is only the two upstream places, archiving and full-write cleanup, whose behaviour is "the object is still there plus one warn", not silent loss.
- **Promotion is only assembled on deployments where the store genuinely honours version comparison.** The assembly step probes the store first: if it answers "written" for any version number (which is to say it does not compare at all), this agent gets the session layer only, no promotion installed, plus one log line saying how to get it back — fix the store's version precondition. Refusal was chosen here rather than degradation, because the merge action is "overwrite the long-term layer, then delete the copy in the session layer": if two sessions are both allowed to write, one of them will necessarily overwrite content the other just settled, and the overwritten one has already cleared its own original as a success. Section 6's throttle slot may degrade to per-process timing, because its failure only costs repeated consolidation; failure here costs lost memory. A probe that reached no conclusion (the store threw outright) does not count as "the store is unusable": promotion is assembled as normal — a fault of that same store will be hit again on the merge path itself, and failing there drops nothing. Only the promotion step is withdrawn: the long-term layer's read-only injection is still mounted, so this agent's behaviour is "the session layer is never merged away", not "this agent has no memory". The probe verdict is remembered per process for ten minutes and asked again once it expires — the reason shares its source with the one in section 6 and matters more here: this rule says "fix the store and promotion comes back", so the answer must not outlive the fix itself. Promotion's own throttle slot is backed by the same store on both assembly branches (`StoreBackedPeriodicGate` wraps the probed gate from section 6), and its fallback shares its source with those two hooks: the same probe verdict, the same wrapper class, only the slot key named separately (`memory-promotion:SESSION:<session>`), so the per-process-timing tier does not constrain the others.
- **A merged result that shrank is treated as the model not finishing the job.** If the merged text is clearly shorter than the long-term layer's existing content (less than half), this attempt counts as failed: no write-back, no cleanup, one log line left. The prompt's "do not drop entries" does not guarantee the model writes both halves in full, and the direction of failure must not be "the long-term layer replaced by this session's few entries" — that is the only content of this layer that enters the context on every call. **This guard sets no exception for "already over budget"**: a draft that drifted above budget is the easiest one for the model to answer with a quarter of its size, and this step deletes the session layer's copy as soon as it writes, so a collapse and a diligent consolidation look identical from outside. An over-budget layer is still consolidated: one window takes in half of it, a few windows converge it back inside budget, and the cost is only slowness, not loss.
- **One merge has a time cap (5 minutes by default).** It runs on the blocking scheduler shared by sessions and occupies one of its workers, and it is also in the in-flight count graceful shutdown waits for; an unbounded wait means one model that never answers holds that slice of concurrency indefinitely. The cap is set looser than a conversation turn's own timeout, because one merge has to rewrite the entire curated layer in a single completion. A timeout is handled as a failure, on the same rule as the two items above: the session layer is left exactly as it was.
- **A failure still spends the whole window, and this is accepted as it stands.** That throttle gate has only "claim", no return: after a version conflict, a model error, a timeout, a shrink, or a refused read or write, this session has to wait out a full window before its next chance. The reason it is accepted is that the direction of failure is already safe — the material stays in the session layer verbatim, and the only cost is latency. Neither alternative removes that cost: writing the slot's timestamp back needs a version-compared return, and two sessions of the same agent are right now contending for the same long-term layer, so writing back is exactly the mutual trampling that "never a blind overwrite" in the "merge action" rule above guards against; shortening the window specially for failures needs one extra piece of "the last attempt failed" state stored on the slot, which is the only thing in this layer that would grow with failures. What is gained is only a retry a few minutes earlier.
- **Three hard rules.** One, a failure never clears: whichever of version conflict, model error, write-back failure, timeout, shrink, or a store refusal on read or write happens, the session layer's object count and bodies are unchanged to the letter; repeating the merge next turn (deduplicating while merging) is preferred over deleting the only copy of memory that has not yet settled. Every attempt lands in a result tier that can be named (no content / merged / version conflict / model failed / store refused), and a storage fault must not be counted as "this layer had nothing in it". Two, promotion is not on the conversation path: if it errors it leaves one log line and the turn's answer proceeds as normal. Three, each session times independently: two sessions of the same agent promote separately and never block each other.
- **The model used follows the memory domain's own** (section 5's model row); if none is configured it follows this agent's primary model, consistent with how extraction picks its model today, and no second piece of configuration is added.

### 11.5 Cleanup: four reclaim paths, plus one explicit "do not clear"

| Path | Which layer it covers | Notes |
|---|---|---|
| Clear on promotion | Session layer | Cleared only when the merge succeeded; see 11.4's first hard rule |
| Deleting this agent from the memory management page | Both layers | The scope is **every raw object name** listed under this agent's prefix, deleted one by one without key parsing; the session layer is nested underneath it (11.2 first bullet), so it is naturally carried away together |
| Deleting a user | Both layers | One pass per tenant the user belonged to (following the existing position from section 6, with no new code for the new layer); every pass likewise lists raw object names by prefix, so keys that cannot be parsed are carried away too |
| Expiry archiving of day-by-day ledgers | The ledgers of both layers | The existing 90-day archiving mechanism holds for both layers equally |
| Clear session, delete session | **Neither clears** | Section 1 rule 6 is kept: those are session-data actions and touch no memory layer |

The price of "deleting a session clears nothing" is stated openly: if a deleted session still has ledger entries that were never merged, those entries thereafter have **no reader at all** (the session-layer injection recognises only that one session) and will never get another chance at promotion (there will be no further assembly of that session); they simply stay in the bucket until the second or third row above takes them away. The archiving tier has one further destination: once a session-layer ledger entry reaches 90 days and is moved into `memory/archive/`, it lands one level below the ledger segment, whereas promotion takes the direct children of the ledger segment — so an archived object is never merged away; it is a piece of this session's history left in the bucket, no longer a draft awaiting settlement. This debt is **visible as a count on the page, with no manual way to settle it**: how many sessions have not been merged yet is stated by the counter in 11.6's third bullet, while the "consolidate now" action is not provided. The reason is that it conflicts with this section's reclamation model: the throttle slot a promotion needs, the probe verdict about the store's version comparison and the material it reads are all attached to the session assembly step (11.4 first bullet), so letting a page action merge without any conversation would mean building a new cleanup chain — precisely the thing 11.8 rejects. Reclamation therefore has only the two existing routes: the next conversation on this agent reaches the window, or one of the two wholesale deletions in rows two and three above carries it away. The ruling on this one is recorded as P15 in 11.9.

### 11.6 What is visible on the page

- The memory management page still lists **the long-term layer only**: one row per agent, the body is that cross-session curated draft, the dates are its ledger dates, same as under a single layer. The session layer shares one prefix with the long-term layer, so this sentence is not "list everything and hope": the read side subtracts by the parsed session segment, and both the listing and the detail keep only objects without a session segment, so an un-promoted draft and that day's ledger never appear on the page just because they lie under the same prefix; the same subtraction also keeps 11.7's progress object out, since its name does not parse as a date. The delete side does not even apply this subtraction — it lists raw object names by prefix, see 11.5 second and third bullets.
- An agent with two layers shows one visible gap on the page, and the gap is stated out loud: its long-term layer holds only the curated draft. Extraction and full writes both land in the session bucket, so the long-term bucket's ledger segment stops growing new files (11.7's progress object follows whichever bucket this assembly mounted — under two layers it lands in the session bucket, under one layer in its owner's long-term bucket, and neither is listed by the page), which means this row's **date column stays empty as a rule** while its body is still overwritten by every promotion as usual. This is not lost memory: ledger entries written before the switch was opened are still in the long-term bucket and still listed with their dates on the page, while new entries are lying in the session layer waiting to be merged. The row therefore also carries whether this agent has the session layer on, and when it is on, that sentence is written into the tooltip of the "Daily records" cell — at which date the records stopped, or that the long-term layer has not merged any records yet. This flag reads `session_memory_enabled` on the agent row: the memory bucket only holds names, the switch lives on the row, so the row is fetched by name **and by the same tenant this listing used** (names are unique only within a tenant, and without the tenant the switch of some other workspace would be used to explain this memory). When no row can be found (memory left in the bucket after a rename or a deletion) the answer is "unknown", not "off": the endpoint drops that entire key, so the page says nothing, because "this agent never had a second layer" is an assertion this page has no basis for. This flag only adds a few by-name point lookups on top of the long-term listing, of the same order as "read the curated draft once per row", and adds no storage read.
- The session layer is not listed separately, but it does have one number on the page: the row carries an extra "pending consolidation" counter, which counts **how many sessions under this agent still have content that has not been merged away**, not how many objects — one session's draft together with that day's ledger is one promotion, not two, and counting objects would show one and the same conversation as two outstanding merges. Which objects count as "still has content" follows promotion's own criterion: the session's `root/MEMORY.md` draft, plus the **direct children** dated objects of the ledger segment. So neither 11.7's progress object nor the archived object of 11.5's closing paragraph is counted — after a successful merge they both stay in the bucket anyway, and counting them would make an agent whose every layer has been merged away show pending consolidation forever, which is the one answer this counter must not give. It is counted out of the same batch of object names produced by the listing's own enumeration, so no new endpoint and no new storage read, and it gives a number rather than bodies, which is why the first bullet's "the page lists the long-term layer only" still holds. The listing groups before subtracting: an agent that **only ever wrote its session layer** still occupies a row (empty body, empty dates, pending N), otherwise it would look on the page like "this agent has no memory".
- The delete row and the warning at the top of the page name **both layers** of this agent (the curated draft, all daily records, the session memory not yet merged), because what carries them away is precisely the prefix-based sweep of 11.5's second row: it enumerates by raw object name and therefore never reaches a "clear the long-term layer only" tier in the first place, so the copy must not under-report what it deletes.
- The chat page and iOS are untouched: memory never appears as a bubble, and section 1 rule 5's invariant holds for both layers after layering.

### 11.7 Consolidation progress: it follows whichever bucket this assembly mounted

- The mechanism has a progress marker for "up to when the last consolidation ran", and upstream keeps it in **one fixed location** in shared storage — the `watermark` under the `["memory","consolidation"]` namespace, with no tenant, no user, no agent.
- Why that cell had to move: every user and every agent in the whole deployment reads and writes the same progress, so one consolidation by A pushes the progress to "now", and B's ledger entries from before that moment are permanently below it and silently skipped. The symptom is "B's memory stops growing every so often, and there is not one error in the logs". This has nothing to do with layering and holds just as much for a single-layer deployment (section 2's fact five recorded the failure of this same marker being unwritable, but recorded its availability; what is at stake here is its ownership).
- Layering needs it even more: the session layer and the long-term layer each require their own progress, and sharing one would let a single full write in the session layer mark its owner's cross-session ledger entries as already consolidated.
- Delivered shape: the coordination-slot row of section 6 already set the precedent of "answer only one specific location from this process and pass everything else through", and the same shape is used again here — `harness/memory/BucketScopedWatermarkStore.kt` rewrites only that one upstream namespace and passes every other key through verbatim; the pipeline, the prompts and the file layout are untouched. Upstream's two constants are private, this repository restated them, and one test case reads the upstream fields back and reconciles them byte for byte: if upstream changes that side and this repository does not follow, the test goes red immediately instead of silently returning every bucket to the same address.
- The landing spot is fixed **inside the day-by-day ledger segment of the bucket mounted this time**, rather than opening a separate progress-only space for it. The reason is reclamation: both existing paths, delete this agent and delete the user, enumerate by prefix and then delete one by one, so a progress object inside that prefix is carried away with them; placed in its own segment, no chain would ever clear it, so it would outlive the very ledgers it counts and would silently suppress the consolidation of the next user given the same bucket key. Under two layers "the bucket mounted this time" is this session's bucket; under one layer it is the owner's long-term bucket — `HarnessAgentLauncher.kt:670` is the single decision point, so the routes, the progress and promotion always read and write the same bucket.
- This landing spot makes the memory page see one extra object, and the price is that the page must not recognise it: the page lists only entries whose name parses as a date, and the progress row's name does not parse as one, so it appears in neither the listing nor the detail; like both layers, it falls inside the scope of deletion.
- The upstream fixed address has no readers at all: this layer writes zero to it, and neither wholesale deletion reaches it — the `memory/consolidation` prefix segment is not inside any owner's prefix, and all four reclaim paths of 11.5 enumerate by owner prefix. If such an object genuinely sits in some bucket, removing it is one manual deployment-side action (delete that one object by name), not a mechanism this layer has to add.
- Promotion does not participate in this cleanup: when the session layer is cleared, this progress is left in place (the closing sentence of 11.4's cleanup rule), otherwise the next full write would re-read entries this layer no longer has.
- Acceptance on both ends: the address rewrite itself is asserted on the store wrapper (`BucketScopedWatermarkStoreTest`, 7 cases: upstream address reconciliation, which bucket a write lands in, reading back the same bucket, one copy per owner, the two layers not sharing one, CAS contended only within this bucket, all other namespaces passed through verbatim); on the assembly side `HarnessAgentLauncherMemoryTest`'s `the consolidation progress follows whichever bucket the routes point at` and two further cases watch "the progress follows the bucket that was mounted". Against real MinIO there is one more assertion that it does sit under the prefix both responses are built from, and that neither response contains its name or its timestamp. The "two owners consolidate one after the other" case was not run separately against real storage: what it asserts is the address rewrite, which is independent of the server, and a stub would not let it pass unnoticed. The cell that remains unverified under section 9 row 2 is the other S3-compatible tier, not this one.

### 11.8 What this layer does not do

It does not offer a tier that is session-only and keeps no long-term memory at all (in direct contradiction with section 1 rule 1); it does not offer a manual editing entry point for the session layer; it does not give the memory management page a "consolidate now" action that forces a promotion by hand (P15 in 11.9, with the cost and the alternatives written in 11.5's closing paragraph); it does not merge session layers across agents; it does not give the session layer its own model or its own capacity budget; it does nothing at all on iOS or on the chat page; it does not build a new cleanup chain (apart from 11.4's clear-on-promotion, reclamation only reuses the three existing paths: delete this agent, delete the user, expiry archiving); it does not replace the daily-report archiving mechanism.

### 11.10 Assertable clauses

The six clauses of section 1 continue to hold verbatim for the long-term layer; this layer adds eight more, each of them assertable. Who asserts each one, and to which depth, is reconciled clause by clause in 11.12.

1. **An agent that did not open two layers behaves verbatim unchanged.** The same set of cases runs on the "on plus off" tier, asserting that the mounted bucket still sits on the owner's segment (immediately after the agent come `root` and `memory`, with no `sessions` in between), that no extra block appears in the model input, and that the promotion step is not installed. The tool manifest is not part of this clause: those four tools are decided by the "long-term memory" switch (section 4), and this switch never takes part in that decision — which is why the first row of the matrix says "the session-memory switch does not take part in the decision here". This is the regression anchor of this layer.
2. **The visible scope under two layers.** A freshly created session of the same user on the same agent gets the long-term layer on its first turn; on the next turn of the same session it gets both the long-term layer and its own session layer, and the two blocks are distinguishable in the input — what makes them distinguishable is precisely that pair of tags on the long-term layer. When the long-term block is over budget, what comes in is its head plus a sentence stating it was truncated, not the whole text.
3. **A failed promotion loses not a single object.** Under each of the six tiers — version conflict, model throw, model silence until the timeout, merged result shrunk, write-back refused, read refused — the assertion is that the session layer's object count and bodies are unchanged to the letter, and only the "merged" tier empties it; every attempt lands on a result tier that can be named, and a storage fault must not be read as "this layer had nothing in it".
4. **Both wholesale deletions cover both layers.** After deleting this agent and after deleting the user, the key snapshot under the prefix is empty to the letter, including the not-yet-promoted objects below the session segment. The scope is taken as the raw object names listed under the prefix per 11.5, so even the class of keys the decoder cannot place (an agent whose own name carries a slash) is inside the assertion.
5. **Two owners consolidate separately.** Against real storage, two users consolidate one after the other, and the assertion is that the second one's ledger entries are not skipped because of the first one's progress; this clause simultaneously pins 11.7's existing defect. The same chain also asserts that the progress follows whichever bucket was mounted this time (the session bucket under two layers, the long-term bucket under one layer), and that neither response contains its name or its timestamp.
6. **Cleanup is not allowed to be wider than the read–delete pair.** Write one more entry into the session layer between the draft this attempt read and the moment it was deleted (appending to the ledger or rewriting the draft whole), and assert that the newly arrived entry is still in place while the rest of what this merge covered is cleared as usual. The delete itself must be read back to confirm: a store that reports a failed delete without throwing means, if it cannot be confirmed, that it was not deleted, and the object is left for the next window.
7. **When the store does not honour version comparison, this agent has no promotion.** Assemble an agent on a store that answers "written" for any version number, and assert that the promotion step is not installed and that a log line is left which explains itself; only the promotion step is withdrawn, while the long-term layer's read-only injection is mounted as usual. The tier where the probe throws by itself does not count, and the assertion is that promotion is installed as normal — a fault of that same store is picked up by the merge path itself. This clause's verdict is remembered per process for ten minutes and asked again once it expires, and the assertion is that fixing the store does not require restarting the process.
8. **An empty layer does not spend the window.** A session shorter than the throttle window, whose first read of the session layer comes back empty (the extraction is still on the model side), must be asserted not to have spent the window; the "could not be read" tier likewise takes nothing. Were the slot claimed before the read, sessions of this kind would never promote at all.
