# Harnax iOS: where the memory domain lands, and its contract

## 0. Terminology and evidence baseline

- This is the landing-and-acceptance piece for the memory domain on iOS: the entry point, the cross-end contract and the acceptance clauses are all written against code that is in the tree, and every screen, payload and gate below was read back from it. Anchors are full repository-relative paths with line numbers.
- The evidence baseline is `dcd9fa28` on `kotlin-dev` for the server side and the same branch's `harnax-ios` checkout for the client side. The three admin read routes, the session-layer decision points on the assembly side, and the client's existing layering and gates were each checked against source.
- Four nouns are fixed: the **long-term layer** is the owner's curated file across conversations (the object named MEMORY.md) plus its daily ledger (`memory/<date>.md`); the **session layer** is one conversation's own layer, nested inside the agent segment, and every conversation has one as soon as this agent has long-term memory; a **candidate** is the new curated text the runtime merges out of one conversation's session layer together with the daily merge targets it names, filed first in the table built by `harnax-admin/src/main/resources/db/migration/V7__memory_draft.sql` (the targets live in the `targets` column added by `harnax-admin/src/main/resources/db/migration/V8__memory_draft_targets.sql`) and written into the long-term layer only once the owner approves it; **pending merge** is how many **conversations** of this agent still hold content that has not been merged.

## 1. The client answers two blocks, not one

| Block | Content | Server evidence |
|---|---|---|
| Read and clear | List the agents of this owner that have memory, read one agent's curated file and daily entries, delete that agent's memory | `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/controller/MemoryController.kt:49`, `:64`, `:83` |
| Per-agent switch | One: long-term memory, on the agent wizard. The session layer has no switch of its own — under an agent that has memory, every conversation has its own layer | `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/dto/AgentResponse.kt:61`, writable on `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/dto/AgentCreateRequest.kt:55` and `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/dto/AgentUpdateRequest.kt:46` |

On the client that switch is one field of the row model it already reads, not a new endpoint: the row model `harnax-ios/Sources/HarnaxCore/Contract/AgentSummary.swift:33` carries `memoryEnabled`, the save model `harnax-ios/Sources/HarnaxCore/Contract/AgentSaveDraft.swift:34` carries the same item, and the wizard's control row is `harnax-ios/Sources/HarnaxFeatures/Agents/AgentFormView.swift:365`, placed at `:216` of the form. The server column already reaches the runtime.

## 2. How far the read side goes (and what that allows on screen)

- The listing groups over both layers (`harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/service/impl/MemoryStoreGateway.kt:94`) and does the subtraction after grouping (`:95`), so an agent that has so far only written conversation layers still occupies a row; its text and dates come from the long-term layer.
- The detail subtracts first and then reads (`harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/service/impl/MemoryStoreGateway.kt:122`), so the curated text and every daily entry it returns are long-term layer objects. The writer of that long-term ledger is approval itself: an approved candidate first writes, one by one, the days it names (the runtime nominates the oldest days in date order, up to 7), then writes the curated file. Session-layer objects sit under the same prefix, but no route addresses them by conversation; what the candidate screen carries is the merged new curated text together with the daily targets it names, not the session layer's own files.
- One signal about the session layer reaches the client today: `pendingSessionLayers` (counted at `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/service/impl/MemoryStoreGateway.kt:108` by `:468`, on the admin-side predicate `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/util/MemoryObjectKeys.kt:382`, whose comment says it deliberately matches what the merge step itself refuses to re-promote or delete — the consolidation progress object and the days already retired into the archive owe nothing — deduplicated by conversation; on the wire it sits at `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/dto/MemoryAgentResponse.kt:35` and in the client model at `harnax-ios/Sources/HarnaxCore/Contract/Memory.swift:29`). It gives a number and no text, and it **does not answer the switch**: the session layer is always on, whether one exists depends on this agent's long-term memory, and that value lives only on the agent row, not in this memory payload.
- The client therefore **shows no session-layer text**. Showing it would first need two admin read routes (list by conversation, read one conversation); the key layout already exists (`harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/util/MemoryObjectKeys.kt:199`), and two consequences have to be accepted: a session layer's text is cleared when the candidate merged out of it is approved, and the clear runs after that candidate's daily targets and the curated file have been written (`harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/service/impl/MemoryStoreGateway.kt:397`, called from exactly one place at `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/service/impl/MemoryDraftServiceImpl.kt:287`), so such a screen shows approval progress rather than an archive; and a team member does get its own layer, on the same long-term memory predicate (`harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/HarnessAgentLauncher.kt:1259`), with a child session key derived from the root session (`harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/team/TeamRuntimeSpec.kt:56`), so listing conversations would show rows that each wait on the owner to approve one merge before they go away.
- The delete (`harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/service/impl/MemoryStoreGateway.kt:153`) enumerates raw object names under a prefix (`:162`) and takes both layers at once. The confirmation copy therefore has to name the curated file, every daily entry and the memory still waiting in conversation layers; naming less under-reports what goes away.

## 4. Cross-end contract clauses

1. The path parameter is spelled `agentId` and carries the **agent name the runtime keys memory on**, not a database id (`harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/controller/MemoryController.kt:70`, `:89`). The row's `name` is the key; addressing by `id` reads back as "no such agent". The client percent-encodes the name into exactly one path segment (`harnax-ios/Sources/HarnaxAPI/Transport/Endpoint.swift:99`).
2. A business failure is a 200 response carrying an error code in the envelope (`harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/controller/MemoryController.kt:58`, `:77`), and the detail answers code `404` when the owner has no memory for that agent (`:73`). "Nothing remembered yet" is an empty state, not an error state, and renders as one — the client gives it its own phase (`harnax-ios/Sources/HarnaxFeatures/Memory/MemoryDetailViewModel.swift:20-29`).
3. The listing returns an array, not a page body (`harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/controller/MemoryController.kt:54`), so the client's shared paged state machine has no scope on this route.
4. The owner never becomes a parameter: tenant and user both come from the session credentials, and the tenant header the shared transport injects is the only lever. The client composes no owner prefix and puts nothing but a validated agent name into a path.
5. The switch is a three-state integer: a row answers `0` or `1`, a save writes the key only for the switch the operator moved and omits it entirely otherwise, following the existing `skillSelfWrite` handling (`harnax-ios/Sources/HarnaxFeatures/Agents/AgentFormViewModel.swift:188` keeps the switch and the "touched" state, writes at `:1107`, prefills at `:1152`). Sending the seeded value back would be a write the operator never asked for.
6. The team lead gets no switch: no agent row stands behind a lead, so the server hands it a fixed `1` (`harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/controller/InternalApiController.kt:666`) and what actually keeps a lead out of the memory domain is the runtime's own `!isLead`; the team save model `harnax-ios/Sources/HarnaxCore/Contract/AgentSaveDraft.swift:175` has no such field, so no step of the team wizard offers the control.

## 6. Copy and the localisation gates

- New keys in the two catalogs are **appended as one block at the end of each file** rather than inserted between existing lines: the list title `memory.list.title`, the empty state `memory.list.empty`, the three kinds of content named in the delete confirmation `memory.purge.warning`, the switch `agent.wizard.memory` with its hint `agent.wizard.memory.hint`, and the explanation of the pending-merge count `memory.pending.why`.
- What each gate guards: `harnax-ios/Tests/HarnaxKitTests/LocalizationKeyTests.swift:28` requires both catalogs to define the same key set, and `:99` requires every key used in source to exist in both. New copy therefore lands in Chinese and English in the same batch; one side missing turns the build red.
- The list row's title key and the key the list screen passes to its own `navigationTitle` are one and the same, and a gate that reads the source enforces it (`harnax-ios/Tests/HarnaxFeaturesTests/SystemHomeTests.swift:44`); the path a confirmation sentence promises has to exist on the screen that renders it, and the "memory still waiting in conversation layers" it names is taken by the server's prefix sweep, so the item stays in the copy even while the client shows no session-layer text.

## 7. Assertable clauses

1. **The listing shows only the long-term layer.** An agent that has so far only written conversation layers appears in the list with empty text and empty dates plus a pending-merge number; its detail reads the long-term curated file and no session-layer text appears on screen. Tests: `harnax-ios/Tests/HarnaxFeaturesTests/MemoryListViewModelTests.swift:73`, `:91`, `harnax-ios/Tests/HarnaxFeaturesTests/MemoryDetailViewModelTests.swift:93`.
2. **"Nothing yet" and "could not read" stay apart.** Code `404` renders as the empty state, any other error code or a transport failure renders as the error state, and the two never share one sentence. Tests: `harnax-ios/Tests/HarnaxFeaturesTests/MemoryListViewModelTests.swift:121`, `:136`, `:150`, `:166`, `harnax-ios/Tests/HarnaxFeaturesTests/MemoryDetailViewModelTests.swift:144`, `:164`.
3. **The delete names all three kinds of content.** The confirmation shows the curated file, every daily entry and the memory waiting in conversation layers; after a successful delete the agent leaves the list and `deletedObjects` is reported as the number it is. Tests: `harnax-ios/Tests/HarnaxFeaturesTests/MemoryListViewModelTests.swift:214`, `:236`, `:249`, `:273`.
4. **The three states of the switch hold.** Opening the wizard and saving without touching it leaves the key out of the body entirely; a touched switch writes `0` or `1` and the value the row carried takes no part. Tests: `harnax-ios/Tests/HarnaxCoreTests/AgentSaveDraftTests.swift:62`, `:74`, `harnax-ios/Tests/HarnaxFeaturesTests/AgentFormWizardTests.swift:505`, `:515`.
5. **Addressing is by name.** The jump from a list row to its detail carries the agent name, and an agent whose name contains a dot or a hyphen reads back its own memory instead of "no such agent". Tests: `harnax-ios/Tests/HarnaxAPITests/MemoryWireTests.swift:45`, `harnax-ios/Tests/HarnaxFeaturesTests/MemoryDetailViewModelTests.swift:35`, `harnax-ios/Tests/HarnaxFeaturesTests/MemoryListViewModelTests.swift:436`.
6. **No switch on the lead screen.** No step of the team wizard offers the long-term memory control, and the type itself carries that clause — the model at `harnax-ios/Sources/HarnaxCore/Contract/AgentSaveDraft.swift:175` has no such field, so the wizard has no row that could render it.
7. **"Pending merge" is not "waiting for you".** The number counts conversation layers that have not been merged, not candidates sitting in front of the owner: a rejection leaves the session layer in place (`harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/service/impl/MemoryDraftServiceImpl.kt:314`) and the next pass proposes that merge again, so the copy may only say "not merged yet" and never a candidate count. Tests: `harnax-ios/Tests/HarnaxFeaturesTests/MemoryListViewModelTests.swift:378`, `:396`.

## 8. Out of scope, and the settled items

Out of scope on the client: showing session-layer text (no route addresses a conversation); editing memory content by hand; deleting one conversation's memory; a "consolidate now" action that forces a merge into a candidate; rendering memory as chat bubbles; an owner-wide roll-up across agents.

All four items are settled, each with its landing shape:

| Item | Landing shape |
|---|---|
| Entry point | One row inside the governance hub on the Agents tab's fourth segment; the segment name key `agent.segment.governance` and the screen name key `governance.title` are two keys on purpose, and the reasons for rejecting B, C and D are in the candidate table in section 3 |
| Whether both blocks ship together | Together: the switch's control sits on the agent wizard and the read-and-clear screen sits in the governance hub, so splitting them only adds one more regression pass |
| The approval screen | Shipped on iOS: all four routes have a client exit (list `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/controller/MemoryDraftController.kt:56`, detail `:94`, approve `:111`, reject `:129`), on `harnax-ios/Sources/HarnaxFeatures/MemoryDrafts/MemoryDraftListView.swift:38` and `harnax-ios/Sources/HarnaxFeatures/MemoryDrafts/MemoryDraftDetailView.swift:33` |
| Session-layer text | Not done: a team member does get its own layer (the predicate is in section 2 above), so listing by conversation would be a screen of approval progress rather than an archive, and the candidate itself already has a table carrying it |
