## 0. 结论卡

**一句话**：主流实践不是「主管调工具」和「主管只调度」二选一，而是**主管以调度为主、只保留决策型与只读型能力，重执行和有副作用的动作下放**。

**三条判据**（对任一能力逐条过）：

| 判据 | 为「是」时的处置 | 理由 |
|------|------------------|------|
| 这次调用的返回体会不会长期占住主管上下文 | 下放 | 主管上下文是全局最贵的资源，所有成员结果最终都要汇聚回它 |
| 它做的事是不是可并行 / 重复的 | 下放 | 并行是委派唯一确定的收益来源 |
| 它有没有副作用需要归口 | 下放，且**只留一个出口** | 并发写与审计归口问题 |
| 纯知识型（skill、方法论、验收口径） | **留主管** | 不回填大段内容，反而降低误派发概率 |

**一个反面警告**：只有 1 个主管 + 2~3 个成员、任务又多线程不可分时，多一跳委派通常是净损失（传话损耗 + token 翻倍）。多智能体的回本点在**广度优先、可并行分解**的任务上。

## 1. 先把术语钉死：委派有三种不同语义

面试里最容易被一句话问穿的，就是把这三种混着说。

| 语义 | 控制权 | 上下文 | 典型实现 | 适用 |
|------|--------|--------|----------|------|
| **交接式 handoff** | **转移**给子 agent，主管不再介入 | 对话历史整体带走 | OpenAI Agents SDK（handoff 本身以工具形式暴露给模型） | 分诊/路由到专家，专家直接面对用户 |
| **调用式 agent-as-tool** | 留在主管 | 子 agent 只见调用参数，返回摘要 | 把子 agent 注册成一个工具 | 主管要综合多个专家结论 |
| **编排式 orchestrator-workers** | 留在主管 | 主管动态拆解、并行派工、事后综合 | Anthropic 研究系统 | 广度优先检索、可分解的探索型任务 |
| **群聊 / 协商** | 无固定主体 | 共享广播消息 | AutoGen GroupChat | 多视角讨论，终止条件难控制 |
| **固定流水线 / 图** | 由图决定 | 由节点契约决定 | LangGraph 显式图 | 步骤确定、要可复现 |

**为什么这个区分有实质后果**：三件事全不一样——谁持有中断/取消的语义、人工确认回到哪个运行体、token 成本记在谁头上。选了 handoff 却又想事后综合，或选了 as_tool 却给了成员完整对话历史，都是常见设计错误。

## 2. 角色职责切分

| 职责 | Leader | Sub-agent |
|------|--------|-----------|
| 目标澄清、向用户提问 | ✅ 独占（只有它面向用户） | ❌ |
| 任务分解与边界设定 | ✅ 独占 | ❌ |
| 给每个子任务写自包含说明 | ✅ 独占，质量决定成败 | — |
| 取证型工具调用（检索、读文件、跑查询） | 🔸 只读小范围可以 | ✅ 主力 |
| 生产型 / 有副作用动作（写文件、提交、发消息、部署） | ❌ | ✅ 单一出口 |
| 进度协调、重派、超时与取消 | ✅ 独占 | ❌ |
| 验收成员产物 | ✅ 必须有能力复核，否则退化为盲信 | — |
| 最终综合与对外表达 | ✅ 独占 | ❌ |

关键在倒数第三行：**主管必须保有「能自己复核」的最小能力**。纯路由器（零工具）和「什么都自己干」是两个相反的失败端——前者盲信成员报告，后者把委派做成了转述。

## 3. 核心辩论：主管要不要亲自调工具

### 3.1 外部立场光谱

| 立场 | 出处 | 对主管工具的态度 | 关键论据 |
|------|------|------------------|----------|
| 主管持有规划与记忆类工具，取证动作全部下发 | Anthropic《How we built our multi-agent research system》 | 中间态：主管有 memory/plan，search 等重动作归子 agent | 子 agent 各自有独立上下文窗口，可并行覆盖查询的不同侧面 |
| orchestrator-workers 定义为「拆解—委派—综合」 | Anthropic《Building Effective Agents》 | 主管调用的对象是**其他 LLM**，不是业务工具 | 原文：a central LLM dynamically breaks down tasks, delegates them to worker LLMs, and synthesizes their results |
| **主管少自己动手** | LangChain《Benchmarking Multi-Agent Architectures》 | 明确收紧主管的直接调用 | 实测中 supervisor 架构的性能损失主要来自它在用户与子 agent 之间「传话（telephone）」产生的**翻译误差**；修法是让主管少做、把完整任务描述交出去 |
| 交接与调用两种语义并存，agent 始终保留自己的工具 | OpenAI Agents SDK 文档 | 不设限制，由选择语义承担后果 | handoff 是「以工具形式呈现给模型的控制权转移」；as_tool 才是嵌套专家 |
| **反对把执行交给上下文很薄的子 agent** | Cognition《Don't Build Multi-Agents》 | 执行动作的一方必须看到全量上下文；建议子 agent 只回答问题、不做写操作 | 两条原则：share full context and traces；actions carry implicit decisions |
| 收窄域系统里主管直接持有本域工具是常见做法 | arXiv 2412.05449（AgentOrchestra） | 允许主管带业务工具 | 文中示例 supervisor 拥有本域工具并负责团队目标 |

**光谱结论**：没有任何一家主张「主管零工具」，也没有任何一家主张「主管和成员工具集相同、谁调都行」。分歧集中在**主管可以调多少**，而收敛点是「按返回体大小和副作用切，不按业务/非业务切」。

### 3.2 三种可选设计

| 设计 | 优点 | 缺点 | 适用规模 |
|------|------|------|----------|
| **A. 纯路由器**（主管零业务工具） | 权限边界最干净；成本归口清楚；不可能与成员并发改同一状态 | 缺方法论→派发描述写不具体；无法复核→盲信成员；小任务也要多一跳 | 成员多、任务真能并行、有严格合规要求 |
| **B. 只读主管**（保留 skill + 小返回只读工具，无写、无重取证的 MCP） | 兼顾判断力与上下文卫生；副作用仍单一出口 | 需要一份**白名单**并长期维护；「只读」边界随新增工具被侵蚀 | 通用最优，1~10 个成员都成立 |
| **C. 全能力主管**（主管与成员工具集基本相同，主管按需亲自执行） | 最简单，省一层传话；单线程任务效率最高 | 主管上下文快速膨胀；权限与审计出口不唯一；实际会退化成「单 agent + 偶尔多开一个 agent」 | 成员 ≤3、任务不可并行 |

我的看法：**默认选 B**。规模小且任务串行走 C；有强合规/多租户要求、且愿意接受派发质量下限时才选 A。

### 3.3 为什么 skill 该给主管，而 MCP 要分半

**Skill 和工具不是同一类东西。** Skill 是「该怎么做、怎么验收」的说明，命中后进入的是指令层，不回填大段返回体。主管没有对应 skill，会出现两个具体故障：

1. 写不出合格的委派说明（客观上不知道该要求什么输出格式、什么工具边界）；
2. 无法判断成员交回的东西是否合格——于是 §2 倒数第三行失守。

**MCP 与业务 Tool 是在真的执行动作**，按 §0 三问切：

- 留在主管侧：查一个对象的状态、列可选项、小范围检索、向用户发确认。这些是**复核与决策**所需。
- 下放成员侧：全量检索、抓网页正文、跑大结果集查询、遍历目录（大返回体）；写、提交、部署、发消息给第三方（副作用需归口）。

### 3.4 两个反模式

- **主管把工具全调一遍，再把结论转述给成员**：既付了两遍 token，又在转述中丢信息。这是 LangChain「传话损耗」的成因形态。
- **主管事后重做成员的工作**：通常出现在主管有全套写工具、且验收口径没写清时。它把多 agent 变成了成本 2 倍的单 agent。

## 4. 能力归属矩阵（落设计时直接抄）

| 能力类型 | 归主管 | 归成员 | 备注 |
|----------|--------|--------|------|
| 规划 / 待办 / 任务协调 | ✅ | 🔸首期不给 | 首期建议单层，不给成员继续委派 |
| 流程与方法型 Skill | ✅ | ✅ | 双向都给；给主管是为了写好派发和验收 |
| 执行型 Skill（含 CLI/Shell） | ❌ | ✅ | 一旦给主管就可能顺手自己做 |
| 只读、小返回的查询类 Tool/MCP | ✅ | ✅ | 主管侧用于复核 |
| 大返回体检索/抓取 | 🔸仅极窄范围 | ✅ | 主要怕污染主管上下文 |
| 有副作用的写操作 Tool/MCP | ❌ | ✅ 单一出口 | 并发写 + 审计归口 |
| 人工确认的发起 | ✅ 独占 | 🔸经主管上行 | 面向用户的出口要唯一 |
| 用户身份与凭证（如 MCP OAuth 令牌） | ✅ 根运行持有 | 🔸以根身份作用域下发 | 绝不能让成员用「成员创建者」身份 |
| 执行沙箱 | ❌ | ✅ 各自独立 | 成员环境互不污染 |

一条容易漏的防线：**能力收紧必须落在装配层与运行时校验，不能靠提示词写「请勿亲自执行」**。默认注册路径（框架自带的 Shell、默认子 agent、必须工具集合）会把能力重新泄漏回来。

## 5. 上下文经济学（为什么上面这套切分成立）

已核对的量化事实（均来自 Anthropic 工程博客，2026-09-20 复核）：

- 智能体对话相对普通聊天约用 **4×** token；**多智能体系统约 15×**。
- 在其内部研究评测上，多智能体相对单智能体基线高 **90.2%**。
- 并行执行工具调用/子 agent，把复杂查询的研究时间缩短**最多 90%**。
- 委派说明必须包含四要素：**objective、output format、工具与来源指引、clear task boundaries**。

**怎么读这四个数**（面试里被追问成本时的抓手）：

1. 15× 与 90.2% 是**同一枚硬币**——多智能体的准确率买自「更多 token + 更多并行窗口」，所以它天然只在**广度优先、可并行**的任务上回本；把它当默认架构就是拿 15 倍成本换一份不一定需要的收益。
2. 那 90.2% 出自**研究类评测**，不是编码类评测。跨任务类型引用这个数字是错的（Cognition 的质疑正落在这里）。
3. 委派的本质是一种**上下文工程手段**：用隔离的窗口换取主管窗口的干净，而不是「为了多 agent 而多 agent」。所以判断「压缩上下文 vs 委派子 agent」的标准是——需要被处理的内容是否属于当前决策？属于就压缩后留在原地，不属于就派出去只带回结论。
4. 15× 也解释了为什么**主管每多调一次大返回体工具，代价是复利的**：这段内容会在后续每一步都被重新计费一次。

## 6. 反方论证（必须能自己复述，否则会被问穿）

Cognition《Don't Build Multi-Agents》的两条原则：

1. **Share full context and traces**，而不是摘要。
2. **Actions carry implicit decisions**——每次工具调用/每段代码都携带隐含决策（选什么风格、对边界情况怎么处理、和既有代码怎么衔接）。让只看到任务摘要的子 agent 并行执行，等于把隐含决策权交给上下文最薄的一方，结果是**基于冲突假设各自行动**。

它给的替代是：单线程线性 agent + 上下文压缩；或子 agent 只回答问题、只给建议，不做写操作。

**它哪里没说错**：写操作密集、步骤间强依赖的任务（典型是编码），并行委派确实是净损失。LangChain 自己也承认「多数编码任务真正可并行的部分比研究少」，并同意上下文共享是关键。

**它的边界在哪**（反驳抓手，三条）：

1. 它反对的是**并行执行写操作**，不是反对角色分离。广度优先的检索/取证类工作，子 agent 只回结论、不做写决策，两边其实不冲突。
2. 它的前提是「单个上下文窗口装得下」。**装不下时**，摘要委派不是可选优化而是唯一路径——所以真正的问题是「什么内容值得留在主管窗口」，而不是「要不要委派」。
3. 它没处理**权限与身份归口**。多租户平台上「谁能调哪个 MCP、以谁的身份调」需要结构化边界，纯单 agent 把这个问题变简单了，但没解决它。

一句话立场：**Cognition 的约束适用于执行侧，Anthropic 的实践适用于取证侧；两者合起来正好导出 §3 的中间态——主管留判断与复核，成员做执行。**

## 7. 什么时候不该上多 agent

出现任一条就退回单 agent + 上下文工程：

- 任务步骤之间强依赖，前一步的输出决定后一步的**具体动作**（编码、调试、迁移）。
- 需要同一份状态被反复读改（写出口无法唯一）。
- 成员数量上限只有 2~3，且没有可并行的检索面。
- 正确性依赖跨轮次记忆，而端到端评测无法容忍 15× 成本。
- 目标本身模糊到无法写出「objective + output format + boundaries」——**写不出委派说明，说明还不该拆**。

## 8. 生产级失败模式清单

| # | 症状 | 根因 | 防线 |
|---|------|------|------|
| F1 | 主管在用户与成员间反复转述，答案漂移 | 传话/翻译误差（LangChain 实测主要损失来源） | 委派说明自包含；主管不做二次转述 |
| F2 | 多个成员重复做同一件事，或都漏掉同一块 | 任务边界没写死 | 边界四要素：目标/输出格式/工具来源指引/边界 |
| F3 | 简单问题也派出 50 个子 agent | 没有「按复杂度调节投入」的规则 | 显式 scale rule：简单 1 个，复杂才 10+ |
| F4 | 两个成员写同一份产物，互相覆盖 | 写出口不唯一 | 副作用单一 owner；或不可变产物 + 引用交接 |
| F5 | 主管照收成员结论，最终答案含幻觉 | 主管没有复核能力 | 保留只读小查询能力（§4） |
| F6 | 成本失控且说不清贵在哪 | 成本未记到根运行 | 根运行统一记账；子运行成本可归属不重复计 |
| F7 | 无限深挖、永不收敛 | 无完成条件与预算 | 每个子运行带步数/时限/预算三重闸门 |
| F8 | 嵌套委派成环，或取消只停了根 | 深度与取消传播未定义 | 首期锁单层；停止必须阻断新委派 |
| F9 | 成员用了不该用的凭证身份 | 身份在委派时丢失 | 以根用户身份作用域下发；未知子 ID 拒绝换发 |
| F10 | 失败被静默换成主管模型跑完，结果口径不一致 | 框架回退被当成功能 | 成员失败不得静默降级；显式上报 |
| F11 | 「能选团队」被当成「所有入口都支持团队」 | 新入口未单独验收 | 渠道/定时任务等入口逐个验收并发、确认、身份传播 |

F1、F5 正好是光谱两端：一端是委派太多导致传话，一端是委派太彻底导致盲信。**F1 和 F5 必须同时防**，这就是中间态成立的经验理由。

## 9. 怎么证明它有效（评测与可观测）

面试常问「你怎么知道多 agent 比单 agent 好」，这题答不出，前面全是背的。

- **LLM-as-judge + 明确 rubric**：适合短程任务，Anthropic 的说法是「做得好时能规模化」。rubric 要把「是否用了全部来源、是否正确拆分」这类过程指标写进去，只判最终答案会漏掉 F2。
- **终态/基于状态的评测**：长程任务不能只看轨迹，要看环境最终状态。难点在「每个动作都会改变环境」，与只读检索任务不同——这决定了有副作用的场景必须用可重置的沙箱环境评测。
- **消融而非对比**：同一任务集跑「单 agent / 主管零工具 / 只读主管」三档，比较准确率、token、延迟、重复劳动率。三档就够回答 §3 的选型。
- **过程可视化**：把各 agent 的思考与委派树画出来调试。多 agent 的 bug 大多是**结构性的**（派发边界错），只看最终答案永远定位不到。
- **指标要含成本**：只报准确率提升会被当成拿 token 换分数。准确率与 token 必须成对报告。

## 10. 回到本项目：我们的落点与代价

本项目（自托管 Agent 系统，个人项目）选的是**接近 A 的收紧版本**，而非 §3.2 推荐的 B：

- 团队是独立的组队配置，主管与成员都引用现有 Agent，原 Agent 独立使用行为不变。
- 主管只做拆解、委派、协调、验收、重派、汇总；**业务 Tool 与 MCP 不装载，执行型 Skill / CLI / Shell 不暴露，不创建执行沙箱**；成员按各自配置装载，使用独立沙箱。
- 成员之间不共享可写工作区，走 MinIO 产物发布/引用/获取。
- 限制由装配与运行时校验保证，不依赖提示词。

**与外部共识的偏差，以及付出的代价**（诚实记账，别在面试里只讲优点）：

| 外部推荐 | 本项目选择 | 换来的 | 付出的 |
|----------|------------|--------|--------|
| 主管保留流程型 skill | 执行型 skill 一律不给主管 | 主管侧零执行入口，V2 验收口径简单 | 主管可能缺验收方法论 → F5 风险 |
| 主管保留小返回只读 MCP/Tool | 主管不连任何 MCP | 身份/凭证出口唯一，OAuth 作用域干净（F9 直接消解） | 主管只能信成员报告 → F5 风险 |
| 按任务规模决定是否委派 | 首期固定单层顺序委派 | 事件关联、确认续跑、取消传播可验收 | 广度型任务的并行收益拿不到（F3 的对应收益也没了） |

也就是说：**本项目用「主管能力为零」换取「权限与审计边界为零漏洞」**，是一个有意选择的严格档位，不是通用推荐。若后续 F5 真实发生（主管验收不了成员产物），第一个要放宽的是**只读、小返回**的复核能力，而不是写能力。

详细决策与验收清单见 [multi-agent-team-design.zh-CN.md](./multi-agent-team-design.zh-CN.md)（D3/D5/D6、§5、V2/V3/V10）。

## 11. 追问链演练

**链 1｜「你们主管 Agent 能调工具吗？」**

- 为什么问：一句话分辨你是真设计过多 agent，还是抄的架构图。
- 追问：那它怎么判断成员做得对不对？→ 那为什么不给它只读工具？→ 你们怎么定权限边界？→ 成本怎么算？
- 抓手：先给判据（返回体大小 + 副作用），再给我们的选择（收紧到零，为的是凭证出口唯一），最后主动交底代价（F5，以及若要放宽先放宽哪一类）。
- 撑腰：本文 §0、§3.2、§10；prod_doc §5、V2、V10。
- 风险：🟢 有支撑，且能讲出自己方案的非最优处，是加分项。

**链 2｜「多 agent 一定比单 agent 好吗？」**

- 为什么问：测你是不是跟风。
- 追问：那你为什么用？→ 有数据吗？→ 那 Cognition 说不要做多 agent 你怎么看？
- 抓手：引用要带任务类型限制（研究评测上 90.2%，代价是约 15× token）；承认多数编码任务可并行部分少；再给退回单 agent 的清单（§7）。
- 撑腰：§5、§6、§7。
- 风险：🟡 注意**别把外部数字说成自己的实测数据**（个人项目一律不给数字）。说「Anthropic 公开的量级是…」才是安全口径。

**链 3｜「子 Agent 挂了 / 结果不对 / 跑太久，你们怎么办？」**

- 为什么问：真实生产感。
- 追问：超时会不会转后台？→ 有副作用的操作中断后重放吗？→ 取消怎么传播？→ 失败会不会被主管模型接走？
- 抓手：三重闸门（步数/时限/预算）→ 停止必须阻断新委派 → 有副作用操作不自动重放 → 成员失败不得静默降级（F10）。
- 撑腰：§8 F7/F8/F10；prod_doc §9.3、V9、V12。
- 风险：🔴 若被追到「具体阈值是多少」，照红线答定性口径，不编数字。

**链 4｜「Skill 和 MCP 在多 agent 里怎么分？」**

- 为什么问：只有真做过能力装配的人才会被这个细节绊住。
- 追问：为什么 skill 和工具要分开说？→ 主管不装载成员的工具，怎么委派？→ 成员的工具凭证从哪来？
- 抓手：skill 进指令层不回填上下文，故归双方；工具会执行动作，故按副作用切；成员能力由**各自完整装配**获得，不是从主管集合裁剪（把成员工具并集挂给主管是明确否决项）。
- 撑腰：§3.3、§4；prod_doc §10.3。
- 风险：🟢 这是区分度最高的题，答得具体就是加分。
