# Harnax Product Overview

> Nature of the project: a solo, independently owned project. Architecture, interface contracts, every line of implementation and the whole deployment environment are mine; this is not work-for-hire. This document describes what the current codebase actually does. It is the front page for the domain documents under `prod_doc`: only "which component provides this capability, along which path" belongs here, with the detail left to those documents.
>
> Scale: 11 top-level Maven modules plus 14 submodules — 4 under `harnax-agent`, 6 under `harnax-channel`, 3 under `harnax-client`, 1 under `harnax-tools-external`. Every line of backend main code is Kotlin; there is no Java source. Schema is carried by Flyway scripts, and each service owns exactly one schema baseline against its own datasource. The delivery shape is one `harnax-deploy/docker-compose.yml` that brings up the whole chain.

## 1. In One Sentence

Harnax turns an AI Agent from "one call" into "a long-running system": declarative assembly, interruptible and resumable streaming execution, sandboxed tool execution, session-sticky routing across instances, cluster-scheduled triggering, Web and IM multi-channel access, and a full admin plane around all of it.

The engineering problem it takes on: an Agent's mutable state — the ReAct loop context, the workspace files, a run parked on human confirmation — does not live in a database, it lives in one process's memory and disk. The moment you need horizontal scale, self-starting schedules or an IM-side entry point, the "stateless service plus polling gateway" model breaks down, and the whole architecture is organised around that constraint.

## 3. Core Capabilities

### 3.1 Agents and Sessions

Agent specs are registered and edited in `harnax-admin` and run in `harnax-agent/harnax-agent-service`. An agent configures a model, a system prompt, an iteration ceiling, a tool set, MCP servers, skill packages and a CLI toolchain; the bindings live in `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/AgentToolBinding.kt`, `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/AgentMcpBinding.kt`, `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/AgentSkillBinding.kt` and `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/AgentCliBinding.kt`, with tool-level parameters and environment placeholders in `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/AgentTool.kt`, `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/AgentToolEnvParam.kt` and `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/EnvVariable.kt`.

The kernel never reaches back into a configuration source: it asks its host for information through interfaces, and `harnax-agent/harnax-agent-service/src/main/kotlin/com/agnetix/harnax/agent/service/adaptor/` supplies nine implementations — model config (`harnax-agent/harnax-agent-service/src/main/kotlin/com/agnetix/harnax/agent/service/adaptor/ChatModelConfigAdaptorImpl.kt`), MCP config (`harnax-agent/harnax-agent-service/src/main/kotlin/com/agnetix/harnax/agent/service/adaptor/McpConfigAdaptorImpl.kt`), tool config (`harnax-agent/harnax-agent-service/src/main/kotlin/com/agnetix/harnax/agent/service/adaptor/ToolConfigAdaptorImpl.kt`), skills (`harnax-agent/harnax-agent-service/src/main/kotlin/com/agnetix/harnax/agent/service/adaptor/SkillAdaptorImpl.kt`), token statistics (`harnax-agent/harnax-agent-service/src/main/kotlin/com/agnetix/harnax/agent/service/adaptor/TokenStatAdaptorImpl.kt`), process logs (`harnax-agent/harnax-agent-service/src/main/kotlin/com/agnetix/harnax/agent/service/adaptor/ProcessLogAdaptorImpl.kt`), tool call logs (`harnax-agent/harnax-agent-service/src/main/kotlin/com/agnetix/harnax/agent/service/adaptor/ToolCallLogAdaptorImpl.kt`), plan notes (`harnax-agent/harnax-agent-service/src/main/kotlin/com/agnetix/harnax/agent/service/adaptor/PlanNoteAdaptorImpl.kt`) and the MCP access-token source (`harnax-agent/harnax-agent-service/src/main/kotlin/com/agnetix/harnax/agent/service/adaptor/AdminMcpAccessTokenSourceFactory.kt`). The assembly entry points are `harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/HarnessAgentBuilder.kt`, `harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/HarnessAgentLauncher.kt` and `harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/HarnessAgentWrapper.kt`. The same kernel therefore both sits inside the service and, via `harnax-client`, runs without a config centre.

Sessions and messages are carried by `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/Session.kt`, `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/MpSession.kt` and `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/MpChatMessage.kt`. Runtime endpoints sit in `harnax-agent/harnax-agent-service/src/main/kotlin/com/agnetix/harnax/agent/service/controller/AgentController.kt`: alongside chat and streaming there are three side channels — `/confirm`, `/command` and `/chat/interrupt/{sessionId}` — which, together with in-instance state, let a parked run resume on the same instance that holds it; there are also two read endpoints: `GET /chat/history/{sessionId}` for history and `GET /context/{sessionId}` for occupancy.

Page history and model context are two separate datasets: the model-side `AgentState.context` may be rewritten by compaction, while the page reads the append-only `session_message` table in the session database (`harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/agent/session/MysqlSessionMessageStore.kt`). After one compaction or ten, `/chat/history` still returns every original bubble, and a summary bubble never appears. The `COMPACT` branch of `/command` compacts on demand and `GET /context/{sessionId}` reports occupancy (its numerator is the billed figure); both have entry points on the session chat page in `harnax-webui` and `harnax-ios`. The denominator comes from the `context_window` column in the model domain, falling back to inference from the model name and then to a fixed ceiling.

### 3.2 Multi-Agent Teams

The team entity `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/Team.kt` holds the lead's whole configuration directly: `systemPrompt` and `modelId` exist only on the team row, while members stay ordinary `Agent` rows keeping their own tool, MCP, skill and CLI bindings. An agent therefore has exactly two possible roles — conversable on its own, or a member of some team — and no row impersonates a lead. Membership lives in `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/TeamMember.kt`, team-level skill bindings in `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/TeamSkillBinding.kt`, and the artifacts members exchange in `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/TeamArtifact.kt`.

Runtime orchestration sits in `harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/team/`: `harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/team/TeamOrchestrator.kt` assigns and collects work, `harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/team/TeamRole.kt` defines roles, `harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/team/TeamRuntimeSpec.kt` describes the runtime shape, `harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/team/TeamToolBoxes.kt` assembles toolboxes per role, and `harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/team/TeamArtifactGateway.kt` defines the artifact exchange channel with MinIO as its object-store implementation. The console entry point is `harnax-webui/src/pages/team`.

### 3.3 Skills

Skill content and versions live in MySQL, managed by `harnax-admin`. A skill may come from a registered repository (`harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/SkillRepository.kt`, `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/Skill.kt`) or from an uploaded package; the upload path runs the content check in `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/skill/SkillContentScanner.kt` and the unpacking in `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/skill/loader/ZipSkillLoader.kt`, the source kind is decided by `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/skill/SkillSourcePolicy.kt`, and registration is served by `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/controller/SkillSourceController.kt`. Agents and teams reference skills through binding tables.

A skill is not just a prompt fragment: `harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/skill/SandboxSkillProjector.kt` projects the skill package into directories and files that genuinely exist in the session workspace once the sandbox is ready, and the model reads them with file tools. The console entry point is `harnax-webui/src/pages/skill`.

### 3.4 MCP Servers

MCP servers are registered in `harnax-admin`; at runtime `harnax-agent/harnax-agent-utils/src/main/kotlin/com/agnetix/harnax/agent/adaptor/mcp/` opens the connections and folds remote tools into the model's tool set. The transport types are `sse` and `streamablehttp`. A `stdio` row may be registered but never participates in runtime; that decision sits in one place, `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/service/McpStdioPolicy.kt`, because stdio means a child process spawned directly by agent-service and that runtime is not process-isolated.

Auth types are the constant set in `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/McpAuthTypes.kt`, shared by two processes: admin decides what to store and deliver, the agent runtime branches on the value to choose between a static header and a per-user bearer token. The set the runtime honours is `NONE`, `STATIC_HEADER`, `OAUTH2`.

Per-user authorisation is OAuth 2.1: the authorize and token-exchange endpoints are in `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/controller/McpOAuthController.kt`, client registration and metadata discovery in `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/service/impl/McpOAuthServiceImpl.kt`, and the user-level code-for-token exchange plus centrally held, auto-renewed refresh tokens in `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/service/impl/McpOAuthUserServiceImpl.kt`, with credentials stored as `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/McpOauthClient.kt` and `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/McpUserCredential.kt`. The `state` parameter is held by `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/util/McpOAuthStateStore.kt` so the callback can be validated. Stored credentials are encrypted with AES-256-GCM (`harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/util/AesUtil.kt`, with field-level wrapping in `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/util/SecretFieldEncryptor.kt`); at runtime `harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/mcp/PlaintextMcpConfigDecryptor.kt` turns them back into usable configuration, and the access token is injected per call context (`harnax-agent/harnax-agent-service/src/main/kotlin/com/agnetix/harnax/agent/service/adaptor/AdminMcpAccessTokenSourceFactory.kt`). Every MCP call is recorded in `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/McpCallLog.kt`. The console entry point is `harnax-webui/src/pages/mcp`.

### 3.5 CLI Plugin Packages

`harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/registrar/CliPackageParser.kt` parses a package descriptor and `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/registrar/CliPackageAutoRegistrar.kt` writes the shelf's packages into the `cli` table at startup; management and build triggering run through `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/controller/CliController.kt` and `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/service/impl/CliServiceImpl.kt`, and a registered package is carried by `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/Cli.kt`.

At runtime the CLI artifacts a sandbox needs are prepared per package: `harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/sandbox/CliPackageStore.kt` holds the artifacts, `harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/sandbox/CliImageBuilder.kt` builds a sandbox image per package, and `harnax-agent/harnax-agent-service/src/main/kotlin/com/agnetix/harnax/agent/service/sandbox/CliArtifactReaper.kt` reclaims expired ones. Agent-to-CLI bindings are in `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/AgentCliBinding.kt` and the shelf itself is `cli-packages`. The console entry point is `harnax-webui/src/pages/cli`.

### 3.6 Tools and Tool Registration

The tool contract is `harnax-agent/harnax-tools-sdk/src/main/kotlin/com/agnetix/harnax/tools/sdk/ToolBox.kt` and the registry is `harnax-agent/harnax-tools-sdk/src/main/kotlin/com/agnetix/harnax/tools/sdk/registry/ToolRegistry.kt`: at startup it scans the Spring context for `ToolBox` beans, registers them by name, extracts their specifications from the tool and metadata annotations on their methods, and assembly then picks the visible set from the agent's tool bindings. `harnax-tools-external/harnax-tools-buildin` supplies the built-in toolboxes that ship with the image (`harnax-tools-external/harnax-tools-buildin/src/main/kotlin/com/agnetix/harnax/tools/buildin/TimeToolBox.kt` and `harnax-tools-external/harnax-tools-buildin/src/main/kotlin/com/agnetix/harnax/tools/buildin/EmailToolBox.kt`); team roles get theirs from `harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/team/TeamToolBoxes.kt`. File and command tools are provided on the sandbox side, and MCP and CLI each fold remote tools and command-line tools into the same set.

Tool registration, enablement and parameter specs live in `harnax-admin`, with the console page at `harnax-webui/src/pages/tool`. Cross-module tool metadata comes from `harnax-agent/harnax-tools-sdk/src/main/kotlin/com/agnetix/harnax/tools/sdk/ToolMeta.kt` and `harnax-agent/harnax-tools-sdk/src/main/kotlin/com/agnetix/harnax/tools/sdk/ToolEnvParamDef.kt`, and the runtime context from `harnax-agent/harnax-tools-sdk/src/main/kotlin/com/agnetix/harnax/tools/sdk/ToolCallContext.kt` and `harnax-agent/harnax-tools-sdk/src/main/kotlin/com/agnetix/harnax/tools/sdk/ToolEnvContext.kt`. A call that needs human confirmation returns a confirmation event to the caller via `harnax-agent/harnax-agent-service/src/main/kotlin/com/agnetix/harnax/agent/service/controller/AgentController.kt`, and every tool call is recorded in `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/ToolCallLogEntity.kt`.

### 3.7 Scheduled Tasks

`harnax-scheduler` is a standalone deployable service that hands triggering to the Quartz JDBC clustered JobStore, so one task fires once regardless of replica count. It uses its own database `harnax_scheduler` (created and granted by `harnax-deploy/sql/init-databases.sql`), which holds both the 11 `QRTZ_*` cluster tables and the three agent-task tables: the task definition `harnax-scheduler/src/main/kotlin/com/agnetix/harnax/scheduler/entity/AgentTask.kt`, the execution ledger `harnax-scheduler/src/main/kotlin/com/agnetix/harnax/scheduler/entity/AgentTaskExecution.kt` and the execution log `harnax-scheduler/src/main/kotlin/com/agnetix/harnax/scheduler/entity/AgentTaskLog.kt`. The admin side keeps no duplicate copy of task data; `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/service/SchedulerClient.kt` (implemented by `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/service/impl/SchedulerClientImpl.kt`) synchronises tasks between the two services. The console entry point is `harnax-webui/src/pages/agent-task`.

The task-to-Quartz mapping is established by `harnax-scheduler/src/main/kotlin/com/agnetix/harnax/scheduler/job/TaskQuartzRegistrar.kt`, and `harnax-scheduler/src/main/kotlin/com/agnetix/harnax/scheduler/service/TaskScheduleReconciler.kt` with `harnax-scheduler/src/main/kotlin/com/agnetix/harnax/scheduler/job/SchedulerReconcileJob.kt` reconcile by difference: the table set and the JobStore set each get their missing entries added and their stale ones removed, rather than being dropped and rebuilt. There are two execution entry points — `harnax-scheduler/src/main/kotlin/com/agnetix/harnax/scheduler/job/AgentTaskJob.kt` permits overlap, `harnax-scheduler/src/main/kotlin/com/agnetix/harnax/scheduler/job/AgentTaskNonConcurrentJob.kt` forbids it through Quartz's `@DisallowConcurrentExecution` — and both extend `harnax-scheduler/src/main/kotlin/com/agnetix/harnax/scheduler/job/AbstractAgentTaskJob.kt`, which carries one invariant: a shared JobStore may hand a node a fire for a job it never registered, and that node then walks away.

The execution log is a six-value state machine — 0 failed, 1 success, 2 timeout, 3 running, 4 stopping, 5 stopped — and the transition rules are documented in `harnax-scheduler/src/main/kotlin/com/agnetix/harnax/scheduler/mapper/AgentTaskLogMapper.kt`: a terminal row may only be written by the execution thread that actually produced the result; rows that outrun 1.5x their task's timeout are batch-expired to timeout so that whatever a node that died mid-execution left behind gets reclaimed, and a row the reaper judged wrongly can have its real outcome written back; `harnax-scheduler/src/main/kotlin/com/agnetix/harnax/scheduler/job/SchedulerHousekeepingJob.kt` performs the retention sweep and deletes terminal rows only. Re-entrancy is guarded by `harnax-scheduler/src/main/kotlin/com/agnetix/harnax/scheduler/service/AgentTaskExecutionGuard.kt`, metrics come from `harnax-scheduler/src/main/kotlin/com/agnetix/harnax/scheduler/metrics/SchedulerMetrics.kt` (sampled per node, so the cluster total is a sum across nodes and any single non-zero node is the alert condition), and health endpoints live in `harnax-scheduler/src/main/kotlin/com/agnetix/harnax/scheduler/health/`.

Log visibility follows the task: a log row is readable only through a task the caller can see — public, or created by them — the same rule as the task list, and deliberately with no tenant condition.

### 3.8 Channel Integration

The channel layer abstracts "how a platform delivers messages in" into two modes: callback push and long connection. The contracts live under `harnax-channel/harnax-channel-sdk/src/main/kotlin/com/agnetix/harnax/channel/sdk/`: the unified message model `harnax-channel/harnax-channel-sdk/src/main/kotlin/com/agnetix/harnax/channel/sdk/message/ChannelMessage.kt`, the adaptor interface `harnax-channel/harnax-channel-sdk/src/main/kotlin/com/agnetix/harnax/channel/sdk/adaptor/ChannelAdaptor.kt` and the reply pipeline `harnax-channel/harnax-channel-sdk/src/main/kotlin/com/agnetix/harnax/channel/sdk/service/ChannelChatService.kt`. `harnax-channel/harnax-channel-service` carries the runtime, and platform differences sit in `harnax-channel/harnax-channel-feishu`, `harnax-channel/harnax-channel-wechat`, `harnax-channel/harnax-channel-wecom` and `harnax-channel/harnax-channel-dingtalk`. Feishu uses a WebSocket long connection (`harnax-channel/harnax-channel-feishu/src/main/kotlin/com/agnetix/harnax/channel/feishu/FeishuWebSocketMode.kt` and `harnax-channel/harnax-channel-feishu/src/main/kotlin/com/agnetix/harnax/channel/feishu/FeishuWsTransport.kt`) and needs no public callback ingress.

Under multiple replicas, listener rights for one channel are claimed by a single instance using a MySQL named lock — the guard is `harnax-channel/harnax-channel-service/src/main/kotlin/com/agnetix/harnax/channel/service/bootstrap/ChannelListenerLockGuard.kt`; de-duplication lives in `harnax-channel/harnax-channel-sdk/src/main/kotlin/com/agnetix/harnax/channel/sdk/util/MessageDeduplicator.kt` and text chunking in `harnax-channel/harnax-channel-sdk/src/main/kotlin/com/agnetix/harnax/channel/sdk/util/TextChunker.kt`, both called from inside the reply pipeline. Capability toggles on a channel (thinking mode, web search, plan mode) are stored as columns on the `channel` table, configured at `harnax-webui/src/pages/channel`.

File delivery is an optional adaptor capability: `supportsFileDelivery()` in `harnax-channel/harnax-channel-sdk/src/main/kotlin/com/agnetix/harnax/channel/sdk/adaptor/ChannelAdaptor.kt` is off by default, and today only the personal-WeChat adaptor `harnax-channel/harnax-channel-wechat/src/main/kotlin/com/agnetix/harnax/channel/wechat/WechatAdaptor.kt` declares it. A channel without the capability triggers no byte fetching at all; the user is told once, with every file named (`deliverFileAttachments` in `harnax-channel/harnax-channel-sdk/src/main/kotlin/com/agnetix/harnax/channel/sdk/service/ChannelChatService.kt`). Inbound messages enter the conversation pipeline as text, and non-text kinds are recorded in the session as placeholder content.

### 3.9 Models and Providers

Providers and models are two layers of objects, both managed by `harnax-admin` at `harnax-webui/src/pages/model`: a provider records the protocol family, endpoint and credential (`harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/ModelProvider.kt`), a model records the concrete identifier and parameters and belongs to one provider (`harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/Model.kt`). A model row also carries an optional `context_window` (in tokens), which is the denominator of the session occupancy reading; left empty, the runtime infers it from the model name and otherwise falls back to a fixed ceiling. `ModelProvider.type` takes `dashscope`, `openai` or `ollama`, where `openai` covers OpenAI and OpenAI-compatible endpoints. At runtime the three configuration classes in `harnax-agent/harnax-agent-utils/src/main/kotlin/com/agnetix/harnax/agent/adaptor/model/ChatModelConfig.kt` build the clients, and `harnax-agent/harnax-agent-service/src/main/kotlin/com/agnetix/harnax/agent/service/adaptor/ChatModelConfigAdaptorImpl.kt` translates admin configuration into the shape the kernel needs.

### 3.10 API Keys and Tenant Isolation

Outbound call credentials are carried by `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/ApiKeyEntity.kt`, registered and maintained by `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/controller/ApiKeyController.kt` (implemented by `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/service/impl/ApiKeyServiceImpl.kt`) at console page `harnax-webui/src/pages/api-key`. Each key belongs to one tenant; a tenant is described by `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/TenantEntity.kt` and maintained at `harnax-webui/src/pages/tenant`, and user-to-tenant membership lives in `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/UserTenantEntity.kt`.

"Which tenant does this request act within" is answered in exactly one place, `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/util/TenantResolver.kt`, and every admin service shares that chain, first answering step wins: the membership-verified tenant in the request context, the tenant claim on the caller's own token, the tenant on the caller's user row, then the default tenant. `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/interceptor/TenantInterceptor.kt` populates `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/context/TenantContext.kt` only when an `X-Tenant-ID` header arrives, and verifies membership first; the later steps can only ever name a tenant the caller actually belongs to, so the chain may resolve something more accurate than the header alone but can never place a caller in a workspace they do not belong to.

Where isolation is written matters: this project has no MyBatis-layer automatic tenant interceptor, so isolation exists only inside SQL statements that state it. Core configuration objects carry a tenant column — `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/Team.kt`, `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/Agent.kt`, `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/ModelProvider.kt`, `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/McpServer.kt`, `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/Skill.kt`, `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/Cli.kt`, `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/ApiKeyEntity.kt` — while the three binding tables carry none, so the tenant predicate belongs on the `agent` rows they query (see `selectByEnvVarRef` in `harnax-entity/src/main/kotlin/com/agnetix/harnax/mapper/AgentMapper.kt`, where `tenantId` is a hard parameter with no default). The tenant basis for statistics and logs is written on the tables themselves: admin's schema baseline `harnax-admin/src/main/resources/db/migration/V1__init_schema.sql` declares, for each of `token_stats`, `process_log` and `tool_call_log`, a nullable `tenant_id` column plus an `idx_tenant_ts (tenant_id, ts)` composite index — the tenant leads because a tenant-scoped read is always "tenant equality plus a time range". NULL is a real state there rather than an alias for tenant 1: a run nothing attributed its tenant to writes NULL, and no tenant-scoped read ever matches it.

### 3.11 Token Usage and Call Logs

Usage accumulates per model and per time window; the stored shape is `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/TokenStats.kt` and the write path is `harnax-agent/harnax-agent-service/src/main/kotlin/com/agnetix/harnax/agent/service/adaptor/TokenStatAdaptorImpl.kt`. There are four observational record types, all written asynchronously: token statistics, process logs (`harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/ProcessLogEntity.kt`), tool call logs (`harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/ToolCallLogEntity.kt`) and MCP call logs (`harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/McpCallLog.kt`); plan notes are carried by `harnax-entity/src/main/kotlin/com/agnetix/harnax/entity/PlanNoteEntity.kt` so a long task can look back when it resumes. The gateway keeps a separate cross-request call log, shaped by `harnax-session-router/src/main/kotlin/com/agnetix/harnax/router/entity/ApiCallLog.kt` and written by `harnax-session-router/src/main/kotlin/com/agnetix/harnax/router/config/ApiCallLogFilter.kt`, covering caller, tenant, session, agent, model, endpoint, status code, duration and requestId. Console page `harnax-webui/src/pages/token-monitor` provides the queries and dashboards.

### 3.12 Sandbox Execution Environment

Tools, CLIs and skill projections all execute inside a Docker sandbox. The sandbox is created by `harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/sandbox/SandboxFactory.kt`, commands run through `harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/sandbox/DockerCommandExecutor.kt`, `harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/sandbox/KeepAliveSandboxManager.kt` maintains a keep-alive pool so already-warm sandboxes get reused, and `harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/sandbox/SandboxFileWriter.kt` writes files into the workspace. Images can be built on demand per CLI package, and state recovery across restarts relies on MinIO: `harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/minio/MinioSnapshotClient.kt` and `harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/minio/MinioBaseStore.kt`.

Pre-execution interception happens in `harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/permission/DangerousInputCheckingTool.kt`, alongside each tool's own confirmation requirement. Output detection and persistence live in `harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/output/OutputFileDetector.kt` and `harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/output/OutputFileStore.kt`, and workspace files reach the front end through `harnax-agent/harnax-agent-service/src/main/kotlin/com/agnetix/harnax/agent/service/controller/SandboxWorkspaceController.kt`. Process logs and tool call logs are written asynchronously, producing a traceable execution record.

### 3.13 Session Routing and Multiple Instances

`harnax-session-router` holds exactly three pieces of state: the instance registry, session bindings and circuit-breaker state. It carries no business data. It offers session-sticky routing, periodic health probing, requestId idempotency and failover: the dedupe key is held by `harnax-session-router/src/main/kotlin/com/agnetix/harnax/router/service/IdempotencyService.kt`, failover retries only on connectivity errors while the request has not yet been delivered, the retry ceiling is configurable (`router.proxy.failover-max-retries` in `harnax-session-router/src/main/kotlin/com/agnetix/harnax/router/proxy/SessionRouterService.kt`, defaulting to 2) and has its own counter metric. The circuit-breaker contract is `harnax-session-router/src/main/kotlin/com/agnetix/harnax/router/service/InstanceCircuitBreaker.kt` with three states — `CLOSED`, `OPEN`, `HALF_OPEN` — and the decision is separated from the transition: refusing traffic is a pure read that performs no state change. Health checking lives in `harnax-session-router/src/main/kotlin/com/agnetix/harnax/router/health/HeartbeatHealthChecker.kt`.

The data plane has two shapes. Standalone uses SQLite plus in-process state with zero external dependencies — `harnax-session-router/src/main/kotlin/com/agnetix/harnax/router/config/SqliteInitConfig.kt` and `harnax-session-router/src/main/kotlin/com/agnetix/harnax/router/config/SqliteDirectoryInitializer.kt`. Clustered uses MySQL plus Redis, with breaker implementations split across `harnax-session-router/src/main/kotlin/com/agnetix/harnax/router/service/impl/LocalInstanceCircuitBreaker.kt` and `harnax-session-router/src/main/kotlin/com/agnetix/harnax/router/service/impl/RedisCircuitBreaker.kt`. In the clustered shape the read-modify-write of a session-to-instance binding is one Lua script (`harnax-session-router/src/main/kotlin/com/agnetix/harnax/router/service/impl/RedisSessionMappingService.kt`), because a read-modify-write in Kotlin would let a second node overwrite the first; when Redis is unavailable the router degrades to a shadow cache and lets traffic through, and a shadow entry carries a TTL no longer than the binding it describes. Redis Cluster is not supported — cross-slot scripts cannot be satisfied — and that is a design constraint.

## 4. Engineering Quality and Observability

- Schema is managed by Flyway scripts, and each service owns exactly one schema baseline against its own datasource — each module's migration directory holds nothing but that init script: `harnax-admin/src/main/resources/db/migration/V1__init_schema.sql` writes the whole admin database, all 34 tables plus its initial data, in one script; `harnax-scheduler/src/main/resources/db/migration/V1__init_schema.sql` writes the 11 `QRTZ_*` cluster tables plus the three task-domain tables `agent_task`, `agent_task_log` and `agent_task_execution`, recorded in that service's own history table `flyway_schema_history_scheduler`; `harnax-session-router/src/main/resources/db/migration/V1__create_session_router_tables.sql` is the router's own baseline; the `harnax_scheduler` database itself is created and granted by `harnax-deploy/sql/init-databases.sql`. A schema change edits the baseline itself and the environment is rebuilt from it: a database already created from the old shape rejects a changed baseline, so changing the structure and rebuilding the database are one action.
- Persistence tests start real MySQL through Testcontainers rather than mocking, under `harnax-entity/src/test/kotlin/com/agnetix/harnax/mapper/`, covering real reads and writes for Agent, Team, Model, ModelProvider, McpServer, McpOauthClient, McpUserCredential, Skill, SkillRepository, Channel, Cli, Session, Token, PlanNote, ProcessLog, McpCallLog, SysUser and Tenant entities.
- Service-level integration tests are suffixed `IT` or `IntegrationTest` and each uses its own `*_it` database, for example `harnax-scheduler/src/test/kotlin/com/agnetix/harnax/scheduler/it/BaseSchedulerIT.kt`; `harnax-channel/harnax-channel-service/src/test/kotlin/com/agnetix/harnax/channel/service/it/ChannelServiceContextIT.kt` brings up the full channel service context.
- The Redis-side behaviour of the router has dedicated integration tests under `harnax-session-router/src/test/kotlin/com/agnetix/harnax/router/integration/`, covering instance registration, session mapping and circuit breaking.
- End-to-end cases live in `harnax-ui-test`, driving real console pages through Playwright.
- Deployment and end-to-end verification go through `harnax-deploy` as the only entry point: `harnax-deploy/build.sh` produces the images, `harnax-deploy/docker-compose.yml` orchestrates the full chain, and `harnax-deploy/deploy-all.sh` plus `harnax-deploy/deploy-service.sh` handle whole-stack and single-service releases. `harnax-deploy/nginx.conf` fronts the console and reverse-proxies the API, and for the SSE routes it turns off `proxy_buffering` and `proxy_request_buffering` and sends `X-Accel-Buffering: no`.
- Runtime observation rests on three log kinds (process, tool call, MCP call) plus token statistics, with a cross-request call log at the gateway; router health probing, breaker state and channel listener ownership are all queryable.
- Formatting is enforced uniformly by Spotless, configured in the root `pom.xml`.

## 5. Current Boundaries

- Backend runtime code is Kotlin. `harnax-cli` is Go; `harnax-webui`, `harnax-app`, `harnax-wechat-app` and `harnax-ui-test` are TypeScript, and none of them take part in the Maven build.
- Session stickiness presupposes that one session returns to the same instance: when an instance goes away, the parked state in its memory is picked up by state restoration and MinIO snapshots, and no routing decision by the router changes that fact.
- The router's clustered shape requires Redis that is not in Cluster mode; when Redis is unavailable traffic goes through the degraded path rather than being refused.
- The MCP `stdio` transport exists only as registration data; no local process-type connection is opened at runtime. Among MCP auth types, `BASIC` is present in the data model but is not in the set the runtime honours.
- File delivery on a channel depends on whether its adaptor declares the capability; a channel without it receives one notice naming the files. Inbound non-text messages are recorded in the session as placeholder content.
- Provider protocol families are limited to `dashscope`, `openai` and `ollama`; `openai` covers OpenAI and OpenAI-compatible endpoints.
- Triggering for scheduled tasks belongs to the Quartz JDBC cluster JobStore, and the task definition, execution ledger and execution log all live only in the `harnax_scheduler` database; the admin side holds no duplicate.
- Execution log visibility follows the owning task (public or creator), and that read path carries no tenant condition.
- Tenant isolation has no automatic ORM-layer interceptor: it is composed of the shared tenant resolution chain plus SQL statements that state the predicate, so any new query must carry one itself.
- The deployment shape is Docker Compose, operable by one person on one machine. There is no Kubernetes port, and no production concurrency or latency figures to cite.
- The project is positioned as self-hosted and single-operator: tenants isolate configuration and statistics, and do not constitute a billing boundary for resale.
