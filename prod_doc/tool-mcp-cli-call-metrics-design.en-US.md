# Tool / MCP / CLI Call Metrics · Design Specification

- Date: 2026-10-05, hour grain and five dimensions revised 2026-10-08
- Status: implemented
- Modules touched: `harnax-agent/harnax-harness-core` (event source), `harnax-agent/harnax-tools-sdk` (write contract), `harnax-agent/harnax-agent-service` (write implementation), `harnax-entity` (two tables), `harnax-admin` (roll-up and read endpoints), `harnax-webui` (new page), `prod_doc`
- Supersedes: the whole `tool_call_log` chain (table, entity, Mapper, Adaptor, the logging wrapper in `ToolBox`); `mcp_call_log` stays, with its responsibility spelled out

## 0. Where the requirement and the current state diverge

The request: fill in the tool / MCP / CLI call metrics under "Monitoring & Governance" and turn them into a page people can actually look at; the logs recorded so far are incomplete, so re-do them from a clean sheet.

Four places where the current state diverges from that, each one checked against the source:

1. **The built-in tools only record themselves.** The only writer of `tool_call_log` (`harnax-admin/src/main/resources/db/migration/V1__init_schema.sql:759-778`) is `ToolBox.execute { }` (`harnax-agent/harnax-tools-sdk/src/main/kotlin/com/agnetix/harnax/tools/sdk/ToolBox.kt:88`, `:125`). It writes `tool_name` as `ToolBoxClassName::methodName`, which is not the same string as the registration identity `@Tool.name`; and any execution that does not go through `ToolBox` — MCP tools, the harness's own `execute` / `read_file` / `memory_*` / `load_skill_through_path` — never lands a single row.
2. **Nothing reads it.** `ToolCallLogMapper` has exactly one `insert` (`harnax-entity/src/main/kotlin/com/agnetix/harnax/mapper/ToolCallLogMapper.kt:15`), and `ToolCallLogMapper.xml` is 18 lines in total with one insert in it. The table has been written for three years without a single SELECT.
3. **The MCP table is not a metrics table.** `mcp_call_log` (baseline `:248`) records authorization actions (`action` takes ISSUE / REFRESH / REVOKE / CALL); not one tool call lands in it. It is a live OAuth ledger and must not be cut down by a metrics retention window.
4. **CLI has zero records.** A CLI package is only ever used inside the sandbox in the shape of a shell command, and no table in the whole repository has ever recorded that "some CLI was run".

The four share one root cause: **the recording point is attached to the implementation style, not to the execution channel**. Any registration that bypasses `ToolBox` goes unrecorded, and registrations that bypass it are exactly the form this project later took.

The reference point is "Monitoring & Governance → Skill Usage": `skill_usage` (baseline `:584`) has a writer (`SkillUsageAdaptorImpl`, asynchronous batch reporting), a read endpoint (`/api/admin/skill-usage/summary`) and a page (`harnax-webui/src/pages/skill/usage.tsx`), but it only reports `VIEW`; the hint text of the page's "Uses" column admits on its own that there is no data behind it (`src/locales/zh-CN/pages.ts:209`).

Goal: one event source, one detail table, one hourly aggregate, three read endpoints, one new page, covering the five origins `builtin` / `mcp` / `cli` / `shell` / `framework`, and while at it giving Skill Usage a writer for `USE` too.

## 1. Decision list (finalized)

| # | Decision | Reason |
|---|---|---|
| D1 | The single event source = a middleware implementing `MiddlewareBase.onActing`, attached to the agent at assembly time | agentscope 2.0.4's `onActing` receives `record ActingInput(List<ToolUseBlock> toolCalls)`, and `ToolUseBlock` carries `getId()` / `getName()` / `getInput(): Map<String,Object>`; `ProcessLogMiddleware.kt:86` already uses the same hook. | D2 | One row per tool call, and it lands only in a terminal state | `ToolResultEndEvent` carries `getToolCallId()`, `getToolCallName()` and `getState()` at the same time, so joining by id works (`ToolUseBlock.getId()` is nullable, fallback in §3); `ToolResultState.RUNNING` means an external execution has not returned yet, so wait for the terminal state. A half-finished row enters neither the success rate nor the durations |
| D3 | One detail table + one hourly aggregate; the `tool` / `mcp` / `cli` tiers read the aggregate, while the agent / session dimensions and the per-call drill-down read the detail | Only a second table makes it possible both to delete detail (volume) and still answer trends that cross the retention window. agent / session stay out of the aggregate because their cardinality is unbounded |

| D10 | Aggregation and cleanup both live in admin, three steps at the 5th minute of every hour: fill in the missing hours → recompute hour by hour idempotently (always carrying the previous hour and the running one) → delete only detail that is already rolled up and past the window | Filling in makes the recompute self-healing (a missed cycle or a first launch needs no backfill switch); deletion hangs on the fact "already rolled up" rather than on date arithmetic, so several replicas running at the same time are harmless. The running hour is recomputed as well, otherwise the page would trail a whole hour on every read |
| D11 | P95 is approximated from duration buckets, and the page states that it is an approximation | The aggregate table has count columns only; a real quantile needs every detail row kept |
| D12 | The tenant is decided server-side only: `TenantResolver.resolve(jwtUtil)` on the read path, carried with the row at assembly time on the write path | Same rule as `TokenStatsController.kt:37` and `SkillUsageController`. | D13 | Detail is kept for 90 days, `args_json` / `result_excerpt` are truncated to 2000 characters, and both are configurable and switchable off | Command-line arguments and tool receipts contain credential literals, so truncate by default and allow the whole thing to be switched off |
| D14 | The window is an hour range `start` / `end` (`yyyy-MM-dd HH:mm`, both bounds inclusive hour starts), not a number of days | The three read endpoints and the drill-down share one and the same range, and only then do you get "pick the time once and every chart on the page follows". Days and a range are two shapes of one state, and keeping both leaves every request with a "who wins" question; the presets (last 7 / 30 / 90 / 365 days) become pure front-end time arithmetic, and the server only accepts a range. Stopping at the hour is a pinned definition: the aggregate stores exactly one hour per row, so a picker that goes down to minutes and seconds only lets the page ask for a boundary the storage cannot answer |
| D15 | The row-name column and the Calls column each open a drawer: the first gives that row's profile plus its metrics inside the window, the second gives the individual call records | A row name reads as "who is this", a count reads as "what were these calls". | D16 | Origin-bucket display names: `builtin` is called "Available tools", `framework` is called "System built-ins" | "Available tools" is what this set of things is already called elsewhere (`/api/admin/tools/available`, iOS's "No tool to choose", the available-tools/required-tools split in `prod_doc/tool-integration-design`), so calling it "Delivered tools" on this page too means one object with two names; "System built-ins" against "Available" is the two ends of one ruler |
| D17 | The dimension dropdown is a per-tab matrix: tool tab = tool / agent / session, MCP tab = MCP / agent / session, CLI tab = CLI / agent / session | With one shared "tool / agent / session" list across the three tabs, "by tool" inside the MCP tab lists every tool one server exposes and there is no tier for one row per server; same for CLI. So `mcp` and `cli` become dimensions of their own, and when you switch tabs and the current dimension is not in that tab's matrix it converges onto the tab's first tier |
| D18 | The row name comes out of the server's SQL as `subjectName`; the front end never queries a registration endpoint per row, and an unresolved name falls back to the row's own key | A page of several dozen rows queried row by row turns one table into dozens of round trips. Falling back rather than leaving the cell blank: a deleted registration row (the server is gone while its call records remain) and ids like `chn-` / `task-` that have no line in the `session` table at all still have to say which row they are, and a blank cell reads as missing data |

## 2. Data model

Both tables come in through the `harnax-admin` forward increment `V3__tool_invocation_metrics.sql` and are not folded into the baseline. The default path in the README (`harnax-admin/src/main/resources/db/migration/README.md`) is "editing the baseline and rebuilding the database are one action", and this database is the exception it states: it holds model provider api_keys that only a human can refill. So an existing database starts as usual and Flyway applies V3 on top, while a fresh one replays V1 → V2 → V3 → V4 → V5 and lands in the same shape; at the next wipe-and-rebuild V3, V4 and V5 are folded back into the baseline. Dropping the old table goes through the same channel: `V4__drop_tool_call_log.sql` is one `DROP TABLE IF EXISTS`, and what it drops is the table V1 created (the create-table block itself cannot be edited, see §10). Moving the aggregate table from one row per day to one row per hour goes through the same channel too: `V5__tool_invocation_stats_hourly.sql` changes the column (`stat_hour datetime`), swaps the unique key and the secondary index, and runs `DELETE FROM tool_invocation_stats` before it changes anything — an old day-row carried over unchanged into the hour shape reads as "the 00:00 hour held a whole day", the pending set considers that hour already folded, and the detail is then released and can never be re-folded. Emptying it is not losing data: every detail row inside the retention window is still there, the next sweep re-folds hour by hour, and that window is bounded. `harnax-entity/src/test/resources/schema-test.sql` is still synced **verbatim** — drift is guarded by `SchemaBaselineDriftIT`, which compares the tables, columns and index names Flyway finally builds and does not look at which file a name came from, so the changes on both the increment side and the baseline side have to be merged into this copy, and a table dropped by DROP must not survive in the copy either.

Naming follows `docs/database-design-conventions.md:30`: log/statistics tables use the `_log` / `_stats` suffix, so the aggregate table is called `tool_invocation_stats` rather than `..._daily`. Indexes follow the newest shape, `skill_usage`, using table-name-qualified `idx_tool_invocation_log_*` / `uk_tool_invocation_stats_*`; column comments are always English; every create-table block in the baseline carries the three-line `/*!40101 SET character_set_client ... */` guard, while the increment file uses bare `CREATE TABLE` — the two build the same shape.

### 2.1 `tool_invocation_log` (detail, append-only)

```sql
CREATE TABLE IF NOT EXISTS `tool_invocation_log` (
  `id` bigint NOT NULL AUTO_INCREMENT COMMENT 'Invocation event ID',
  `tenant_id` bigint DEFAULT NULL COMMENT 'Owning tenant; NULL when the delivered spec named none, and no tenant-scoped read returns such a row',
  `agent_id` bigint DEFAULT NULL COMMENT 'Owning agent; NULL for a team lead, which has no agent row',
  `session_id` varchar(255) DEFAULT NULL COMMENT 'Session that produced the call',
  `user_id` bigint DEFAULT NULL COMMENT 'End user behind the call, NULL for channel sessions and service keys',
  `kind` varchar(16) NOT NULL COMMENT 'Origin (builtin: delivered tool, mcp: MCP server tool, cli: delivered CLI package run through the shell, shell: bare shell command, framework: harness built-in)',
  `tool_name` varchar(255) NOT NULL COMMENT 'Tool name as the model sees it; the matched command name when kind = cli',
  `mcp_id` bigint DEFAULT NULL COMMENT 'MCP server row, set only when kind = mcp',
  `cli_id` bigint DEFAULT NULL COMMENT 'CLI package row, set only when kind = cli',
  `outcome` varchar(16) NOT NULL COMMENT 'Terminal state (SUCCESS, ERROR, DENIED, INTERRUPTED)',
  `error_message` varchar(512) DEFAULT NULL COMMENT 'Failure reason, truncated',
  `args_json` text COMMENT 'Tool input as JSON, truncated; NULL when payload capture is off',
  `result_excerpt` text COMMENT 'Leading part of the tool result, truncated; NULL when payload capture is off',
  `duration_ms` bigint NOT NULL COMMENT 'End time minus start time',
  `start_time` datetime(3) DEFAULT NULL COMMENT 'Call start; milliseconds because a second-resolution column collapses two calls inside one second onto one instant',
  `end_time` datetime(3) DEFAULT NULL COMMENT 'Call end',
  `ts` datetime(3) NOT NULL COMMENT 'Recorded time, equal to end_time; aggregation and indexes key on it',
  PRIMARY KEY (`id`),
  KEY `idx_tool_invocation_log_tenant_ts` (`tenant_id`,`ts`),
  KEY `idx_tool_invocation_log_tenant_kind_ts` (`tenant_id`,`kind`,`ts`),
  KEY `idx_tool_invocation_log_mcp_ts` (`mcp_id`,`ts`),
  KEY `idx_tool_invocation_log_cli_ts` (`cli_id`,`ts`),
  KEY `idx_tool_invocation_log_session` (`session_id`),
  KEY `idx_tool_invocation_log_tool_name` (`tool_name`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='One row per tool invocation, kept for a bounded window';
```

`tenant_id` being nullable follows the same shape as `token_stats:748` (`AgentSpec.tenantId` is itself nullable, no guessing at a workspace); `agent_id` being nullable follows `AgentSpec.attributableAgentId` (a team lead has no `agent` row).

### 2.2 `tool_invocation_stats` (hourly aggregate, permanent)

Unique key `(stat_hour, tenant_id, kind, subject_id, tool_name)`.

```sql
CREATE TABLE IF NOT EXISTS `tool_invocation_stats` (
  `id` bigint NOT NULL AUTO_INCREMENT COMMENT 'Aggregate row ID',
  `stat_hour` datetime NOT NULL COMMENT 'Hour the calls fall in, `tool_invocation_log.ts` truncated to the hour; minutes and seconds are always zero',
  `tenant_id` bigint NOT NULL COMMENT 'Owning tenant; detail rows without one are not aggregated at all',
  `kind` varchar(16) NOT NULL COMMENT 'Origin bucket, same vocabulary as the detail table',
  `subject_id` bigint NOT NULL DEFAULT '0' COMMENT 'mcp_id when kind = mcp, cli_id when kind = cli, 0 otherwise; 0 rather than NULL because a unique index does not treat NULLs as equal, and NULL would make the upsert insert a second row for the same hour',
  `tool_name` varchar(255) NOT NULL DEFAULT '' COMMENT 'Tool name as the model sees it; every kind carries it, so two tools of one MCP server are two rows in an hour',
  `calls` int NOT NULL COMMENT 'Total invocations',
  `successes` int NOT NULL COMMENT 'Invocations ending SUCCESS',
  `errors` int NOT NULL COMMENT 'Invocations ending ERROR',
  `denials` int NOT NULL COMMENT 'Invocations ending DENIED',
  `interruptions` int NOT NULL COMMENT 'Invocations ending INTERRUPTED',
  `sum_duration_ms` bigint NOT NULL COMMENT 'Duration total; the mean is this divided by calls',
  `max_duration_ms` bigint NOT NULL COMMENT 'Longest single call of the hour',
  `le_100ms` int NOT NULL DEFAULT '0' COMMENT 'Calls of at most 100 ms',
  `le_500ms` int NOT NULL DEFAULT '0' COMMENT 'Calls over 100 ms and at most 500 ms',
  `le_2s` int NOT NULL DEFAULT '0' COMMENT 'Calls over 500 ms and at most 2 s',
  `le_10s` int NOT NULL DEFAULT '0' COMMENT 'Calls over 2 s and at most 10 s',
  `le_30s` int NOT NULL DEFAULT '0' COMMENT 'Calls over 10 s and at most 30 s',
  `gt_30s` int NOT NULL DEFAULT '0' COMMENT 'Calls over 30 s',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_tool_invocation_stats_hour` (`stat_hour`,`tenant_id`,`kind`,`subject_id`,`tool_name`),
  KEY `idx_tool_invocation_stats_tenant_hour` (`tenant_id`,`stat_hour`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='Hourly rollup of tool_invocation_log; rows are kept permanently';
```

The table stores **the hour grain and nothing else**. The four terminal counters, the six duration buckets and `sum_duration_ms` are all additive over hours, and `max_duration_ms` is a per-hour max, which is additive the same way, so the day / week / month views on the page are these rows summed per bucket and no second set of rows is needed; keeping both grains would count the same instant twice in any cross-grain sum, and no reader needs one. The price is that hour rows come in 24 times the volume of day rows, on a table designed to be kept permanently.

The six buckets are **half-open intervals** (`le_500ms` = `(100, 500]`); otherwise "exactly 500 ms" would be claimed by two buckets and `calls` would stop being equal to the sum of the buckets.

### 2.3 Invariants

- I1 At most one detail row per tool call; how `kind` and `mcp_id` / `cli_id` are filled is decided uniquely by the order of checks in §3.
- I2 `outcome` takes only the four terminal values, and `RUNNING` never lands in the database.
- I3 A detail row's `tenant_id` and `agent_id` are fixed at write time; the read side never guesses again.
- I4 On any aggregate row, `calls` = the sum of the four terminal counters = the sum of the six buckets.
- I5 The aggregate can be recomputed as a whole with an unchanged result (idempotent), so both recomputation and concurrent replicas are harmless.
- I6 No detail hour is deleted before it has been rolled up into the aggregate (the delete statement is conditioned on "that `(hour, tenant_id)` already exists in the aggregate table", the hour being `ts` truncated down to the hour). The one exception is detail with `tenant_id IS NULL`: the aggregate's `NOT NULL` on that column (§2.2) keeps such rows out of every aggregate, so they are governed by the retention window alone — otherwise they could never be deleted.

## 3. Event source and classification

A new `ToolInvocationMiddleware`, in the same package and the same directory as `ProcessLogMiddleware`: `harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/agent/provider/middleware/ToolInvocationMiddleware.kt`; mounted through the existing `agentBuilder.addMiddleware(...)` (current examples `HarnessAgentLauncher.kt:587`, `:601`). The middleware gets a new instance per assembly, for the same reason behind `ProcessLogMiddleware`'s `initial()` lesson (the comment at `:585-592` of the same file records how a shared instance crossed the attribution of two Sessions).

Inside `onActing` a start table is built for this acting batch, keyed by `toolCallId` and falling back to `toolCallName` when there is no id, seeded from `input.toolCalls` (recording `name`, `input` and the start instant); calls in one batch that compute the same key (same-named calls without an id) append a sequence number to the key, and on top of that a FIFO queue of not-yet-terminal keys is kept per `name`, so every start is addressable. The name of a `ToolUseBlock` is nullable upstream (it is deserialized from JSON the model produced, and the upstream constructor does not validate it): a nameless call computes no key and has no writable `tool_name` either (that column is `NOT NULL`), so it does not enter the start table and does not land; the registration step itself never lets an exception escape `onActing` — D9's "never throw" holds before the event stream starts as well. Over the event stream of `next.apply(input)`:

| Event | Action |
|---|---|
| `TOOL_RESULT_END` | First hit a not-yet-terminal start by `key(toolCallId, toolCallName)`; on a miss take the earliest entry in that `toolCallName`'s queue (within one turn the model receives its own answers in the order it sent them, so FIFO is the only guess that stands up, and a wrong guess costs a duration measured against the wrong start, not a lost row; matching only peeks and never removes a key from the queue; the queue and the start table correspond one to one by key, both are added at the same place during registration, and both the emit path and the stream-end path remove at the same place using the `name` recorded on the start, so what a peek finds is necessarily a not-yet-terminal start), produce `outcome` and `duration_ms`, and hand them to the adaptor; when `toolCallName` disagrees with the start's name, the `name` recorded on the start wins and a warn is logged. The start is removed from the table before it is emitted, and the same key in the queue is located and removed using the `name` recorded on the start rather than the terminal frame's `toolCallName` — removing by frame name would leave an already-consumed key behind in the queue, and the next same-named call would be displaced by that ghost key and lose a row. A duplicated terminal frame for the same id finds no start when that name has no other not-yet-terminal start, so no second row lands; but if calls of the same name are still in flight at that moment, the fallback looks the queue up by the frame's `toolCallName` rather than by id (`matchKey`), and it displaces that one start — the duplicate frame lands a row while the real call it displaced has from then on neither a start nor any presence in the stream-end fallback (`started` and the queue both no longer hold its key), and the row disappears entirely. This is the only guess left standing besides "match rather than guess", and it has exactly one precondition: the same terminal frame arriving twice. |
| Stream `onComplete` still has non-terminal ids | Land an extra `INTERRUPTED` row, the duration runs to the completion instant, `error_message` says `stream ended before the tool returned` |
| Stream `onError` / `onCancel` | Same as above, `error_message` takes the exception text; the incremental text this call had already streamed out still goes into `result_excerpt` (truncated on the write side), because the most useful thing about an interruption is what it said before it stopped |

Incremental text accumulates under the key each event carries (the id when there is a `toolCallId`, the name when there is not); at emit time it is fetched first by the start's key and, if that misses, by the terminal frame's own key, so a pairing where one side carries an id and the other does not does not lose the body already streamed out; a start that was never emitted is fetched the same way at stream end, first by its own key and then by the recorded `name`. What really share one buffer are same-named calls whose frame side has no distinguishable key: when a delta carries no id, the increments of both sides land in the same name-keyed buffer, regardless of whether those two starts have ids themselves. In that case what is preserved is the row count; merging the text is a known concession, and which row the merged body lands in depends on the iteration order at stream end and is not stable. The loss on the other side is just as known: when a terminal frame carries neither an id nor a `toolCallName` that hits any name queue, it matches no start, and that call is recorded as `INTERRUPTED` by the stream-end fallback. No "if only one non-terminal start is left this turn, pair it up" fallback is introduced here — that is already guessing, and a wrong guess would record a genuinely interrupted call as a success, which by I4 moves that row from the aggregate table's `interruptions` into its `successes` and misstates both counters at once; recording an interruption is at least a countable loss. Each key's buffer also carries a heap bound of 32,000 characters (`MAX_ACCUMULATED_RESULT_CHARS`), deliberately set above the write side's configurable `capture-max-chars` ceiling of 20,000 (`MAX_CAPTURE_MAX_CHARS`): body text truncated only at this layer was already longer than any column could hold, so truncation still has exactly one meaning, and it is the write side's.

`ToolResultState` mapping: `SUCCESS→SUCCESS`, `ERROR→ERROR`, `DENIED→DENIED`, `INTERRUPTED→INTERRUPTED`, `RUNNING→not persisted`.

Order of the `kind` checks; the first hit settles it:

| Order | Condition | Result |
|---|---|---|
| 1 | The tool name is in the MCP map (that map is built by enumerating the final registry) | `kind=mcp`, `mcp_id` takes the mapped value |
| 2 | The tool name is the shell tool and its `command` hits a CLI delivered to this session | `kind=cli`, with `cli_id` and `tool_name` (the command name hit) taken from the CLI map |
| 3 | The tool name is the shell tool but nothing hits | `kind=shell` |
| 4 | The tool name is in `AgentSpec.toolSpecs[].toolName` | `kind=builtin` |
| 5 | Anything else | `kind=framework` |

The shell tool name has two sources and both are accepted: harness's `ShellExecuteTool.NAME = "execute"` (`io.agentscope.harness.agent.tool.ShellExecuteTool:32` in `agentscope-harness`) and core's `ShellCommandTool` (`execute_shell_command`, `io.agentscope.core.tool.coding.ShellCommandTool:354` in `agentscope-core`); the argument name is `command` in both. A CLI hit still records only one row, and a second CLI appearing inside the command string does not duplicate the row (see §12).

Classification and attribution are written as one pure function, taking `(toolName, input, mcpIdsByTool, cliIdsByCommand, builtinToolNames)` and returning an `InvocationKind` value object (`kind` / `mcpId` / `cliId` / attributed command name); the middleware only collects, which keeps exhaustive unit tests easy. It lands in `ToolInvocationClassifier.kt` in the same directory.

The skill-loading tool `load_skill_through_path` is not in `toolSpecs`, so it lands as `kind=framework` — a skill is not one of the five `kind` values, and its USE goes only into `skill_usage` (§9).

## 4. Three assembly-time maps

All three are assembled while `HarnessAgentLauncher` builds the agent and are handed to the middleware constructor, the same shape as how `SkillViewRecorder` attributes today (`HarnessAgentLauncher.kt:472`, `:490`).

- **MCP**: once every `addMcp` has completed, enumerate the already assembled `Toolkit` — take `getToolNames()` and call `getTool(name)` on each; for a hit that is an `McpTool`, take `getClientName()` (upstream returns `clientWrapper.getName()`, and this project's `McpHelper` builds the wrapper with `McpClientBuilder.create(mcpConfig.name)`, see `harnax-agent/harnax-agent-utils/.../McpHelper.kt:186-205`), then match it against this session's `mcpServices` name→id. The three feasibility facts are verified: `HarnessAgentBuilder.addMcp` is `registerMcpClient(...).block()` (`harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/HarnessAgentBuilder.kt:76-80`, synchronous, the registration takes effect on the spot); `toolkit` is a private field of that class, so a read-only accessor has to be added; `HarnessAgent.Builder.build()` deep-copies that toolkit and only then mounts the harness's own tools, so what the enumeration sees is "MCP + the `addTool` half", without `execute` / `read_file` — this section only wants MCP ownership, and not having them is enough.

## 5. Write path

```
ToolInvocationMiddleware → ToolInvocationAdaptor(defined in harnax-tools-sdk)
  → ToolInvocationAdaptorImpl(harnax-agent-service: single thread + bounded queue + batch insert)
  → ToolInvocationLogMapper.batchInsert → tool_invocation_log
```

Configuration (`harness.metrics.invocation.*`, agent-service side): the write side belongs to the `harness.*` family — that is the prefix this service puts its middleware assembly switches under (`harnax-agent/harnax-agent-service/src/main/resources/application.yml:42`), while `harnax.*` holds service infrastructure (same file, `:137`). The aggregation and cleanup of §6 run inside the admin process, so their keys sit under the other prefix and the two sides are not one and the same configuration.

| Key | Default | Effect |
|---|---|---|
| `enabled` | true | switching it off does not install the middleware at all, and not one row is recorded |
| `queue-capacity` | 512 | |
| `batch-size` | 64 | |
| `flush-interval-ms` | 200 | rows land at this interval even when a batch is not full |
| `capture-payload` | true | governs exactly those two columns: when off, `args_json` and `result_excerpt` are always NULL; `error_message` is not under its control, because for a non-terminal call the failure reason is the tool's own output (§3) |
| `capture-max-chars` | 2000 | the truncation length of each of the two, with `…(truncated)` appended at the tail |

The adaptor contract matches `SkillUsageAdaptor`: `emit` returns immediately and never throws. Every lost row adds to the same counter, because "the page is empty" needs a number to explain it, and three paths all produce that empty page: the queue is full and refuses a new event, refusals after `shutdown()` has already set `running` to false (folded into the first rather than counted as a separate number), and a batch that already left the queue being rejected wholesale by the database — the last one is absorbed and counted by `flushBatch`, so draining, shutdown and the steady-state loop share this one layer of guarding instead of carrying three separate policies. The warn density is split by the shape of the loss: per-row losses log once at the first row and then every 50th (`DROP_LOG_EVERY`) with the running total, per-batch losses log once per failed batch.

A full queue means tool calls are already running at hundreds per second — at that point recording a few rows fewer is cheaper than stalling a whole answer on a database round trip. A batch rejected by the database is likewise released rather than retried: retrying would spin while the database is down, and queued behind it sits the counter.

`batchInsert` uses a `foreach` with multi-row VALUES (current example `harnax-entity/src/main/resources/mapper/MpChatMessageMapper.xml:25`); an empty batch returns early on the Kotlin side, because handing an empty list to `foreach` generates invalid SQL. `--` must never appear inside a Mapper XML comment: `MapperXmlParseTest` parses every XML and would therefore blow up the `SqlSessionFactory` of every service.

## 6. Aggregation and cleanup

Lives in admin: a new `ToolInvocationRollupService` plus one `@Scheduled` entry point. admin had no `@Scheduled` at all before (`docs/deploy-harnax-admin.md:166` states plainly that "all scheduling lives in the separate service `harnax-scheduler`"), so `@EnableScheduling` has to be added to `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/HarnaxAdminApplication.kt`.

**No distributed lock is introduced**: the repository has neither ShedLock nor a lock table; `harnax-scheduler`'s Quartz JDBC cluster (`harnax-scheduler/src/main/resources/application.yml:56`, `:94`) has nothing to do with this table. Concurrency safety is covered by the idempotency of step 2 below.

Each run does three things in order:

1. Take every hour that appears in the detail with `tenant_id IS NOT NULL` (`DATE_FORMAT(ts, '%Y-%m-%d %H:00:00')`), subtract the `stat_hour` values `tool_invocation_stats` already holds, and get the set of hours that "should have been rolled up but were not". Detail without a tenant is excluded, otherwise those hours would be reported as pending every single run while the aggregate never produces a row for them (the aggregate table's `tenant_id NOT NULL`), and the difference would never close. The lower bound is hardcoded to `1970-01-01 00:00:00` rather than a rolling start: any bound lets an hour that was never folded fall out of the pending set and stay unfolded forever, and the delete in the next step refuses to release exactly the rows of such an hour. The bound compares `l.ts` and not its truncated value — applying a function to a column cannot use the index; the difference is one `NOT EXISTS` plus `GROUP BY` instead of a subquery difference against the aggregate table, which a single pass over the `(tenant_id, ts)` index is enough for.
2. Recompute that set **plus the running hour and the previous one** hour by hour, with one `INSERT INTO tool_invocation_stats SELECT ... FROM tool_invocation_log WHERE ts >= ? AND ts < DATE_ADD(?, INTERVAL 1 HOUR) GROUP BY ... ON DUPLICATE KEY UPDATE` overwriting whole rows (an hour is bounded by an instant range instead of `DATE_FORMAT(ts, ...) = ?`, because applying a function to a column cannot use the index). Hours in the future are skipped outright, so a parameter later than the running hour never folds. The running hour must be in the set whether or not it showed up in step 1's difference: it is still being written, and waiting for it to close would make the page read one hour short every time. The previous hour must be in the set too: the sweep fires at the 5th minute of every hour, so an hour's last fold happens before it closes, detail landing between that fold and the hour boundary would never report the hour as pending again, and the retention window deletes it as soon as it comes due — without recomputing the previous hour, the closing slice of every hour is permanently undercounted. A missed cycle or a first launch is caught by step 1's difference, so no extra backfill entry point is needed.
3. Delete detail with `ts < now - retentionDays` and (its `(hour, tenant_id)` already exists in the aggregate table **or** `tenant_id IS NULL`). Why deletion hangs on the fact "already rolled up" is in I6; the no-tenant half is the only exception exit, since those rows enter no aggregate and therefore cannot wait for an aggregate to release them.

`harnax.metrics.retention-days` defaults to 90, `harnax.metrics.rollup-enabled` defaults to true, and the schedule expression is the 5th minute of every hour. The retention band is clamped into `1..3650` at service start and the clamp logs a warn instead of refusing to boot: with `retention-days: 0` the cleanup bound equals the running instant, so the next :05 releases every detail row whose hour has been folded — the one mismatch at this layer that destroys data instead of merely freezing the counters; the upper bound is not a column width but a horizon: aggregate rows are kept permanently and a larger retention value only extends the window the detail can still answer. Both keys go into the `harnax:` block of `harnax-admin/src/main/resources/application.yml` (`:135-172`, same shape as `harnax.cli.archive-retention-days`, injected through a constructor `@Value` — the whole repository has exactly one `@ConfigurationProperties` and it exists because it needs `@ConditionalOnProperty`).

Quantiles: bucket boundaries at 100 / 500 / 2000 / 10000 / 30000 ms. The P95 algorithm is "accumulate bucket by bucket until ≥ 0.95·calls, report the upper bound of the bucket it lands in, and report `>30s` when it lands in `gt_30s`". While the window's detail has not expired, the real per-call durations returned by `/invocations` are the basis for checking that number.

## 7. Read-side API

`ToolMetricsController`, prefix `/api/admin/tool-metrics`, following the same rules as `SkillUsageController` / `TokenStatsController`: Kotlin primary-constructor injection (zero `@RequiredArgsConstructor` anywhere in admin), `@Tag` / `@Operation` / `@Parameter` all present, method bodies are expression functions of the shape `= try { ... } catch (e: Exception) { log.error(...); ResultVo.error(ApiErrors.message(e, fallback)) }`, the tenant comes from `TenantResolver.resolve(jwtUtil)` and is never a query parameter, and the window is one `start` / `end` range of whole hours whose clamping happens entirely server-side.

| Endpoint | Parameters | Returns |
|---|---|---|
| `GET /summary` | `start`, `end` (`yyyy-MM-dd HH:mm`, both optional; a bare `yyyy-MM-dd` day is accepted as well and read as that day's 00:00 hour), `kind`, `groupBy`=`tool` (default) \| `mcp` \| `cli` \| `agent` \| `session` | Card counters plus the row list (`kind` / `subjectKey` / `subjectId` / `subjectName` / `parentName` / `toolName` / `calls` / the four terminal counters / `successRate` / `avgDurationMs` / `p95Operator` (`<=` or `>`) / `p95Ms` (Long) / `lastSeenAt`). The `tool` / `mcp` / `cli` tiers read the aggregate table, `agent` / `session` read the detail table. P95 is given as two fields, "operator + number", instead of one display string: the wording is built by the front end's `pages.callMetrics.*`, the server only gives numbers, and sorting and bar drawing want the number. Row names always come out of the server (D18), so the page never has to work out from an id who a row is |
| `GET /time-series` | `start`, `end`, `granularity`=`auto` (default) \| `hour` \| `day` \| `week` \| `month`, `kind`, `subjectId` | A bucket-zero-filled time series (`timePoint` × dimension, each row carrying `dimensionId` / `dimensionName`); the response also returns `granularity` — the bucket is chosen server-side, so the page labels its axis with the tier that came back instead of computing it again |
| `GET /invocations` | `start`, `end`, `kind`, `toolName`, `mcpId`, `cliId`, `agentId`, `sessionId`, `outcome`, `pageNum` / `pageSize` | Paged detail as `ResultVo<Page<...>>`, including `error_message` / `args_json` / `result_excerpt` |

Range parsing lives in exactly one place (`ToolMetricsServiceImpl.window`), shared by the three endpoints and the drill-down: `end` defaults to the current hour and a value the clock has not reached is clamped back to it; `start` defaults to 719 hours before `end` (that is the 720-hour, 30-day default window), is clamped to `end` when later than `end`, and when the span exceeds 8760 hours (365 days) `start` is pushed to `end - 8759 hours`; if either value cannot be parsed, the whole thing runs on the defaults and one `log.info` line is written. Clamping always rewrites the value to the boundary rather than refusing the request, and every clamped value leaves one log line. The two window ends come back in the response as `from` / `to` (`/time-series` returns those two fields too, plus `granularity`), and there is no day-count field in the response: a day count is derived from the range, and what the page has to annotate are the two hours it selected.

The trend bucket is chosen server-side: an explicit `hour` / `day` / `week` / `month` in the request wins, and on `auto` or nothing the span decides — up to 48 hours answers hours, up to 92 days answers days, anything wider answers weeks. The zero-filled bucket starts use exactly the same four alignments as the SQL (the hour itself, 00:00 for a day, Monday for a week, the 1st for a month); two different origins would find no row in any bucket and answer a field of zeros.

`groupBy=mcp|cli` reads the aggregate table just like `tool` and can answer windows past the retention period; `agent` / `session` go through the detail table (the aggregate carries neither of those two dimensions), so they are bounded by the retention window. The detail path has no duration buckets to answer with, so on those two views each row's P95 is `<=` paired with that row's **longest measured call** inside the window (`MAX(duration_ms)`, see `ToolMetricsServiceImpl.detailRows`) — it is an upper bound of the quantile, not the quantile itself, while the window P95 on the cards of the same response is still computed from buckets (`p95()` in the same file). The detail read and the aggregate read must answer one and the same range: both start at the starting hour, but the aggregate compares `stat_hour <= to` (such a row covers sixty minutes) while the detail compares `ts < to + 1 hour`, and any other pairing puts the last hour of every window one step out of step between the two tables. Paging keeps `PageHelper.startPage` + `admin/dto/Page.fromPageInfo` (current examples `AgentToolController.kt:26-39` and `AgentToolServiceImpl.kt:26-31`).

The response shape is constrained by admin's existing output conventions: `default-property-inclusion: non_null` in `application.yml` makes Jackson 3 drop keys whose value is null, so DTOs always declare non-null defaults; a business error is HTTP 200 carrying a `code`.

The `0` in `subjectId` lands exactly on that convention. In the aggregate table `subject_id` is defined as "`mcp_id` when `kind=mcp`, `cli_id` when `kind=cli`, `0` otherwise" (DDL `V3__tool_invocation_metrics.sql`), and the three origins share that one field for the same value; the service side folds `0` into null before returning it (`ToolMetricsServiceImpl.subjectIdOf`), and combined with `non_null` that means the JSON of a builtin / shell / framework row **has no `subjectId` key at all**, rather than the key being equal to `null`. `subjectKey` is the row's ownership key: on the `tool` tier it is the tool name itself, on the other four it is the id as a string (the session tier uses its `session_id` string). `parentName` has a value only on rows whose `kind` is `mcp` or `cli` — it is what lets a tool-tier row say which server or which package answered it.

## 11. Tests and acceptance

- Unit tests: the `kind` classification pure function, exhaustive over the five input shapes and the priority conflicts; CLI command parsing (pipes, `&&`, absolute paths, quoted strings containing spaces); the `ToolResultState` → `outcome` mapping; the `INTERRUPTED` fill-in for non-terminal calls; truncation and the switch that turns it off; the dropped counter. Pure-function tests use JUnit5 `org.junit.jupiter.api.Assertions` plus backtick-sentence method names (current example `harnax-agent/harnax-harness-core/src/test/kotlin/com/agnetix/harnax/harness/skill/TenantSkillVisibilityFilterTest.kt`); middleware stream tests use the `reactor-test` the module already has.
- Persistence-layer tests (`harnax-entity`, a real MySQL 8 container): `harnax-entity` has no failsafe and no `integration-test` profile, so the container tests of this layer are called `*MapperTest`, shaped like `TokenStatsMapperTest.kt:33-61` (`@Testcontainers @MybatisTest @AutoConfigureTestDatabase(NONE) @ActiveProfiles("test")` plus one `MySQLContainer("mysql:8.0").withInitScript("schema-test.sql")` per class in the companion). Gates: three calls in one session must land three rows at three distinct instants; a `batchInsert` of N rows returns N and an empty batch sends no SQL; recomputing the upsert twice leaves the result unchanged; the six buckets sum to `calls`, which equals the sum of the four terminal counters.
- End-to-end persistence tests (`harnax-admin/src/test/kotlin/com/agnetix/harnax/admin/it/`, extending `BaseAdminIT`): the gates for aggregation, the read-side tenant predicate and cleanup live here, because only the admin-side IT replays the real full `db/migration` set (the baseline plus every forward increment in the directory; a shared container, schema built by the migrations). Both classes clear the two metrics tables in `@BeforeEach` and then mint their own fixtures, and the read side additionally writes one `agent` row, one `mcp_server` row and one `cli` row — the admin IT database seeds no registration row besides `skill_repository`, so the name-resolution gate has nothing to borrow, and the three must be deleted again afterwards (a re-run against the shared container collides on the unique key, and the other classes that read these tables expect only the rows they inserted). The read side writes into tenant 1 and opens a neighbour at `950_500`: only assertions in both directions prove the tenant predicate is converging the data rather than one batch happening to sit alone.
  - Read side: the tenant predicate must filter out its own data — the neighbour tenant's two rows land in a different whole hour of the very day this page's data sits in, so one response missing the tenant predicate answers with those two rows included. Each of the four clamps on a whole-hour range has its own case: `end` later than the current hour clamps to the current hour (`futureEndClampsToTheCurrentHour`), `start` later than `end` collapses onto `end` (collapsing beats flipping, since a flipped range answers an empty table while still claiming a window), a span over the cap keeps `end` and pushes `start` back to the 8759th hour before it (refusing to answer would blank the whole row of cards over a range no reader would ask for), and when neither value parses the request runs on the default 720-hour window with `totalCalls` asserted non-zero, which proves a broken picker answers the chart rather than the error card. All four assert on the `from` / `to` the response echoes rather than on the log, and the two echoes themselves must land on a whole hour: echoing the requested value tells the page "I answered the boundary you asked for", and that boundary does not exist. Granularity has a case of its own, taking both sides of each of the 48-hour and 92-day boundaries (a boundary belongs to the finer tier) and proving that an explicit `granularity` overrides the range. In the fixtures `start` / `end` are written as bare dates while everything else carries `HH:mm`, so both parsing paths are exercised inside this one class.
  - Aggregation and cleanup: `retention-days=0` is out of reach — `ToolInvocationRollupService.clampToWindow` clamps it back to the floor of 1, so the gate at this layer is not "how small the window is" but "not rolled up, therefore not deleted". The fold and the sweep each have a full set of cases (`ToolInvocationRollupIT`, every one recognisable by method name): an hour missed entirely is rolled on the next run (`missedHourIsCaughtUp`, which also asserts the half-open bucket — 120 ms lands in `(100,500]`, not in `<=100ms`); the running hour is re-rolled and a row written after it is brought in on the next pass (`currentHourIsRerolled`); a row that arrives after its hour was folded is caught by the forced revisit of the hour before the running one (`lateRowOfTheClosingHourIsFolded`); tenantless detail never enters the fold at all (`tenantlessRowIsNeverRolled` — the aggregate table declares `tenant_id NOT NULL`, and counting such a row as pending would make the difference set never empty and starve the hours that can be rolled); a row dated in a future hour is not folded (`futureDatedRowIsNotFolded`, six hours ahead so it stays future to every round the case makes rather than merely later than midnight); an hour past the window is folded and released inside the same run and the order cannot be swapped (`expiredRowWaitsForItsRollup`); the delete never touches an hour the rollup did not fold (`unrolledHourIsNeverReleased`, proved at the mapper seam, since a normal round folds before it releases); expired rows with no tenant are released without waiting for an aggregate (`tenantlessExpiredRowsAreReleased`); a row just inside the window survives (`rowInsideWindowSurvives`, which makes the window's value observable instead of a number copied between the test and `application-it.yml`); the hourly rows add up to the detail they were folded from and the buckets travel with the hour (`hourlyRowsSumToTheirDetail`); folding the same hour twice changes nothing (`foldingTheSameHourTwiceChangesNothing`); and the kill switch leaves both tables untouched (`killSwitchWritesNothing` — `rollUpHourly()` is the only reader of `rollup-enabled`).
  - `SchemaBaselineDriftIT` is the invisible gate: putting the new tables only into the migrations (V3) and not into `schema-test.sql` turns all six of its assertions red; conversely, a table dropped by a DROP (V4's `tool_call_log`) left in `schema-test.sql` means the fixture carries a table production cannot build — `DROP TABLE` is a statement shape it already models, so dropping it on both sides keeps the gate green. Columns and indexes are compared in both directions as well: V5 renames `stat_date` to `stat_hour` and replaces the two keys, so if either side fails to follow, the run is red twice — "in the migration, missing from the baseline" and "in the baseline, missing from the migration" — and a half-applied rename cannot hide behind a single red line.
  - Timezone trap: Testcontainers' MySQL is UTC while the Java side writes `LocalDateTime` into `datetime` using the JVM timezone, so every aggregation and cleanup case pushes relative whole hours forward and back from `LocalDateTime.now().truncatedTo(ChronoUnit.HOURS)` instead of writing an absolute date — a hard-coded day drifts an hour between UTC and the JVM timezone, and a fixture one hour off lands exactly on the "not yet rolled up" side, which makes the case fail in a way nobody can explain.
- How to run: `mvn -o test -pl harnax-entity`; on the admin side `mvn -o verify -pl harnax-admin -am -Pintegration-test -Dit.test=<ClassName> -Dtest=<ClassName> -Dsurefire.failIfNoSpecifiedTests=false -Dfailsafe.failIfNoSpecifiedTests=false` (neither `-am` nor the two `failIfNoSpecifiedTests` flags may be dropped, `docs/unit-test-cases.md:799-810`). ## 12. Known boundaries and non-goals

- When two delivered CLIs appear inside one shell command string, only the leftmost hit is recorded (splitting a compound command across rows would break I1, and the cost is an undercount; the full command string sits in `args_json` for checking).
- CLI command aliases come only from `name` plus the first word of each `checkCommand` segment (with the path prefix stripped): the alias set is computed at assembly time (`HarnessAgentLauncher.kt:619-623`) while package materialization happens further down the same method (`resolveImage` at `:686` of the same file), so there is no "classify once against an unmaterialized alias set" branch. A binary inside a package that appears neither in the package name nor as the first word of any `checkCommand` segment cannot be attributed and lands as `kind=shell`. `checkCommand` is a mandatory manifest field (without it the parse is a failure outright, `harnax-admin/src/main/kotlin/com/agnetix/harnax/admin/registrar/CliPackageParser.kt:252-253`) and it executes inside the image, so its first word is on the PATH by construction — which is also why "scan the `/bin` directories to supplement the aliases" was rejected in the first place.
- When two MCP servers expose a tool under the same name, the overwrite by name happens in upstream's `io.agentscope.core.tool.ToolRegistry` — it keys by tool name (`tools` is a name-to-tool map and `registerTool` does `tools.put(toolName, tool)` directly), and `Toolkit` merely holds and forwards to it, so the model side can only ever see the one registered last. Attribution follows that registry's enumeration (`HarnessAgentBuilder.kt:305-307`), so the call is credited to the server that survived, which matches who was actually invoked at runtime. This project's `com.agnetix.harnax.tools.sdk.registry.ToolRegistry` is a different class carrying the same name: it keys the admin-delivered `ToolBox` beans by Spring bean name (`harnax-agent/harnax-tools-sdk/src/main/kotlin/com/agnetix/harnax/tools/sdk/registry/ToolRegistry.kt:23`, `:29-30`) and takes no part in MCP registration.
- The harness's own `read_file` / `memory_*` are not in the MCP enumeration (they are mounted only at build) and are not in the admin-delivered `toolSpecs` either, so they land as `kind=framework` rather than `builtin`; on the page the two origin buckets are named per D16: "Available tools" (the list admin delivers) and "System built-ins" (what the harness brings itself). `execute` is the exception to this line: the shell check runs ahead of `builtinToolNames` (`ToolInvocationClassifier.kt:50-58`), so it tries CLI attribution first and, on a miss, lands as `kind=shell` — it is framework on neither side.
- The row-name drawer has content only when "there really is a row in a registry": the `agent` dimension queries the `agent` table, the `mcp` / `cli` dimensions query the `mcp_server` / `cli` tables, and the `session` dimension queries the session configuration — all four answered by admin's existing read endpoints. Rows whose `kind` is `shell` / `framework`, and names under `builtin` that miss the admin tool registry, have no row to query at all: the drawer then gives only that row's own counters plus one `pages.callMetrics.profile.empty` note, rather than inventing a profile, because the identity of a system built-in tool exists only in the Toolkit at assembly time. The `tool` dimension does not query the registry by name (`AgentToolController`'s `/{id}` is a Long); it matches by name against the list, and a miss lands on the same "nothing is registered behind this row".
- The time-series bucket is chosen server-side from the range (`granularity=auto`), and an explicit `hour` / `day` / `week` / `month` overrides the range; the page offers no tier selector, because the bucket on this read path was never what the reader asked for — what they ask for is a line they can read. Pulling the range to its 365-day ceiling gives 53 week cells rather than 8760 hour cells.
- No OTel / distributed trace; no per-tool cost accounting; no metrics read endpoint on `mcp_call_log`; no external metrics store such as ClickHouse; no distributed lock introduced for admin.
- `args_json` in the detail may contain sensitive literals, so it is truncated by default and can be switched off as a whole with `capture-payload=false`; this design does no field-level redaction.
- Read side: the `agent` / `session` rows of `/summary` come from the detail table, so the hours of the selected range that fall outside the retention window (90 days by default) necessarily cannot be answered in full — detail is cleaned up on "rolled up, therefore released", and when the range is pushed back past the window that stretch only has the aggregate left; the card total in the same response goes through `selectWindowTotals` (the aggregate table) and is the only figure on those two tiers unaffected by the window, and the drill-down drawer is bounded by the range just the same. The `tool` / `mcp` / `cli` tiers read the aggregate and are not bounded by this line. The page's hint is given per **dimension** rather than per range length (it shows only when `readsAggregate` is false, `harnax-webui/src/pages/call-metrics/dimensions.ts`) — an agent/session range lying wholly inside 90 days still only sees detail, so this definition must not be read as "a range of ≤ 90 days is complete".
- A team lead's calls have no `agent` to be attributed to: `AgentSpec.attributableAgentId` folds `LEAD_ID` into null (`harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/agent/AgentSpec.kt:64-72`), and there was never an `agent` row behind a lead, so its calls appear only in the `session` dimension and in the window cards. The `HAVING subjectKey IS NOT NULL` on the agent branch of `selectSubjectTotalsFromDetail` (`harnax-entity/src/main/resources/mapper/ToolInvocationLogMapper.xml`) excludes this whole group, so within one and the same `/summary` "adding up the calls of all rows" comes out smaller than the card total, and the difference is exactly the lead's share.
- Roll-up: `rollUp()` recomputes only "the hours the aggregate table does not have yet" plus the current hour and the hour before it, and `deleteRolledOut` looks only at the window, so **a detail row that arrives late for an hour that was already folded — and is no longer the current or previous hour — is released outright and never enters the aggregate**. That is a price paid deliberately: producing such a late row takes a clock rolled back by more than an hour, and reopening every already-folded hour for its sake means re-reading the entire detail table inside the retention window every run (the trade-off is written in the KDoc of `ToolInvocationRollupService.rollUp()`). Integration tests cannot see this one — the cleanup never reaches rows that are still inside the window.
