# Harnax Multi-agent Team 设计与方案取舍（中文）

> 英文版本见 [multi-agent-team-design.en-US.md](./multi-agent-team-design.en-US.md)。
>
> 决策日期：2026-09-18。本文整理本轮讨论确认的产品边界、目标设计、备选方案与取舍，不代表功能已经实现。
> 当前交付仅为设计文档：没有新增 Team 表、管理页面、团队运行接口或团队文件工具；没有完成运行原型验证。
> 用户最终选择为：**独立 Team、复用现有 Agent、主管只编排、成员执行、成员独立沙箱、MinIO 产物交接、过程可见与人工确认**。早期共享沙箱和主管开关方案不再作为实施依据。
>
> **2026-09-20 修订（D1/D2 变更）**：主管不再引用一个现有 Agent，改由 Team 自带主管配置——原智能体向导「基本信息」一项（名称、说明、系统提示词、模型）即团队配置，`team.instructions` 并入系统提示词；主管只可再配 Skill，Tool、MCP、CLI 一律不要。成员侧口径不变。本文相关章节已按此改写，落地细节见 [团队主管配置内聚设计规格](../docs/superpowers/specs/2026-09-20-team-own-lead-config-design.md)。

## 1. 目标与设计原则

目标是在尽量少改现有代码的前提下，支持可配置的多智能体协作（Multi-agent）：用户组建团队、向主管提出目标，由主管安排成员执行具体任务。

“少改代码”有明确边界：

- 复用现有 Agent 定义、配置下发、模型与工具装配、会话路由、沙箱管理和 MinIO 基础设施。
- 团队只自带主管这一份配置（模型、提示词、Skill）；成员的能力仍完全保存在它自己的 Agent 上，不为组队复制第二套 Tool、MCP、CLI 或凭证，也不引入新的工作流引擎或远端 Agent 服务发现系统。
- 不以成员能力缩水、主管权限扩大、跳过人工确认为代价减少代码。
- 原有 Agent 的配置和独立使用方式不变，不等于所有原有代码完全不用修改。

## 2. 最终决策与工程建议的边界

| 编号 | 结论 | 状态 |
|------|------|------|
| D1 | Team 是独立的组队配置，不是新的 Agent 类型，也不是主管 Agent 上的一个开关；它同时是**主管配置的宿主**（模型、提示词、Skill 存在 Team 上） | 已确认（2026-09-20 修订） |
| D2 | **成员**引用现有 Agent，同一 Agent 可在多个 Team 复用；**主管不引用任何 Agent**——`agent` 表里只有「可独立对话的 Agent」和「作为团队成员的 Agent」两种身份 | 已确认（2026-09-20 修订） |
| D3 | 主管只负责拆解、委派、协调、验收、重派和最终汇总；成员负责具体执行 | 已确认 |
| D4 | 团队角色限制只作用于本次运行实例，不修改原 Agent 的持久化配置 | 已确认 |
| D5 | 主管与成员在同一 agent-service 实例内运行；成员使用独立会话状态和按需创建的独立沙箱，主管不创建执行沙箱 | 已确认；独立沙箱替代早期共享方案 |
| D6 | 成员通过 MinIO 发布、获取不可覆盖的文件产物，不共享完整可写工作区 | 已确认 |
| D7 | 展示成员执行过程，需确认的动作交给用户；批准后恢复对应成员，再交回主管 | 已确认；不得静默降级 |
| D8 | 优先复用 AgentScope 原生委派机制，以成员工厂装配各自完整能力，不混用两套委派协议 | 推荐接法，需原型验证 |
| D9 | 首期建议单层、顺序、前台委派，先跑通 Web UI；不同时交付并行后台任务、嵌套团队、A2A 或工作流画布 | 范围建议，不是已交付能力，也不是撤销 D7 的理由 |

D9 旨在控制工程范围。后续若增加并行或新的入口，需要单独验收并发关联、确认、取消与身份传播，不能因为 UI 能选 Team 就宣称所有渠道都已支持。

## 3. 产品模型：Agent 是可对话单元与成员，Team 自带主管

### 3.1 三类对象

| 对象 | 存什么 | 不存什么 |
|------|--------|----------|
| Agent | 模型、提示词、Tool、MCP、Skill、CLI 配置 | 不再存在「代表团队主管」的 agent 行；不因加入团队复制另一份能力配置 |
| Team | 名称、说明、**主管配置（系统提示词、模型）与主管技能绑定**、启停及归属信息 | 不持有 Tool、MCP、CLI；不引用任何 agent 作为主管 |
| Team Member | 团队引用、成员 Agent 引用、在该团队中的分工说明 | 不复制成员模型、工具、凭证与技能 |

“成员”仍是引用一个已有 Agent，“主管”已经是 Team 自身的一行配置，不再对应任何 agent 行。同一个 Agent 可以被多个 Team 用作成员，也可以单独对话使用。

### 3.2 数据落点

`team`/`team_member`/`team_artifact` 与 `session.team_id` 已随 V32 落地；下列为 2026-09-20 修订后的最终形状（Flyway V34）：

| 落点 | 必要信息 |
|------|----------|
| `team` | `id`、`tenant_id`、名称、说明、**`system_prompt`、`model_id`**、状态、创建者及时间；不再有 `lead_agent_id` 与 `instructions` |
| `team_skill_binding` | `team_id`、`skill_id`，组合唯一；不设 `env_bindings`（技能级环境变量本就没有消费者） |
| `team_member` | `team_id`、`member_agent_id`、`delegation_description`；团队与成员组合唯一 |
| 会话 | `agent_id` 与 `team_id` 二选一：团队会话 `agent_id` 为 NULL、`team_id` 非空，名称/提示词/模型等快照取自 Team 行 |
| 成员运行记录 | 根会话、本次根运行、成员引用、子运行与子会话标识、状态、关联文件引用 |
| 文件产物元数据 | 文件 ID、归属租户和根会话、生产者子运行、原始文件名、类型、大小及内部存储定位 |

成员运行记录与文件元数据可优先适配现有存储扩展点，本文不要求每个逻辑对象都新建独立数据库表。

会话中的 `teamId` 是团队入口的依据，`agent_id` 为空即「这不是一个 Agent 的会话」：普通入口不会自动启动团队，团队会话也不能按某个 `agentId` 下发主管配置。主管配置一律由服务端从 Team 行解析，客户端不提交主管身份。

### 3.3 权限与有效性

- 创建、编辑和启动 Team 时，校验 Team 自身状态与归属、成员的租户、可使用权限、状态及存在性；主管的模型在保存时校验存在、按模型下拉同一口径可见（`is_public` 或本人创建）、已启用、类型为 chat——不按租户判，共享的公开模型照旧可用。运行时不再有一次「换用别的模型」的机会。模型保存之后被停用不会有任何提示，也不会挡住对话：下发只看模型行是否存在，运行侧对「停用」没有第二道闸门（普通智能体同此口径），团队仍会照它跑；只有模型被删除才会在下发时因取不到配置而失败。
- 至少选择一个成员；成员不重复。主管不再是 Agent 引用，因此不存在「主管同时是成员」这种校验。
- 能看见 Team 不等于可以使用其中任意私有 Agent；团队配置不能绕过成员自身的访问控制。
- 首期单层建议下，成员作为执行者时不加载其自己的团队关系，不允许继续派生子团队；不需要为此自建任意 DAG 执行器。
- Team 或 Agent 失效时，在启动或下一次委派前给出明确错误，不静默遗漏成员或换用主管模型。
- 一次运行及其确认恢复期间固定已解析的配置；不能在等待用户批准时换成另一套成员、工具或参数。配置变更生效和缓存失效方式须在实现阶段验证。

## 4. 页面如何组建和使用团队

管理台新增独立的「团队管理」入口，采用两步向导组队，不做拖拽连线。第一步就是原智能体向导的「基本信息」，第二步是成员。

```text
第 1 步 · 基本信息与技能                        [下一步]
团队名称    [研究报告团队]
团队说明    [负责资料收集、分析与报告生成]
系统提示词  [你是本次协作的负责人……]            ← 主管的全部提示词，含原团队指令
模型        [qwen3-max]
技能        [资料检索规范] [报告撰写规范]         ← 只可配 Skill，无 Tool/MCP/CLI

第 2 步 · 团队成员                              [添加成员]
资料研究员    分工：搜集资料并提供来源
数据分析员    分工：分析数据、提炼结论
报告撰写员    分工：根据资料和结论撰写报告
                                              [上一步] [取消] [保存]
```

### 4.1 配置交互

1. 第一步填写团队名称、说明、系统提示词与模型，按需挑选技能。说明与系统提示词必填，与智能体向导第一步一致。
2. 技能的可选范围与写时校验与 Agent 侧同一套规则：缺失、停用、内置 CLI 仓库来源、同名冲突都在保存时拒绝。
3. 第二步添加成员，分工说明默认带入 Agent 描述，允许按团队需要修改，不回写原描述。
4. Tool、MCP、CLI 只能在成员自己的 Agent 页面配置；Team 不收这三类字段，运行侧另有主管守卫。
5. 保存时执行成员与权限校验；独立沙箱模式不要求成员 CLI 版本或环境变量彼此一致。
6. 编辑团队复用同一个向导，回填当前配置。

团队成员使用稳定的服务端标识，显示名称和分工说明用于阅读与委派决策，不把可重名的显示名称作为运行唯一键。

### 4.2 对话交互

- 团队列表提供「编辑」和「开始对话」入口；开始对话创建绑定该 Team 的新会话。
- 原有选择 Agent 单独聊天的入口保持不变；不在已有普通会话中途悄悄切换为团队模式。
- 对话区展示主管安排、成员状态、可展示的执行文本、工具调用、文件产物和最终汇总。
- 成员过程折叠在主管那一次委派的工具卡内，不混入主管最终答案，也不另开并列气泡；“过程可见”不是展示凭证或要求模型披露内部思维链。卡片形态、收口信号与刷新后的回放规则见 §9.4。
- 人工确认明确显示成员、动作和参数；最终文件通过 Web UI 的受鉴权附件入口提供。
- 新文案遵循现有中英文国际化方式；暂不为团队引入独立子会话聊天窗口。

## 5. 主管与成员的能力边界

| 能力 | 团队主管 | 团队成员 | 原 Agent 单独使用 |
|------|----------|----------|------------------|
| 模型与提示词 | **配置来自 Team 自身**，叠加主管角色与成员名册块 | 自己的模型，叠加本次分工和任务说明 | 保持原有行为 |
| Skill | 装载：SKILL.md 文本与其资源内容进入主管上下文/技能读取工具；**带脚本或需落盘执行的部分不可执行**，装载时点名降级 | 按各自 Agent 配置装载 | 保持原有行为 |
| 业务 Tool、MCP | 不装载、不连接（Team 也不收这两类配置） | 按各自 Agent 配置装载 | 保持原有行为 |
| CLI、Shell、执行沙箱 | 不提供，主管无 shell 也就无工作区 | 保留自身配置与权限约束 | 保持原有行为 |
| 委派、进度与任务协调 | 允许使用本 Team 的编排能力 | 首期单层建议下不开放继续委派 | 保持原有行为 |
| 文件产物 | 接收和传递引用，选择最终交付文件 | 发布、获取并在自己沙箱中处理 | 保持原有行为 |

主管权限限制应由装配与运行时校验保证，不依赖“请勿亲自执行”这一句提示词。现有必须工具、框架默认 Shell、动态子代理及技能加载也要经过团队角色策略，不能从默认注册路径重新泄漏能力。

这不改变普通 Agent 的“必须工具”规则：主管没有 agent 行，也就没有可被收紧或删除的绑定；它的 Tool/MCP/CLI 为空是 Team 不收这类配置的结果，运行时守卫只是第二道线。

主管仍需理解成员报告、判断是否满足目标和汇总回复；“只编排”不是只能机械转发消息。必要的资料处理、数据库查询、文件生成等具体工作交给成员。

## 6. 配置下发与成员加载

### 6.1 目标链路

```text
Web UI 创建 Team 会话
    ↓ 根 sessionId 沿现有 router 路由
agent-service 获取团队运行配置
    ↓ admin 校验 Team 与成员：主管配置取自 Team 行与 team_skill_binding，成员配置取自各自 agent
装配主管 + 成员工厂（尚未创建成员运行实例）
    ↓ 主管按分工委派
创建子运行标识 → 按成员配置懒创建运行实例
    ↓ 子会话状态 + 该成员自己的 Tool / MCP / Skill / CLI
按需创建独立沙箱，执行任务
    ↓ 结果、文件引用、事件与确认请求
主管验收、继续委派或汇总 → 原 SSE 通道返回用户
```

### 6.2 配置与实例分离

- 成员复用 Agent 的配置定义，不复用另一个普通会话的运行实例、聊天历史或沙箱；主管的配置只存在于 Team 行与 `team_skill_binding`，运行侧拿到的是一份与 Agent 同形状的主管 spec（`agentId` 固定为 0，`agentName` 为团队名）。
- admin 下发成员完整配置，不能只给 `modelId`、`toolId` 后假设主管适配器能解析所有成员。
- 工厂捕获对应成员配置和受信任的运行作用域。现有 `AgentSpecContextHolder` 是同步创建阶段的 `ThreadLocal`，不能假设懒创建时它仍存在，更不能让成员读到主管的配置。
- 不把任意派生子会话 ID 直接交给现有按 `web-`、`mp-`、`chn-`、`task-` 前缀解析的 admin 入口；子运行由根会话已授权的团队配置派生。
- 子会话标识采用可被状态存储和沙箱管理接受的不透明安全标识，不直接使用事件来源字符串中的斜杠路径。
- 工厂懒创建不等于“每次调用后自动销毁”。首次委派创建子会话；明确续跑同一委派时复用它，新任务或重试是否复用须由运行记录明确，不只按成员 Agent ID 猜测。

### 6.3 AgentScope 接入选择

优先验证原生 `SubagentsMiddleware`、`SubagentEntry` 与带父运行上下文的 `SubagentFactory`，用工厂装配成员完整能力，保留原生委派思路；不自建调度引擎，不以声明式父工具子集替代成员配置。

这是推荐接缝，不是已经验证可直接插入的成品适配：需要正确处理 middleware 初始化、工具注册、任务仓库、真实子会话标识、Harness 生命周期、确认续跑和清理。不能只调用 `addMiddleware` 就认为所有工具自动就绪，也不能只返回裸 ReAct delegate 而跳过 Harness 的沙箱生命周期。

团队模式只注册配置成员，关闭该模式下的默认通用子代理和工作区动态成员发现；普通 Agent 模式不顺带改变。

### 6.4 用户身份与 MCP

- 子 Agent 代表根会话的已认证用户执行，不使用 Team 创建者或成员 Agent 创建者的 OAuth 授权冒充当前用户。
- 成员只能装载自身配置且经授权的 MCP；主管不连接成员 MCP，也不接收成员凭证。
- MCP 换发仍由 admin 根据受信任会话反查身份，不新增可由调用者指定的 `userId` 换发参数。
- 子运行应区分“状态/沙箱的子会话标识”和“授权所属的根会话标识”。未知子 ID 不能直接作为现有 OAuth 换发 `sessionId`；团队适配需要保留并校验根会话到成员运行的关系。
- 当前换发方法校验会话用户、租户及用户授权，不校验成员关系；团队的成员/MCP 范围校验是新增要求，不能声称现有接口已经完成。
- 沿用 stdio 禁用口径、逐用户授权与运行侧令牌注入；不因成员有独立沙箱就重新开放 stdio 或把 MinIO、Docker 管理凭证注入其中。

相关现状见 [MCP 管理](./mcp-management.zh-CN.md) 与 [MCP 出站授权设计](./mcp-authorization-design.zh-CN.md)。

## 7. 沙箱方案对比与最终选择

| 维度 | 成员共享一个沙箱 | 成员独立沙箱（选定） |
|------|------------------|----------------------|
| 资源与启动 | 一个容器，资源较省 | 多容器，启动与内存成本较高 |
| CLI 与依赖 | 必须统一，版本和环境可能冲突 | 各成员保留自己的 CLI、依赖和配置 |
| 文件协作 | 同目录直接读写，交接方便 | 需要显式发布和获取产物 |
| 凭证边界 | Shell 可接触共享环境，分目录不构成安全隔离 | 更强的成员级隔离，但仍受挂载、网络、容器权限影响 |
| 并行执行 | 容易覆盖文件、争抢端口和修改共同状态 | 文件与进程干扰较少，便于未来并行 |
| 故障影响 | 环境被破坏会影响所有成员 | 通常局限于对应成员 |
| 快照与回收 | 一份工作区，生命周期较少 | 多份状态与快照，生命周期管理更多 |
| 接入成本 | 需专门适配共享对象、凭证与引用生命周期 | 更贴近现有按会话管理沙箱，仍需子运行标识和产物交接 |

**最终选择独立沙箱。** 早期推荐共享主要为了降低资源成本，但资源最少不等于代码改动最少；独立沙箱更符合“成员保留各自 Agent 能力”的目标。

约束如下：

1. 主管只编排，不创建执行沙箱；文件系统能力不得回退到宿主执行。
2. 成员确实需要文件或 Shell 执行环境时才创建容器；单纯模型或远端 MCP 调用不必因此启动 Docker。现有预热和工作区钩子是否允许真正懒创建，属于验证项。
3. 逻辑隔离作用域为租户、根团队会话及成员子运行；底层若仍只接受一个 sessionId，使用唯一的子会话 ID 映射该作用域，不只用 `agentId` 或 `teamId`。
4. 明确续跑同一子会话可以恢复自己的工作区和快照；不同用户、不同根会话、同成员的不同并发任务不能误用同一容器。
5. 根运行停止时级联取消成员；容器、MCP 客户端、任务记录和快照均纳入生命周期管理，不依赖缓存过期碰巧清理。
6. 独立容器不是完全隔离承诺：不挂宿主 Docker socket 或其他成员工作区，不共享成员秘密环境，沿用部署层网络与资源限制。

## 8. 文件共享：MinIO 产物交接

### 8.1 为什么不共享完整工作区

| 方案 | 优点 | 代价或问题 | 选择 |
|------|------|------------|------|
| 同一可写目录或共享卷 | 直接读写，传递成本低 | 并发覆盖、权限交叉、工作区耦合，削弱独立沙箱价值 | 不选 |
| 整个工作区或沙箱快照交接 | 可以重建完整环境 | 体积大，可能携带凭证；快照用途是恢复，不是业务文件共享 | 不选 |
| 文件内容全部塞进提示词 | 小文本方便 | 大文件昂贵或超限，二进制无法直接交接 | 仅小型文字摘要 |
| MinIO 不可覆盖产物 + 文件引用 | 可鉴权、可追踪，适合独立沙箱 | 有上传下载延迟，需要元数据和生命周期 | 选定 |

团队文件区是“按租户和根会话隔离的逻辑产物集合”，不要求新建一套对象存储服务，也不是给所有容器挂同一块磁盘。

### 8.2 两个新增逻辑动作

| 动作 | 输入与行为 | 输出 |
|------|------------|------|
| 发布文件 | 从当前成员获准的工作区读取指定文件，上传 MinIO，登记产物元数据 | `fileId`、文件名、类型、大小及生产者关联 |
| 获取文件 | 校验当前子运行可访问该根会话产物，将指定 `fileId` 下载到本成员工作区 | 本成员的本地文件引用 |

这两个动作尚未实现，名称是业务语义，不是已经发布的工具名或 HTTP 接口。优先复用现有文件存储原语，但不能把现有 `persist/retrieve` 当成具备团队权限与跨沙箱写入能力的完整接口。

```text
研究员沙箱：生成 data.csv
    ↓ 发布，获得 fileId=A
MinIO 团队会话产物集合
    ↓ 主管把任务说明和 A 交给分析员
分析员沙箱：获取 A，分析后生成结论
    ↓ 发布，获得 fileId=B
撰写员沙箱：获取 B，生成 report.md
    ↓ 发布，获得 fileId=C
主管验收并将 C 作为最终附件引用交付用户
```

### 8.3 不可省略的文件边界

- `fileId` 是引用，不是授权凭证；获取、预览和用户下载都要校验租户、根会话权限和运行归属。
- 模型不能指定任意 MinIO bucket/objectKey；服务端根据已授权元数据解析存储位置。
- 发布只允许读取当前成员获准目录内的文件，获取只允许写入自己的工作区；拒绝路径穿越及符号链接越界，限制大小与传输资源消耗。
- 每次发布产生新文件 ID，不覆盖旧产物；同名文件可以共存，主管显式选择交给后续成员的版本。
- 仅发布明确选择的产物，不自动上传整个工作区、环境变量、密钥或完整快照；秘密文件不应进入可发布目录和结果提示。
- 上传完成并登记可读取元数据后，才返回可用引用；发布失败不能返回看似成功的文件 ID。
- 文件引用及归属需持久化，不能随某个沙箱回收而丢失；产物清理与会话保留策略关联，不能永久无限累积。
- MinIO 不可用时，明确报告产物交接失败，不能悄悄改用公共临时链接、宿主目录或大文件提示词传递。

主管只传引用和摘要，不下载到主管沙箱；必要的文件内容核验仍委派成员完成。

### 8.4 现有附件链路的复用限制

当前 `OutputFileStore` 已提供 MinIO 文件写入/读取原语，但现有下载 Controller 对 web/task 文件只检查登录状态，没有团队会话级所有权校验。**团队产物不能直接放到这个可按旧规则读取的位置，再声称已隔离。** 实现时必须补齐对应下载入口的对象级授权，或选择无法由旧入口访问的受保护存储范围并提供受鉴权入口。

复用基础设施不等于复用其所有默认权限。现有沙箱快照用于工作区恢复，不作为团队产物；最终文件交付先走 Web UI，不借此扩展渠道文件投递能力。

## 9. 事件、确认与失败处理

### 9.1 统一根会话，保留子运行来源

外部继续使用根会话的 SSE 通道与粘性路由；成员在同一实例内执行，不给每次委派创建独立外部路由请求。

团队事件至少需要可关联根运行、成员、子运行及必要的工具调用。可采用明确字段或服务端映射，但不能只用 `agentId`、显示名称或 SDK 的 `source` 字符串区分同成员的多次任务。工具参数与结果缓冲也必须考虑子运行作用域，而不是假定所有 `toolCallId` 全局唯一。

只把成员报告和产物引用作为主管的输入，不将成员每段流式文本直接拼成主管最终答案。成员执行日志、用户可见文本与 token 统计应标记来源；根会话汇总成本时避免重复计数。

### 9.2 人工确认闭环

```text
成员请求确认
    ↓ 记录根会话、子运行、工具调用及待确认参数
前端展示成员和动作，用户批准或拒绝
    ↓ 服务端校验用户、归属、待确认状态和一次性决定
将决定交回原子运行，而不是主管自己的工具列表
    ↓ 成员执行或处理拒绝，产生结果
主管收到成员状态与结果后继续
```

等待确认不能当成任务成功；拒绝、过期、已取消和重复提交必须有明确处理，不能导致工具重复执行。等待期间保留原运行上下文；超时、断线或进程退出后不能默认批准，也不能以已完成状态恢复。

等待期间根流不能静默。会话路由对 120 秒无事件的流判空闲，渠道侧为 180 秒，而等待用户回答本身可以持续数分钟，静默会把还能继续的运行误杀。运行时在等待中按 `harness.team.confirm-heartbeat-seconds`（默认 30 秒）在根 SSE 上补发 `KeepAliveEvent`：只带子运行来源，不带内容也不带用量，所有消费端一律忽略，既不当作输出也不当作结束。

心跳只防得住还没断的流。等待期间被切断的流（超时、关页、进程退出）其待确认工具只剩持久化状态里的 ASKING 记录，下一次请求必须按原参数把确认卡重放出来，让用户继续回答；只回一个无法处理的错误等于把会话判死——新消息一直报同一个暂停，确认又报没有待确认工具。

不能用以下替代方案冒充 D7：自动批准、把需确认工具从成员删除、统一自动拒绝、让主管代执行所有危险动作。无交互能力的入口若要接 Team，必须另行定义确认策略，不属于默认支持范围。

### 9.3 生命周期与预算

- 成员失败时向主管返回明确失败状态、可用结果和已发布文件引用；是否重派由主管决定，不能返回伪成功。
- 用户停止根运行时停止正在执行的成员，阻止后续委派，关闭运行资源；Shell/MCP 已发出的外部副作用不能靠取消回滚。
- 明确限制总委派次数、成员迭代、运行时间、活动容器与文件传输量；具体阈值由实现和验证确定，不在本设计编造默认数字。
- 若采用前台顺序委派建议，需要在运行时限制并发和禁止超时自动转后台，不能只写进主管提示词。
- 进程崩溃或路由迁移后，快照可用不等于在途任务可以无损续跑；首期不得自动重放有副作用的工具调用。标记中断并允许受控重新发起，确认恢复与沙箱恢复分别验证。

### 9.4 成员消息在会话页的呈现与回放

呈现只回答「这句话是谁说的」，不改变 §9.1 的来源契约、§9.2 的确认闭环和 §9.3 的生命周期语义。

**同一份来源标识同时服务实时与历史**。实时事件带 `ChatEvent.source`。历史消息落库时不带来源，成员会话也与主管会话分开存放，所以回放时按根会话的 Team 名册为每个成员子会话补齐一份字段一致的 `EventSource`：团队、成员、子运行、子会话。名字取当前名册而不是当时的快照——成员改名后，用户看到的应该是它现在的名字。运行标识从未落库，回放时由子会话标识顶替——它能说清「这是一次成员运行」，但成员子会话会被多次委派复用，所以单靠它分不清出自第几次委派、该嵌进哪张委派卡。前端依旧不得用显示名称或 `agentId` 反推归属：判定是不是一次成员运行只看子运行标识，判定它属于哪次委派另按调用顺序认领（见下）。

**成员运行嵌在主管的委派卡内**。主管的一轮回答仍是同一个持续追加的气泡，成员不再另开并列气泡，而是渲染在它所属那次 `team_delegate` 工具卡里面。归属在消息创建时就定下，不留到渲染时再找：实时按 FIFO 取该成员已发出、尚未被认领的卡片，回放按顺序扫该轮已有的卡片，两条路都只认成员标识与调用顺序、不认时间戳，所以实时看到的顺序与重开后看到的顺序仍然一致。认领不到卡片的成员运行照旧单独成气泡——委派被拒绝、历史里主管那一轮没留下调用记录、名册读不到时的降级，任何一种都不能把成员输出从界面上弄丢。不在委派处把主管气泡切开——切开后 `team_delegate` 的工具卡片会与它自己的结果事件分家，工具状态无法归位。

**成员运行的收口信号只有主管的委派结果**。服务端会过滤成员的结束事件，前端收不到「子运行结束」。收口依据是主管 `team_delegate` 的结果事件：用工具调用标识关联本次委派，再按参数中的成员标识定位它所属的卡片与运行。成员运行同时只允许一个未收口、且委派为前台阻塞，这使映射保持唯一。卡片已经返回结果却没有运行认领它（委派被拒绝，或委派本身失败），要把它从待认领里摘掉——留着会抢走该成员下一次委派的位置。另有三个兜底：主管结束、主管报错、根流断开，都必须把仍未收口的成员运行置为终态。「没有更多事件」不等于「完成」，中断要显示成中断。

**收口不等于成功**。主管要靠委派返回值决定改派还是收口，所以除成员自己抛出错误事件那一条路径之外，其余失败收场（执行中被用户停止、反复请求确认被中止、等确认超时、成员没有返回内容、成员运行抛异常）都以正常返回值回到主管手里，`team_delegate` 的结果事件不带失败标记，这些运行在界面上显示已完成。因此「已完成」当前的确切含义是「这次委派已收口，且期间没有收到失败事件」。要让它诚实，要么给委派结果一个失败态，要么在成员运行结束处补一条带来源的收口事件；两者都改到渠道侧共同消费的事件流与模型可见的工具结果，另行决策。历史回放不带任何生命周期信息，重开后的成员运行一律显示已完成；但那一轮里没等到结果日志的工具卡片会显示已中断——工具级状态看得出这轮被切在哪里，整轮状态看不出。

**折叠：委派卡默认收起，有运行在跑时自动展开**。折叠控件就是 `team_delegate` 卡片自己的头部，不再另有一套成员气泡头。收起时也要看得出这张卡给了谁：卡片头部右侧标成员名，一张卡里挂着多次运行时标「名字 +N」。展开后每个成员运行有自己的标题行——成员名、团队、状态、工具次数、耗时——正文是它自己的文本与工具卡，确认入口也在其中。任务首行不在这里重复，它本来就在同一张卡片的委派参数里；只有认领不到卡片、单独成泡的成员运行才在标题行上显示它。有运行在执行或等待确认时卡片自动展开，收口后自动收起；用户手工开合优先于自动态，覆盖只对当前卡片生效，切换会话即清空。状态四态可见——执行中、等你确认、已完成、失败，其中「等你确认」是 §9.2 的入口，等确认期间卡片保持展开，入口不会被折叠藏掉。

**历史回放靠合并子会话，不引入迁移**。读取历史时以主管会话为主线，按子会话命名规则找回成员会话的消息，只保留成员的可展示文本与工具调用，再穿插进去。穿插与归运行都以「一轮」为最小单位，不能只按时间戳排序。对主管而言，把一条 assistant 消息与它自己的工具结果拆开，会破坏前端依赖的配对；对成员而言，两个成员可以并发跑，混在一起排序会让一个成员的日志插进另一个成员的调用与结果之间，前端的工具卡片就永远收不了口。因此以主管的一轮（assistant 消息加上紧随其后的工具结果）为插入单位，成员日志落在产生它的那一轮之后、主管下一轮之前；前端回放时把它们按调用顺序认领到该轮的 `team_delegate` 卡片里，与实时看到的顺序一致。落库的工具日志不带工具调用标识，回放要按消息内序号给每张卡片补一个合成标识——认领只要求它在同一条消息内稳定，不要求跨会话唯一。委派是前台阻塞的，这个落点因此是确定的。子会话标识不区分委派次数，回放以连续性为准：与上一条同属一个子会话的成员日志并入当前运行，被主管的日志打断就开新运行——实时看到几个成员运行，重开后还是几个，各自嵌在自己的那张委派卡里。成员任务首行从主管已落库的委派参数中取得，因为成员的任务简报不进入合并后的时间线；取法是顺序扫：委派参数落库在成员跑之前，扫到主管这一轮就记下「该成员最近一次的委派原文」，其后的成员运行直接取用，只用在它单独成泡时的标题行上。不按成员建任务队列——委派没写任务、或成员一条日志都没产出，队列就会与运行错位，而成员被派两次时后一次覆盖前一次，正好与它自己的日志对上。一轮里可以有多个工具调用，回放必须在这条 assistant 日志之后把同来源的工具结果按名字逐个配对，只配第一条会让其余调用永远停在「正在调用」。同一条规则也管工具级的中断：回放里配对不上的调用、实时流收口时（主管结束、主管报错、根流断开）仍没等到结果的调用，都收口成「已中断」，处于等待确认的卡片除外——它已有自己的状态，不能被覆盖。晚于主管最后一条落库消息的成员运行（被中断，或主管没来得及汇总）仍追加到时间线末尾，不能消失。名册读不到或成员子会话没有内容时只返回主管历史——不能因为团队历史读不全而让整个会话打不开；成员被移出团队后也走这条降级，它的历史运行因此不再出现，那次委派只留在主管气泡的 `team_delegate` 结果文本里。不引入迁移的代价在找回成员会话这一步：先列出全部会话标识再按前缀过滤，而「有没有成员子会话」只能靠这一步判断，所以每次读会话历史都会做一次全量会话扫描——普通会话也一样，只是扫完就返回，不再取名册、也不读成员会话。扫描成为热点时改为按前缀查询，而不是给会话加第二份索引。

**主管标识只在团队会话出现**。主管名字取自会话配置已有的智能体名称，仅当会话绑定团队时在气泡上标出，用于与委派卡内的成员运行对读；标识缺失时不显示，不为此新增字段或请求。

## 10. 历次方案对比与取舍记录

### 10.1 协作范式

| 方案 | 适用点 | 主要代价 | 本轮结论 |
|------|--------|----------|----------|
| 主管—委派 | 主管动态安排专业成员，贴合目标 | 多一层模型调用，需要预算和验收 | 选定 |
| 固定流水线或图 | 顺序确定、易复现 | 需要额外流程配置与运行语义 | 首期不选；不是断言 SDK 完全没有相关能力 |
| 群聊协商 | 多视角讨论 | 消息广播、发言顺序和终止控制更复杂 | 不选 |
| 跨服务 Agent/A2A | 独立部署与跨系统复用 | 远端身份、发现、任务协议与故障处理扩大范围 | 不选；不代表未来禁止 |

### 10.2 Team 建模

| 方案 | 好处 | 问题 | 结论 |
|------|------|------|------|
| Agent 上增加团队开关和成员绑定 | 数据和页面较少 | 团队不是独立对象，普通使用与带队使用耦合 | 已撤回 |
| Team 一对一挂主管，访问主管即访问团队 | 可以复用原入口 | 同一个主管的普通会话与不同组队不易区分 | 已撤回 |
| 独立 Team + 主管引用现有 Agent + 明确团队会话 | 主管能力零重复维护 | 团队无法脱离一个现成 Agent 存在，「配团队」变成「先配 Agent 再挑它」 | 2026-09-18 选定，2026-09-20 被下一条替代 |
| **Team 自带主管配置（模型、提示词、Skill）** | 团队是自包含对象，向导一步配完主管；`agent` 表只剩「可对话」与「成员」两种身份 | 下发侧要为主管合成一份 spec；会话的 `agent_id` 必须允许为空 | **选定**（2026-09-20） |
| Team 持有一条隐藏的 `agent` 行做主管 | 运行侧完全不动，`session.agent_id` 也不用改 | 引入幽灵 agent：列表与选择器每处查询都要记得过滤，命名与 workspace 键要防撞，直连改删要另加守卫 | 评估后否决——把一次性成本换成永久陷阱 |
| Team 另存 Tool、MCP、CLI 绑定 | 团队配置完全自包含 | 与成员 Agent 的能力定义重复维护、易漂移，且主管本就不该执行 | 不选；Team 只带来主管这一份模型、提示词与 Skill |

父子绑定表本身也能表示多对多复用；选择独立 Team 是产品边界，而不是因为“绑定表只能归属一个团队”。

### 10.3 AgentScope 接法

| 接法 | 优点 | 局限 | 结论 |
|------|------|------|------|
| 原生声明式子代理 | 少量声明即可沿用原生能力 | 默认继承父 toolkit/skill 等，不能原样表达成员独立配置；空工具列表也不能视为零权限 | 不作为主方案 |
| 把成员工具/MCP 并集挂给主管 | 便于从父集合裁剪 | 扩大主管能力、混淆凭证；提示词不是权限边界 | 明确否决 |
| 原生委派 + 完整成员工厂 | 复用委派机制，同时保留成员自身配置 | 需适配作用域、Harness 生命周期、确认与取消 | 推荐主方案，需验证 |
| Agent-as-tool | 容易以工具方式调用专业 Agent，SDK 也有会话状态支持 | 与 Harness 的 task、沙箱和确认语义不等价 | 不与主路线混用；不声称它没有会话能力 |
| 自研完整编排引擎 | 控制自由 | 重造状态、事件、调度和恢复，不符合少改目标 | 不选 |

### 10.4 主管、可见性与文件策略

| 分叉 | 最终取舍及原因 |
|------|----------------|
| 主管亲自执行还是只安排 | 只安排、验收和汇总；运行时收紧能力，原 Agent 独立使用不变 |
| 共享还是独立沙箱 | 独立；保留成员环境并减少相互干扰，接受更高容器成本 |
| 共享目录还是产物交接 | MinIO 文件引用；接受传输成本，换取明确权限与可追踪版本 |
| 只看最终答案还是成员过程可见 | 过程可见；需要事件归属和前端展示，不能宣传零前端改动 |
| 确认事件展示还是完整批准续跑 | 完整闭环；事件上传不等于能恢复原子运行 |
| 越少代码越好还是保留完整成员能力 | 在保留能力与安全边界前提下少改，不以工具子集或自动降级换取表面简单 |

### 10.5 已纠正的技术判断

- 没有配置业务成员，不代表 SDK 没有子代理工具；本地 2.0.2 源码会添加默认 `general-purpose` 成员。
- `AgentEvent.source` 是字符串，不是旧 `EventSource` 对象；不能直接读取并不存在的 `source.agentId/depth/path`。
- `persistSession=false` 不代表每次调用自动清空所有实例和状态；续聊、缓存和恢复须按实际运行语义处理。
- 本地子确认可以上行，不代表确认决策已经能定向回传；`RemoteAskPolicy` 不能当成本地闭环的实现。
- 独立会话状态或不同 workspace 路径不等于独立 Docker 沙箱；必须显式验证真实文件系统和容器归属。
- 成员模型失败不能以“框架可以回退”为由静默换成主管模型。

## 11. 改动面与复用边界

| 模块 | 拟新增或调整 | 保留边界 |
|------|--------------|----------|
| `harnax-entity` / admin | Team（含主管的模型、提示词与技能绑定）、成员关系、会话 Team 关联、权限校验和团队配置下发 | 成员仍由现有 Agent 与其能力绑定唯一持有；主管由 Team 唯一持有，`agent` 表不再有代表主管的行 |
| `harnax-agent-service` | 根团队运行与子运行关联，成员配置作用域、确认和停止分派 | 普通 Agent 入口与行为保留 |
| `harnax-harness-core` | 主管/成员角色装配、原生委派接缝、独立沙箱生命周期、产物动作 | 尽量复用模型、Tool、MCP、Skill、CLI 与沙箱组件 |
| `harnax-protocol` / 消费端 | 团队事件来源、子运行确认关联、文件引用 | 继续使用根 SSE 通道，不混淆原事件含义 |
| `harnax-webui` | 团队管理、创建团队会话、成员过程与确认卡片 | 既有 Agent 配置入口不重复建设 |
| 文件存储 / admin 下载 | 产物元数据、团队范围授权、发布获取和受保护下载 | 复用 MinIO，不把旧登录检查当对象级权限 |
| `harnax-session-router` | 核验新增请求/事件字段透传，保留根 session 路由 | 不按成员建独立外部路由或引入 A2A |
| channel / scheduler / client | 按实际入口与协议消费点评估兼容 | 首期不宣称自动支持 Team，不改变已有渠道文件与 OAuth 口径 |

部署仍沿用 `docker-new`，本轮不引入新服务。独立沙箱增加容器、镜像、快照与文件传输资源需求；实际实现时同步容量限制、生命周期与部署说明，不能仅更新页面文档。

## 12. 原型验证与验收门槛

以下均为待完成的工程验证，不是本次文档交付的测试结果。

| 编号 | 验证点 | 通过标准 |
|------|--------|----------|
| V1 | 独立 Team 与普通会话 | 同一个 Agent 可单独使用并被多个 Team 作为成员引用，普通会话不误启动团队；Team 不需要先建一个主管 Agent 才能成立 |
| V2 | 主管能力约束 | 最终工具集合中没有业务 Tool、MCP、Shell 或默认路径泄漏；不创建执行沙箱；Team 为主管配置的技能文本可见，其脚本与资源文件不可执行且在装载时点名 |
| V3 | 成员完整装配 | 不同模型、Tool、MCP、Skill、CLI 和环境分别生效，主管没有成员能力也可委派 |
| V4 | 懒创建与配置上下文 | 不依赖失效的 ThreadLocal，不复用主管 ToolBox、日志身份或秘密参数 |
| V5 | 独立容器与快照 | 两成员环境互不影响；跨租户、跨会话和重复任务不串容器，续跑恢复正确 |
| V6 | 产物交接 | A 发布、B 获取并处理、最终 Web UI 下载闭环；越权、越界路径和旧下载入口绕过被拒绝 |
| V7 | 事件关联 | 同成员多次任务、相同工具名或重复局部调用 ID 不串流、不误合并；成本不重复统计 |
| V8 | 人工确认 | 用户批准/拒绝只影响原子运行；重复、过期、取消后确认不重放工具；主管随后正确继续 |
| V9 | 停止与失败 | 根停止能停止成员并阻止新委派；超时不意外转后台；资源可清理，失败不伪装成功 |
| V10 | MCP 身份 | 根用户、租户及成员 MCP 范围正确，未知子 ID 不误换发，不改为成员创建者身份，不开放 stdio |
| V11 | 原有功能回归 | 普通 Agent 的工具、模型、MCP、文件输出、确认和会话路由行为不因团队角色限制改变 |
| V12 | 容量与恢复 | 活动容器、委派与文件预算有界；进程中断不自动重放有副作用操作，不宣称仅靠快照无损恢复 |

建议验证顺序：先做最小的主管与两个成员原型，验证工厂、独立沙箱、事件及人工确认，再实现 Team 管理与完整文件交接，最后做回归和部署验收。若 D8 的接缝不成立，先修订工程接法，不静默削减已确认的 D1–D7。
