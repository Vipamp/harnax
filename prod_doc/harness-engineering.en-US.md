# Harnax Harness Engineering Plan (English)

This document fixes the version baseline, the data sources and the anchor convention of the harness domain, and condenses the delivered shape of context compaction and the occupancy ratio into statements that can be checked. The module-by-module change list, the boundary matrix, the nine primary assertions and the real-stack re-verification record live in `prod_doc/harness-compaction.en-US.md` in the same directory; both documents share the anchor convention in section 0 below.

## 1. Context compaction and occupancy ratio

### 1.1 Three acceptance criteria

1. **`/compact` really compacts.** After a session has run a few turns, sending `/compact` replaces the model-side context with a summary, and the next turn's `input_token` in `token_stats` drops accordingly; one command costs one extra summarization call and nothing else.
2. **The page always shows every original bubble.** Whether the session was compacted once or ten times, the bubble sequence returned by `GET /api/agent/chat/history/{sessionId}` (`AgentController.kt:105`) is verbatim what it was before compaction, and no "compaction summary" bubble ever appears. This is the domain's primary assertion.
3. **Occupancy is queryable.** `GET /api/agent/context/{sessionId}` (`AgentController.kt:123`) returns the estimated occupancy, the real occupancy, the window value and its source in a single call; the ratio is computed from the real occupancy, while the two estimated numbers keep answering "would automatic compaction trigger".

### 1.2 Three facts determine the shape

- **Compaction is already running.** The initial values of `HarnessAgent.Builder` are `compactionConfig = CompactionConfig.builder().build()` and `disableCompaction = false` (`HarnessAgent.java:1227,1230`); under the default assembly `CompactionMiddleware` is always installed (`HarnessAgent.java:2600-2609`); the default tier is `triggerMessages=50`, `keepMessages=20`, with the dynamic token tier and flush/offload all enabled (`CompactionConfig.java:273-286`, `:67`). So this domain does not introduce a mechanism: it adds a controlled entry point and visibility to one that is already running.
- **User-visible history was the model context itself.** `loadSessionMessages()` (`HarnessAgentLauncher.kt:1035-1048`) reads `AgentState.context`, and the only readers are `DefaultAgentRunner.kt:353` (chat history) and `TeamHistoryReplay.kt:44` (member bubble merge). Compaction overwriting `context` trims the chat log along with it, so **separating history from model context is a precondition of shipping compaction** — see 1.3.
- **The `/compact` command path was always connected.** `/compact 500` parses to `CommandType.COMPACT` with `args="500"` (`harnax-protocol/src/main/kotlin/com/agnetix/harnax/agent/protocol/AgentRequest.kt:67,90,199`), `POST /api/agent/command` already accepts it (`AgentController.kt:77`), and the webui and iOS slash-command tables each register it (`harnax-webui/src/pages/session/components/ChatWindow.tsx:957`, `harnax-ios/Sources/HarnaxFeatures/Chat/ChatSlashCommand.swift:33`). The only thing missing was the server-side branch.

### 1.3 Full history separated from model context

Session messages are archived one by one into an append-only table, `session_message`, in the same database as `agent_state`; the writer creates it with `CREATE TABLE IF NOT EXISTS` during initialisation (`MysqlSessionMessageStore.kt:63`), so it does not enter admin's Flyway baseline and this table needs no database rebuild. The unique key is `(user_id, session_id, msg_id)`, where `msg_id` is the UUID every core `Msg` already carries; `ON DUPLICATE KEY UPDATE` keeps the **longest body**, because upstream both delivers a more complete message under the same id and, when pruning, delivers a shorter preview under the same id. The model context remains what `AgentState.context` holds, and compaction may overwrite it however it likes.

Three write points: one full back-fill at each of the three turn epilogues (`DefaultAgentRunner.kt:163` blocking turn, `:195` streaming turn, `:425` HITL confirmation resume); one first back-fill at assembly time if that bucket has no archive yet (`HarnessAgentLauncher.kt:919` → `HarnessAgentWrapper.kt:331`); and `/compact` writes once more before compacting — if that write fails, the command is refused. The read path consults the archive first, falls back to `agentState.context` when the session has zero archived rows, then falls back to legacy `memory_messages`, and filters out summary messages with `name == __compaction_summary__` — a summary is constructed with the USER role, so archiving it would put an extra user bubble carrying the whole summary text on the page.

One hidden invariant: the compaction write-back, the archive reads and writes, and the history read path must land in the same user bucket. All three sides normalise an empty value to `__anon__` (`MysqlAgentStateStore.kt:70`, `ReActAgent.java:394-399`); harnax's single wrapper construction point passes no userId (`HarnessAgentLauncher.kt:891-916`, the field defaults to `null`, see `HarnessAgentWrapper.kt:91`) and the history read path hard-codes `""` (`:1036`) — both sides land in the same bucket. The moment either side starts passing a real user id on its own, the hard-coded `""` diverges from the live slot, and the symptom is "it compacted, but the history reads back the old one". The command path therefore takes all three keys from the wrapper itself (`HarnessAgentWrapper.compactManually`), so a caller cannot introduce a second userId.

### 1.4 Where command compaction lands

`executeCommand` at `DefaultAgentRunner.kt:247` routes the `COMPACT` branch (`:264`) to `handleCompact` (`:917`). The runner side only performs precondition checks and result mapping; the three steps that fetch the live `AgentState`, call `ConversationCompactor.compactIfNeeded(...)` (`ConversationCompactor.java:92-96`) and overwrite plus persist only on success live in `harnax-agent/harnax-harness-core/src/main/kotlin/com/agnetix/harnax/harness/compaction/ContextCompactionService.kt`. The tier is `triggerMessages(1)` with flush and offload both disabled, which means "the user pressed the command, do not block me behind a threshold"; whether compaction is worth doing is decided by upstream's cutoff check (`ConversationCompactor.java:112,118`). A summarization failure does not persist and returns a failure outright; `task-` prefixed sessions and team member child sessions are refused; a running stream or blocking call on that session is refused; the command returns synchronously end to end, and the single `Mono` from `compactIfNeeded` is `block()`ed in place.

### 1.5 Occupancy terminology

Two numerators are reported together because they do not answer the same question: `estimatedTokens` shares its source with the automatic compaction trigger (`TokenCounterUtil.calculateToken`, `TokenCounterUtil.java:73`, thinking blocks included); `lastCallInputTokens` is the billed truth (`TokenStatsMiddleware.kt:41-67` writes one row per model call, read back at `harnax-entity/src/main/resources/mapper/TokenStatsMapper.xml:36`). The two are **not proportional**: the estimate cannot see the system prompt or the tool manifest, yet it counts thinking that is never replayed into later turns — so the `ratio` numerator takes the billed number and falls back to the estimate only when no billing row exists (`HarnessAgentWrapper.kt:441`), while the estimate keeps answering only the trigger question. The denominator falls back through three tiers: the model domain column `model.context_window` (`harnax-admin/src/main/resources/db/migration/V1__init_schema.sql:351`, with `harnax-entity/src/test/resources/schema-test.sql:335` following it verbatim) → the window upstream infers from the model name → `160_000`; `windowSource` takes `MODEL_FIELD` / `UPSTREAM_TABLE` / `FALLBACK` so the caller knows whether this denominator was configured or guessed. `triggerTokens` runs the algorithm in `CompactionMiddleware.java:164-190` against the window the model itself reports, which is the same number the automatic path uses.

The occupancy reading is only served by the instance that holds that session's agent (the window denominator belongs to that session's model, and only the assembly knows which model that is), so the router must forward by session binding: `harnax-session-router/src/main/kotlin/com/agnetix/harnax/router/controller/AgentProxyController.kt:183` → `harnax-session-router/src/main/kotlin/com/agnetix/harnax/router/proxy/SessionRouterService.kt:397`. Neither of the two shapes where no reading can be produced means "occupancy is 0": when the session is bound but this instance does not hold the agent, `code: 500` plus a sentence saying the instance holds no such session; when it was never bound, `code: 200` with `data: null` (`:400`).

### 1.6 Entry points on both clients

The webui session chat page (`ContextUsageTag` in `harnax-webui/src/pages/session/index.tsx`, the three predicates in `pages/session/components/contextUsage.ts`, `getContextUsage` in `services/ant-design-pro/chat.ts`) and the iOS chat page (contract `harnax-ios/Sources/HarnaxCore/Contract/ContextUsage.swift`, transport `Sources/HarnaxAPI/ContextUsageClient.swift:24`, view model `Sources/HarnaxFeatures/Chat/ChatViewModel.swift:1471`, screen `Sources/HarnaxFeatures/Chat/ChatView.swift:89`) share one set of predicates and one set of refresh moments (a turn's answer completes, a compaction returns). Neither client adds an interface: the reading travels the same router channel as chat history, and compaction travels the existing command channel. With no reading available the title bar block does not render at all, rather than drawing a `0%`; when the automatic compaction threshold is reached the reading turns to the warning colour. The wording of a compaction result splits four ways: a real compaction reports the counts, a success that trimmed nothing reports "still too short", a backend refusal is replaced by the server's own reason, and an envelope-level failure takes the failure's own body.

## 2. Items this domain still leaves open

| Item | Current state | Where the criterion lands |
|---|---|---|
| Making the automatic compaction tier explicit | the assembly layer pins no `triggerTokens` / `keepTokens` / `prune`, everything runs on upstream defaults | `CompactionConfig.java:273-286`; touching it would make the regression surface of "command compaction shipped" undecidable |
| Middleware switch closure | `disableTranscript()` is called unconditionally once after the three assembly branches converge (`HarnessAgentLauncher.kt:809`, passed through at `HarnessAgentBuilder.kt:242`); three items remain open: `disableMemoryTools()` / `disableToolsConfig()` / `disableAtPathExpansion()` | the disable family lives at `HarnessAgentBuilder.kt:224-242` |
| The other direction of the concurrency gate | while a compaction runs, a new chat message is not refused (the busy predicate is only read on the compaction side, `DefaultAgentRunner.kt:87` / `:96`). What is at risk is the model side; the page is safe because the archive is append-only and keeps the longest body | three-way exclusion would require spreading the busy predicate across chat's three entry points |
| The archive table's retrieval surface | `session_message` serves chat history only, not cross-session retrieval (the `session_search` kind of capability) | key layout and read points: `MysqlSessionMessageStore.kt:63` |
| Recovering trimmed content | with offload disabled there is no entry point that replays the archive back into `context`, and no recovery path has been measured | handled as "no benefit unless it can be retrieved", the same reasoning as flush/offload |
